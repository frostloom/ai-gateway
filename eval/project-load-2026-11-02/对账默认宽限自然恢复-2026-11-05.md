# 默认宽限期下的自然对账：合成账单

## 方法和范围

在新建隔离 MySQL/Redis 和真实 billing gRPC、gateway、router、reconciler 中，先运行 20 请求/秒、2 秒的本地模拟上游烟测；发压结束后，测试 fixture 通过真实 gateway billing 客户端以严格 V2 创建两笔独立合成预占：一笔上报 50/0 token 但故意不调用 Settle，另一笔不报告 usage。**两笔 fixture 没有调用上游，也没有 HTTP 200 客户端响应**，不是先前高负载中那笔账单的重放。随后不再发压，保留服务并用单调时钟自然等待 650 秒；没有修改账单时间。

reconciler 使用 `-grace 600 -interval 30 -no-rebuild -no-auto-reverse`：600 秒与 30 秒是当前命令行默认宽限和扫描间隔，禁用重建与显式保留是本实验设置。测试 runner 在等待前后通过独立只读查询记录两笔账单、四类指定 Outbox、结算行及账户 Redis/账本，并在等待后保存 `/status`。Kafka relay/Agent 关闭。状态快照是进程内最近一轮，不是持久审计。

## 结果

短烟测先用 1 秒等待确认严格 V2 能创建两笔 pending、已用量账单含 reserve/usage 事件、无用量账单仅有 reserve；它没有跨越宽限期。正式自然等待**一次**，实际 650.010 秒：

| 账单 | 等待前 | 等待后 | 指定事件 |
|---|---|---|---|
| 合成已报用量 | pending，50/0 token | settled，50/0 token，一条 settle 账单 | reserve、usage、settle 各一；reverse 零 |
| 合成无用量 | pending，无 usage | pending，无 usage、无 settle | reserve 一条；usage、settle、reverse 均零 |

等待期间读取并保存的一次 `/status` 显示 `last_scanned=2`、`last_settled=1`、`last_held=1`、`last_settle_errors=0`，且最早 held 时间与无用量 fixture 的创建时间一致；等待结束时保存的状态相同。该状态记录于已报用量账单创建约 624 秒后，实际调度时间不是恢复时效保证。两笔账单属于同一合成账户，等待前 Redis 余额和账本均为 999999590，等待后均为 999999640；没有其他发压请求在等待期间运行。全局快照 pending 从 2 到 1、settled 从 45 到 46（45 含正常烟测），所有 139 条 Outbox 未发送，因为 relay 关闭。

本次支持在所测单实例、空闲、无故障条件下：已持久化用量可由真实常驻对账器结算，无用量仍保留。它**不证明**此前压测中 HTTP 200 对应的 pending 已恢复，不证明真实供应商未执行、费用可核清、所有故障自动恢复，也不保证高负载、并发扫描、多实例、旧版本、订阅、充值、数据库/Redis 故障或 Kafka 投递。该实验只运行一次，不能作为恢复 SLO 或生产容量。
