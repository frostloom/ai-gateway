## 正确性和限制

两组逐轮账务核对均为 pending 0、余额差异 0、settled 数与有效 HTTP 200 数相等；候选最终 18794 笔 settled 含 5 条烟测，56382 条 Outbox 均未发送（relay 关闭）。这只证明合成正常流量下指定账务核对，不能证明事件消费、实际模型收费或故障恢复。

候选仍**不可直接部署**：已有真实组件测试显示其数据库回报写入失败时 HTTP 200、内存失败计数为 1 而 DB 为 0；它未解决事件身份与去重、跨实例顺序、数据库失败恢复、自动封禁/探测与失效竞争，也有 provider 锁 map 无界增长问题。此前 [缩锁原型报告](路由回报缩小锁范围原型-2026-11-04.md) 记录这些故障复现。不能为了吞吐关闭这些安全约束。两组均使用一个模拟渠道，未验证多渠道故障及负载分散。

候选累计 MySQL 最大连接 104/151、连接上限错误 0、InnoDB 行锁等待 4 次共 64ms，未统计命名锁；Redis 累计命令 602128、峰值内存 11.24 MiB（均含启动、烟测、核对及全部场景）。容器采样在 `resources.jsonl`；不能将累计资源归因于单一档次或解释所有超时。未覆盖流式、长时持续、真实生产流量或完整消息系统。
