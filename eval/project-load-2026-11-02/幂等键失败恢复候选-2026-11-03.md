# 幂等键失败恢复：受控时序试验

## 背景与范围

完整链路实验 `Redis故障完整链路-2026-11-03.md` 已实际观察到 Redis 恢复后失败请求仍留有幂等键：原请求 HTTP 500 且无 reserve，再用同键同请求重试得到 409。这里探索的不涉及生产中间件修改，仅测试一种 Redis 层原子协议能否处理迟到的写入。

## 测试候选

`idem_recovery_impl_test.go` 给每次尝试独立 owner；acquire Lua 先检查该 owner 的取消标记，再原子 SET NX；cancel Lua 写入该 owner 的短期取消标记，仅当现有键值仍为同 owner 时删除。这样在**取消标记存在期间**，先于失败的操作即使迟到也不能重新取得请求键，且旧 owner 的取消不会删除新 owner 的键。它只有在能确认对应尝试尚未向后续计费或上游提交时才可考虑取消；本例用人为调用模拟这个条件，不等于网关已能证明该条件。

miniredis 控制时序及真实隔离 Redis 7 的 100 次并发 acquire/cancel 检查见 `idem-real-redis-tests.txt`，启用 race 检查并通过。通过表示限定场景下的断言成立，并非生产安全证明：

- `TestIdemExpiredCancellationCanArriveLate` 明确复现了取消标记过期后旧操作仍可占键。
- `TestIdemCancelAfterForwardAllowsDuplicate` 明确复现了如果第一个尝试已经转发上游而取消，其后另一个 owner 可成功取得键，带来重复执行风险。测试通过是证明危险可发生。
- Redis 不可用期间无法写取消标记；丢失回复、进程停止、标记丢失、Redis 故障转移、跨集群节点顺序、多个 gateway 版本以及实际上游状态都未验证。该候选与数据库账单/Outbox 没有原子事务，不能保证财务幂等或回复重放。
- 取消标记和操作 id 的安全生命周期、租户隔离、防滥用、状态存储大小、Redis Cluster 同槽以及旧客户端兼容都没有完成；不能靠加长 TTL 宣称消除了不确定性。

在没有能证明“请求尚未进入后续动作”的持久状态机前，不建议简单删除任何用户的原幂等键，也不建议将本实验候选接入项目。后续需针对不同失败点设计状态与核对协议，完整实测并发、超时、进程中断和账单/上游行为。

复现：`./eval/project-load-2026-11-02/run-idem-redis.sh`；脚本创建随机名称、随机本地端口的临时 Redis，并在退出时清理。也可仅运行 `go test -race ./eval/project-load-2026-11-02 -run '^TestIdem' -count=1 -v`；未提供隔离 Redis 环境变量时真实 Redis 并发测试会跳过。
