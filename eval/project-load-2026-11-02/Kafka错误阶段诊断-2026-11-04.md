# Kafka 链路压测的错误阶段诊断

## 环境和方法

在 `run_kafka.py` 新增 `KAFKA_LOAD_DIAGNOSTIC=1`，选择项目已有 `diagnostic-load` 发压器，对非 200 JSON 的已知错误 message 分类，同时保留与 seed 核对兼容的三列 request trace。测试 gateway/mock overlay 仍为诊断目的传播并记录合成 request ID；发压器为每次请求设置幂等键。已知类别以外归为 other 或 non_json，不记录完整响应正文或每条错误类别。该分类只表明网关返回错误的阶段，不提供底层 gRPC 错误或物理根因。

隔离真实 gateway/billing/router/reconciler、MySQL 8.0.40、Redis 7、本地 Kafka relay/consumer 和模拟模型，32 个合成账户、每账户允许多个并发请求、模型延迟 15ms；非流式总 256 和 512 worker，流式总 128 worker。每轮 5 秒闭环、排空后统计、各两轮、顺序固定且事件积压累计；同机共享资源。与上一轮使用不同发压器和时间，不能直接作为改造前后对照或生产容量。完整环境及源码/二进制哈希见 `kafka-runs/20261104-172137/config.json`。

## 结果

| --- | --- | --- | --- | --- |
| 256 非流 | 272/460、748/748 | 32.43、108.97 | 5590、2897 | 第一轮 188 个 billing unavailable；第二轮 0 |

256 第一轮 188/460 为 40.87% 错误；512 第二轮 177/849 为 20.85%。同档两轮波动大、采样短，不能称零错误轮可持续或断言 512 优于 256。完整平均、P99 和状态在原始 `results.jsonl`；未收集可靠的逐次超时分类、服务器 CPU/I/O 归因或 MySQL 锁等待。

当前真实 `internal/gateway/handler/chat.go` 在路由调用失败时返回 `routing unavailable`；预占 RPC 设有 3 秒 context，非特定错误、空响应或异常预占码可返回 `billing unavailable`。本测试没有记录这些请求的底层错误，因此不能将 188 个都断定为超时、数据库锁或 MySQL 连接耗尽，也不能将 177 个路由错误直接归因全局锁。上一轮的 81 个 503 未采错误类别，不能用本轮分类倒推。

## 账务及积压

256 第一轮 188 个 503 的快照：175 条无 reserve，13 条 pending 且无 usage/settle；该轮有 reserve 的异常条目均出现在 `trace-256-32-0-1-audit.json`。512 第二轮的 177 个 503 快照均无 reserve。分类是整轮聚合，不单独将错误类型写入追踪 CSV；但对应轮次各只有一种已分类错误。最后一轮账务快照 settled 3964 与累计有效 HTTP 数相等，pending 13，余额差异为空；观察期未再次核对 pending，不能称已恢复。测试无付费上游，未证明任何真实费用。

事件观察期约 32.8 秒，未发送从 9449 降至 7998，最终事件 ID 核对缺审计 7940、未发送 7940、额外审计 0；未等待排空，也未逐条校验 payload。不能以余额核对代替消息最终交付。

## 底层错误类别与已成功响应的未结算快照

后续 runner 新增 `KAFKA_LOAD_STAGE_DETAIL=1`：仅测试 gateway overlay 在首次路由错误记录 `net.Error.Timeout()` 与请求 context 是否结束，在预占 RPC 错误记录 gRPC 状态和预占 context 是否结束；只记录合成 request ID 和分类，不记录请求正文或密钥。与现有 trace/诊断发压器共同运行；额外错误日志增加开销，不可直接比较吞吐。实验 `kafka-runs/20261104-172725/` 退出 0，HEAD `42d8ef8e5ca2471b18800e50f8e7a57fbcfdd47f` 加未提交工作树，环境、32 账户、256/512 非流和 128 流、每档两轮与上节一致。

整次运行的 gateway 日志共有 374 个预占 RPC 错误：350 个 `DeadlineExceeded`（其中 324 条预占 context 已结束、26 条尚未结束）和 24 个 `Unavailable`（7 条 context 已结束）；另 312 个路由错误均报告 `Timeout()=true` 且客户端请求 context 当时未结束。这些是错误表象；不能仅据此把预占的所有 deadline 归因数据库、把路由超时归因某把锁，或推断客户端 context 尚未结束就没有其他层的 deadline。上述计数只属于本轮，不能倒推前面的 503。

本轮首个 256 worker 非流轮：349 个请求 180 个有效 HTTP 200、169 个 503；发压器将 503 分为 76 个 billing unavailable 与 93 个 routing unavailable。追踪快照中 9 个有效 HTTP 200 对应 pending reserve、usage 已报告但无 settle 行；另 6 个 503 对应 pending 无 usage、163 个 503 无 reserve。9 个有效成功请求的 ID 与 gateway 中 9 条 `settle failed, reconciliation will catch up` 日志完全匹配，且日志均为 `rpc error: code = Unknown desc = request lock timed out`、usage 上报无错误。当前 `Store.Settle` 先经 `lockCash` 获取租户 named lock；通用 `lockNamed` 的错误文字虽为 request lock，但此路径可能来自租户锁获取，**不能凭这一文字确认具体持锁者或等待根因**。账单快照是发压结束后一次读取，并非证明永久丢失或真实费用；无测试主动等待 600 秒 grace 后结算。

最后一轮账务快照 settled 2304、累计有效 HTTP 2313、pending 38、余额差异为空；差额为 9，但没有再次逐条查证最初 9 笔在最后快照的状态。事件观察约 34.7 秒未发送 4310→3144，最终 ID 核对缺审计/未发送各 3104、多余 0，未排空、未逐条核对 payload。此轮负载波动很大，不能用它作为可靠容量评估。
