## 结论与安全边界

在本机 64 个合成账户、同账户可多请求的短测中，两组 140、180 计划请求/秒各两轮均无 HTTP 错误和发压丢弃；140 档测试候选延迟较低，180 档两组 P95 均超过 3 秒。两组先后运行而非随机交叉、共享宿主且每档只有两轮，不能将差异归因于缩锁，也不能作为生产容量或最大用户数。

缩锁候选**不可部署**：先前真实组件故障测试已观察到数据库回报持久化失败但 HTTP 返回成功、内存与数据库失败计数不一致；稳定事件身份、跨实例、半开探测、故障恢复及锁 map 增长问题尚未解决，见 `路由回报缩小锁范围原型-2026-11-04.md`。本次没有覆盖这些故障，不改变此结论。

## 补充：真实 MySQL 容器中断

为检验原先仅由 GORM 回调注入的持久化问题，新增 `router_mysql_outage_report_test.go`，在脚本单独创建的隔离 MySQL 上直接 `docker kill`、重启同一容器（固定 loopback 端口）。测试通过真实 router `/report` handler 和 Registry，HTTP 使用 recorder；先缓存选路，MySQL 停止时发送一次失败回报，重启并确认数据库可连接后读取状态，再发送第二次失败回报。

当前实现和本次压测使用的缩锁测试 overlay 分别运行三轮 Go race，每轮观察一致：第一次 `/report` 返回 200、内存失败数 1；数据库恢复后计数仍为 0；第二次回报亦返回 200，最终内存失败数 2、数据库为 1。两份测试的 PASS 表示**故障现象被成功复现**，不代表结果安全；日志中的连接 EOF 来自主动终止隔离容器。此测试没有重启 router、真实 HTTP 网络、并发请求、半开或阈值封禁，也不能证明生产发生相同事件。它表明此次性能较好的候选没有解决现存持久化确认缺口。

## 相同回报重复发送的风险

真实当前路由 `/report` 只接收 provider ID 与成功标志，没有单次尝试事件 ID。`router_report_duplicate_real_test.go` 对真实本地 HTTP router 和隔离 MySQL 顺序发送两次完全相同的失败回报；三轮 race 均返回 200/200，内存和数据库连续失败计数均为 2。两次请求也可能对应两次真实调用，因此服务端无法仅凭相同内容区分合法的两次调用与一次调用的重试。测试 PASS 表示复现当前行为，并非幂等正确性通过。

这里没有实际丢弃响应、模拟网络分区或 COMMIT 确认丢失；它只证明如同一尝试重复发送，当前接口无法去重。因此不能单独将持久化失败改成 503 并自动重试就声称恢复可靠。需要稳定的尝试事件身份、提交确认未知时的幂等处理与有界持久投递，同时定义乱序、失败/成功、跨实例和半开语义。测试事务候选的受控结果及缺口见 [路由事件事务候选](路由事件事务候选-2026-11-04.md)，现尚未接入正式协议。
