# 非流式不完整用量修复

当前工作树 HEAD `63b9d1ed4d64bb583d15fa884c37468e5c53044c`。此前完整 2xx JSON 中存在 `usage` 对象但字段缺失或为 null 时，Go 整数字段默认为 0；handler 以该值上报并结算。现有网关非流式处理在 usage 对象存在时要求 `prompt_tokens` 和 `completion_tokens` 均为非 null 整数且非负，否则返回 502、当次 handler 不报告用量、结算或冲正。两个字段明确为 0 仍可接受；整个 usage 缺失或为 null 时沿用现有估算行为。这是兼容 OpenAI 风格字段的本项目校验假设，其他上游格式需单独适配。

在真实 loopback HTTP 上游、测试替身 billing/router 条件下，五个空对象、缺项及 null 字段用例修复前均返回 200 并调用结算，记录 `incomplete-usage-red-2026-11-04.txt`；修复后通过。包括明确零值、完整无 usage 的兼容用例和整个 handler 包的 race 测试通过，见 `incomplete-usage-zero-green-2026-11-04.txt`。复现 `python3 eval/project-load-2026-11-02/run_upstream_truncated_safety.py --suite`。

测试没有真实 billing/MySQL/Redis 或付费模型；返回 502 不证明供应商未执行。账单无 usage 后旧对账器仍可能错误冲正，本次没有解决。流式 usage 解析另有相似的零值问题，未由本次修改覆盖；不应把这项修复当作完整协议校验或上线安全证明。完整 JSON 对象整体缺失 usage 沿用既有估算，无法证明真实费用等于估算。
