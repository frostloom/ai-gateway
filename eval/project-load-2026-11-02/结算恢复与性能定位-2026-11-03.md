# 结算恢复与性能定位（2026-11-03）

## 条件

当前分支 `codex/billing-mysql-comparison`，HEAD `63b9d1ed4d64bb583d15fa884c37468e5c53044c`，包含未提交改动；源文件与二进制哈希、镜像、配置在 `recovery-runs/20261103-151559/config.json`。独立随机 MySQL/Redis 容器、64 合成账户和本机模拟上游（15 ms），Kafka 关闭；限流为测试用 100000/分钟，不能代表生产配置。收集器、客户端与服务共用机器，当时系统负载约 32–35，其他进程运行，因此数字不代表容量，不能与之前低负载环境直接对比。

每轮 5 秒闭环发压、排空后做逐请求映射和余额快照，等待 40 秒再做同批请求映射。reconciler 间隔 5 秒、宽限期为测试专用 30 秒，不做重建；该宽限期短于先前实验的 600 秒，且可能与长请求竞争，不能由此证明 600 秒实际恢复时间。查询采样在运行中途开始，属于旁路采样并有自身开销。

## 恢复结果

| 场景 | 初次快照 | 后续快照 |
|---|---|---|
| 单账户 512 并发，第 1 轮 | 47 笔有效 200 已结算；3 笔 503、无用量 pending | 47 仍已结算；3 笔变 reversed |
| 单账户 512 并发，第 2 轮 | 无有效 200；1 笔 503、无用量 pending | 1 笔变 reversed |
| 64 账户共 512 并发，第 1 轮 | 95 笔有效 200：94 笔已结算、1 笔有用量 pending；28 笔 503、无用量 pending；1 笔客户端超时但已结算 | 95 笔有效 200 均已结算；28 笔变 reversed；超时请求仍已结算 |
| 64 账户共 512 并发，第 2 轮 | 192 笔有效 200 已结算；40 笔 503、无用量 pending | 192 仍已结算；40 笔变 reversed |

这是该次运行的观察值；特别是有用量 pending 恢复只观察到 1 例。每次恢复后余额核对均无差异，最后累计 `pending=0`、`settled=344`、`reversed=72`。逐请求 settle 行数在映射中可见；余额核对采用现有种子程序的账本公式，不能代替所有故障场景的完整审计。最后 Outbox 有 1176 条未发送，原因是本测试关闭 Kafka/relay，不是丢失或发送故障证据。未验证消费者去重、事件发布或最终恢复。

之前及本轮日志有用量上报成功但 settle RPC 超时；本轮另有 request lock timeout。单个客户端超时但账单结算的例子说明不能仅凭客户端结果推断是否已计费；模型响应重放与账务幂等仍须分别处理。

P95 包含失败请求，并非成功请求延迟；请求数随负载和排空变化。有效 key 测试下 billing 日志存在 `ValidateAPIKey` SQL context deadline exceeded，但没有逐个将 401 对应至日志，不能归因所有 401。采样期间 MySQL `Max_used_connections` 达 126、采样 `Threads_connected` 最高 104、`Threads_running` 最高 54；`Connection_errors_max_connections` 和 InnoDB 行锁等待累计值各为 0。采样过程看到 `User lock` 状态，及结算 request lock timeout；InnoDB 行锁指标不包括 MySQL 命名锁等待，不能用其为零证明无锁竞争。采样不覆盖完整第一轮，且无法确定连接池逐服务等待、各阶段 P95、CPU/I/O 因果或瓶颈占比。

关键证据：`trace-audit-*.json` 与 `trace-recovered-*.json` 是前后同 ID 映射；`audit-recovered-*.json` 是余额和累计状态；`results.jsonl`、`resources.jsonl`、`mysql-observation.txt` 及 `gateway.log`、`billing.log` 保留原始数据。SQL 采样为本次旁路采集，未内置到复现脚本。
