# 上游结果未知与故障切换：隔离验证

代码基线为 HEAD `63b9d1ed4d64bb583d15fa884c37468e5c53044c` 加当前未提交工作树；测试于本地执行，未使用真实供应商、付费 API 或生产数据。本记录针对网关故障切换，不是容量测试或完整账务验证。

## 发现

当前 `internal/gateway/handler/chat.go` 的 `forwardNonStream`（约 170 行起）和 `relayStream`（约 250 行起）在 `http.Client.Do` 返回错误或者收到 5xx 时调用 `failover`，尝试另一个 provider。`Do` 返回错误不证明服务端未收到或执行请求；5xx 本身也不证明供应商没有执行或收费。

测试通过 Go overlay 将 `upstream_unknown_regression.go.txt` 加入真实 handler 测试，使用真实 loopback HTTP 服务和 fake billing/router。第一个模拟服务完整读取 body 后断开连接，或返回 503；第二个模拟服务正常响应。流式和非流式共四种情况下，现有 handler 均观察到 primary=1、secondary=1、HTTP 200，fake billing 记录一次 usage 和 settle。详见 `upstream-unknown-red.txt`。这证明请求可重复送达两个模拟上游，不证明真实供应商已经执行或产生费用，也不证明真实数据库账本的最终状态。

## 保守候选及其不足

仅测试用的 `gateway_unknown_candidate.go.txt` 对 Do 错误及 5xx 不再自动切换，返回 502，且不立即冲正；四个定向场景通过，见 `upstream-unknown-green.txt`。它不区分确定未连接的故障与结果未知的故障，因此可能放弃安全且有用的故障切换。

对候选运行原有 handler 测试得到预期失败，完整输出 `upstream-unknown-candidate-handler-suite.txt`：`TestRelayStreamFailoverThen502Reverses` 失败；`TestChatReportsSuccessfulFallbackProvider` 的三个子例失败；`TestRelayStreamDoesNotWaitForFailedResponseBody` 的 refund、failover 两子例失败。该运行没有修改原有测试；它证明候选改变了既有的切换与冲正行为，不能作为等价的生产修复。

候选也没有持久记录发送/未知状态。`internal/billing/reconciler/reconciler.go` 的扫描按账龄处理 pending，缺少 usage marker 时会调用 Reverse；`cmd/reconciler/main.go` 默认宽限 600 秒。因此单纯不立即冲正并不能阻止之后自动退款。这里是基于代码的风险推断，并非本次针对该候选实际等待 600 秒的验证。此前缩短到 5 秒的独立在途竞争实验及其限制见 `对账与在途请求竞争-2026-11-03.md`。

下一步需在真实网关和账务链路统一设计持久的请求及尝试状态：发送前持久化、结果未知时禁止基于超时推断未执行、在有可信证据证明未执行时才允许重发或退款；同时明确供应商幂等能力、混版、对账与人工核查路径。现有离线原型及其缺口见 `../billing-comparison-2026-11-02/渠道尝试持久身份原型-2026-11-03.md`。这仍需真实组件集成、故障注入和性能复测，不能声称已解决。
