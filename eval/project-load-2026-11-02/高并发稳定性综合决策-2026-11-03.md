## 优先解决的正确性问题

1. `上游结果未知与故障切换-2026-11-03.md`：模拟服务完整收到请求后断开或返回 503，真实 handler 可能再调用第二个模拟渠道。不能仅把所有故障都禁用切换：测试候选会破坏现有可用性，而且现有对账仍会冲正未知请求。
2. `对账与在途请求竞争-2026-11-03.md` 和 `对账扫描与用量提交竞争-2026-11-03.md`：缩短 grace 或安排扫描/上报交错可复现错误冲正；不把缩短后的结果冒称默认 600 秒自然触发。
3. `../billing-comparison-2026-11-02/转发与自动冲正协调原型-2026-11-03.md`：测试 gate 若不在所有权威入口强制，真实旧对账器仍可绕过；退款完成而 intent 未完成时，普通 pending 扫描也不会恢复 intent。
4. `真实路由回报合并候选-2026-11-03.md`：过载、失败反馈、持久化和请求重试语义必须先明确；不能把 HTTP 200 自动视作已持久化，也不能无事件身份地重试失败回报。
5. `非流式截断响应-2026-11-03.md`：非流式上游响应提前截断时，当前 handler 仍可能返回 200 并以零输出用量结算。实验是本地 HTTP 与模拟计费，未证明真实损失；不能简单重发或退款未知上游结果。
6. `../billing-comparison-2026-11-02/账单发送退款状态竞争-2026-11-03.md`：测试恢复器已覆盖扫描后证据变化、Outbox 插入失败、MySQL 提交前连接中断、提交后执行进程终止、驱动层模拟提交成功但返回错误，以及四个独立本地进程在屏障后竞争同一记录；这些测试没有解决完成观察写入前丢失、混版绕过、正式授权、真实网络中的提交确认丢失或消息投递，不能把它视为生产恢复协议。
7. 同一报告新增反例：完成观察写入前 attempt 状态可并发变为失败，V5 测试候选仍会把该失败 attempt 写作完成证据，并同时产生失败事件与用量事件；必须统一写入口的状态约束后才能继续评价该候选。
8. `真实路由回报合并候选-2026-11-03.md` 的高负载自然等待实验中，155 笔 pending 经 620 秒后全部终态，但其中 5 笔有效 HTTP 200 因无 usage 最终 reversed；本地模拟上游无实际费用。不能将 pending 清零和余额一致视作已正确计入所有成功请求。

## 验证顺序与退出条件

1. **统一持久请求/尝试状态和冲正入口。** 在发送前持久化有界状态；上游可能收到请求时保留 unknown，不以 TTL 到期证明未执行。结算、恢复和所有冲正入口遵守相同协议；旧实例、历史账单、订阅、充值以及回退需要明确处理。测试不同进程终止、提交确认丢失、连接断开、Redis 丢失、超时及真实对账交错。已有测试原型不能直接当生产实现。
2. **可靠路由回报。** 为每次真实渠道尝试定义持久且不可跨请求冲突的身份，定义接收、持久化、超时未知及过载后的响应；确认失败事件不丢失、不重复改变熔断统计，验证半开、AutoBan、跨实例、关闭和重启。再比较同步、批处理和队列成本；性能候选现阶段只作为实验对照。
3. **鉴权与 Redis 可用性。** 按用户指定的 New API 参考边界验证实际 key/session/租户变更入口、缓存失效失败和 Redis 恢复；将失效延迟明确为实际测得/设计允许的边界，不冒称立即生效。对核心计费和非计费缓存分开决策。
4. **整网关重新压测。** 使用真实 gateway/billing/router/reconciler、模拟上游，多账户和多请求，阶梯及持续开放到达率；记录成功/错误/超时、平均/P95/P99、资源和锁等待，并按请求核对最终余额、账单及 Outbox。至少覆盖零错误及 ≤1% 错误口径，单独报告延迟；未指定 P95 SLO 时不自行声称达标。保留失败样本并等待实际恢复或清楚标为未观察。
5. **部署前验证。** 比较具有相同业务规则和恢复能力的最终方案，覆盖混版、迁移和回退；完成安全审查和真实拓扑容量试验后才能做上线决策。此处没有进行部署、提交、付费调用或生产数据访问。

预占事务再补充：同一事务已执行账单和 Outbox INSERT、提交前，实际杀停隔离 Redis 和 MySQL 事务连接；重试前两行均回滚，Redis 恢复后手动重试一次预占并核对账本，两种恢复顺序各三轮通过。非 COMMIT 确认丢失或整库宕机，详见上述预占中断报告。

预占提交确认补充：真实 MySQL 已提交后测试驱动人为返回确认丢失，同时实际杀停隔离 Redis；初次调用报错但账单已存在，重启后同请求严格重放均识别为重复，三轮账单、事件和余额核对通过。是提交已成功一侧的驱动模拟，不是真实网络确认丢包或全部提交未知情形；详见上述预占中断报告。

预占确认丢失并发补充：MySQL 已提交后模拟丢确认并杀停 Redis，恢复后先让 8 个其他请求竞争；剩余余额不足全部请求时均拒绝，只够一笔时恰有一笔预占，其余 7 笔拒绝，原请求重试仍识别为重复；各三轮账本、余额和预占事件核对一致。是已提交一侧的驱动模拟、单进程 Store 测试，不代表真实网络故障或完整业务。详见上述预占中断报告。
