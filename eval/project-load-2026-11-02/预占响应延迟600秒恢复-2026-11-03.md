# 预占响应延迟后的 600 秒恢复

测试使用本机随机命名的独立 MySQL 8.0.40、Redis 7、真实 gateway/billing/reconciler、64 个合成账户和模拟模型。通过 Go overlay 仅在测试 billing 中让成功预占完成后延迟返回 4 秒；网关预占超时为 3 秒。两轮各 32 总并发、闭环 4 秒，共 128 次 HTTP 503，逐请求对应 128 条 pending reserve、无 usage；这是一项**人为故障注入**，不是自然压测结论，也不是真实付费上游结果。

对账器测试扫描间隔 5 秒，grace 保持真实的 600 秒，关闭余额重建；从负载结束后另等 620 秒，不调整数据库时间。结束时实际记录为 pending 0、reversed 128、settled 0；128 个 trace ID 均匹配唯一一条 reversed reserve、各有 reserve 和 reverse Outbox、无 usage/settle Outbox。64 个账户 Redis 余额与账本核对无差异。完整快照由等待进程在容器清理前读取，独立校验输出为 128/128。共 256 条 Outbox 均未发送，因为 relay 被关闭；此结果不能证明投递成功。

原始目录 `delayed-reserve-recovery-runs/20261103-185252/`：含 overlay 和二进制哈希、请求 trace、恢复前后账务分组、原始 SQL 行及审计。运行进程及快照进程均 exit 0，临时容器已清理。此运行涉及 32 worker、64 个账户种子，负载实际落在前 32 个账户，不能解释此前 1024 总并发产生的自然 pending，也不代表最大容量。未覆盖 Redis/MySQL 崩溃、relay、上游已发送但结果未知、默认 30 秒扫描周期或全部失败时序。

复现：在项目根目录先运行 `python3 eval/project-load-2026-11-02/run_delayed_reserve_recovery.py`；在其输出 `natural pending` 后，从另一终端确认唯一的 `project-delayed-reserve-...-mysql` 测试容器和该次 `delayed-reserve-recovery-runs/...` 目录，运行 `python3 eval/project-load-2026-11-02/watch_delayed_recovery.py <测试容器名> <本次目录>` 以在清理前保存 SQL 快照。两进程结束后运行 `python3 eval/project-load-2026-11-02/verify_delayed_recovery.py <本次目录>`。不要将这些脚本指向任何现有或生产服务。
