# 多账户流式客户端断连与对账

> 版本说明：下面原始结果描述 11 月 4 日的代码；当前工作树对账器已改为默认保留无用量账单。`TEST_CANCEL_DEFAULT_SWEEP=1` 现在显式调用 `WithAutoReverse`，变量名是历史遗留，不能再称其为当前默认配置。当前复测见文末。

## 方法

当前分支 HEAD `63b9d1ed4d64bb583d15fa884c37468e5c53044c` 加未提交工作树，handler SHA256 `68963d65a00062da1d8a878f3155e158ad7e69e22abd16c4503139bfb57b6cf1`、Store `e4a53b0eaca810e385a7336c0ace3b05723313b362342b6094b822bee0d8f98c`。使用随机隔离 MySQL 8.0.40 / Redis 7、真实 handler、billing gRPC/Store 和真实 `SweepOnce`，路由为固定测试替身，没有启动鉴权/限流中间件或完整网关进程。mock 上游在收到并读完请求后发送一帧内容，等待网络上下文取消；客户端在接收该内容后关闭流。每轮 8 个账户各 2 个同时启动的请求，race 三轮。

网关 handler 显式启用 `holdUnknown=true`。16 个 mock 上游各收到一次并观察客户端连接取消；handler 完成后，测试人为将这批 reserve 时间移到一小时前，立即执行两次对账扫描。人为改时间用于触发扫描，未真实等待账单到期；不模拟服务器和客户端之间所有真实网络分区或供应商是否已计费。

## 结果

- `concurrent-stream-cancel-hold-sweep-final.txt`：对账器启用 `WithoutAutoReverse`，三轮中每轮新请求 16 笔均保留 pending、无 usage；每笔一条 reserve Outbox，无 usage/settle/reverse Outbox；八账户 Redis 余额等于账本。两次扫描均保留这批账单。由于三轮在同一隔离数据库运行，扫描统计可包含前轮仍 pending 的账单，逐请求断言只针对本轮。
- `concurrent-stream-cancel-default-sweep.txt`：相同网关保守设置，但对账器采用**默认自动冲正**。三轮中每轮 16 笔无用量账单均被冲正，存在各一条 reverse Outbox，无 usage/settle；第二次扫描无重复冲正。每账户余额与账本仍一致。测试通过表示**复现保守网关与默认对账器组合的风险**，不表示自动冲正安全。mock 不会收费，不能推断实际供应商费用。

这直接说明单独启用网关保守选项不足；默认配置仍可能在上游可能已执行的情况下退款。禁用自动冲正只会保留未知账单，未解决可靠用量获取、自动核对、人工处理、长期积压、旧实例绕过、进程崩溃及完整消息投递。测试中只有一个 mock provider，不证明所有 failover 或 HTTP transport 的行为。两种模式均未启动 relay，事件记录不等于消息消费。
