# 计费入口保护未知状态：保守测试原型

目的：在真实组件组合中验证未知状态必须由计费权威入口保护。`billing_unknown_candidate.go.txt` 仅用于 Go overlay：给测试构建的 Bill 增加 `execution_unknown`，余额和订阅新预占在创建账单的事务中标记 true；测试构建的 `reverseCash` 在操作 Redis 前拒绝该状态的 Reverse。网关同时使用 `gateway_truncated_candidate.go.txt` 返回 502。真实生产源码、配置和数据库未改，测试 billing 的 AutoMigrate 只运行在隔离数据库。

`python3 eval/project-load-2026-11-02/run_unknown_billing_e2e.py` 使用真实 gateway、billing、router、reconciler、独立 MySQL/Redis 和本地截断模拟服务；人为将 grace 缩短到 5 秒、每秒扫描、relay 和余额重建关闭。两轮 `unknown-billing-runs/20261103-205651/`、`20261103-205811/`：模拟上游各调用一次，网关各返回 502，预占在宽限期后仍 pending、`execution_unknown=1`、无 usage 和 reverse；真实对账器日志记录 FailedPrecondition，Outbox 各仅 reserve，余额与账本一致。候选源码及二进制哈希、日志和审计在运行目录中。首次 `20261103-205636/` 因候选生成脚本缩进匹配断言失败，billing 构建在服务启动前失败；记录保留，修正后才进行上述两轮。测试没有真实模型调用或供应商费用。

`bash eval/billing-comparison-2026-11-02/run-unknown-billing-test.sh --candidate` 通过真实 Store、隔离 MySQL/Redis 和 race 重复三轮：明确要求“构造上游请求失败”的 Reverse 也被拒绝；之后提交合成 usage 可以正常 Settle，余额与账本均为 960、指定 reserve/usage/settle 三条 Outbox。输出 `../billing-comparison-2026-11-02/unknown-billing-candidate-test-final-output.txt`。测试 opt-in，仅在测试 overlay 下运行；此试验不声称请求真的未发送，reason 是模拟调用者传入的文字。

**不可部署，亦非最终方案：**

- 所有新预占在发送前即永久标为 unknown，无法区分确定未发送；任何直接或人工 Reverse 都被拒绝，正常退款和恢复行为不等价，pending 会无限积累。
- 当前对账器不知道如何处理该状态，会每次扫描、每次报错；没有限流、状态专用索引/查询、监控、人工处理或可证明的安全解除机制。
- 老账单默认 false、旧版 billing 或其他写入口可能绕过保护；未经验证的混版、迁移和回滚都不安全。上游失败时网关仍可能自动换渠道；本原型没有解决重复上游调用。
- 使用无 usage 的截断场景，未测进程崩溃、发送与退款的真实竞争、Redis/MySQL 故障、订阅、充值/退款、鉴权、多实例、长时负载或性能。5 秒实验不代表默认 600 秒自然等待；另一个旧 billing 的默认 600 秒反例见 `非流式截断响应-2026-11-03.md`。

这个实验表明保护放到真实 billing Reverse 入口可以阻止测试中旧对账器误退款，但只是证明方向。下一步必须设计并验证原子地从确定未发送切换为可能已发送、对已发送结果做可靠回收，以及不依赖自由文本 reason 的可信冲正许可；同时阻断旧服务绕过并提供可审计恢复。
