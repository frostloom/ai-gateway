# 新网关连接旧协议计费的隔离验证

两次隔离实测确认：当前新网关连接不确认重放协议的计费服务时，缺少确认并不意味着预占没有发生。两次首请求均返回 503、模拟模型收到 0 次调用，真实账本各有一笔 pending 预占及 reserve Outbox；同键立即重试为 409。测试对账宽限 30 秒后，两次预占均转为 reversed，无余额差异；同键稍后重试仍为 409。第二次在重试后再次检查，模拟上游调用仍为 0。Outbox relay 关闭，两条 Outbox 均未发送，不能据此判断投递能力。

复现：`python3 eval/project-load-2026-11-02/run_replay_mixed.py`。脚本使用随机名称的独立 MySQL 8.0.40、Redis 7、合成账户和可计数的本地模拟模型。使用当前源码构建新网关；测试用 Go overlay 从当前 billing 的 store 和服务移除重放信号与确认，其余当前修复仍保留。这是**旧协议行为的构造版本**，不是历史版本二进制。对账间隔 5 秒、宽限 30 秒，仅用于加速测试，不代表正式 600 秒。无付费调用及生产数据。

原始记录：`replay-mixed-runs/20261103-175043/`、`replay-mixed-runs/20261103-175257/`，含 HTTP 内容、账本、Outbox、余额 audit、二进制和部分关键源码摘要；第二轮记录额外的协议源码摘要和末次重试后的快照。两轮进程均正常退出且容器已清理。这里未在部署版本间滚动升级，也未验证旧网关接新计费、多实例、Redis 故障、网络不确定结果或所有账务类型。

因此当前协议不是无副作用的能力探测，不能仅凭新网关拒绝缺确认的响应就宣称可安全混部。升级设计还需在开放请求前验证所有路由目标的能力、考虑目标切换与版本降级，以及旧网关仍按旧语义调用的风险；这些措施需要独立实现并测试。账单冲正后，现有 Redis 提交去重键仍会阻止同键重试，不能无条件删除以免已转发请求重复执行。
