# 整网关 Redis 中断与恢复

## 实验

隔离环境运行真实 gateway、billing、router、reconciler、本地模拟模型、MySQL 和 Redis。64 合成账户、请求带不同幂等键；每阶段 20 次/秒、3 秒（60 个计划请求）。依次正常运行、实际 `docker kill` 本次创建的 Redis、重启同一容器并在 `redis-cli ping` 成功后立即发下一阶段。gateway 未重启；严格 V2 和保留未知开启，对账重建关闭，Kafka/Outbox relay 关闭。固定端口只用于本次容器，发压不使用生产数据或付费服务。

| 阶段 | HTTP 结果 | 平均 / P95 / P99 ms | 峰值在途 | 账务观察 |
|---|---|---|---:|---|
| Redis 正常 | 60 个 200 | 70.42 / 87.64 / 130.76 | 3 | 累计 65 笔 settled 含 5 烟测，pending 0 |
| Redis 停止 | 60 个 500，均为 idempotency unavailable | 369.87 / 1271.88 / 1384.76 | 23 | 恢复后按请求 ID 核查，60 个均无 reserve、usage 或 settle |
| 重启并 ping 后立即发压 | 57 个 200、3 个 500（idempotency unavailable） | 74.13 / 97.49 / 205.62 | 4 | 57 个各有已上报 usage 和一次结算；3 个无 reserve |

三个阶段均无发压丢弃。最终累计 settled 122（含 5 烟测）、pending/reversed 0，存在的 Redis 余额键与账本无差异；**7 个余额键缺失**，其中 3 个账户账本已发生消费、另 4 个初始余额未消费。缺失不等于余额错误或余额一致：需要后续读取触发重建及并发安全验证，本实验没有验证这些账户再次请求。最终 366 条 Outbox 均未发送，relay 被关闭，不能说明交付成功。PING 只说明 Redis 能应答，不证明 gateway 的连接池已恢复；3 个错误的具体根因尚未定位。

这只是一次短时故障实验，不是性能容量。只覆盖带幂等键、停机前没有在途请求的情况；没有验证无幂等键、流式、停机发生在预占/结算期间、重试相同键、Redis 主从或持久化、长时间恢复、事件投递及并发重建。Redis 停机时目前返回 500，不应将单纯鉴权回退描述为整网关可用。

## 首次运行与核对工具

首次运行 `gateway-open-load-runs/20261105-012229/` 中，正常/停机分别 60 个 200/60 个 500，重启后 57 个 200、3 个 500；第三阶段逐请求核对通过，但全量余额核对的 seed 工具退出 1，原 runner 未保存其 stderr，因此不能确定失败原因或宣称当次核对成功，原日志保留。

为了不把缺失键误判成一致，测试 seed 增加仅由 `TEST_AUDIT_ALLOW_MISSING=1` 启用的缺失键报告：分别读取相应账本值并列出 `missing_balance_keys`，其他 Redis 错误仍失败；通常运行仍对缺失报错。runner 现在保存核对 stderr，Redis 停机阶段延迟核对并在重启后逐请求检查。复测的 7 个缺失键证明此类状态需要单列，但不能反证首次失败具体原因。脚本端口先释放再由 Docker 绑定，存在端口竞争，失败需保留并退出。

## 补充：缺失余额账户再次请求

新的独立运行 `gateway-open-load-runs/20261105-012704/` 沿用上述 20 次/秒、每阶段 3 秒：正常 60/60 成功；Redis 停止时 60 个 500，恢复后逐请求核查均无预占；重启并 ping 后立即发压有 46 个 200、14 个 500，成功请求各有用量和一次结算、失败请求无预占。没有发压丢弃。重启后首次全量检查发现 18 个余额键缺失（14 个先前有消费、4 个未消费）；不把缺失视作一致。

测试随后**顺序**对这 18 个账户各发送一次新的带幂等键请求，均为有效 HTTP 200；按请求 ID 检查各有已报告用量及一条结算。最终全量检查 64 个余额键均存在且与账本一致、pending/reversed 0、settled 129（含 5 烟测、正常 60、恢复后 46、探针 18），Outbox 387 条均未发送。该结果验证此单次运行中特定账户再次正常请求后的恢复，**不验证同账户并发重建、故障时在途操作、重复旧幂等键或自动全量重建**；请求促使键出现并一致，不单凭结果断言所有内部时序均安全。

重启后 14 个错误高于上一次的 3 个，且 PING 不保证 gateway 的 Redis 连接池立即可用；没有采集逐次拨号原因或定义恢复时间，不能判断根因、上限或生产可用性。一次顺序探针不是容量或稳定性统计。记录 `missing-probes.json`、`missing-probes.csv`、`missing-probes-audit.json`、`audit-before-wait.json` 和 `audit-final.json` 均在原始目录。

## 补充：余额键缺失且余额不足的并发预占

`gateway_missing_balance_insufficient_test.go` 使用真实 gateway APIKey、Idempotency、RateLimit、handler，经回环 gRPC 调用真实 billing 服务和 Store，隔离 MySQL/Redis、本地模拟上游；HTTP 入口使用 recorder，router 为固定测试替身。两个合成账户各有 10 分初始余额、各发 4 个不同幂等键请求，并在开始前删除各自 Redis 余额键。模型价格和请求使每笔预占大于 5 分且不超过 10 分，因此同一账户不可能同时承担两笔预占。

模拟上游在收到请求后暂停，不让首笔先结算；三轮 Go race 均观察每个账户各 1 笔进入上游并保持 pending，另外 3 笔返回 402，合计上游调用 2 次。随后释放上游（合成实际用量 4+2），每个账户各 1 笔 200、1 个 settled reserve、1 条 settle 行，Redis 与账本各为 4 分；每个成功请求的 reserve/usage/settle Outbox 各一条，reverse 为零。失败请求没有产生额外 reserve（逐账户 reserve 行数为 1）。

这是对 Redis **余额键删除**后重建的受控测试，Redis 服务保持可用，不是进程中断/主从切换；客户端请求同步起跑，未插桩确认同时进入重建临界区。测试没有真实网络 gateway、真实模型收费、跨进程、订阅额度、充值、上游等待中再次宕机或 Outbox 投递；不能推广为全部业务和任意并发的安全证明。

## 补充：预占进行中 Redis 实际重启

`gateway_pending_redis_restart_insufficient_test.go` 扩展上一余额不足测试：两个账户各 10 分、各 4 个并发请求；模拟上游暂停时各有 1 笔 pending、各有 3 笔余额不足。此时实际终止并重启测试脚本创建的隔离 Redis，确认两个余额键均丢失；原始上游仍暂停，重启后两个账户各发 3 个新幂等键请求。三轮 Go race 均各 3 个 402，没有新增模拟上游调用；各用原幂等键重试一次均 409，上游调用总数仍为 2。释放上游后每账户各一笔结算，Redis 和账本各 4 分；核对每账户一条 reserve、一条 settle 行及指定 reserve/usage/settle Outbox 各一、reverse 零。

这是单进程 gateway 中间件/handler、回环 gRPC、真实 billing Store、独立 MySQL/Redis 和本地 mock；入口使用 HTTP recorder，router 是固定替身。显式启用 billing 严格 V2，实际默认配置不强制 V2；请求结束状态和幂等保证不能推广到旧客户端/旧 billing 混部。Redis 在预占已经落库、上游开始后被终止，而非 Lua 执行中或 SQL 提交过程中；使用同一容器且测试确认余额键丢失，没有模拟主从或复制、数据库中断、订阅、充值、消费 Outbox 或真实模型费用。新请求按账户并发起跑，不证明进入重建锁的精确交错。
