# Outbox 公平扫描测试候选

## 问题和候选

当前正式 relay 每次从最小未发送 ID 开始取批，持续失败的低 ID 可反复占满批次，参见 `kafka-offset-repro/outbox-starvation.json`。测试目录的 `kafka-offset-repro/fair_scan_test.go.txt` 构建了一个**尚未接入正式代码的原型**：每轮记录当时可见的最大未发送 ID；批次按 `cursor < id <= ceiling` 升序读取；成功或失败均不删除事件，取消时不推进 cursor，扫完后清空内存游标并从头开始新一轮。失败行留在数据库下一轮重试；新的大 ID 留待下一轮。重启时游标从零开始。

该 ceiling 是扫描范围的上界，不是一致性快照。低 ID 事务可能在 cursor 经过后才提交，必须依靠下一轮重新扫描。原型假设连续调用 `step` 以推动轮次；测试中每批只有 1 条，用来显式暴露边界，不代表生产配置或吞吐。

## 真实隔离 MySQL 结果

`kafka-offset-repro/fair-sweep-current.json`：

1. 第一条主投递和 DLQ 持续失败，第二条仍正常标记；失败行保持未发送。
2. 第一轮开始后插入第三条，旧轮按原上界结束，下一轮处理第三条；预先取消的 context 不推进 cursor。
3. 关闭模拟故障并构造新的扫描器（模拟内存游标重置），首条失败事件重新处理。
4. 使用两个真实 MySQL 事务：较小 ID 未提交、较大 ID 已提交并被扫描后，提交较小 ID；旧轮结束后新轮找到并投递它。

上述投递器为内存替身，MySQL 及 Store 为真实实现。Go race 测试通过；原始输出、源码和测试 SHA、镜像 ID、退出码见 JSON；本机链接器有 LC_DYSYMTAB 警告。先前 `fair-sweep.json` 只运行了第一个测试，后续追加测试期间文件有修改，不能用该记录作为当前文件完整覆盖的证据；以上结果以新运行的 `fair-sweep-current.json` 为准。

## 真实 Kafka + MySQL 结果

`kafka-offset-repro/fair-kafka.json` 使用真实 Kafka producer、consumer、relay 和 MySQL Store，但在 producer 前用测试门控对首事件模拟失败：故障期间 1 条保持未发送、后两条已发送；打开门控后下一轮恢复首条，最终 3 个 event ID 均在审计表，0 未发送、0 缺审计。race 测试通过。门控不是实际 broker 崩溃或网络分区；测试也没有验证 payload 的每个字段。

## 限制与后续

该原型不做跨实例领取、分区顺序、持久 cursor、失败退避或 DB 索引优化；多实例可重复发送，进程持续反复重启可反复从低 ID 扫描，超大积压或慢失败会让轮次很长。没有证明严格延迟上界、持续高写入下吞吐、故障暴露期间的数据库负载、真实 broker 失败、长时恢复或和并发投递组合后的正确性。需对 SQL 执行计划、合适索引、有限批次和重试节奏做实测，并结合领取/幂等方案后才能作为正式实现候选。

## 积压分布与查询计划补测

`kafka-offset-repro/outbox_plan_probe.py` 从当前 `scripts/schema.sql` 提取真实 Outbox 建表语句，在隔离 MySQL 8.0.40 内插入 10 万条合成数据；分别令 1% 和 90% 的行未发送，`attempts=id % 7`。对现有索引 `(sent_at, attempts, id)` 和额外测试索引 `(sent_at, id)` 依次运行 `ANALYZE TABLE` 与三次 `EXPLAIN ANALYZE`，不修改正式 schema。只比较数据库执行计划，不执行 relay、Kafka 或并发写入；两种索引顺序固定，缓存热度及优化器统计不可控。

| 未发送比例及索引 | 查询 | 三次执行计划顶层结束时间（毫秒） | 观察到的计划 |
| --- | --- | --- | --- |
| 1%，现有 | 当前取前 100 条 | 3.75 / 2.11 / 2.57 | 按现有索引读 1000 条后按 ID 排序 |
| 1%，现有 | 公平扫描中段取 100 条 | 1.22 / 1.32 / 1.40 | 读取符合范围的 500 条并排序 |
| 1%，测试索引 | 公平扫描中段取 100 条 | 0.168 / 0.247 / 0.169 | 三次均使用新索引范围扫描并返回 100 条 |
| 90%，现有 | 公平扫描 MAX(ID) | 18.6 / 18.3 / 17.5 | 三次均遍历 90000 条未发送索引记录聚合 |
| 90%，测试索引 | 公平扫描 MAX(ID) | 0.000125 / 0.000125 / 0.000167 | 三次显示 `Rows fetched before execution` |

新索引存在时，稀疏数据的当前取批和公平扫描首批仍选择旧索引并排序；密集数据下取批选择主键扫描。因此不能说新增索引会让所有查询都变快。MAX 的 `Rows fetched before execution` 是优化器提前求值，表中时间**不包含完整优化或网络耗时**，不能与普通执行节点计时简单相除。原始 JSON 有每次计划及其余组合；上表不代表稳定延迟、吞吐或生产容量。未测索引维护对预占写入、标记发送、存储空间、锁和高并发的代价，也未测生产数据分布；不建议据此直接添加索引或部署公平扫描。

## 额外索引的并发写入短测

`kafka-offset-repro/indexwrite/main.go` 在隔离 MySQL 建立与 Outbox 同字段及索引的合成表，比较现有索引与额外 `(sent_at,id)` 索引。每组先清空表，16 个并发 worker 各执行合计 2000 次独立自动提交插入，再合计 2000 次通过唯一 event_key 更新 `sent_at`；每次更新检查恰好影响一行，阶段后统计状态行数。三轮交替测试顺序（现有/候选、候选/现有、现有/候选）。这是直接 SQL 微基准，非真实 Store 事务或网关请求，且每组仅 2000 行、没有历史数据、持续读写或故障。

| 索引及操作 | 吞吐（次/秒，三轮） | P95（毫秒，三轮） | P99（毫秒，三轮） |
| --- | --- | --- | --- |
| 现有，插入 | 1889 / 1628 / 1711 | 16.839 / 22.479 / 16.981 | 27.700 / 40.701 / 22.365 |
| 候选，插入 | 2488 / 2061 / 2215 | 9.882 / 14.138 / 11.859 | 11.554 / 32.209 / 15.475 |
| 现有，标记 | 1787 / 1421 / 1699 | 16.460 / 27.009 / 20.140 | 21.807 / 46.978 / 33.966 |
| 候选，标记 | 1654 / 2400 / 1914 | 18.642 / 10.105 / 14.903 | 27.845 / 12.181 / 18.273 |

所有 12 组各 2000 操作零错误，计数核对均为 2000；均值和完整精度在原始 JSON。没有设置单操作超时或单独采集 CPU、I/O、锁等待和索引磁盘大小。结果波动明显，部分候选组反而更快，不能把它解释为新增索引降低了写入成本；主机负载、顺序、建索引和缓存影响没有消除。该短测未证明索引维护代价可接受，尤其不能外推 10 万或百万历史行及业务事务混合负载；继续保留不直接上线的结论。
