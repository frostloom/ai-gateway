# Outbox 死信标记和并发 relay 的恢复测试

## 发现

在修改前，死信已发布但 `MarkOutboxDLQ` 写入失败时，回退逻辑仍增加 attempts；当 attempts 达到上限而 `sent_at` 为空时，`PollOutbox` 不再返回该行。隔离 MySQL 测试 `kafka-offset-repro/outbox-red.json` 实测 `sent_at=NULL, attempts=5`，之后轮询不到。此测试使用替身模拟主 topic 失败和 DLQ 发布成功，并通过 GORM callback 注入标记失败，因此证明的是状态卡住，不能据此断言 Kafka 死信丢失。

另一个独立原因是多 relay 同时读取同一行后各自递增 attempts。`outbox-multi-red.json` 中两个 relay 同时读到 attempts=3，主投递均失败并各加一，结果 attempts=5、未发送且没有任何死信发布；后续轮询不到。实验使用同一进程内两个真实 relay 对象、真实 MySQL Store 和同步屏障控制重叠，生产者是替身；它不是跨进程或真实 Kafka 结果。现有 billing 启动会创建 relay，不能仅凭注释假设多实例中必然只有一个。

## 当前工作树修复

`internal/billing/outbox/relay.go` 在 DLQ 标记失败时不再增加 attempts；`internal/billing/store/outbox.go` 轮询所有 `sent_at IS NULL` 行，不因 attempts 超过上限而排除，具体是否转投 DLQ 仍由 relay 判断。这也让先前已经卡住的未发送记录重新可见。发布成功、标记失败可能重复发布，消费者需要按 event ID 幂等。

`outbox-green.json` 对第一种故障的真实 MySQL + 替身生产者测试通过；`outbox-multi-green.json` 对两种场景均通过，第二次正常 flush 将并发测试的行标记为 DLQ。后者使用 race 检测；链接器有 LC_DYSYMTAB 警告。既有 outbox 包 race 测试也通过。测试原始输出包含代码与测试 SHA、镜像 ID 和退出码。

原有 `TestOutboxLifecycle` 的上限断言已同步修改；`outbox-lifecycle.json` 显示它在独立 MySQL 和 Redis 上通过。运行时仅通过 Go overlay 将测试内硬编码的 MySQL 地址替换成随机端口，Redis 通过环境变量指向独立容器。

复现（只创建、清理脚本自己命名的独立 MySQL 和 Redis 容器）：

```sh
python3 eval/project-load-2026-11-02/kafka-offset-repro/run_outbox.py trial --race
```

## 边界

此改动不提供 relay 领取锁、跨进程顺序保证或恰好一次投递：并发实例仍可能重复发布，主 topic 与 DLQ 也可能都收到同一事件。还没有真实 Kafka 的 broker 故障、提交确认丢失、重复消费端到端核对、多实例长期负载，以及去掉 attempts 筛选后的查询计划和积压性能测试。若永久失败的低 ID 行占满批次，后续事件可能饥饿；需要后续测试和调度设计。现有消费端遇到损坏消息直接提交跳过，消费者在存储故障时暂停所有分区，均不由本次改动解决。

后续已在隔离环境实际复现队首阻塞，并完成一次开启真实 Kafka 的完整网关短测；结果及尚未覆盖的边界见 [开启 Kafka 完整链路并发与积压](开启Kafka完整链路并发与积压-2026-11-04.md)。
