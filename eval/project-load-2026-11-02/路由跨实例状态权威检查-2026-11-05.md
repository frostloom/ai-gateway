# 路由跨实例封禁：MySQL 状态检查候选

上一轮在同进程两个 Registry 中复现：一个 Registry 已将 provider 标记 banned，另一个仍从本地缓存选择该渠道。本次在测试 overlay 的刷新缩锁与可取消取锁候选上增加检查：对缓存里的 provider ID 每次查 MySQL `status=0`，仅让查到的 ID 参与选择；数据库错误时返回错误，不用旧状态放行。它不是生产实现，当前源码的 router 未改。

隔离 MySQL/Redis、Go race 各三轮：两个 Registry 均预热后，第一个提交 ban，第二个随后启动的 Route 不再选择它；老的组合候选三轮返回旧渠道，红灯 `../billing-comparison-2026-11-02/router-fresh-status-red-20261105.txt`。但在读到 active **之后**、返回结果之前人为暂停该查询，再由另一个 Registry 提交 ban，已在途请求仍可能选择该渠道，随后新查询才拒绝。该测试 PASS 表示成功复现时间窗口，不是严格立即封禁保证。这里用主库、同进程对象和受控应用回调，没有副本延迟、跨进程或真实网络故障。

缓存只用数据库核对状态，不重新读取 URL、上游密钥、模型列表或权重；更新地址和密钥后仍可选到旧值，测试三轮复现。关闭测试数据库连接后，候选拒绝选路；这是关闭连接池，不是真实服务器崩溃或分区。因每次命中增加数据库依赖，即使缓存已有渠道，在数据库不可用时也会降低可用性。无法从这次实验推断所有渠道配置或权限已及时更新。

首版候选的包级 race 回归发现空数据库注入会 panic，日志 `../billing-comparison-2026-11-02/router-authority-packages-20261105.txt`；测试原型后续改为返回错误。现有 router 包两个依赖 `New(nil)` 的内存测试因新候选明确拒绝无数据库而失败，gateway client 包通过，日志 `router-authority-nil-packages-20261105.txt`；不能称整包回归通过。最终测试原型对空数据库冷路径也返回错误而非 panic；隔离状态、过期交错、关闭连接、旧配置、nil 以及之前的刷新锁/取消/阈值检查各三轮 race 通过，`router-authority-verified-v2-20261105.txt`。其中旧配置和读后封禁两个通过测试是复现缺陷。没有修改或删除原有包测试。

## 决策与复现

逐请求读取权威状态是一个可验证的参考，但仍有读后竞态和其他缓存字段陈旧，并在数据库故障时拒绝服务；本机短测显示高负载下表现不稳定，**不建议直接接入生产**。Redis 的潜在价值是减少每次数据库读取，但必须另行解决丢失、失效竞态、重启和可接受的陈旧边界；本实验不证明 Redis 方案已经满足这些条件。回报写库失败、半开和混版等问题仍未解决。
