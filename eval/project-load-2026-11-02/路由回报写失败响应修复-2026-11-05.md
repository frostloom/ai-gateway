# 路由回报写失败响应

`Registry.Report` 仍先更新内存，再在对应渠道锁下同步持久化；现在将 MySQL 操作错误返回给 `/report`，HTTP 返回 503 而不是 200。gateway 的现有 `client.Router.Report` 会将非 200 计入 `http_error`，不自动重试，不影响主请求。成功清零、失败计数、AutoBan 三种数据库操作均传播错误，成功路径保留 200。SQL 影响行数为 0 而无数据库错误仍沿用原行为；不能将 200 理解为目标行必然已更新。

隔离 MySQL/Redis，通过 GORM 回调在写前注入失败：原代码三轮均返回 200（`router-report-failure-http-red-20261105.txt`）；修复后写失败返回 503，成功清零、失败计数和 AutoBan 三路径各三轮通过，同渠道顺序、不同渠道并行、刷新/封禁与取消用例同次通过（`router-report-failure-http-green-20261105.txt`）。router 和 gateway client 包 race 通过（`router-report-error-packages-20261105.txt`，含链接器警告），`git diff --check` 通过。

503 只表示没有确认成功：内存可能已经改变，数据库提交结果在真实断连下也可能未知。不能盲目重试，当前没有事件 ID、去重、持久队列、跨实例顺序或自动恢复；gateway 主请求仍会继续。测试注入是写前应用回调，不证明真实网络断开、提交确认丢失、数据库恢复或多实例收敛。该修改提升错误可见性，不是完整可靠回报方案；可能影响外部调用方对 503 的重试行为，应先验证其策略。
