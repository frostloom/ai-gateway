# 有界并发 relay 的完整网关对照

## 方案和验证范围

测试候选由 `kafka-offset-repro/make_parallel_overlay.py` 基于固定 SHA 的当前 relay 源生成，仅在测试目录保留：每个 poll 批最多 8 条并发发布和标记，等待整批结束；现有单条发布/失败/DLQ 逻辑不变。正式 relay 未切换。候选不引入行领取或跨实例排他，可能改变事件发送顺序，也不能解决队首失败占满批次。

已有 relay 测试在 overlay 下以 race 检测通过；`kafka-offset-repro/candidate-fault.json` 的真实隔离 MySQL 故障注入、两个 relay 重叠与既有生命周期测试通过；队首阻塞诊断仍重现。`candidate-kafka-replay.json` 在真实隔离 Kafka 上验证一条消息首次成功发布但标记失败、重投两次消费只形成一条审计记录；此单条测试没有覆盖并发重投。真实 broker 故障、批次部分失败、进程强杀、并发跨实例重平衡和长期可靠性均未验证，不能据此上线。

## 2026-11-05：首条确认后的 broker 停机

扩展上述隔离实验：测试门控让首条真实 Kafka `Publish` 成功返回后暂停，并让其他调用等待；确认该切点后实际 kill 本次 Kafka 容器，再释放门控。当前串行与 8 路 overlay 各在独立环境跑一次：停机时 16 条中 15 条仍未标记，首条已标记；重启并由测试手动重复 flush 后，未发送 0，16 个合成 event ID 均有审计。串行日志中一次 `bump attempt` 遇 context deadline，是测试超时后的可见错误；没有断言每条 attempts 精确值。每组仅一轮，race 通过。

## 两个 relay 重叠读取的真实 Kafka 反例

新测试 Store 包装器让两个同进程独立 relay 分别通过真实 MySQL `PollOutbox` 读到相同 16 条，双方都读取完才释放；此后各自真实向单节点 Kafka 发布并标记，真实 consumer 写 MySQL。当前串行 relay 和更新后的 8 路 overlay 各一个独立环境、各一次 race：每个 relay 均读取并发布 16 条，consumer 成功处理 32 次，audit 16 行、未发送 0，16 条 JSON 与 Outbox 一致。PASS 表示复现重复投递及所测相同内容的审计去重，非恰好一次发布证明。

两个实例在**同一进程**共享 producer 和数据库连接池，通过测试屏障强制重叠，不是两台机器或两进程，也不证明自然流量的重复概率。没有发送失败、broker 崩溃、消息内容冲突、顺序、重平衡或外部副作用核对；其他消费者不能假定都有相同幂等约束。它说明重复来源包含无领取的跨 relay 读取，并非单实例并发特有；候选仍不可部署。

## 标记错误累计指标

工作树 relay 在 `MarkOutboxSent` 或 `MarkOutboxDLQ` 返回错误时新增 Prometheus counter `billing_outbox_mark_errors_total{operation="sent|dlq"}`；标签仅两个固定值，不包含请求、租户或错误文本。计数代表调用返回错误，**不代表数据库确认回滚**。它在本进程内跨 flush 累积，进程重启后重置，需要外部抓取；仍需积压、事件差异和实际告警监控，不能单凭它证明投递成功或自动恢复。

先前单元红灯为发送标记 counter 缺失；修复后 outbox 包 race 通过，含发送及 DLQ 两类错误和后续空 flush。真实隔离 Kafka/MySQL 一次整批重投复测，用 recorder 调用项目 Prometheus handler：首轮 16 次注入发送标记错误后抓到 sent=16，第二轮成功后仍为 16；consumer 处理 32 次、审计 16 行且 JSON 匹配。该抓取不是实际运行的 billing admin 网络端口，DLQ 指标仅单元替身测试；故障为应用层注入，非数据库提交不明或进程死亡。没有全仓回归。
