# 路由熔断阈值计数修复

真实 `Registry.Report` 在失败数达到 `FailThreshold` 时转换 OPEN 并提前返回，漏掉了其他普通失败路径调用的 `persistFail`。修复只在该分支返回前增加一次现有数据库计数更新；仍在原全局锁内同步执行，更新失败仍只记日志。它可能增加一次该分支的锁持有和数据库写入，性能影响未测。

隔离 MySQL 8.0.40 与真实本地 HTTP `/report` 测试设阈值 3：修改前连续三轮在第三次失败时数据库仍为 2，红灯 `router-threshold-red-20261105.txt`；修改后三轮依次检查四次失败各计一次、随后成功清零，全部通过。修正先前用于复现旧行为的多实例测试后，同轮观察两个 Registry 各 10 次失败、数据库 20，重建第三个 Registry 后本地从 1 开始、数据库为 21。重复回报测试仍显示两次相同失败回报被计两次。三种测试各三轮 `-race` exit 0；`go test -race ./internal/router ./internal/gateway/client` 通过。

**边界：**这不解决数据库写失败时 `/report` 仍返回 200、不提供尝试事件身份及幂等、网络重试、提交确认未知、多实例聚合熔断、进程重启、跨实例状态一致性或半开竞态。AutoBan 仍使用本地计数写状态，多个实例连续失败不会自动合并成统一熔断阈值。当前已有缩锁 overlay 是旧源码生成的测试候选，不包含本次修复，禁止用其旧结果代表新工作树。没有做性能测试、全仓测试或部署；不得据此宣称分支适合上线。

## 新增写入的锁竞争风险

`router_threshold_lock_test.go` 使用真实 Registry、隔离 MySQL：为两个不同模型各建渠道，预热渠道 B 的路由缓存；另一个事务以 `SELECT ... FOR UPDATE` 持有渠道 A 的行，再触发 A 首次失败、达到设为 1 的熔断阈值。GORM 回调证实 A 的数据库 UPDATE 已开始；在行锁释放前，A 的回报尚未返回。此时发起 B 的已缓存路由并给 50ms context 截止时间：测试等待 250ms，B 仍未返回；释放数据库行锁后，A 的回报完成、B 返回 `context deadline exceeded`，A 的数据库失败计数最终为 1。三轮 race 均复现。PASS 表示成功复现阻塞，**不是稳定性通过**。

原因是 `Report` 在 `r.mu` 内同步写数据库，而 `snapshot` 也等待同一把 `sync.Mutex`；context 在取锁前后检查，但等待锁的过程不可被 context 中断。新增阈值写入使此前该分支也会遇到这种竞争；原有成功、普通失败及封禁分支已经存在同类锁风险。该测试使用人为长期持锁和单进程直接调用，不说明实际故障的发生频率，也不量化正常负载的性能影响。数据库故障返回 200、重复回报和多实例等风险仍在，**此修复不是上线就绪的路由方案**。不能用牺牲计数或直接套用旧缩锁原型掩盖问题；后续须验证限时锁等待、回报排序、半开和持久化正确性及完整网关负载。
