# 流式 EOF 末行修复

代码基准 HEAD `63b9d1ed4d64bb583d15fa884c37468e5c53044c`，工作树包含此前未提交修改。本次仅使用本机模拟上游及临时隔离 MySQL、Redis，不访问付费服务或生产数据。

`internal/gateway/handler/chat.go` 的流式转发此前在 `ReadBytes` 返回 EOF 时丢弃同时返回的非空末行。因此末行无换行的完整 usage 会被忽略并使用正文估算；末行无换行的 `[DONE]` 不会转发。修复后，干净 EOF 同时返回非空行时先处理该行，然后结束；其他读取错误的部分数据仍不作为完整行处理。

## 验证

- `upstream_truncated_safety_test.go.txt` 的 `TestStreamFinalLineWithoutNewline` 在修复前两个子例失败，记录见 `stream-eof-line-red-2026-11-04.txt`；修复后通过。完整 handler 测试通过 race 检查：`python3 eval/project-load-2026-11-02/run_upstream_truncated_safety.py --suite`。
- `gateway_stream_eof_usage_test.go` 使用真实 HTTP handler、billing gRPC、Store 和隔离数据库，模拟末行无换行的完整 usage。三轮 race 通过，分别核对 HTTP 200、一次上游调用、usage 7+9、实际扣减 16、Redis 与账本余额均 984、三条预期 Outbox 事件。运行 `bash eval/billing-comparison-2026-11-02/run-gateway-stream-eof-usage.sh`，原始输出见 `stream-eof-integration-green-2026-11-04.txt`；脚本启动并清理自己的容器。

这是对现有逐行解析行为的兼容性假设，并非完整 SSE 规范解析；干净 EOF 不证明上游真实执行或费用，也不证明已经收到 `[DONE]`。非 EOF 中断的部分行仍被丢弃。已知无 usage 的已发送未知请求可能被旧对账器自动冲正，相关风险尚未解决，本修复不能作为生产安全保证。
