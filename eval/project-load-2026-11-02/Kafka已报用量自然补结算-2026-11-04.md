# 已报用量但结算失败的自然恢复

## 结果

在隔离完整链路的一个受控样本中，测试 gateway 客户端对一个合成请求的结算 RPC **发送前**返回一次人为 `DeadlineExceeded`。该请求返回有效 HTTP 200；首次逐请求快照为 pending、usage 已报告、settle 行 0。保持默认 600 秒 grace 和 5 秒扫描间隔，负载及初步事件观察后实际等待 **620.006 秒**；真实 reconciler 随后补结算，该请求在重新核对时为 settled、usage 已报告、settle 行恰好 1。日志中人为错误恰好出现一次，前后 trace 对应同一请求 ID。

该结果证明本次**定点发送前失败**在指定条件下能自然补结算，不证明上一次负载自然发生的 9 或 12 笔已恢复，也不是 MySQL 实际锁超时、RPC 网络结果不明或供应商费用的测试。模拟上游不收费；该测试没有通过缩短 grace 或修改账单时间制造恢复。

## 环境和事件

真实 gateway/billing/router/reconciler、Kafka relay/consumer，隔离 MySQL/Redis/Kafka 和 15ms 模拟模型。32 个测试账户、非流 8 个总 worker 两轮，流式固定 128 个总 worker 两轮，每轮 5 秒闭环及排空；使用合成请求追踪。测试 overlay 只针对首个 `idem:` 请求的 gateway `Billing.Settle` 原子注入一次错误，**没有调用那一次 billing Settle RPC**；usage 上报及后续 reconciler 均为真实服务。其他请求不被故意注入，日志确认命中一次。默认禁止无 usage 自动冲正，周期余额重建关闭。

第一轮 89/89 有效 HTTP 200，其中 88 已结算、目标一笔已报 usage 但 pending；最终追踪该轮 89 笔均为 settled 且有一条 settle 行。另一轮流式出现 32 个 billing unavailable，12 笔无 usage 的 reserve 在最终仍 pending；最终全局 settled 653、pending 12、reversed 0、余额差异为空。保留无 usage 的账单不是自动恢复，不能推断上游是否实际收到请求。

最终 Kafka 事件 ID 核对 Outbox/audit 均 1971、未发送 0、缺审计 0、多余审计 0；该核对仅比较 ID 和数量，不是 payload 或实际 broker 故障下交付保证。未覆盖真实锁争用、并发扫账、进程重启、对账期间 Redis/MySQL 故障、多实例/旧版本及未报告 usage 的真实计费恢复，不能据此声明整体安全或生产容量。
