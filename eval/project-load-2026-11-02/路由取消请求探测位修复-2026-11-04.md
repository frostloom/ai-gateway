# 路由取消请求的探测位和缓存刷新

当前分支基于 HEAD `63b9d1ed4d64bb583d15fa884c37468e5c53044c` 和未提交工作树。原 `router.NewHTTPHandler` 使用不带请求 context 的 `RouteExclude`，其 `snapshot` 和选路均等待全局 mutex；客户端断开后，服务端仍可能在拿锁后查询渠道或占用 half-open 探测位。

## 受控复现与修复

`router_canceled_probe_test.go` 使用真实 router HTTP handler/Registry、隔离 MySQL 和 GORM 回调：渠道 B 的 Report 在数据库更新前持有路由全局锁；渠道 A 已进入可探测状态；HTTP `/route` 已进入服务端后客户端取消，再释放 B。修改前三轮，取消的请求仍占用 A 的探测位，后续有效 Route 返回 nil；红灯 `router-canceled-probe-red-20261104.txt`。测试将 cooldown 人为设为负值，确保目标可进入 half-open；不是自然等待，也不代表生产出现频率。

第二个用例使用未缓存模型，在同样的锁等待期间取消请求；首次修复只在选路锁后检查 context 时，取消请求仍在 snapshot 处执行一次 provider 查询，三轮红灯 `router-canceled-refresh-red-20261104.txt`。这是 GORM 查询回调计数、受控同进程交错，不是网络故障模拟。

工作树现添加 `RouteExcludeContext`；HTTP 路径传入请求 context，snapshot 拿锁后先检查取消并在 SQL 使用 `WithContext`，选路拿锁后再次检查，避免已取消请求在这些检查点之后刷新缓存或占用探测。原 `Route`/`RouteExclude` 保持签名，使用 `context.Background()`，其他直接调用者不自动获得取消能力。最终两个定向用例各三轮 race 通过：`router-canceled-probe-final-20261104.txt`、`router-canceled-refresh-green-20261104.txt`；`go test -race ./internal/router -count=3 -v` 通过，日志 `router-canceled-final-suite-20261104.txt`。复现 `bash eval/billing-comparison-2026-11-02/run-router-canceled-probe.sh` 和 `bash eval/billing-comparison-2026-11-02/run-router-canceled-refresh.sh`；脚本只创建并清理自身隔离容器。

## 边界

mutex 等待仍不可中断，取消请求需要等持锁者释放后才返回；检查与占位之间仍可能发生并发取消，不能声称完全杜绝所有取消时序的探测位占用。数据库驱动与连接取消语义、连接中断、实际网关超时及多进程尚未验证。该修复不缩短 Report 持有全局锁的时间，也不能解决回报丢失、全局熔断一致性或直接证明吞吐提升；需要重跑全链路性能。没有部署、提交或访问生产。

## 已进入数据库阶段的取消对照

`TestRouterCanceledInflightCacheQuery` 使用隔离 MySQL、真实 Registry 和 GORM 查询回调，在缓存未命中持有路由锁时注入 `SELECT SLEEP(5)`，请求 context 超时 200ms；随后验证新的正常请求仍可选到渠道。为对照构建测试 overlay，只去掉 provider 查询的 `WithContext(ctx)`，保留其余检查。基线三轮均约 5.00 秒才返回 deadline 错误，`router-canceled-query-red-20261104.txt`；当前代码三轮约 201–202ms 返回，随后正常选路成功，`router-canceled-query-green-20261104.txt` SHA-256 `ee1dd27cc02735013c7cb219fd2db3d5ba80c2b8c9d76973377942930f5ce37f`。这验证受控慢 SQL 场景下应用侧路由锁能提前释放，并非证明 MySQL 服务端的语句立刻终止，也不证明真实网络断连或高负载吞吐。
