# 对账库默认保留未知账单

## 变化

上一轮只将 `cmd/reconciler` 的启动默认值改为保留未知账单，直接调用 `reconciler.New` 仍默认自动冲正。现在 `internal/billing/reconciler/reconciler.go` 的 `New` 也默认保留无用量 pending；新增显式 `WithAutoReverse()` 恢复旧规则，已有 `WithoutAutoReverse()` 保留。`cmd/reconciler` 在显式 `-no-auto-reverse=false` 时使用 `WithAutoReverse()`，因此原命令行兼容开关继续生效。已记录 usage 的账单仍按原逻辑补结算。

这会改变未显式设置选项的库调用方行为：未知账单可能长期保留预扣。旧进程、显式启用旧规则的调用方、直接调用 billing Reverse 的入口以及旧版混部仍可退款；缺失 usage 不证明上游没有执行。此改动不是跨服务权威状态协议，也没有完成自动核查或资金释放流程。

## 测试

独立本地 MySQL 8.0.40 / Redis 7、真实 Store 与 `SweepOnce`、合成账单、race 三轮：

- `reconciler-default-hold-red.txt`：修复前无选项时，未知账单被冲正、已上报用量账单结算，违反保留断言。
- `reconciler-default-hold-green.txt`：修复后无选项时，未知账单 pending、已知用量账单 settled；重复扫描后 Redis 和账本均为 860 分，指定 reserve/usage/settle/reverse Outbox 数符合断言。
- `reconciler-explicit-legacy-cancel-green.txt`：流式客户端断连场景显式使用 `WithAutoReverse()`，三轮每轮 16 笔无用量账单仍被冲正，余额与账本一致；这是旧规则风险复现，不是安全通过。
- `reconciler-legacy-scan-after-default.txt`：显式旧规则下仍复现扫描后 usage 已提交但冲正先行的竞争；`reconciler-legacy-stats-after-default.txt` 验证已结算不被错误计作冲正。为保留此前风险和旧路径测试的原意，相关测试和 `stale-sweep` 测试工具现显式使用 `WithAutoReverse()`，没有把旧路径标记为安全。
- `reconciler-library-default-process-green.txt` 使用不传保守选项的真实 gateway/billing/router/reconciler 和本地 mock；上游收到请求后返回 503，账单在测试宽限后及对账器干净重启后仍 pending。`reconciler-library-explicit-legacy-green.txt` 验证重启时显式 `-no-auto-reverse=false` 仍执行旧冲正。每项一次，grace 5 秒仅为加速测试，未测试真实收费、强杀或混版。

`go test -race ./cmd/reconciler ./internal/billing/reconciler ./eval/project-load-2026-11-02/stale-sweep` 编译通过，以上三个包无直接测试文件；行为证据来自上述隔离集成测试。当前 `cmd/reconciler/main.go` SHA256 `2754d55661d77179c7ec1754fcfafd037a026a92d6c08a1431edc76f23ac09a0`，`internal/billing/reconciler/reconciler.go` `8fb86eb5009f556b1e5e1dc44a372d23afba7df76c883d0ae5bacf65d47cfa6e`。Outbox relay 关闭，未验证事件投递。
