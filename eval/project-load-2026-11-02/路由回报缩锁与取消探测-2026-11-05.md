# 路由回报缩锁与取消探测

当前工作树的 `Registry.Report` 持全局状态锁等待数据库。随机隔离 MySQL/Redis 下应用回调暂停一次写入，三轮均复现缓存命中选路和另一渠道回报被阻塞；同渠道先成功后失败的顺序测试三轮通过（`router-report-main-red-20261105.txt`）。这是受控阻塞，不证明前次 80/s 全部超时的原因。

尝试按渠道串行回报、在状态锁外写数据库，并在 AutoBan 写入前后使缓存失效；同渠道顺序、跨渠道并发、缓存选路及刷新/封禁定向测试三轮通过。但 `TestCanceledRouteDoesNotConsumeHalfOpenProbe` 三轮失败：该测试通过阻塞另一渠道回报来迫使路由等待，发送请求后取消，再检查半开探测位。缩锁后路由可能在客户端取消前完成选路并占用探测位，后续选路得到 nil。测试的信号只保证 HTTP handler 已开始，不保证取消先于选路，因此不能单凭该失败断言服务端在已知取消后仍选择了渠道；但它暴露了“选路已完成、客户端取消或响应丢失”与探测位释放之间的未解决窗口。日志 `router-report-main-green-20261105.txt` 包含这三次失败，文件名不代表整套通过。

因此暂未采用本次回报缩锁，将 `registry.go` 恢复到此前已验证的缓存刷新缩锁版本，SHA-256 `d4072bc427069995bbd1086164836d431cc0bf5adf8e8c28f8e62b4261b8bd88`。回退后取消探测、取消刷新、刷新竞争与阈值定向测试三轮 race 通过（`router-report-reverted-check-20261105.txt`），router/gateway client 包 race 通过（`router-report-reverted-package-20261105.txt`）。当前仍存在回报写失败可能返回 200、持锁慢写阻塞选路、跨实例顺序和已选路后取消窗口；不能声称该问题已修复。下一步需明确探测尝试身份和过期/回报关联，构造确定性屏障覆盖取消前选中、取消后选中及迟到回报，再重新考虑缩锁。

测试只使用脚本新建隔离数据库，未连接生产数据、调用付费模型、部署或提交。

## 选路和取消的确定顺序

`router_probe_cancel_order_test.go` 使用真实 Registry 与隔离 MySQL，先使渠道进入可探测状态：已取消 context 的选路被拒绝、探测位未被占用；另一请求明确完成选路后再取消，不发送回报，则下一次选路发现探测位仍被占用，随后模拟成功回报才恢复。三轮 race 通过，日志 `router-probe-cancel-order-20261105.txt`。该测试使用直接函数调用，证明的是工作树既有行为，不是网络断连或真实 HTTP 何时收到响应，也未等待 30 秒自然过期。

这一结果说明上节缩锁后的 HTTP 测试失败可以由「已完成选路后客户端取消」这一旧有窗口解释，不能单凭它证明缩锁引入新的探测错误；也不能因此证明缩锁后所有竞态安全。当前回报缩锁仍未重新接入。
