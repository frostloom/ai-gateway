## 提前补结算的边界核查

当前 `ReportUsage` 对 reserve 行加锁，首次写入用量 marker 与 usage Outbox 在同一事务，后续同值可重放、不同值拒绝；`SweepOnce` 目前以 `created_at` 对所有 pending 统一应用 grace。可以研究仅对已持久化用量、且 marker 已有一定年龄的账单提前补结算，但 marker 是否为所有调用者的最终用量、与正常结算/冲正并发、数据库压力和多实例扫描均需验证；不能将无用量账单一起缩短等待，不能仅凭缺少 marker 推断上游未执行。

## 冲正调用入口核查

按当前工作树非测试 Go 源码搜索：billing gRPC `Service.Reverse` 直接调用 `Store.Reverse`，服务端统一要求控制面令牌；`Reason` 用于日志，Store 的现有冲正路径不按 reason 或 usage marker 禁止冲正。gateway 的非流式和流式路径在构建上游请求失败时调用冲正；旧非保守模式还在上游 4xx、所有渠道失败时冲正。默认保守模式对收到的非 2xx 或未知网络结果保留 pending。reconciler 默认禁止对无 usage 自动冲正，但可显式启用旧行为；扫描后无用量变为有用量的竞争已有独立复现 `reconciler_usage_scan_race_test.go`。本次搜索覆盖仓库内非测试 Go 调用，无法排除其他服务通过持有令牌的 gRPC 客户端调用，也不能据此证明所有冲正均只发生在无用量时。

已记录用量的提前结算会缩小后续显式冲正获胜的时间窗口，和当前允许冲正的语义不完全等价；若要落地，必须先明确冲正原因、授权和状态转换，验证已在途调用、旧实例/外部调用与订阅等路径。不能为了减少恢复时间直接在所有已报用量账单上禁止 Reverse，也不能把默认关闭自动冲正等同于所有冲正入口受保护。
