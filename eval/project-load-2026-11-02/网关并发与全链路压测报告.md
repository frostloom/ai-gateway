# 网关并发与项目链路压测报告

## 判断

在这台本机、模拟上游和下述配置中，**64 个账户共享 256 个非流式并发请求**，两轮 HTTP 错误均为 0，成功吞吐 104.8–108.5 次/秒，完整响应 P95 为 2.69–2.93 秒；增加到 512 并发，两轮错误率为 4.9%–5.1%。每个账户可以同时发多个请求，64/256 场景为每账户四个并发 worker。类似地，256 个独立账户各发一个请求，两轮也零响应错误，但 P95 为 3.23–3.67 秒。

这些是**两轮、每轮 5 秒**的观察，不是生产最大容量；未约定 P95 可接受阈值，因此即使错误率为零也不能认定满足业务目标。8 账户共享请求时结果非单调：64 并发一轮错误 6.1%，另一轮零错误，而 128 并发两轮零错误；短时波动和运行顺序使其不能被解释成可靠的单一阈值。单独测试到更高并发并不表示系统稳定支持该并发。

启用 Kafka 后，64 账户/256 并发的 HTTP 两轮也零错误，但 Outbox 积压持续增长，停止负载后约 33 秒仍有 13,550 条未投。因此**不能把 256 称为整个项目可持续稳定并发**。一项高压逐请求测试还确认了 HTTP 200 但账单仍 pending 的情况，见下文。

## 覆盖与隔离

测试真实本分支 gateway → API key 鉴权、Redis 限流 → router → billing gRPC 预占 → 本机 mock provider → billing 用量/结算 → MySQL bill/Outbox；并行运行 reconciler，设置 5 秒 sweep、600 秒宽限期，不运行 rebuild。非流式及 SSE 皆测。客服单独测试 gateway `/portal/chat` → agent → 本机 mock；计费事件单独启动隔离 Kafka、Outbox relay 和 event-consumer。

尚未覆盖：真实模型/网络及多地域、真实 JEV、客服工具调用和写操作、充值/退款/订阅规则压力、管理员/门户其他业务、浏览器渲染、多条业务链路同时混合、Kafka 多副本和故障切换、长时耐久、生产部署拓扑以及对账修复的完整过程。本报告不能称为全项目所有功能的容量验收。

所有容器与业务库为一次性隔离实例，使用 1,024 个合成租户及 API key、模拟模型和虚构余额；mock provider 只监听本机，非流式固定附加 15 ms，流式另分块间隔 50 ms，输出上限 100 token。客服固定 model 路由，JEV 关闭、LLM URL 显式指向本机 mock；不调用付费 API。业务实例只连接脚本创建的随机 loopback 端口；Kafka 为独立单 broker/3 分区。所有容器和自有进程在测试结束后清理，测试数据库不保留；原始响应统计、账本快照和日志留在各结果目录。没有部署或提交。

机器 Apple M1 Pro、8 逻辑 CPU、16 GiB 内存，Go 1.25.12、Docker 29.8.2；进程 `GOMAXPROCS=8`；MySQL 8.0.40，默认 151 最大连接、128 MiB InnoDB buffer pool，billing SQL 池最多 100；Redis 7.4.11。机器其他服务持续运行，压测发起端与服务同机，并非隔离资源。各测试阶段顺序固定、持续 5 秒再排空，非随机且负载运行期间采样资源，账单历史逐步增长。

主要多账户测试保留 gateway 默认 **600 次/分钟/租户**限流；worker 以 `worker_index % 账户数` 分配账户，同一个账户可以有多个同时请求。单账户对照 `runs/20261102-174857` 为研究热点临时提高至 100,000 次/分钟，不能与默认限流直接等同。请求不携带幂等头；下文逐请求定位实验另行启用唯一幂等头。RPS 是**有效响应完成数 / 从发起到在途排空的墙钟时间**，P95/P99 为所有完成请求（含错误）的端到端延迟；流式要求完整收到 `[DONE]` 与 usage。错误率分母含 HTTP 非 200、超时、传输错误及无效 200。每组两轮、每轮仅 5 秒；不等于开放到达率或稳定长时流量，不能排除客户端发压瓶颈或协调遗漏。

## 逐请求账务核查与错误

最初提高限流的单账户 512 并发阶段，最终累计出现 144 笔 pending，累计有效 HTTP 200 数比 settled 行多 129；余额与账本公式一致，因为公式包含 pending。该差额是聚合对比，不能单独把每一笔差额归因到特定响应。日志中该阶段出现 MySQL 1040 `Too many connections` 和结算超时；一次全局状态快照显示最大连接使用 152、`max_connections=151`、连接上限错误累计 135（管理员保留连接可使读数高于设置）。这是该隔离运行中的证据，不证明所有 401/503 均由连接数造成。

为确定 HTTP 与账务的对应关系，补测给每个请求加独一无二的合成 `Idempotency-Key` 并保存请求状态/账单映射；该额外 Redis 操作使它不是无幂等头基准的完全相同负载。在 `trace-runs/20261102-182754` 的单账户/512 并发两轮，分别有 **6 和 3 个有效 HTTP 200** 对应 reserve `pending`、usage 已上报、settle 行为 0；还分别有 2 和 2 个 HTTP 503 对应 pending、usage 未上报。该运行随后因测试发压器错误地限制账户数为 8 而在下一组退出 1；前两组已完成、映射和失败日志均保留。

修正发压器账户数上限后，在独立的 `trace-runs/20261102-182956` 以 64 账户/512 并发跑两轮，分别有 953 和 1,017 个有效 HTTP 200，逐笔均为 settled 且各一条 settle；另有 10 个 401、8 个 503 对应无 reserve。该受控样本未在多账户 512 复现 HTTP 200/pending，不能推断其他分布或更长时间都不会发生。用户密钥均为合成有效 key；`internal/gateway/middleware/apikey.go` 将 billing 鉴权调用的错误和无效密钥都映射为 401，隔离账务日志亦观察到 `ValidateAPIKey` 查询 `context deadline exceeded`；不能仅凭 HTTP 401 判断密钥错误，也无法由现有数据将每个 401 精确归因。

非流式处理在 `internal/gateway/handler/chat.go` 调用 `settleAndLog` 后仍写 HTTP 200，而该函数在用量或结算失败时只记录日志并返回；流式已发送内容后也可能遇到后置结算失败。这是高压下需要优先评估的行为，不能以 HTTP 状态代替账务终态。余额/账本一致不等于账单已结清。测试未运行针对这些 pending 的 600 秒后实际修复。

## 资源与瓶颈线索

`resources.jsonl` 保存约每秒的 `docker stats` 和服务进程 `ps` 样本，进程名映射见相应 `process-identities.txt`；不含独立发压进程的 CPU，且采样不能保证抓到峰值。多账户共享、Kafka 关闭的一次运行中，采到 MySQL 容器 CPU 最高约 260.6% 和内存约 544.7 MiB、Redis 约 18.1%/11.1 MiB；这是全运行各采样点的最大值，Docker 多核 CPU 可超过 100%，不是单一场景的平均值，也不能单独证明饱和或因果。具体 I/O 快照、网络流量在原始 JSON；未取得磁盘设备字节级消耗、连接池逐服务峰值或负载端资源占用。

64 账户/1,024 并发的混合测试中，网关在途接近发压 worker 数但失败率超过 44%，说明接受连接/请求数量和成功服务能力不同。高压热点测试的 1040、billing 使用最多 100 连接、router 未显式设置池上限和 reconciler 的 10 连接池都值得继续定位，但不能在未逐进程观测连接及排队前断言某一个是唯一根因。优先建议：区分鉴权故障与无效 key 的响应；对 HTTP 成功但账单未终态建立明确对账/告警和恢复语义；测量并优化 Outbox 发布积压和分区键；补充连接池、队列、数据库和依赖故障指标，再在接近实际部署及读写比例下重复长时开放到达率测试。
