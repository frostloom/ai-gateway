# Kafka 账户锁插桩：本机环境启动失败

为区分连接池等待、MySQL `GET_LOCK` 调用耗时及账户锁持有段，`run_kafka.py` 增加测试开关 `KAFKA_TEST_LOCK_TIMING=1`，只在临时 billing overlay 对 `billing:cash:` 锁记录客户端耗时；保留原锁和业务逻辑。连接池计时从进入锁函数到开始 GET_LOCK，GET_LOCK 包含网络和客户端调度，持有段到释放闭包开始为止，不是服务端精确持锁时间。按锁逐次写日志会影响负载，不能与无插桩结果直接比较。

两次尝试均未进入发压，**没有产生锁等待分布或网关吞吐结果**：

1. `kafka-runs/20261104-182124/` 在本机隔离 MySQL 初始化期间超过旧就绪探测上限，脚本 exit 1、`error.txt` 显示 MySQL readiness timeout。观察到 MySQL 初始化持续数分钟；这不证明产品数据库的实际启动时间或物理根因。
2. runner 改用单调时钟、有界 MySQL 就绪等待和单次探测超时，设置 `KAFKA_MYSQL_READY_SEC=600` 后重新启动隔离环境。MySQL 后续报告 ready，但 Kafka 就绪探测持续未完成，容器日志多次出现控制器心跳 `REQUEST_TIMED_OUT`。期间本机 `uptime` 曾显示 load averages 27.37/38.75/38.03，后为 19.50/24.90/29.92；不能仅据此证明 Kafka 故障原因。环境准备超过十分钟且持续心跳超时后，主动向本次 Python 测试进程发送 SIGINT，exit 130；负载从未开始。Python 的清理后，发现本次 Kafka 容器已退出但仍存在，已额外只删除 `project-kafka-load-63d4cc6033b2-kafka`；两个本次运行的随机容器前缀最终查询均无残留。本次不是正常完成，不能用于判断插桩或性能收益。

HEAD `42d8ef8e5ca2471b18800e50f8e7a57fbcfdd47f` 加未提交工作树；当前 runner SHA-256 `dcd9af71ea4c549d01a71162801f5463eeac58a146c1e4ce676428a3f23299b8`，第一次 `error.txt` SHA-256 `d1e2288cc38f0485cc91528006dd5e489e8dc8bd2cc884f14e3f46d00219fcb2`。第二次为主动中断产生的 KeyboardInterrupt，不属于脚本的 `Exception` 分支，因此没有 `error.txt`；以上为运行中读取的进程状态和容器日志摘要，不伪称保存了完整容器日志。两次编译出的临时 overlay 摘要记录在各自 `billing-lock-timing-sha256.txt`，临时构建目录已清理。

```sh
  KAFKA_LOAD_STAGE_DETAIL=1 KAFKA_TEST_LOCK_TIMING=1 \
  python3 eval/project-load-2026-11-02/run_kafka.py
```
