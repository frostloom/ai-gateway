64 合成账户、每个账户可多个请求；模拟上游等待 15ms 后发送 8 个内容块，每块间隔 250ms，随后发送 usage 和 `[DONE]`，总模拟输出约 2 秒。模拟服务为仅测试 overlay，其 hash `b055ffe50d3ea38fc1b482ff39a676fa6a1d2288492dda49c74cfc7a75bcdacf`。gateway 使用错误诊断 overlay；hold-unknown 与 v2 屏障开启，600 秒对账宽限、自动无用量冲正与余额 rebuild 关闭，Kafka/Outbox relay 和 Agent 关闭。各开放到达率 15 秒×2，发压上限 1000 在途。

## 核对和资源

319 个失败均为 HTTP 503 路由不可用；诊断为路由 deadline，无法仅凭本次结果判定具体锁或数据库根因。最终审计 14086 笔 settled（含 5 条非流式烟测）、pending 0、余额差异 0，逐轮累计 settled 与有效完整 HTTP 数一致；Outbox 42258 条均未发送（relay 关闭），不证明消息交付。MySQL 最大连接 103/151、连接上限错误 0、行锁等待 10 次共 108ms，未包括命名锁；Redis 全过程累计命令 454014、峰值内存 8.91 MiB，含初始化与核对。资源采样不支持逐请求 CPU/I/O 归因。

测试发压器现以读取第一个响应体字节记录首体时间，只对最终完整成功流计算首体分位数；日志中的完整延迟也包括失败。旧 400ms 流测试使用不同时间的先后运行和先前发压器构建，不能把差异作为严格因果比较。未覆盖真实供应商、数分钟流、长时间稳定、Kafka 和完整管理面，目标继续。
