# 预占空查询日志与网关负载对照

## 问题、修改和正确性

之前的 20261104-224746 全网关运行中，billing 日志约 4.65 MB，共 11833 次 `record not found`，均来自 `getReserve`；首次预占时不存在账单是预期结果，但 GORM `First` 以 error 级输出查询和合成请求 ID。它可能产生额外日志负载，日志数量与超时同时出现不证明因果。

工作树 `internal/billing/store/mysql.go` 的 `getReserve` 改为按 ID 升序 `Limit(1).Find`，用 `RowsAffected == 0` 表示无记录；数据库错误仍直接返回并由现有 GORM logger 记录。原本的查询顺序、余额及幂等规则不变。`reserve_lookup_log_test.go` 在隔离 MySQL/Redis 验证首次预占、重复预占、账本及余额 900、不存在的结算返回 NotFound、关闭测试数据库后错误不被忽略且有日志；原实现三轮因预期错误日志失败（`reserve-lookup-log-red-20261104.txt`），当前实现三轮 race 通过（`reserve-lookup-log-green-20261104.txt`）。完整 Store 包 race 通过，两个 opt-in 测试跳过（`reserve-lookup-log-full-store-20261104.txt`）。这不是整项目测试，也未验证所有数据库版本和真实故障。
