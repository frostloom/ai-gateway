# 路由刷新与取消：组合测试及跨实例缺口

缓存刷新缩锁候选仍会被 `Report` 持有的全局状态锁阻塞。真实隔离 MySQL 中人为持有 provider 行锁，使达到熔断阈值的回报在写入时占住状态锁；另一个已缓存渠道的选路 context 为 50ms。刷新缩锁候选三轮均在释放数据库锁之前没有返回，失败日志 `router-refresh-report-lock-red-20261105.txt`。释放后才返回 deadline；此实验只证明该受控时序，不量化线上发生概率。

在测试 overlay 中组合现有 1ms `TryLock` 轮询与刷新缩锁：只修改选路与刷新中需要状态锁的等待，使 context 到期可返回；回报、MySQL 写入和全局锁本身未改。隔离 MySQL/Redis、race 三轮中，被锁住的回报仍等待，而另一个选路在释放数据库行锁前返回 deadline；之前的刷新并发、单实例封禁代次、刷新许可取消及半开探测取消、阈值计数测试同次通过。日志 `router-refresh-deadline-combined-20261105.txt`。这是受控次序，不证明精确时间上限、公平性或所有取消窗口；轮询的 CPU/内存成本尚未独立测量。组合 overlay 下 router 和 gateway client 包 race 回归通过。

## 跨实例失效风险

`TestRouterRefreshLocalGenerationDoesNotInvalidateOtherRegistry` 使用同一隔离 MySQL 和同进程两个独立 Registry，均预热同一渠道。第一个 Registry 将 provider 的 DB 状态更新为 banned 后，第二个仍从本地热缓存选中该渠道。当前生产代码与组合 overlay 各三轮均复现；测试 PASS 表示风险已复现，不是正确性通过。两个 Registry 是同进程对象，不是两个独立进程或网络分区；不代表所有状态变化都存在相同现象。当前代码中的缓存 TTL 为 30 秒，但本测试没有自然等待到期，也不能保证 30 秒是任何故障条件下的严格失效上限。一个实例内的代次检查不能传播到其他实例；简单 Pub/Sub、Redis 投影或 TTL 都需要处理丢消息、重连、状态回滚、写入与回填交错。
