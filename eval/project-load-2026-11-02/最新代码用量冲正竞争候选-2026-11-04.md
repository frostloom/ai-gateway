# 最新 Store 用量与冲正竞争候选

## 范围

`build-current-usage-reverse-candidate.py` 从当前 Store SHA256 `e4a53b0eaca810e385a7336c0ace3b05723313b362342b6094b822bee0d8f98c` 构建测试 overlay `usage_reverse_current_candidate.go.txt` SHA256 `095480cd590d6dcfd8ae7895e0b1aee28b06c1aa4a665acf0c85f70104f5fc84`，避免旧版完整源码覆盖后来的余额重建、指纹及订阅修复。ReportUsage 持请求级 MySQL advisory lock；Reverse 在现有租户锁后获取同一请求锁，并在请求锁内重读账单。仅当 `Reason` 精确为 `recon:no_usage` 且账单已有 usage 时拒绝冲正。发生终态恢复前先释放请求锁以避免持请求锁等待租户锁，并 defer 释放以处理 panic。测试 overlay 没有接入生产。

`Reason` 是自由文本，不能用于可信授权；已有账单的人工冲正规则与无用量、已发送未知结果均没有由该候选解决。故**不能部署**，也不能将该结果当作完整计费安全。

## 正确性与故障

- `usage-reverse-current-regression-final.txt`：基线在 usage 先提交后仍成功冲正，预期失败；overlay 在隔离 MySQL/Redis 下通过 usage 先、reverse 先、并发各 15 次及选定 Store race 回归。用量成功后仍 pending 时再结算，逆序则冲正；逐轮账本与 Redis 一致。并发轮次不保证锁竞争实际重叠，固定顺序覆盖各自结果。输出中的基线 FAIL 是有意保留的反例。
- `usage-reverse-current-disconnect-final.txt`：两个受控切点各三轮，实际 `KILL CONNECTION`：用量事务在写前断连后新冲正成功；冲正检查后、Redis 变更前持锁连接断开，新用量成功后结算。unexpected EOF 为注入结果。
- `usage-reverse-current-terminal-kill-final.txt`：结算与冲正各三轮，在 Redis delta 后、事务提交前杀连接；当前 Store 的重锁修复在 overlay 上恢复账本投影，显式重试得到各一条事件。测试没有在两个锁之间注入并发竞争，也没有验证 COMMIT 确认丢失。
- `usage-reverse-panic-lock-final.txt`：真实 Store 测试 overlay，在冲正写 MySQL 的应用回调中注入 panic，确认 request advisory lock 已释放；后续用量与结算成功、余额和账本 460，三轮通过。这是进程仍存活并由测试捕获 panic，非进程杀死。
- `usage-reverse-reason-bypass-final.txt`：三轮均复现先提交 usage 后，以 `Reason=manual` 调用 Reverse 仍成功、之后无法结算；测试 PASS 是确认候选**可被不同原因绕过**，不是安全通过。此行为也可能对应现有人工冲正规则，不能不经明确协议就把它当作可直接删除的行为。

受控测试没有验证已发送但无用量的退款许可、真正的服务端身份授权、旧版本绕过、混版或跨服务恢复、不同请求竞争、长期死锁/负载和 Outbox 消费。候选会增加一次请求锁，未在最新工作树做整网关性能对照；它只是为后续正式协议提供局部证据。
