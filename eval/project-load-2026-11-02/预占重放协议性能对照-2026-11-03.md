# 预占重放协议：隔离完整请求短测

## 条件和可比性

`replay-perf-runs/20261103-172541` 在同一隔离 MySQL 8.0.40、Redis、本地 15 ms 模拟上游上启动两组 gateway/billing：baseline 由测试时 Go overlay 仅移除重放协商和 Store 的重放信号，保留该时点其他修改；strict 使用当前新增协商。两者业务语义不同：baseline 对 pending 同 ID 重放可能再次调用上游；strict 返回 DUPLICATE 并在 gateway 拒绝。本实验只发送无客户端幂等键的正常请求，不能测这项安全收益或故障恢复。

两组服务同时常驻但顺序发压，共用 router、reconciler、MySQL 和 Redis，768 个测试账户分成 12 组，每阶段使用不同的 64 个账户；第 769 个只用于两组冒烟。16、64、256 均表示**所有账户共享的总并发请求数**，不是每账户。每档各两轮，每轮闭环 3 秒并排空，第二轮反转两方案顺序；每阶段账户历史起点相同但全局表和宿主缓存随运行增长，不是随机严格配对。模型调用为免费本机模拟，Kafka 关闭，限流 600/账户/分钟；采样过程中运行 docker stats 和 ps 会增加负载。宿主机还有其他服务和工作负载。两组 billing 各最多 100 数据库连接，为避免第一轮复现的连接上限影响，**本轮仅隔离 MySQL 调整为 500 连接**；不反映生产配置或部署建议。

源码/baseline overlay 的 Store、billing service、gateway client SHA 和二进制 SHA、镜像与配置在 `config.json`，完整结果在 `results.jsonl`。实验运行后才发现脚本未记录 handler 源文件哈希：发压开始后为防止空 bill ID 增加了一行校验，已经构建的两个二进制不受影响。恢复这一行之前的 handler 文本哈希与前一次 `idem-expiry-runs/20261103-171618/config.json` 中已记录的哈希一致，但不能当作本轮构建时完整冻结证明；因此本轮仅是诊断证据，不是最终代码版本的性能验收。

每秒以有效 HTTP 200 完整响应数除以含排空耗时；P95/P99 是每阶段所有请求的客户端延迟。两轮结果方向不一致且延迟较高，不能据此认定新协议更快或更慢，也不能把 256 当作最大可用并发；未设具体 P95 目标，未做持续负载、流式、真实模型和故障场景对照。用户此前允许报告零错误和 1% 错误条件，但只有每档两次 3 秒样本，不支持长期达标判断。

最终 audit 中 769 个账户余额与账本无差异、pending 0、settled 4120；阶段与冒烟共有效响应 4120，但这是总量核对，非逐请求映射。Outbox 12360 条未发送是 Kafka/relay 关闭的测试配置，不证明投递恢复。最终 MySQL 状态快照 `Max_used_connections=203`、`Connection_errors_max_connections=0`、`max_connections=500`，`Innodb_row_lock_waits=0`；后者不包含本项目 MySQL 命名锁。仅最终快照/累计值，不足以定位每档瓶颈。

第一次对照脚本尝试 `.../20261103-172140` 在启动前因测试脚本变量命名错误退出；第二次 `.../20261103-172240` 完成 12 档发压但 audit 退出 1，额外 MySQL 监测连接收到 1040。该旧脚本未保留 audit stderr，不能断言 audit 失败的准确原因；不能把它作为成功对照。第三次为上述结果，所有尝试保留。

## 最终 handler 校验后的关键源码重测

`replay-perf-runs/20261103-172939` 为 bill ID 校验加入后的重测。脚本在编译前及结束后分别记录 16 个列出的关键源文件 SHA，匹配才写 `completed`，另记录 baseline overlay 和二进制哈希；并非整个仓库归档，不能称完整源码冻结。两套 billing/gateway 及 MySQL 500 连接、769 个合成账户、其他条件与上表相同；各组 3 秒且第二轮反转顺序，主机负载波动。本轮响应均不带客户端幂等键，不测试重复请求安全性。

256 并发严格模式两轮错误率分别约 4.2%、36.9%；baseline 分别 0%、98.0%。各轮顺序、共享主机负载和不同账户/累计账本导致不可控波动，不能归因于协议或定义稳定上限。最终 MySQL `Max_used_connections=202`、`Connection_errors_max_connections=0`、`max_connections=500`，这不能排除连接池排队、命名锁或其他等待。

最终 audit 显示余额与账本无差异，settled 2364，与有效 HTTP 200 总数（含冒烟）相等；仍有 **52 个 pending**，账本公式本身包含 pending 预占。该实验关闭 Kafka/relay，7144 个 Outbox 未发送属配置；未采逐请求映射、未等 600 秒对账宽限，容器随实验结束清理，不能断言这 52 个对应哪些响应、是否会恢复或永久遗留。必须在新的隔离实验中按请求关联并观察实际配置的对账期。
