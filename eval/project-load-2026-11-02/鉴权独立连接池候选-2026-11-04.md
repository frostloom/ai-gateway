# 鉴权独立数据库连接池：测试候选

## 候选及正确性边界

上一轮插桩观测到现金操作取得连接的长尾，可能与共享池资源竞争有关，但没有将单个等待关联到鉴权错误。本候选只在 Go overlay 中构建：真实 billing Service 的 ValidateAPIKey 改用独立 `Store`，该 Store 使用**同一 MySQL DSN、相同权威查询和同一 Redis 客户端**；billing 连接上限由 100 改 84，鉴权池上限 16，总上限仍 100。没有引入鉴权缓存、TTL 或 Redis 判断，也没有修改正式 Service/启动代码。固定 84/16 只是实验比例，不代表推荐配置。

`auth_pool_isolation_test.go` 用隔离真实 MySQL/Redis 和真实 billing Service：主池设为 1 并显式占住唯一连接后，500ms 内鉴权仍能通过独立池读取有效 key；释放主池后分别禁用 key、禁用 tenant，后续读取拒绝；关闭独立池后鉴权返回 Unavailable。原共享池版本三轮均因主池占满超时而按预期失败（`auth-pool-isolation-red-20261104.txt`）；测试 overlay 三轮 race 通过（`auth-pool-isolation-final-20261104.txt`）。这是本进程直接调用 Service、明确占用连接，不是真实网络分区或多实例故障；测试未覆盖浏览器会话、过期时间、MySQL 提交与读取竞态、连接创建失败恢复、数据库整体耗尽、进程重启、租户/密钥更新的所有入口。数据库是同一权威库，拆池不保证数据库故障时可用，也不证明立即吊销的分布式语义。

## 整网关对照

先候选 B，再共享池基线 A；每组独立 MySQL/Redis，真实 gateway/billing/router/reconciler、64 合成账户、本地模拟模型 15ms；开放到达率各 10 秒两轮、非流式，最多 1000 在途。v2 与未知保留启用，Kafka relay、Agent、周期重建关闭，grace 600 秒。客户端平均/P95/P99 包含错误；成功吞吐除以发压及排空时间。共机共享资源、顺序固定、各档仅两轮；不同库及主机负载使其不能当因果证明或生产容量。

## 补充：网关中间件与真实 gRPC 并发饱和

`auth_pool_grpc_concurrency_test.go` 使用真实 gateway APIKey 中间件、真实 billing 客户端及回环 gRPC、控制令牌拦截器、真实 Service 和隔离 MySQL/Redis；HTTP 使用 `httptest.ResponseRecorder`，没有启动完整网关 HTTP 服务。测试人为从主池同时借出并持有全部连接，然后并发发起 32 个同一有效合成 key 的鉴权请求，验证释放之后禁用密钥为 401、关闭鉴权池为 503。

- 基线主池上限与实际配置相同为 100，借出全部 100 个连接：三轮各 32 个 503，符合本次期望失败，见 `auth-pool-grpc-100-red-20261104.txt`。测试为了构造同一测试夹具还创建了一个未被基线 Service 使用的独立连接池，因此不是运行时连接数严格相同的生产系统模拟。
- overlay 候选主池上限 84，借出全部 84 个连接，鉴权池上限 16：三轮各 32 个 204；释放后禁用密钥 401、关闭鉴权池 503，见 `auth-pool-grpc-84-final-20261104.txt`。两个池的配置上限仍合计 100。
- 先前两组以主池上限 1、以及两组均设主池 84 的 `auth-pool-grpc-red/green-20261104.txt`、`auth-pool-grpc-84-red/green-20261104.txt` 为中间实验，原样保留；上面最终比较明确使用当前共享池实际上限 100。

这是强制持有连接的同进程实验，并非计费负载自然产生的耗尽，也不证明实际 HTTP 网络、多个 billing 实例、MySQL 总连接耗尽、读写分区、数据库重启或故障时自动恢复。不同 key、浏览器会话和请求混合未覆盖；也没有验证独立池与服务负载下的连接保留是否足够。之前端到端负载对拆池收益不明确，不能把此隔离性测试当成吞吐或上线证明。

## 补充：真实 MySQL 容器杀停与重启

`auth_pool_mysql_restart_test.go` 在 runner 随机创建的本地 MySQL/Redis 上，使用真实 gateway 鉴权中间件、billing 客户端、回环 gRPC、控制令牌和真实 Service；HTTP 为进程内 recorder。每轮先鉴权成功，测试通过 Docker SIGKILL **本次 runner 的 MySQL 容器**，确认鉴权返回 503，再启动同一容器、确认回环端口不变并等待 MySQL ready，重试鉴权直至 204，随后在权威库禁用该 key 并确认 401。仅测试本机合成 key；没有在数据库中断期间修改密钥，也没有模拟网络分区、主从切换或磁盘永久丢失。

独立池 overlay 三轮 race 全通过：重启命令及端口检查后到 ready 与首次成功鉴权分别耗时 2.674、2.569、2.242 秒，三个样本均在 ready 后首次鉴权成功；日志 `auth-pool-mysql-restart-fixed-20261104.txt`。共享池基线独立容器三轮也通过，同口径 2.466、1.992、2.029 秒；日志 `auth-shared-mysql-restart-20261104.txt`。这只是本机单次环境中的计时，不包含杀停到重启命令完成的全部时间，不是服务可用性 SLO；数据库不可用时两者均不可鉴权，结果不支持独立池提升数据库故障可用性。

第一次候选 `auth-pool-mysql-restart-20261104.txt` 在首次杀停/重启后发现 Docker 随机回环端口由 59539 变为 59587，按设计失败；剩余两轮因 DSN 与实际端口不匹配提前退出，没有恢复结果。runner 新增测试专用 `TEST_MYSQL_STABLE_PORT=1`：先在回环申请一个端口，释放后用于本次独立容器；申请到 Docker 绑定之间仍有竞争，若被占用启动会失败，不会尝试连接其他服务。测试在 kill 前检查容器名称、回环 DSN 与端口映射，重启后再检查映射。没有设置该变量时原随机端口路径的独立池隔离测试三轮仍通过，日志 `auth-pool-runner-default-regression-20261104.txt`。
