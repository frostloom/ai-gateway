# 路由回报缩小锁范围：测试原型

当前 `internal/router/registry.go` 的 `Report` 在全局 `mu` 内同步执行 MySQL 写；缓存命中的 `RouteExclude` 也需要该锁。`router_report_lock_scope_test.go` 在隔离 MySQL 上先预热缓存，再用 GORM 回调将真实 Report 的数据库写阻塞，要求同模型的缓存选路可完成。基线 `run-router-lock-scope.sh` 三轮均超过 500ms 而失败（`router-lock-scope-red-fixed.txt`）；首次 `router-lock-scope-red.txt` 的第三轮被上轮通配模型污染，不作为此反例证据。回调是应用层阻塞，不是模拟 MySQL 网络故障。

测试 overlay `router_registry_lock_scope_candidate.go.txt` 为同一 provider 的 Report 增加独立锁：其内存状态在全局锁中更新，SQL 在释放全局锁后同步执行；相同 provider 回报持独立锁直至 SQL 返回，不同 provider 可并发，选路可在 SQL 等待时读取已更新的内存状态。它没有引入异步队列或合并回报。`bash eval/billing-comparison-2026-11-02/run-router-lock-scope.sh --candidate` 的 race 三轮证明受控阻塞期间缓存 Route 完成、释放后 Report 完成；另一个受控用例以成功回报先进入 SQL、失败回报随后启动，检查最终 DB 和内存失败数为 1，日志 `router-lock-scope-order-green.txt`。第二 goroutine 的启动信号不保证它已抵达互斥锁，因此该测试不是全部顺序的证明。`router-lock-scope-circuit.txt` 是 overlay 下现有 router 包 race 三轮通过，覆盖现有熔断及半开测试。

**不可部署：**持久化失败仍仅日志、HTTP 调用方不获知；没有事件 ID、去重、跨实例顺序或可靠恢复。状态现在先于 DB 写对并发 Route 可见，AutoBan 写入、缓存失效和探测竞争的细节不同；同 provider 的 SQL 仍串行，不保证解决单热点吞吐。测试用 `sync.Map` 不清理任意 provider ID，存在内存增长风险；还未覆盖 DB 断连、提交不确定、并发禁用/删除、不同实例、失败风暴、关闭和长期负载。账务未知状态和用量恢复问题不由此解决。候选仅供后续验证，不能用上述短测替代安全方案。

## 多渠道隔离及写入失败补充

`bash eval/billing-comparison-2026-11-02/run-router-lock-scope.sh --candidate` 新增两个真实 router 组件测试，隔离 MySQL、race 三轮，输出 `../billing-comparison-2026-11-02/router-lock-scope-write-failure.txt`：

- 通过 GORM 回调暂停渠道 A 的失败回报写入时，渠道 B 的失败回报可完成，释放 A 后两条数据库失败计数均为 1。基线同样测试三轮均等待超过 500ms，输出 `../billing-comparison-2026-11-02/router-lock-scope-independent-red.txt`；基线在同一组中的缓存选路用例也如预期失败，而同渠道顺序用例通过。这里的暂停是应用层回调，不代表真实 MySQL 故障的全部表现。
- 对候选的真实 `/report` handler，在 SQL 更新前通过 GORM 应用回调注入错误。三轮均复现 HTTP 200、内存失败计数 1、数据库失败计数 0。该测试的 PASS 表示**成功复现确认与持久化不一致**，不是安全通过；未重启进程、未测试真实数据库连接中断或网络丢包。该缺口沿用现有 HTTP/Report 行为，原型没有解决；无法以重试替代事件身份及幂等，否则可能重复计数。

上述补充扩大了对跨渠道锁隔离的证据，但不证明持久化失败时可以安全恢复，不能改变不可部署结论。\nEOF
