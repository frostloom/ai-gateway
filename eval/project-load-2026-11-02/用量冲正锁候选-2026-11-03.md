# 用量与冲正同步候选（仅隔离测试）

候选以 Go overlay 构建测试 billing，不修改生产源码：`usage_reverse_candidate.go.txt` 在 ReportUsage 使用现有请求级 MySQL advisory lock 并将事务绑定该连接；Reverse 在已有账户锁后取得同一请求锁，锁内重读并拒绝已上报用量的冲正。正常 Reserve 的锁顺序已有账户锁→请求锁，候选 Reverse 沿用该顺序；ReportUsage 仅取得请求锁。候选还会改变所有已报用量账单的显式冲正语义，目前只是供验证的假设。

在 `run_stale_sweep_candidate.py` 的受控交错中，第一次对账扫描后先成功提交 usage，再尝试 Reverse：冲正被 FailedPrecondition 拒绝，账单保留 pending 和用量；启用第二次 sweep 后实际结算一笔，余额与账本一致，Outbox 有 reserve、usage、settle。首轮 `stale-sweep-candidate-runs/20261103-180508/` 仅观察 pending；第二轮 `20261103-180603/` 实际完成结算。以上为单次固定交错、合成数据，relay 关闭；未证明一般并发安全或投递。

复现：`python3 eval/project-load-2026-11-02/run_stale_sweep_candidate.py`。原始目录含候选摘要、测试源码和二进制摘要、账单及日志。候选重放基于具体源码快照，源码变更后必须重新生成并审查，不能直接复制上线。

未覆盖：Reverse 先取得锁的竞争、事务/连接断开与 advisory lock 释放、取消、死锁、崩溃与孤儿 guard、老版本混部、订阅及其他显式冲正规则、锁开销和高并发。最重要的是，候选不阻止对账在上游尚未返回且尚无 usage 时冲正，故不能声称解决在途请求问题。完成这些验证与解决未知上游状态之前，不将它接入生产链路。

## 补充：相反顺序、并发与现有行为

先运行 `run_usage_reverse_regression.sh`：原代码在 usage 先完成时出现“用量和冲正均成功”，测试按预期失败。最初候选对所有已报用量冲正一律拒绝，但 `TestTerminalSQLFailureRebuildAndRetry/reverse` 证明它破坏了现有显式冲正恢复行为；失败保留在 `usage-reverse-regression-global-guard-failed.txt`。

当前候选将该拒绝限定为 `recon:no_usage`，而用量提交和所有冲正仍共享请求锁。在真实隔离 MySQL/Redis 上，15 次 usage 先、15 次 reverse 先、15 次并发以及选定的原有预占、结算、冲正、恢复、订阅、Outbox 测试，在 race 模式下通过；原代码仍在首个 usage 先用例失败。完整日志 `usage-reverse-regression-scoped-output.txt`，命令 `bash eval/project-load-2026-11-02/run_usage_reverse_regression.sh`。并发测试验证两者不会同时成功及最终余额与账本一致，但没有控制每次竞争的实际锁获取顺序；固定顺序测试覆盖两种先后。

**限制：**依赖自由文本 `Reason` 区分对账操作不是可靠的协议边界，旧服务实例仍可绕过新锁，其他原因仍允许报量后冲正；不能将候选直接接入生产。应以明确的服务端语义和混版策略替换，验证崩溃、连接丢失、Redis 故障和真实对账，并处理上游已发送但无 usage 的未知状态。

## 补充：持锁数据库连接中断

`bash eval/project-load-2026-11-02/run_usage_reverse_disconnect.sh` 在随机隔离 MySQL/Redis 中，以 MySQL `KILL CONNECTION` 定向终止被测持锁会话；Go race 模式下两个受控时序各运行 3 次，完整输出为 `usage-reverse-disconnect-both-output.txt`，exit 0。日志中的 MySQL unexpected EOF 对应主动断连。

- 用量事务在数据库更新前暂停并断连，新的对账冲正随后完成；旧用量事务返回错误，最终账单冲正、无 usage marker 或 usage Outbox，余额和账本均恢复到初始值。
- 对账冲正在检查账单后、Redis 变更前暂停并断开其持锁连接；新的用量提交成功，旧冲正返回错误，随后结算完成，账单 settled 且有 usage marker，余额与账本均为预期值。

这是两个精确切点的测试，不证明提交确认丢失、数据库或 Redis 重启、长期网络分区、多进程版本混部及所有崩溃位置。仍须验证明确协议、上游未知结果的处理及完整系统性能；候选尚未合入生产源码。
