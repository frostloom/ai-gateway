# Outbox 并发投递隔离候选

## 方法

在本机隔离 MySQL 8.0.40、单分区 Kafka 3.7.0 中使用真实 `Relay.FlushOnce`、项目 Kafka producer、event consumer 和 MySQL Store。每轮插入 400 条自包含合成事件，预先读出行；串行组由一个 relay 处理，并发组把同一批预读行按下标分成互不重叠的 8 份，每份由一个真实 relay 处理，使用同一个 producer。每条仍单独标记 MySQL。运行顺序为串行、并发、并发、串行，测量从开始投递到所有 relay 返回的时间，再等待审计入库并逐 event ID 检查缺口和未发送行。

这是**测试目录内的固定分片候选**，不是正式代码实现：两组都绕过了真实轮询查询、ticker、并发领取和完整网关请求，不测新事件持续到达；不代表生产可直接部署。当前实现对所有行串行执行同一个 relay，本实验可以隔离观察并发调用的潜在收益，但不证明全网关吞吐提升。HEAD、源码和测试 SHA、输出见 `kafka-offset-repro/relay-parallel-final.json`；同目录 `relay-parallel.json` 保存较早一次独立运行。两次运行各自启动独立的随机端口 MySQL 和 Kafka。

## 结果

| 400 条事件，最终源码 | 两轮 flush 秒 | 约事件/秒 | 每轮 event ID 缺审计 / 未发送 |
|---|---:|---:|---:|
| 串行 | 7.335、7.078 | 54.5、56.5 | 0 / 0 |
| 8 路固定分片 | 0.890、0.885 | 449.4、452.0 | 0 / 0 |

较早独立运行分别为串行 7.048、7.033 秒，并发 1.013、0.930 秒；两轮均核对 400 个审计 event ID、0 未发送。测量仅包括投递及标记，不含种数据、等待审计、轮询间隔；未测 CPU、I/O、消息内容逐字段相等或延迟分位。结果支持继续研究有界并发或批量发送，不足以认定唯一瓶颈或推断生产收益。

另在全新隔离容器中以真实 Kafka 验证单事件重复投递：GORM callback 模拟首次 `MarkOutboxSent` 失败，实际 producer 已成功，第二次 relay 重新发送后成功标记；实际 consumer 记录 2 次处理，审计表该 event ID 仅 1 行。见 `relay-replay.json`，该次启用 race 检测并有本机链接器 LC_DYSYMTAB 警告。故障是应用层写前注入，不是真实 MySQL 断网或 Kafka 确认丢失。

## 复现

```sh
python3 eval/project-load-2026-11-02/kafka-offset-repro/run_parallel.py trial
python3 eval/project-load-2026-11-02/kafka-offset-repro/run_parallel.py trial-replay --replay --race
```

脚本只创建并清理自己命名的独立容器，随机本机端口，无模型调用。

## 不能直接上线的原因

固定分片没有跨进程领取、租约过期与重试机制；并发发布可改变顺序，目前同一请求不同阶段使用不同 key、已可能落在不同分区。还未测试发布部分成功、broker 故障、取消及崩溃、跨实例重叠、多分区 rebalance、长时稳定、限流、真实网关负载以及队首失败公平性。需定义审计顺序要求，设计有界并发、行领取/恢复、重复投递与监控，并先完成上述故障和端到端负载对比。当前正式 relay 行为未因本实验改变。
