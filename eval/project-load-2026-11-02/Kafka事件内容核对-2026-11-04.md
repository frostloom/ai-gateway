## 事件检查方法与限制

发压完毕先执行原 30 次积压观察，再最多等待 180 秒，每两秒用事件 ID 核对缺审计、多余审计及未发送；本轮额外等待 34.49 秒后均为 0。然后在 MySQL 将 Outbox 与 audit 按事件 ID 连接，得到 4086 对；对两表 JSON 列使用 MySQL JSON 值相等比较（0 不等），并将 Outbox payload 的 `event_id`、`tenant_id`、`request_id`、`phase`、`amount_cents`、`model`、`funding`、`prompt_tokens`、`completion_tokens` 与对应 audit 列比较（0 不等；字符串采用二进制比较，数字转换为整数，缺失用量视为 SQL NULL）。原始计数在 `payload-reconciliation.json`。

这是 JSON **语义值**而非 Kafka 原始字节比较；只比较成功连接的行，完整性由同一次 drain 的 ID 核对辅助。没有负向篡改数据来验证检查器，也没有逐个对照账本的正确金额、验证异常冲突或 broker 故障下投递。audit 的消费时间、partition/offset、source 等投递元数据未比较。已知同 ID 不同内容会被现有 audit Store 静默吸收的风险不因此消失。未等待 600 秒对账恢复，不能以 4086 条事件内容一致说明 12 个 pending 已结算。
