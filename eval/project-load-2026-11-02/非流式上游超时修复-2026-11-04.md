# 非流式上游超时参数修复

当前工作树基于 HEAD `63b9d1ed4d64bb583d15fa884c37468e5c53044c`。`Chat` 将 `upstreamTimeout` 传给 `forwardNonStream`，但此前该形参被丢弃；共享 HTTP 客户端另有固定两分钟总超时。隔离测试通过实际本地 HTTP 上游在响应头前阻塞，传入 100ms，修复前三轮均等待超过 1 秒，见 `nonstream-timeout-red-20261104.txt`。

工作树修改为非流式转发在参数大于零时创建覆盖整个转发过程的 context deadline，并把它绑定上游请求；参数不大于零时沿用原请求 context。共享客户端的两分钟限制仍存在，因此有效上限还受它和原请求 context 约束。当前命令入口传入两分钟；旧式非保守多次 failover 现在共同消耗同一超时预算，而非每次可能各耗共享客户端的两分钟。流式路径没有应用此参数。超时不证明上游未执行：默认保守模式仍返回 502、保留账单、不重试、不立即冲正。legacy 非保守模式原有失败切换/冲正规则仍在，不应将本改动视为未知账务安全协议。

最终 `python3 eval/project-load-2026-11-02/run-nonstream-timeout.py` 在 fake billing/router 和本地模拟上游测试两处：响应头前阻塞，及已发送 200 头和部分正文后阻塞；100ms 超时均在约 100ms 返回 502，没有用量、结算或冲正，三轮 race 通过。红灯只覆盖响应头前，正文子例为修复后补充。日志 `nonstream-timeout-final-20261104.txt` SHA-256 `201b4b8aada5fce42d64a0ca698f95ce73bdd6831c4b2d06c54c4aa5df04b3cd`，测试 SHA-256 `37684168e647f70d3540a9225a9e2fc27787ea0183f63dcc26b388bced93b105`；当前 handler SHA-256 `a4208fd9f55aed6af7361f1b8ee3445bbedc5debb6467eb87d2e057e7c772d0d`。

`bash eval/project-load-2026-11-02/run-gateway-isolated-suite.sh` 的四个 gateway/controlplane 包 race 回归通过，输出 `nonstream-timeout-suite-20261104.txt`；此前错误正文测试也三轮通过，输出 `nonstream-timeout-error-body-regression-20261104.txt`。没有完整服务进程或高并发超时测试、生产模型/数据或部署；未知账单后续恢复、旧实例和直接 Reverse 的风险仍未解决。

## 多账户真实本地进程验证

`python3 eval/project-load-2026-11-02/run_nonstream_timeout_concurrent.py` 在真实 gateway、billing、router、reconciler 及隔离 MySQL/Redis 中执行；仅通过测试 overlay 把两个 `Chat` 调用的两分钟参数改为 200ms，handler 使用当前工作树代码。模拟服务读完请求后一直不发送响应头，等待客户端断开或最多 5 秒；每轮 64 合成账户、每账户 2 个请求、128 线程屏障后突发。两轮目录 `nonstream-timeout-concurrent-runs/20261104-081423/` 和 `20261104-081518/`。

两轮均为上游收到 128 次、网关返回 128 个预期 502、无其他状态或客户端传输错误；HTTP 业务错误率为 100%，输出 `errors=0` 仅指测试无非预期结果。客户端端到端平均 634.4/581.1ms，P95 728.8/680.3ms，P99 735.9/691.7ms；200ms 是上游转发预算，不含此前鉴权、路由、预占等，因此不能把端到端延迟和 200ms 直接等同。测试对账配置 1 秒扫描、5 秒宽限、无自动冲正、禁用 rebuild 与 Kafka/relay；两轮测试宽限后均有 128 笔不同 pending 预占、128 条 reserve Outbox，无 usage/settle/reverse，余额差异空。
