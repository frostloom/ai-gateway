# 计费连接池实际等待诊断

为区分服务端全局连接数与 billing 自身连接池，在 `run_gateway_v2_open_load.py` 增加仅测试构建选项 `OPEN_LOAD_POOL_STATS=1`：通过 Go overlay 在 billing 启动后每 500ms 输出其 `database/sql.DB.Stats` 快照；正式代码和配置未修改。此实验同时启用现有测试专用锁计时和 mock 请求 ID 日志，插桩会改变开销，不是公平性能对照。日志包含时间、池上限、open/in-use/idle 与累计 `WaitCount`、`WaitDuration`；半秒采样可能漏掉瞬间峰值，但累计计数在采样区间内不会因短暂等待消失。

隔离 MySQL/Redis、真实 gateway/billing/router/reconciler、64 个合成账户、50% 浏览器、15ms 本地 mock、严格 V2、保守 unknown；Kafka relay、Agent 和周期重建关闭。20 请求/秒计划三轮各 15 秒，第一轮 300 请求中 276 有效 200、24 个 503（错误率 8%）；客户端分类为 18 鉴权不可用、6 计费不可用。全请求均值/P95/P99 为 702/3048/3899ms，峰值在途 57，发压丢弃 0。两笔 503 与 pending 无用量账单对应，按审计规则停止后续轮次；等待 2 秒后仍 pending，不代表 600 秒后结果。两笔均有预占 DeadlineExceeded，同 ID 的 mock 接收 0；其余四笔预占错误没有在当时审计中观察到 pending，不能推断是否曾提交。总含 5 个 smoke 为 281 settled、2 pending、0 reversed、余额无差异，845 条 Outbox 未发送（relay 关闭）。

服务运行期间采到 58 个 billing 池快照（UTC 06:13:23.935 至 06:13:52.436）：最大采样 open/in-use 均为 56，配置上限 100；所有快照累计 `WaitCount=0`、`WaitDuration=0`。同次 MySQL 全局最大连接 68、服务端上限 151。故该次观察**不支持 billing 池达到上限所致的 database/sql 等待**；不能排除连接创建、SQL 服务、网络、锁、调度、其他服务或采样区间以外的问题，也不能以此解释此前另一次使用 98 个服务端连接的运行。

同次 851 个锁获取计时中，进入锁函数到开始 `GET_LOCK` 的客户端耗时 P95/P99/最大为 0.009/769.647/1329.246ms；锁查询 P95/P99/最大为 24.858/112.172/1219.443ms；851 个锁持有段 P95/P99/最大为 281.994/1474.083/3080.730ms。分位数为排序下标 `floor((n-1)*p)`，统计包含 smoke 和所有锁类别，非逐请求配对；计时包含应用调度和网络，不是数据库内部阶段。没有锁获取或连接获取错误日志。上述长尾提示继续细分阶段，不证明某一项造成超时。
