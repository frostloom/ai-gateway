# 路由成功回报减少数据库写入的边界

当前每次成功 `Report` 都在共享选路 mutex 内将 provider 的数据库连续失败数清零。两种看似简单的减写方式经隔离测试都不能直接作为优化结论。

1. `router_noop_lock_test.go` 在独立 MySQL 8.0.40 中锁住一个失败计数为零的行，比较普通 `UPDATE ... SET consecutive_fail=0 WHERE id=? AND status=0` 与附加 `AND consecutive_fail<>0`。两者在行已锁定时都等待到 350 ms 测试超时；三轮一致。条件版本能清除非零活跃行、不修改 banned 行。它是局部 SQL 锁竞争实验，不说明无竞争时吞吐，也不证明全部 MySQL 版本或执行计划相同。`bash eval/billing-comparison-2026-11-02/run-router-noop-lock.sh`，日志 `router-noop-lock-output.txt`。
2. `router_multinode_regression.go.txt` 用同进程中两个独立 `Registry`、共享隔离 MySQL，先由 A 报失败，再由本地没有失败记录的 B 报成功。原实现将数据库失败数清零（`router-multinode-baseline.txt`）；测试候选仅在 B 的内存失败数非零时执行清零，数据库仍为 1，断言按预期失败（`router-multinode-naive-red.txt`）。命令分别为 `bash eval/project-load-2026-11-02/run-router-multinode-test.sh` 和 `ROUTER_CANDIDATE=1 bash eval/project-load-2026-11-02/run-router-multinode-test.sh`，第二条预期非零退出。这是两个 Registry 而非两个实际进程；没有测试跨进程故障、重启或所有交错。

因此，单纯增加非零谓词未在该受控锁场景消除等待；单凭单实例内存跳过写入会遗漏其他实例产生的状态。候选仅是用于证伪的测试文件，未修改生产代码。仍需设计和测量保持跨实例顺序、故障处理和 AutoBan 语义的方案；此结果不能单独推断整网关性能或生产容量。
