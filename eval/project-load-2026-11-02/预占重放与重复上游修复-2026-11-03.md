# 预占重放导致重复上游调用：复现与有限修复

## 真实隔离链路复现

`run_idem_expiry.py` 启动独立 MySQL/Redis、当前项目 gateway/router/billing/reconciler 和可阻塞的本机模拟上游。首次请求到达模拟上游并等待后，将该合成请求的 Redis 幂等键 TTL **人为缩短到 1 毫秒**，再发送相同账户、参数和键的第二个请求；模拟上游收到第二个调用后释放两个请求。实际生产 TTL 为 5 分钟，此试验证明状态失效后的时序问题，不证明实际五分钟一定发生。

修复前 `idem-expiry-runs/20261103-170443`、`.../20261103-170650` 两次均观察到：模拟上游各收到两次、两个 HTTP 200 返回不同模拟响应 ID、数据库只有一条 reserve 和一条 settle，余额与账本一致。因为两次使用相同 usage，第二次的财务调用按相同 request_id 幂等，账本核对本身无法识别模拟上游已被调用两次。没有调用付费模型或真实用户数据。

## 修复

- Store 新增 opt-in `ReserveWithReplaySignal`；首次预占成功返回 `RESERVE_OK`，相同指纹且仍 pending 的已存在预占返回原 bill ID 和现有枚举 `RESERVE_DUPLICATE`，账务不再扣款。旧 `Reserve` 对仍 pending 的重试保留原 OK 行为；不同参数或已终态/已有用量仍按既有修复拒绝。
- 新 gateway 的 billing client 每次请求 `x-agw-reserve-mode: replay-v1`，server 确认支持后设置 `x-agw-reserve-contract: replay-v1` 并使用 strict Store 方法；gateway 仅将 `RESERVE_OK` 视作可继续转发，`RESERVE_DUPLICATE` 返回 409，未知或空结果返回 503。gRPC 传递内部控制面 token 的拦截器保留。不是模型响应重放，也不会自动重试一个没有结果的请求。
- 新 gateway 对缺失或错误确认头返回 503，不会调用上游。但确认头在 **Reserve RPC 执行后** 才能读到：若实际落到旧 billing，旧服务可能已做预占，网关仍返回 503，可能留下需对账的 pending。`TestOldBillingMayMutateBeforeMissingAck` 用模拟服务复现该兼容风险；不能声称新旧混部无副作用。旧 gateway 未请求新协议，连新 billing 仍走旧行为，重复上游缺口依旧存在。上线前必须设计并验证 billing 先行、完全排除旧实例及旧 gateway 的发布/回滚方案；本工作没有部署。

## 验证

修复后同一脚本 `idem-expiry-runs/20261103-171304`、`.../20261103-171618` 两次均为模拟上游一次、响应 200 和 409、一个 reserve、一个 settle、三个 Outbox、余额核对无差异。每次有意加速 TTL，等待的 8 秒和并发为实验条件，不代表生产容量。原始响应、账单、配置与哈希在各目录；这两轮 Redis/账务正常，没有覆盖服务重启或故障切换。

`strict-reserve-store-v3.txt`：真实隔离 MySQL/Redis 上 8 个并发同 ID strict 请求为 1 个 OK、7 个 DUPLICATE，旧 API 同参数仍 OK，同 ID 修改预估参数拒绝，仅一笔 reserve 和一次扣减；终态/已报用量拒绝。`strict-subscription-results.txt` 覆盖订阅余额不动时新旧语义，及原有预占、结算、冲正、Outbox、重建的定向回归。`strict-gateway-race.txt` 包含 gateway handler/client 包完整 race 测试；`TestBillingReserveRequiresReplayContract`、网关重复/未知 code 拒绝和旧服务模拟通过。初次新增测试因测试变量名遮蔽而编译失败的 `strict-reserve-store-v2.txt` 保留，修正后 v3 通过。

## 仍未解决

- Redis SETNX 超时后可能残留键，导致失败请求恢复后 409；该有限修复不处理此可用性问题。
- 计费成功信号与实际模型发送之间仍非跨系统原子操作；首次预占被对账冲正、网络不确定、进程中断、Redis 丢失、老版本混部和外部服务状态仍需系统性验证。对账/重试不能因返回 409 而自动认定未调用或已结算。
- 第二次到达时强制拒绝，可能造成调用方无法用原 ID 自动恢复；这保守防止重复上游，不是完整的失败恢复协议，也不代表零错误或可上线。长请求、流式、多 gateway、跨实例/跨租户及真实上游的行为没有在本试验中覆盖。
- 尚无控制环境下的完整网关性能 A/B，不能宣称该修复对吞吐/尾延迟无影响。
