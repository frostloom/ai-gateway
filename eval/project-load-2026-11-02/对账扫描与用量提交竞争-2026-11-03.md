# 对账扫描与用量提交竞争

两轮受控隔离测试确认：对账器扫描到 pending 且无 usage 后，如果用量在 Reverse RPC 执行前成功提交，仍会冲正该账单。两轮最终 reserve 状态均为 reversed、usage marker 存在，Outbox 同时存在 usage 和 reverse，无 settle 记录，余额与账本计算一致。账本一致不能证明已计入使用量。

测试程序 `stale-sweep/main.go` 使用真实 `Reconciler.SweepOnce` 和真实 billing RPC；仅在测试客户端转发 Reverse 前同步调用 `ReportUsage`，构造确定的扫描后交错，随后转发原始 Reverse。对账 grace 设为 0，以便立即扫描测试预占；不需要假装等待默认 600 秒。没有模拟模型或付费调用。原始记录 `stale-sweep-runs/20261103-180227/`、`stale-sweep-runs/20261103-180332/`，各自 exit 0，专用容器已清理。Outbox relay 关闭，不验证消息投递。

复现：`python3 eval/project-load-2026-11-02/run_stale_sweep.py`。关键调用点：`internal/billing/reconciler/reconciler.go` 的 `SweepOnce` 将扫描快照用于选择 Reverse；`internal/billing/store/mysql.go` 的 `ReportUsage` 持行锁写入 marker，而 `reverseCash` 读取状态后未以同一同步边界检查 usage。这个受控结果与此前“在途模型尚未返回即冲正”不同：这里 usage 已经持久化成功。

潜在修复必须让用量提交与基于无用量的冲正在同一同步边界上判定；仅在 Reverse 开始再读一次仍存在读后竞态。现有账户锁还承担 Redis 投影、孤儿 guard 和跨进程恢复，ReportUsage 当前使用 SQL 行锁；直接把它接到账户锁可能改变热点吞吐、超时与订阅行为，需要先设计故障恢复与完整回归。本实验尚未修改生产逻辑，也不说明如何处理已发送但结果未知的上游调用。
