# New API 高并发实现与项目改造重点

参考 QuantumNous/new-api 固定源码版本 [`45746eee4de25ab1eb75d4b7fbb8de2199483ea3`](https://github.com/QuantumNous/new-api/tree/45746eee4de25ab1eb75d4b7fbb8de2199483ea3)。下述是源码分析，不是对 New API 的实测容量或新版本行为声明。

1. **渠道路由：缓存快照、缩小锁范围。** [`InitChannelCache`](https://github.com/QuantumNous/new-api/blob/45746eee4de25ab1eb75d4b7fbb8de2199483ea3/model/channel_cache.go#L27) 在锁外读取数据库、建立渠道和模型映射，短暂持写锁替换缓存；[`GetRandomSatisfiedChannel`](https://github.com/QuantumNous/new-api/blob/45746eee4de25ab1eb75d4b7fbb8de2199483ea3/model/channel_cache.go#L117) 在内存缓存启用时使用读锁选择，否则查数据库。Redis 启用时该版本启动逻辑也启用内存缓存；默认同步周期为 60 秒。本项目现已将缓存未命中时的 MySQL 查询移出全局锁，并在发布前检查本实例失效代次；半开探测、跨实例状态与故障边界仍需验证，详见 [候选报告](路由缓存刷新缩锁候选-2026-11-05.md) 和 [落地报告](NewAPI路由缩锁落地-2026-11-05.md)。
2. **鉴权：Redis 缓存减少查询。** [`GetTokenByKey`](https://github.com/QuantumNous/new-api/blob/45746eee4de25ab1eb75d4b7fbb8de2199483ea3/model/token.go#L282) 优先查询 Redis、未命中或出错回查数据库；[`token_cache.go`](https://github.com/QuantumNous/new-api/blob/45746eee4de25ab1eb75d4b7fbb8de2199483ea3/model/token_cache.go) 包含失效和短期围栏。当前项目请求通过 gateway 调用 billing 鉴权。可以参考缓存与失效思路，但应覆盖 key、租户、用户、session 和 Redis 故障；该 New API 版本的失效失败可能继续写库，不能保证严格即时吊销，详见 [鉴权参考](NewAPI鉴权参考与安全边界-2026-11-05.md)。
3. **计费：额度缓存和条件更新。** [`quota_reserve.go`](https://github.com/QuantumNous/new-api/blob/45746eee4de25ab1eb75d4b7fbb8de2199483ea3/model/quota_reserve.go#L105) 在 Redis 中通过 Lua 判断和扣减，写入数据库；Redis 不可用或缺缓存时回退数据库条件更新。可配置批量模式，未启用时仍同步写 MySQL，不能认为用了 Redis 就不写数据库。本项目的现金路径还有账单、Outbox、订阅、幂等、冲正与恢复约束；应学习减少热路径数据库往返和条件更新，不直接替换其账务协议，也不能无条件将批量写入当成安全等价方案。
4. **连接复用：两边均已有。** New API [`service/http_client.go`](https://github.com/QuantumNous/new-api/blob/45746eee4de25ab1eb75d4b7fbb8de2199483ea3/service/http_client.go#L79) 配置并复用 Transport，支持连接池设置；本项目 `internal/gateway/handler/chat.go` 已复用上游 Client，router Client 也复用连接。因此不应把“添加 goroutine”或“启用连接池”作为当前核心改造。应根据实际网络、超时和连接使用情况调参。

实施顺序建议：先将路由数据库查询移出全局锁并验证刷新、取消、半开、失效及多实例；然后按上述失效边界接入鉴权缓存；最后在保持账单/Outbox/失败恢复的前提下减少计费热路径查询。每步运行针对性的正确性测试与同机模拟对照；不凭 New API 的设计或本机短测推断生产并发上限。

补充：本轮转向源码分析前，隔离实验曾使用直接数据库写入绕过生产账户锁，人为维持两项账本数值总和不变；当前四语句 `LedgerBalance` 读取在三轮各 400 次中分别出现 145、150、146 次跨提交快照组合，日志 `../billing-comparison-2026-11-02/ledger-snapshot-baseline-20261105.txt`。这是绕过账户锁的人为反例，并不证明实际账务路径发生该故障；候选未运行该测试，不宣称候选通过。

## 渠道状态回报的进一步对照

再次检出并核对固定版本 `45746eee4de25ab1eb75d4b7fbb8de2199483ea3`：正常 relay 错误由 [`ProcessChannelError`](https://github.com/QuantumNous/new-api/blob/45746eee4de25ab1eb75d4b7fbb8de2199483ea3/service/relay_error.go#L62) 按 `ShouldDisableChannel` 和 AutoBan 条件，将禁用工作交给 goroutine 池；[`ShouldDisableChannel`](https://github.com/QuantumNous/new-api/blob/45746eee4de25ab1eb75d4b7fbb8de2199483ea3/service/channel.go#L60) 受全局开关、错误类型、状态码和关键词影响。渠道自动恢复在 [渠道健康测试](https://github.com/QuantumNous/new-api/blob/45746eee4de25ab1eb75d4b7fbb8de2199483ea3/controller/channel-test.go#L920)中按测试结果和自动启用设置进行。这与当前项目“每次成功都同步清零连续失败计数、每次失败累计、半开探测恢复”的状态机不同，不能简单删除成功回报或将其异步丢弃而声称语义等价。

New API 的正常计费路径还会调用 [`UpdateChannelUsedQuota`](https://github.com/QuantumNous/new-api/blob/45746eee4de25ab1eb75d4b7fbb8de2199483ea3/model/channel.go#L911)：只有批处理配置启用才先聚合，否则仍直接更新数据库；因此不能说它完全没有每请求渠道写入。异步禁用任务的崩溃恢复和丢失边界不因使用 goroutine 自动得到保证。本项目现有候选曾测得合并回报的性能潜力，但失败确认、跨实例顺序及半开身份未闭合；局部内存跳过成功清零已由两 Registry 的反例证伪，见 `路由清零减写边界-2026-11-03.md`、`真实路由回报合并候选-2026-11-03.md`。

当前 `/report` 没有向 `Registry.Report` 传请求 context，渠道锁为 `sync.Mutex`，因此 handler 一旦进入回报，即使客户端取消也不因 context 取消而自动停止等待或写入；但回报可能包含真实失败或探测结果，不能直接在取消时丢弃。下一步应以可核验的事件身份和顺序/故障语义设计可靠减写，而非仅把请求取消当成无效事件。最新网关实测见 `高负载账务异常复测-2026-11-05.md`。
