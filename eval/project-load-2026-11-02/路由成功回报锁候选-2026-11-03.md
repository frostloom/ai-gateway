# 路由成功回报锁候选（仅隔离测试）

现有 `Registry.Report` 在持有与路由选择共享的 mutex 时执行成功回报的 MySQL 清零。候选 `router_registry_candidate.go.txt` 新增回报顺序锁，成功路径先更新内存熔断状态、释放选路锁，再同步写数据库；回报顺序锁直至 DB 操作完成才释放。失败及 AutoBan 路径仍在原选路锁内执行。候选改变可观察时序：内存成功状态可在数据库清零完成前被选路观察；多个回报仍全局串行，数据库慢时回报可能积压。

## 正确性

`bash eval/project-load-2026-11-02/run-router-report-test.sh` 在随机隔离 MySQL/Redis、Go race 下通过 GORM 回调阻塞成功清零：原实现的缓存命中 Route 在 500 ms 内无法完成，`router-report-red.txt` 为预期失败；`ROUTER_CANDIDATE=1 bash eval/project-load-2026-11-02/run-router-report-test.sh` 中候选允许 Route 在阻塞期间返回，并使后来的失败回报等待成功写入，最后数据库失败计数为 1。选定的熔断、半开探测测试同次通过，输出 `router-report-green.txt`。这是单 provider 和受控写阻塞，不代表完整正确性。

## 整网关短时对照

`python3 eval/project-load-2026-11-02/run_router_paired.py`：本地独立 MySQL/Redis、模拟模型 15 ms、64 合成账户，每账户可多个在途；两套网关和 billing 的二进制哈希分别相同，router 基线与候选哈希不同；两套服务同时常驻，每组用不同账户，两个重复反转执行顺序。每组闭环发压 3 秒并等待排空，吞吐为有效完整 HTTP 请求/秒；不含 Kafka/relay，非生产容量。原始数据 `router-paired-runs/20261103-184546/`，candidate 源 SHA `c6c523225bbd33d21bc5ae0f44b855511d2ac0933eb66c593c8c001fa748243b`。脚本继承的旧协议 baseline overlay 文件只生成以记录，不用于本次二进制；`config.json` 的 note 和二进制哈希确认本次比较的是路由实现。

## 未覆盖及决定

候选未测数据库连接丢失、写入不确定、失败/成功回报高并发顺序、多 provider、AutoBan 与缓存刷新并发、跨路由实例或真实上游；并未覆盖 snapshot 缓存刷新期间的锁内 DB 查询。由于性能结果没有支持收益，且语义和故障边界尚未验证，候选留在测试目录，不修改生产路由。后续应先区分 reportMu、数据库和 billing 的等待，探索减少无必要写入或有序持久化，但任何方案都需要保留禁用、熔断和 AutoBan 行为及故障可恢复性。
