# 整网关高并发错误定位

## 方法和范围

`run_gateway_diagnostic.py` 以及 `run_gateway_diagnostic_high.py`、`run_gateway_route_diagnostic.py` 启动随机名称的隔离 MySQL 8.0.40、Redis 7、本地模拟模型和当前 gateway/billing/router/reconciler。64 个合成账户、非流式、模拟模型 15 ms、GOMAXPROCS=8、billing MySQL 连接池上限 100、MySQL max_connections=151、无 Kafka/relay；对账 grace 600 秒、扫描 5 秒且关闭重建。无生产数据或付费调用。每组闭环发压 4 秒后等待请求排空，吞吐按包括排空时间的完整有效 HTTP 请求/秒计算。

通过 Go overlay 对测试网关仅增加失败时的阶段、错误码和耗时日志；测试负载只归类固定错误文案，不记录密钥或请求正文。overlay 和二进制哈希、部分源码哈希、配置、逐请求 trace、账务核对、资源采样见各次运行目录；这是诊断构建，记录日志对结果有开销，并非整个工作树冻结或生产部署配置。所列并发均为网关总请求数，64 个账户可以分别有多个在途请求。

## 结果

低档次 `gateway-diagnostic-runs/20261103-183326/` 两轮 64、128、256 总并发均无 HTTP 失败：64 并发约 140.8/127.4 请求每秒、P95 527/631 ms；128 约 134.3/135.8、P95 1257/1368 ms；256 约 134.2/129.4、P95 2291/2510 ms。吞吐基本持平而延迟上升，表明排队增加，但这不是锁或特定组件的直接证明。

高档次首轮 `20261103-183459/`：512 并发两轮分别 17/995、3/1019 个 503，均是客户端收到“routing unavailable”；1024 分别 410/1422、267/1287 个 503，其中路由不可用 409、267，另第一次一次鉴权不可用。所有有效响应在核对时有 settlement，无余额差异和 pending。

加强路由错误诊断的第二次 `20261103-183629/`：

| 总并发 | 轮次 | 请求数 | 有效成功 | 503 分类 | 有效成功/秒 | P95 ms |
|---:|---:|---:|---:|---|---:|---:|
| 512 | 1 | 985 | 985 | 0 | 132.9 | 4002 |
| 512 | 2 | 830 | 658 | 路由 172 | 82.1 | 5828 |
| 1024 | 1 | 1623 | 731 | 路由 892 | 72.7 | 9646 |
| 1024 | 2 | 1380 | 619 | 路由 452、计费 294、鉴权 15 | 58.4 | 8290 |

同一次诊断构建中，网关记录 1516 次路由错误全部满足 `errors.Is(context.DeadlineExceeded)`，阶段耗时 3000–3115 ms；与网关 router HTTP client 的 3 秒超时一致。最后一组 294 次预占错误中，285 个 gRPC DeadlineExceeded、9 个 Unavailable；15 次鉴权错误为 DeadlineExceeded。日志不包含每阶段成功耗时，也没有独立路由请求排队、服务端 CPU、网络或数据库请求跟踪，因此不能断言路由服务内部物理根因，更不能把本次分类推广为上一次测试所有 503 的根因。更改超时可能改变错误和排队，不能单凭此数据视为优化。

最后一组按 request ID 核对：619 个成功各有一笔结算；753 个 503 无预占；**8 个 503 仍有 pending、无用量**。最终余额投影与账本一致，但容器在等待 600 秒对账前已清理，8 笔未观察恢复，不可将其描述为最终账务恢复通过。Outbox 均未发送是 relay 关闭导致，不能证明投递。

最终 MySQL 累计 Max_used_connections 104、Connection_errors_max_connections 0，行锁等待 2 次/23 ms；这些是整个测试过程累计快照，不排除连接池排队、advisory lock 或其他瓶颈，也不是单阶段归因。Redis 最终累计 total_commands_processed 111371、peak memory 4088280 bytes、累计 user/sys CPU 分别约 2.65/1.58 秒；数值含启动及所有场景，不是单请求归因。CPU/内存和 Docker 采样原件在 `resources.jsonl`，未提取独立进程峰值或 I/O 作为结论。

测试组之间顺序固定、历史数据随时间增长，本机存在不可控负载；每档仅两轮、4 秒，不是生产容量或稳定上限。需要进一步测量 router 服务内部队列、连接与端到端耗时，使用长时间、开放到达率、多账户、不同模型延迟及故障恢复，之后才可评估削减路由热点、增加隔离和限流或调整资源配置。

## 补充：路由锁等待诊断

`run_router_lock_diagnostic.py` 在同类隔离环境中用另一 Go overlay 对 router 的 `snapshot`、`RouteExclude` 选路临界区、`Report` 分别累计调用数、锁等待时间、持锁时间与最大值；只改变测试构建，原始文件为 `gateway-diagnostic-runs/20261103-184120/`。统计在操作完成时更新，快照为累计值；等待时间跨 goroutine 相加，不是墙钟时间，快照和请求分组不保证严格时间隔离。仪表本身带来少量开销。

两轮 512 总并发分别为 4/999 和 0/1019 个路由错误；两轮 1024 总并发分别为 312/1414 和 381/1209 个 503，第二轮分类为路由 221、预占 157、鉴权 3。整个测试 537 个路由错误均为 deadline；预占 149 DeadlineExceeded 和 8 Unavailable，鉴权 3 DeadlineExceeded。

最终累计快照：`snapshot` 4653 次，最长锁等待 5181 ms，338 次等待至少 3 秒；选路临界区 4653 次，最长等待 4498 ms，180 次等待至少 3 秒；`Report` 3959 次，最长等待 6377 ms、1013 次至少 3 秒，最长单次持锁 281 ms。结果证明本次运行中共享锁存在长等待，与路由超时量级一致；并未将每条网关超时关联到特定的锁等待。源码显示 `Report` 在持有共享 mutex 时执行 `resetDBFails`/失败持久化，`snapshot` 缓存失效时也在锁内查询 MySQL；该实测没有将具体一次长持锁与某次 SQL 单独关联。锁竞争、数据库访问、HTTP 排队与主机负载可能同时影响结果，不能只凭统计证明单一根因。

最后一组逐请求核对 828 个 200 对应结算、362 个 503 无预占、**19 个 503 有 pending 无 usage**；余额投影与账本一致。容器清理前未等完整 600 秒，pending 的最终恢复未观察；relay 关闭。累计 MySQL 最大连接数 111、连接数上限错误 0、InnoDB 行锁等待 0，不能排除连接池等待或 MySQL advisory lock。

第一次脚本运行 `20261103-184004` 因局部变量遮蔽启动函数，在服务启动前失败，未发压；失败记录保留。第二次 exit 0，随机测试容器已清理。下一步应在测试中验证缩短 Report 锁内数据库操作，同时保持成功/失败顺序、熔断、AutoBan、缓存失效及持久化故障语义，不能简单把数据库写移出锁后就声称正确或有性能收益。
