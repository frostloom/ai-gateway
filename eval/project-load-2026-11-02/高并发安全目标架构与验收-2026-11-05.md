# AI Gateway 高并发与安全：目标架构及验收

这是一份**待实现和验证的方案**，不是当前已具备的功能或上线批准。适用目标是多租户、单租户多个在途请求、流式与非流式；成功率、尾延迟与账务正确性必须同时看。范围为当前工作树，不能把其他分支或历史实验的结果当成组合回归。

## 当前判断

1. 暂保留现金链路的 Redis 和 MySQL：现有代码不只是用 Redis 做缓存，余额投影、guard 和锁均涉及资金。单 MySQL 现金原型有局部性能结果，但订阅、充值、迁移、恢复和混版未等价，不能据此切换；见 `../billing-comparison-2026-11-02/高并发与稳定性判断.md` 与 `Redis价值补充报告.md`。
2. 鉴权 Redis 正向缓存已接入但默认关闭（`BILLING_AUTH_CACHE_TTL_SECONDS=0`），普通 key 可选启用，浏览器会话始终走数据库。缓存没有 New API 的主动失效和围栏；观察到 Redis 故障的 Store 实例会暂时绕过缓存，新实例仍可能接受有效期内的旧快照。保持默认关闭，见 `可选鉴权缓存验证-2026-11-05.md` 与 `NewAPI鉴权参考与安全边界-2026-11-05.md`。浏览器会话单查询已落地，性能收益仍未独立归因。
3. 当前路由缓存刷新已在锁外查询，并有本实例失效代次；回报按渠道串行，数据库写失败通过 HTTP 503 暴露。仍未解决跨实例状态、回报事件身份、迟到回报、提交确认丢失及半开探测身份；网关记录失败而非盲目重试。保守 unknown 策略为当前默认，但旧模式、旧实例与直接入口仍需统一，见 `路由回报缩锁落地-2026-11-05.md`、`路由回报写失败响应修复-2026-11-05.md`。
4. 当前工作树短测 80 与 120 请求/秒各两轮无错误；160 请求/秒两轮波动大，第二轮发生 346 个 503、214 个发压丢弃，且 3 个 HTTP 200 在短等待后已有用量但尚未结算。对账宽限 600 秒，该次未观察到最终恢复。固定准入候选虽降低成功请求尾延迟，却主动拒绝 12.33%/16.88%；这些非同期短测均不能定义生产容量。见 `当前工作树路由优化网关复测-2026-11-05.md` 与 `高负载账务异常复测-2026-11-05.md`。

补充代码边界：非流式请求的用量上报与结算共用一个独立于客户端的 10 秒 context；前一步耗时会减少后一步的剩余时间。现有高负载日志未记录各自耗时，不能据此认定共享预算是结算超时根因；单纯延长超时可能增加排队，不能代替定位及可靠恢复。

## 建议的权威状态和边界

### 请求与账务

以数据库中的请求、账单与事件为恢复依据。设计一个带租户、请求 ID、请求指纹和每次上游尝试身份的持久状态机，且预占及初始尝试所有权的写入应与账单/必要 Outbox 写入具有明确的事务边界。所有服务端结算与冲正入口需要验证同一权威状态，旧入口和旧实例不能绕过；直接 Store 调用、订阅、充值、管理员操作及历史 pending 都必须纳入迁移设计。

至少区分：预占已提交但尚无发送许可；已授予发送许可/可能已发送；已可靠获得并持久记录用量；已结算；明确可冲正；结果未知需核查。**租约过期、连接超时、进程消失或没有 usage 都不能单独证明上游未执行。** 发送许可提交后到发包之间存在停顿，旧进程可能恢复；因此不能仅凭租约失效就把其作为未发送并退款或启动新的收费尝试。需要上游可验证的幂等/状态查询能力或保守隔离和人工处理；系统不能承诺任意供应商上的恰好一次调用。

已记录有效用量的请求可依照幂等结算；未知结果不得按零用量自动退款。用量和结算事件的持久化、响应确认丢失、Outbox 重投及冲突均需纳入事务/恢复设计。上游输出或本地日志不能在尚未持久化、节点丢失、内容冲突或来源无法验证时当作完整账务证明。账务幂等与模型响应存储和重放必须分别定义。

保留策略需要配套积压总数、最旧年龄、金额及原因的持久可核查视图、人工处理权限和审计；目前对账器 `Held` 是**每轮扫描计数**，不是唯一积压总数。账务与客户可见余额要区分 Redis 投影恢复期间的陈旧读；旧 RDB 实验曾出现余额查询陈旧，不能只看最终账本一致。

### 路由回报与熔断

为每次真实 provider 尝试分配稳定且不可跨请求冲突的事件身份；重投必须复用身份并校验渠道、结果及探测代际。权威状态变化与事件去重记录须有共同事务边界；同 ID 内容不一致必须可见并隔离，不能仅因为 ID 存在就宣布处理成功。被隔离的事件不应阻塞其他事件，重试、保留期限与清理策略应明确。

半开探测许可、结果和状态转换需要可验证的代际及原子保护；旧发送者在许可过期后仍可能恢复，单纯 TTL 不是发送 fencing。没有可信结果时保守持有或明确人工处置，不能假设没发送。成功与失败的顺序语义须明确定义，覆盖跨实例和迟到回报；现有本地内存熔断器、provider 持久计数和任何缓存投影不能各自声称权威。

性能层可在**保持这些语义**的前提下比较分渠道锁、可靠队列/事务批量和本地投影；不得在全局锁内等待慢数据库，也不得将 HTTP 200 当作数据库已提交的证明。队列需要有界容量、超时结果未知语义、健康状态、关闭排空和故障恢复；没有稳定事件身份时不能简单重试失败回报。现有单一 SQL、批量、租约及探测实验只是独立原型，未形成可直接部署的组合。

### Redis 的保留和删除标准

按职责而非全项目二选一：现金预占保留现有 Redis 依赖，直到不依赖 Redis 的候选在现金、订阅、充值、Outbox、权限、迁移、混版及故障恢复中满足相同业务不变量并通过端到端负载。鉴权使用权威查询作为当前安全基线；若引入 New API 风格有限 TTL，必须明确允许的陈旧时间、全部失效入口、回填竞态和 Redis 丢失后的降级，不能声称立即吊销。限流、幂等及其他缓存分别检查可用性和故障语义，不能因单一现金基准而删除。

## 分阶段实施和验收

1. **冻结安全规则并制定迁移：** 明确已在途请求、未知费用、缺失用量、订阅/充值、租户停用、旧实例及历史数据的决策与人工处置。建立真实业务不变量和可回滚的版本门禁，保证旧写者不能绕过新状态；不得用未完成的数据迁移或自动退款掩盖 unknown。
2. **请求/尝试与账务闭环：** 在隔离环境先实现状态事务及权限，逐步接入真实 gateway、billing、reconciler 和所有终态入口；覆盖发送前后真实进程死亡、重复/冲突请求、结算与冲正竞争、MySQL/Redis 故障、提交确认未知、用量持久化故障、订阅/充值和混版。核对余额、账本、状态、事件内容及 Outbox 投递；unknown 在没有证据时保留并可发现。
3. **可靠路由回报：** 将尝试身份、探测代际、去重和持久状态一体化；覆盖同 ID 异参、延迟及乱序、跨进程、半开、AutoBan、丢确认、进程杀死、数据库故障、冲突隔离和故障后排空。确认正确性后再做锁范围/批处理优化，比较故障条件下错误及恢复，不以更快返回错误作为成功。
4. **鉴权和 Redis 故障：** 针对 key、tenant、user、session 每个修改入口、缓存 TTL 与回填竞态、实例重启、状态丢失/分区及恢复分别验证。先确认用户选择的 New API 风格所允许的陈旧边界，再引入缓存；权威查询单 SQL 候选也需不同排序规则、并发变更、会话生命周期及整网关对照。
5. **系统负载与故障验收：** 使用真实所有服务和 Kafka、模拟供应商，混合账户和同账户多请求、流式/非流式，预热后交错多轮阶梯及持续发压；区分计划率、已发率、成功吞吐、总在途并发及发压丢弃。记录成功率、超时、平均/P95/P99、CPU/内存、数据库连接/等待与可靠 I/O、Redis 指标，以及每个请求的终态与事件投递。分别报告零错误和 ≤1% 两个口径，P95 单独展示；未指定延迟 SLO 时不宣称满足 SLO。完成排空与恢复观察，否则列出未完成项目。生产容量需在目标拓扑和资源预算下另测。

## 实施限制与交付门槛

当前工作树混有大量改动和测试原型，先做变更清单与逐项审查；不能通过直接回滚未知文件清理。各原型需要合并前独立审查数据模型、事务锁顺序、安全授权、失败语义和升级/回滚。`高并发稳定性综合决策-2026-11-03.md` 及各报告包含实际源码路径、版本、复现命令和原始结果；目标架构不替代这些证据，也不将任何一项局部通过等同整体验收。

本工作不使用生产数据、付费模型，不自动部署或提交。当前尚未达到以上验收门槛，不能建议将整个分支合并上线。
