# 幂等与限流的原子准入：测试候选

针对 Redis 暂停时 429 后清理可能留下幂等键，`atomic_admission_test.go` 构造独立测试 Lua：先检查现有幂等键，存在返回重复；否则检查测试用 1 秒/1 次窗口，超限直接拒绝而不创建幂等键；允许时在同一脚本占用键并更新滑动窗口。该候选只在测试文件，不接入正式 middleware、billing 或 gateway；脚本的窗口、限额和 TTL 是测试常量，当前项目的全局 `idem:<key>` 跨租户干扰也未解决。

`bash eval/project-load-2026-11-02/run-atomic-admission-full.sh` 使用脚本自己的真实隔离 Redis，三轮 race：64 个不同键同时竞争 1 个限额，恰好 1 个允许、63 个限流拒绝，拒绝者均没有幂等键；已存在键优先返回重复，不消耗新限额；人为清除隔离测试窗口后，一个此前拒绝的键允许；64 次相同键竞争为 1 个允许、63 个重复。miniredis 三轮也通过 `atomic-admission-miniredis-20261104.txt`；未实现 stub 的三轮红灯 `atomic-admission-red-20261104.txt` 保留。没有真实网关、调用方取消或性能对比。

## 重要反例：脚本错误不会回滚

同一真实 Redis 三轮中，人为将计数序列 key 设为非数字，再调用候选。脚本先写了幂等键，随后 `INCR` 报错；测试确认幂等键仍存在而限流集合计数为 0。`TestAtomicAdmissionScriptErrorLeavesLease` 的 PASS 表示**成功复现缺陷**，不是安全通过。Redis Lua 在其他客户端之间是原子执行，但脚本内部运行时错误不会自动撤销此前写入。候选现有写入顺序因此不能部署；参数及 key 类型预检、改变写入顺序或采用可恢复状态需进一步验证，任何方案仍须考虑 OOM、命令执行后响应丢失及异常 key 状态，不能简单称为事务回滚。

完整日志 `atomic-admission-real-full-20261104.txt` SHA-256 `b05d590a97ab5ee3af47227fbd8ad074cc09d49123a1e249e5d167fbae266a60`，测试代码 SHA-256 `5b43e6a41f22390ca9e23658ed8a09774cd6cfa9ea900f5e55709354730fe2de`。第一版单独正常并发日志 `atomic-admission-real-20261104.txt` 是添加反例前版本。

## 接入前未解决项

实际项目支持无幂等键、不同租户、可配置窗口和额度；需对齐 key 作用域、历史键/账单 ID、过渡时新旧实例、过期与响应不明。不同 key 位于 Redis Cluster 不同 slot 时多键 Lua 可能无法运行，当前测试为单实例；需要确认真实拓扑及迁移设计。脚本成功但响应丢失、客户端重试、限流 key 被淘汰或 Redis 恢复旧数据、错误响应和成本核对都未测。前述 Redis 暂停后残留问题不能仅靠本原型声称解决；未修改生产配置或部署。

## 第二版写入顺序与新的部分副作用

测试专用 `atomic_admission_v2_test.go` 将幂等键 SET 放在限流序列与 ZSET 更新之后。先将 V2 暂时指向第一版，真实 Redis 三轮 `atomic-admission-v2-red-20261104.txt` 在序列 key 非数字时复现残留幂等键；调整顺序后，正常 64 并发规则保持通过，序列错误不再产生幂等键，`atomic-admission-v2-green-20261104.txt` 三轮通过。

但脚本仍无回滚。真实隔离 Redis 中创建临时 ACL 用户，允许脚本及其他命令而禁止 SET：三轮均在更新限流集合后因 SET 被拒；结果是没有幂等键，但限流集合已有 1 次记录。以有权限客户端立即重试被限流；人为清除测试窗口后可成功。`TestAtomicAdmissionV2SetDeniedLeavesRateCharge` 的 PASS 是成功复现这个部分副作用，不是完整正确性通过。真实 ACL 错误是刻意构造的确定性故障，不等价于生产 OOM、网络丢包或每一种脚本错误。三轮正常并发、错误序列及 ACL 反例输出 `atomic-admission-v2-final-20261104.txt` SHA-256 `956d52654f34e0b07ec9b9b1de847db049b0461f2b9fe42945fc43c49da3407d`；当前 V2 测试代码 SHA-256 `d877a34f53d1ba3a7ca0eb8e10b3ad36c3d59db8543907a54b5bf63eb82e68f2`。原共用测试文件为复用并发断言调整后 SHA-256 `60527d09f7269dee9832fc639c414867d6df829a020de1308f1f5a28b3e82e1d`；上节旧 SHA 是重构之前的原件。

复现 `bash eval/project-load-2026-11-02/run-atomic-admission-v2-full.sh`，只创建、清理自身隔离 Redis。移动 SET 改变的是故障后果，不能赋予 Redis 脚本事务回滚能力，也没有解决成功后响应不明、Redis Cluster 多 slot、过期/恢复和混版问题；V2 不接入生产。

## 成功响应丢失的应用层模拟

`TestAtomicAdmissionV2LostReply` 在真实隔离 Redis 执行脚本并确认准入成功，随后在调用方人为丢弃成功结果，模拟业务 handler 尚未开始时无法确认结果；用同一幂等键、不同 owner 重试。三轮均观察到原 owner 的幂等键存在、限流计数为 1、重试返回重复。测试 PASS 表示复现该可用性缺口，不代表安全通过或业务已经执行。它没有在网络上丢包或断开连接，也没有覆盖 handler 已启动时的同样故障；无法据此证明实际客户端超时行为、恰好一次执行或自动恢复。

复现仍使用上述脚本，包含 race 和三轮测试；原始日志 `atomic-admission-v2-lost-reply-20261104.txt` SHA-256 `34f719abdf1d4911a6cff116532c81da29453f0d85a8c2a11be183964a3456e7`，测试文件 SHA-256 `b7f00c890c7001707795bf31c2aad78afc7a685c110a621085f80557a558ea15`。需要将准入状态与业务开始、持久请求身份和账务状态一起设计恢复协议；仅删除或重用 Redis 键不能证明不会重复执行。该候选继续保持测试专用。
