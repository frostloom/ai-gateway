# 网关处理器默认保留未知结果

此前 `cmd/gateway` 已默认开启保守行为，但直接调用 `handler.Chat` 并省略可选参数时，处理器仍默认为旧行为。工作树将 `Chat` 省略参数的默认值改为保守：当上游请求返回传输错误或非 2xx 时，不因该结果切换到另一个上游或立即冲正；显式传入 `false` 仍选择原行为。正常启动的 `cmd/gateway` 已显式传入环境配置，因此默认命令行配置下本次改动不改变该入口；显式关闭开关的部署与旧版本仍不受保护。直接调用包内 `forwardNonStream`/`relayStream` 的测试未改变默认值，但实际 `Chat` 会向它们显式传入所选模式。

`run_upstream_unknown_test.py` 以本地 HTTP 模拟上游在读完请求后断连或返回 503，配合 billing/router 替身，对非流式、流式各两个场景测试直接调用 `Chat` 且不传选项。修改前四项均触发第二上游并返回 200，红灯；修改后均仅一次初始上游请求、第二上游 0 次、HTTP 502、无用量上报/结算/冲正。完整 handler overlay suite 的 race 检查通过；原 `TestChatReportsSuccessfulFallbackProvider` 现在显式传入 false，仍验证旧切换行为的三个分支，不代表旧行为安全。另独立运行 handler、gateway client 和 cmd/gateway 包 race 测试通过；cmd/gateway 无直接测试文件。

这是有意偏保守的行为变化：某些确定失败或 4xx 也会留下待处理预占，可能降低可用性并增加积压；任何未传参数的外部源码调用者也会观察到行为变化。这里不证明供应商实际收费、进程崩溃后安全、账务持久恢复或自动核查；替身账务不是实际 MySQL/Redis。直接 Reverse、旧实例、显式关闭选项、缺少统一持久尝试状态和用户使用新请求 ID 均仍有风险，不能据此称完整计费链路安全。此前命令行默认值与全链路隔离验证仍以其报告为准，本次没有重跑完整网关负载。

## 当前源码逐尝试守卫及成功完成标记实验

在上述当前 Store 测试 overlay 基础上，生成器又从当前 `chat.go` 构建**仅测试**的 handler overlay：每次向上游发送前调用测试 bridge 的 `BeginUpstreamAttempt`，用测试数据库中的请求、ordinal 和 provider 建立并启动尝试。实验特意给 `Chat` 显式传入 `false`，使旧模式尝试切换，从而检验守卫本身；不能把效果归因于现有默认保守模式。

三轮基线不加 handler 守卫时，流式和非流式均为首上游 1 次、第二上游 1 次、HTTP 200，安全断言失败。加守卫后同样的上游断连场景三轮均首上游 1 次、第二上游 0 次、HTTP 502、尝试 sending、账单 pending，余额和账本均为 999。这里使用测试 bridge/表及本地上游，未接正式 RPC，也没有实际供应商调用。

进一步以正常成功的模拟流量检查同一个候选：三轮流式与非流式均因尝试仍为 sending 而失败，说明仅 Begin 不形成完整生命周期。随后另加测试专用 Finish：非流式在响应校验后、用量上报前标记完成；流式在收到并成功转发 DONE 后标记完成。三轮正常成功均观察尝试 completed、账单 settled、余额与账本 960；再对断连场景三轮回归，仍无第二上游、尝试 sending、账单 pending。上述成功实验验证的是指定样本，不是所有成功响应。

**候选不能部署。** Finish 和用量上报/结算是分开的操作；完成标记之后进程死亡、用量持久化失败或流式输出已发后标记失败，仍可能出现 completed 与未结算的账单，或用户收到内容而本地结果未知。DONE 未成功转发、无 usage、截断、4xx、请求取消、尝试超时、网络提交确认未知、请求正文指纹、旧实例绕过、混版与多实例恢复均未由本组实验覆盖。成功完成并不证明供应商执行仅一次。现有严格 Store 候选与此非严格测试配置也未组合；不可将它们合并成生产安全保证，尚未进行性能测试。
