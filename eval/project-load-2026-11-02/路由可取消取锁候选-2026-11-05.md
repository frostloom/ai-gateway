# 路由可取消取锁：测试候选

当前 `snapshot` 和选中渠道前均用 `sync.Mutex.Lock`，等待期间不响应 context。测试 overlay 基于当前工作树将这两处改为 `TryLock` 循环：取不到锁则使用 1ms timer 等待或响应 context；取得后仍检查 context，并保留原有互斥区域和探测位操作。其余 Report、数据库写和全局锁没有改变。生成器拒绝找不到或重复的源码替换锚点；不修改正式 `registry.go`。

测试复用真实 Registry 与隔离 MySQL 行锁：锁住渠道 A 后触发达到熔断阈值的写入，再给已缓存的渠道 B 发 50ms 超时请求。基线三轮均直到 300ms 检查后释放行锁才返回，正确性断言失败；候选三轮均在释放锁前返回 `context deadline exceeded`，释放后 A 的失败计数仍为 1。此结果不保证在任意调度、极端过载时 50ms 精确返回；它证明指定故障次序下返回发生在数据库解锁前。候选同时通过阈值持久化和多 Registry 状态测试三轮；带 overlay 的 `internal/router`、`internal/gateway/client` 两包 race 测试通过。失败测试在释放行锁后等待工作 goroutine 退出，避免遗留本次测试任务。

**不能上线或称吞吐改善。** 定时轮询可能带来调度开销、饥饿和公平性变化；没有在高并发或完整网关中测吞吐、P95/P99、CPU 与计费正确性，也没有证明其他路由入口、无限期 context、路由写入的取消、动态扩缩、全局锁长占用、跨实例、回报可靠投递或所有熔断状态。该候选只让有截止时间的选路等待能够返回，不让被阻塞的写入自行恢复；数据库锁等待和持久化失败 HTTP 200 问题仍在。不能把超时更早返回当作更高成功率。
