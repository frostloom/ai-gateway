# 网关未知上游结果保守选项

当前 HEAD `63b9d1ed4d64bb583d15fa884c37468e5c53044c` 加未提交工作树。新增网关环境变量 `GATEWAY_HOLD_UNKNOWN=1`，对流式和非流式：上游 Do 出错、非 2xx 响应时不再主动切换渠道或直接冲正，返回 502 并留下 pending；构造请求在发包之前失败仍沿用原冲正。默认未设置保持旧行为。该模式没有更改任何生产配置。正常响应走原计费流程；在某些确定连接失败或普通 4xx 也会保守保留，降低可用性并可能冻结预占。

`python3 eval/project-load-2026-11-02/run_upstream_unknown_test.py` 在当前默认模式以安全断言复现四个失败：本地上游读完请求后断连或 503，流式和非流式均调用第二个上游，输出 `upstream-unknown-current-red-2026-11-04.txt`。`python3 eval/project-load-2026-11-02/run_upstream_unknown_hold_test.py` 通过测试注入显式开启模式，四种故障均不调用第二上游、不报告 usage、不结算、不冲正并返回 502；另验证流式/非流式正常成功及完整 400 的处理，race 通过，输出 `upstream-unknown-hold-final-2026-11-04.txt`。该测试为真实 loopback HTTP 和 billing/router 替身，不代表所有传输层重试或真实供应商行为。默认模式原有 handler 包 race 回归输出 `upstream-hold-default-regression-2026-11-04.txt`。

`python3 eval/project-load-2026-11-02/run_unknown_hold_combined.py --current` 两轮启动真实本地 gateway、billing、router、reconciler 和隔离 MySQL/Redis、模拟 503 上游。脚本实际给 gateway 设置 `GATEWAY_HOLD_UNKNOWN=1` 并给 reconciler 传入 `-no-auto-reverse`；1 秒扫描，5 秒测试宽限，关闭 rebuild。模拟上游各接收一次，HTTP 各 502，等待 status 的 held=1 后仍 pending、仅 reserve Outbox，审计无余额不一致；记录分别在 `unknown-hold-combined-runs/20261104-020952/` 与 `20261104-021036/`。只有一个配置的模拟渠道，不能据此证明多渠道场景没有第二次调用；多渠道仅由上述受控 handler 测试覆盖。此次仅记录启动脚本和二进制/源码哈希，配置 JSON 未单列 gateway 的该环境变量，以脚本为准。未启动 relay，未调用付费服务。

这是可选缓解，不是权威状态协议：其他 gateway/旧实例仍可能重试或直接冲正；对账器若不启用相应选项仍可退款；预占长期保留且没有自动恢复或人工处置入口。客户端使用新请求 ID 可再次请求，HTTP transport 和供应商执行也没有端到端恰好一次保障；正常响应但 usage 持久化失败、流中断估算、进程死亡、混版、订阅、充值和所有上游语义均未由本实验解决。默认仍不安全，不能直接作为生产部署方案；性能影响与故障率也尚未测量。

## 成功响应但无用量

进一步发现：该保守模式最初仍将 200 响应中缺失 usage 的情况按估算结算。流式与非流式两项定向测试修复前均发现 usage 报告及结算，见 `unknown-hold-missing-usage-red.txt`。现在启用模式时保留 pending，完整非流式响应和已经转发的 SSE 仍可返回 HTTP 200；默认模式保留原有估算行为。定向 race 及正常响应/错误回归通过 `unknown-hold-missing-usage-green.txt`，默认 handler 全包 race 通过 `unknown-hold-missing-default-regression.txt`。复现 `python3 eval/project-load-2026-11-02/run_upstream_unknown_hold_test.py` 和 `python3 eval/project-load-2026-11-02/run_upstream_truncated_safety.py --suite`。

`bash eval/billing-comparison-2026-11-02/run-gateway-hold-no-usage.sh` 使用真实本地 HTTP handler、billing gRPC、Store、隔离 MySQL/Redis：流式和非流式各三轮 race 均返回 HTTP 200、上游一次、pending 无 usage、仅 reserve Outbox、余额与账本均 998；输出 `unknown-hold-no-usage-integration.txt`。该测试直接向 handler 传入选项，未启动独立网关或对账器；因此实际启用与后续保留仍取决于两个服务的正确配置，旧对账器可能退款。HTTP 200 不代表账单最终结算，保留未解决资金冻结和用量核查问题。
