# Redis 暂停与恢复：隔离网关实验

## 优先发现：失败请求的幂等键可能阻断重试

在 `redis-fault-runs/20261103-164120` 两次空闲时暂停 Redis，均以 16 个账户各 1 worker 向真实 gateway 发送带唯一合成 `Idempotency-Key` 的请求：各轮 16 个请求全部 HTTP 500，初始及对账后的逐请求账单映射均为无 reserve。Redis 恢复后采样，这两批失败请求的幂等键分别有 **14/16、16/16** 存在。选择第一批中的一个仍存在的合成键，携带原账户和相同请求体实际重试一次，返回 HTTP 409 `duplicate Idempotency-Key`；`retry-paused-key-1-sample.json` 保留这个人工补充请求的结果（其本身发生在对账等待期间）。不是响应重放测试；不能因此声称所有失败请求都无法重试，或证明每个 Redis 命令的准确执行时序。

调用链：`cmd/gateway/main.go` 的 `APIKey → Idempotency → RateLimit → Chat`，`internal/gateway/middleware/idempotency.go` 使用 Redis SETNX，出错时返回 500、键已存在时 409；网关无法在此次命令超时的返回中确定服务端是否已经执行。直接无条件删键可能破坏并发去重，不能在未解决晚到 SETNX、已进入后续链路的请求以及账务/上游状态的情况下草率补偿。最终设计需独立处理命令结果不确定、同请求并发、可恢复状态及账务幂等；模型响应保存和重放是独立能力。

## 条件与结果

代码版本和哈希、镜像与端口在各次目录的 `config.json`；用户工作树含未提交改动；fresh MySQL/Redis 使用随机本地端口，64 合成账户、本机模拟上游 15ms、Kafka 关闭。只对脚本创建的 Redis 执行 docker pause/unpause，其他服务未操作。先空闲暂停 2 次，再在发压后约 0.42 秒和 0.87 秒暂停各约 3.45 秒与 3.17 秒；实际操作时间见 `timing-inflight-*.json`。不知道暂停时每个请求位于哪一步。对账 5 秒扫描、测试专用 30 秒宽限，恢复后等待 40 秒，不代表生产恢复时间。

| 阶段 | 并发 / 账户 | 请求结果 | 全请求 P95 |
|---|---|---|---:|
| 暂停前带键 | 16 / 16 | 209 个 200 | 393 ms |
| 暂停前不带键 | 16 / 16 | 197 个 200 | 458 ms |

全请求 P95 包括失败请求；闭环 3 或 4 秒、运行顺序固定且与其他主机工作负载共享，不能表示生产容量。第二个请求中暂停场景出现 409，所有这些 409 对应账单缺失；尚未查清其产生的具体时序，不能归因于某一种重试机制。

请求中暂停的首轮：33 个有效 200 对应已结算账单；95 个 503 中，93 个初次无 reserve，2 个是无用量 pending。对账等待后这 2 个转为 reversed。第二轮 64 个有效 200 都映射到 settle。最终 64 个测试账户余额核对无差异、pending 0、reversed 2、settled 1054；输出 `audit-reconciled.json`。Outbox 3166 条均未发送，因本实验未启动 Kafka/relay，不能当成消息丢失或投递恢复证明。网络分区、Redis 重启/故障转移、Redis/数据库提交边界、计费后断电、真实上游、长期负载及多实例均未覆盖。

首次空闲实验 `redis-fault-runs/20261103-163737` 两轮均出现失败和恢复，最终账本一致，未记录 Redis 幂等键快照。首次事后尝试读取该已清理容器的快照失败（连接拒绝），不当作测试结果；第二次改为恢复后即时查询并完成上述实测。隔离容器已清理。

复现：`python3 eval/project-load-2026-11-02/run_redis_fault.py`。脚本如今在 Redis 恢复后自动对仍存在的失败合成键重试一次；原运行中的 `retry-paused-key-1-sample.json` 是手工补测，其他原始文件未覆盖。复现结果有时序差异，若无仍存在的键会记为 null。

## 自动重试脚本复验

更新脚本后运行 `python3 eval/project-load-2026-11-02/run_redis_fault.py --no-inflight`，结果目录 `redis-fault-runs/20261103-164847`。两轮空闲暂停的带键请求各 16 个 500、对账后均无 reserve；恢复后的 Redis 快照分别有 14/16、16/16 个键存在。脚本各选其中一个相同账户、相同请求体和相同键实际重试，均返回 409；该命令的 `retry-paused-key-{1,2}.json` 和快照、初始/最终 trace 均留存。恢复后的正常新请求可以成功，最终 64 账户余额核对无差异、pending 0；Outbox 3990 条未发送是 Kafka/relay 关闭的预期配置。此复验不含请求在途暂停，仅验证自动重试脚本以及上述空闲故障场景；关键业务修复尚未实现。
