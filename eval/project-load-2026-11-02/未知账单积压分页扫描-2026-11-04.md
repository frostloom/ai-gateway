# 未知账单积压时的对账分页

## 问题与实现

默认保留未知账单后，`SweepOnce` 原先会一次 `Find` 所有超期 pending 并加载完整账单结构。隔离实验每轮增加 1025 条未知账单，连续三轮单次读取分别为 1026、2051、3076 行，超过测试的 256 行上限（`reconciler-backlog-red.txt`）。单次结果数量随积压增长，存在进程内存增长风险。

现在 `internal/billing/reconciler/reconciler.go` 在每次 sweep 开始时获取符合条件账单的最大 ID，以固定 cutoff 和 `id > last AND id <= upper` 升序分页，每页最多 256 行，仅读取扫描需要的 ID、请求 ID、usage marker 和创建时间。逐条分类及 billing RPC 保持原规则：默认无 usage 保留、有 usage 补结算；显式旧选项仍可冲正。固定 ID 上界防止扫描期间持续新增更大 ID 的记录导致本轮无法结束；它**不是数据库一致性快照**，已有记录在分页之间状态变化仍可能影响本轮结果，原有旧冲正竞争也没有被修复。

## 验证

随机隔离 MySQL 8.0.40 / Redis 7，真实 `SweepOnce` 和 Store、race 三轮：

- `reconciler-backlog-green.txt`：三轮累计约 1025、2050、3075 笔合成无 usage 账单，每页最多 256；每轮追加的一笔真实 reserve + usage 均被扫描并结算，余额和账本均为 960 分。
- `reconciler-backlog-10k-green.txt`：每轮新增 10000 笔，累计分别扫描 10001、20001、30001 行，其中未知账单分别 10000、20000、30000，一笔已上报用量账单结算；单页均不超过 256 行。三轮 sweep 墙钟分别 380、414、609ms（含一笔本地结算 RPC 替身），仅为本机合成样本，不是生产容量或旧/新性能对比。合成未知账单金额为 0，不代表真实账务历史或资金处理。
- `reconciler-new-id-fence-green.txt`：在首个分页读取后插入一笔人为设旧时间的新自增 ID，第一轮不包含它，第二轮包含它；三轮通过。未覆盖手工指定旧 ID、所有并发更新或跨数据库事务隔离的交错。
- `reconciler-backlog-default-regression.txt`、`reconciler-backlog-legacy-regression.txt` 通过默认保留、已知用量结算和显式旧冲正行为；`reconciler-backlog-race-regression.txt` 继续复现显式旧规则下扫描后用量提交仍被冲正的既有风险，不表示已修复。
- `reconciler-paging-process-green.txt` 真实 gateway/billing/router/reconciler 进程及 mock 上游，默认保守设置下未知账单在短测试宽限和对账器重启后仍保留。相关包 race 编译通过；`cmd/reconciler` 和 `internal/billing/reconciler` 无独立测试文件，行为以隔离集成测试为准。

该修改限制每次 SQL 结果集和应用层账单切片，不限制整轮处理条数，也不会自动解决未知账单。每轮仍会扫描全部符合条件的积压；数据库 CPU/I/O、百万级数据、慢 RPC、同时间其他业务负载、持续故障/重启、复杂锁竞争及 Outbox 消费尚未测量。不能据此声称可无限积压或已达到生产目标。当前 reconciler SHA256 `1c4dd1a858ba8490b5ede1ea865a76ad3fb923381d227001f0af4cc6726b4e2a`。
