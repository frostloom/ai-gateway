# 限流拒绝后的幂等键

当前工作树基于 HEAD `63b9d1ed4d64bb583d15fa884c37468e5c53044c`。`cmd/gateway/main.go` 对 `/v1` 和 portal 依次使用 APIKey/PortalSession、Idempotency、RateLimit、Chat。原中间件先以 `SETNX idem:<key>` 占用 5 分钟，再执行租户限流；若限流拒绝 429，下游 Chat 没有运行，但原幂等键仍存在。`TestRateRejectedKeyCanRetry` 先用一个键占满 1 秒测试窗口，另一键收到 429，模拟窗口过期后用同一键重试；原代码三轮均返回 409，见 `idempotency-rate-red2-20261104.txt`。首次测试因包名写错而编译失败，原记录 `idempotency-rate-red-20261104.txt` 保留。

工作树中 RateLimit 在明确拒绝时设置内部标记；Idempotency 在下游返回后仅针对该标记，用 Redis Lua 比较最初 SETNX 的随机 owner，仅匹配时删除键。这样不根据 HTTP 状态猜测：若业务 handler 自己返回 429，不释放键；如果原键过期并由别的请求重新持有，也不删除新 owner。没有改全局键命名、TTL、请求 ID 或正常成功链路，也不把响应保存/重放当作账务幂等。

miniredis 的三个受控测试：限流窗口过期后同键可进入 handler；handler 自身返回 429 时重复仍 409；拒绝后清理前人为替换 owner 不被删除。三个测试 race 十轮通过，`idempotency-rate-repeat-20261104.txt`；gateway client/middleware/handler/controlplane 的隔离 race 回归通过，`idempotency-rate-suite-20261104.txt`。这些测试不证明真实 Redis 故障和网络异常的行为。

## 完整本地链路

`python3 eval/project-load-2026-11-02/run_idempotency_rate_e2e.py --current` 启动真实 gateway/billing/router/reconciler、独立 MySQL/Redis 与本机 503 模拟服务，临时设置每账户每分钟上限 1。先请求一次得到 502（模拟上游故障），第二个不同键得到 429，检查该键已不存在；**人为删除此隔离 Redis 的 rate 键**模拟限流窗口结束，再用第二个键重试得到 502，模拟上游总共收到两次。两次独立运行 `idempotency-rate-e2e-runs/20261104-090507/`、`20261104-090635/` 均同，测试宽限后 2 个 pending、2 个 reserve Outbox、0 结算/冲正、余额差异空。5 秒 grace、1 次/分钟是测试设置；没有等待真实一分钟。Kafka/relay 关闭、未调用付费模型。

## 限制

若清理失败或 Redis 命令结果不明，键可能仍保留到原 TTL，不能保证立即可重试；重试发生在清理完成前也可能得到 409。清理用独立 context 设一秒 deadline，但当前 Redis 客户端未启用 `ContextTimeoutEnabled`，网络读写在某些故障下可能超过该预算；实际网络无响应、Redis 重启、并发多实例及负载下延迟尚未验证。只修复明确的 RateLimit 429，不释放 Redis 错误或其他中间件拒绝的键。原项目跨租户同名幂等键、账单未知结果和旧版本混跑问题不由此解决；不能据此声称完整幂等协议或生产安全。没有部署、提交或连接生产。

## Redis 暂停时的清理延迟

`bash eval/project-load-2026-11-02/run-idempotency-redis-stall.sh` 只创建随机命名隔离 Redis；测试使用真实 `redisx.New` 客户端、真实 Gin 中间件和 Docker pause。在 RateLimit 已明确返回 429 后、Idempotency 清理前暂停 Redis，4 秒后恢复，记录 handler 返回耗时和是否进入业务。原实现仅给清理 context 设置 1 秒，真实客户端未启用 `ContextTimeoutEnabled`，两轮约 3058/3047ms，超过测试 2 秒阈值，红灯 `idempotency-redis-stall-red-20261104.txt`。最早一次验证第一轮约 3086ms，第二轮因复用同一测试租户限流窗口提前失败；修正为每轮不同租户后保留原失败记录 `idempotency-redis-stall-20261104.txt`，完整重复结果 `idempotency-redis-stall-final-20261104.txt`。

工作树现对清理使用 `rdb.WithTimeout(time.Second)` 克隆：与原客户端共享连接池，只改变清理命令的读写超时，同时保留一秒 context；不改变其他 Redis 调用配置。相同 pause 两轮约 1061/1052ms，均返回 429，业务 handler 只被第一次正常请求调用，日志 `idempotency-redis-stall-green-20261104.txt` SHA-256 `bfcc792cf6a679b6caa672e63f822942ef2952b0286cd8979db5edeb73ffb728`。Redis 恢复后两轮键均不存在，但调用方可能在超时后服务器才执行命令，不能推断清理返回成功或保证一般故障可立即重试；有 owner 比较以避免误删替换持有者。两秒测试阈值只是本实验验收，1 秒读写超时不保证各种拨号、排队、重试和调度下严格的端到端一秒上界。

五轮 miniredis 功能回归、四个 gateway/controlplane 包 race 回归通过，分别见 `idempotency-stall-logic-regression-20261104.txt`、`idempotency-stall-suite-20261104.txt`；完整本地服务正常限流与重试再跑一次通过 `idempotency-stall-e2e-20261104.txt`，目录 `idempotency-rate-e2e-runs/20261104-091214/`。pause 只覆盖单个本机 Redis 进程暂停，不代表所有断网、连接池耗尽、Redis 重启/切换、多实例及高并发恢复。当前 `idempotency.go` SHA-256 `dcc985f6834b566863cceea46605ccb9fb6f82cd458db156ea607369a294a4c8`，stall 测试 SHA-256 `90225cb84e0131dac65fc5831b0ccda4c0f53c082e17761cef123234b0b0900d`；上节旧 SHA 和延迟限制是此次调整前状态。

## 64 个并发限流拒绝与 Redis 暂停

`bash eval/project-load-2026-11-02/run-idempotency-concurrent-stall.sh` 用真实 Gin 中间件、`redisx.New`（共享连接池 20）和脚本独立 Redis。先占满一个租户的测试限流窗口，再并发提交 64 个不同幂等键；测试屏障确保 64 个请求都已被 RateLimit 判定 429，然后暂停该 Redis 4 秒并同时释放清理。两轮 race 均得到 64 个 429，业务 handler 在这 64 次中未被调用；请求平均 1269.9/1226.1ms，P95 2084.6/2072.1ms、最大 2085.5/2072.8ms。计时包括并发 SETNX、限流和测试屏障，不只是清理。客户端连接池等待计数增量 129/128、累计等待约 21.8/20.5 秒；这是并发等待时长之和，且包含测试请求各阶段，不能仅归因清理。

Redis 恢复后两轮各有 44/64 个键仍存在。测试人为删除该隔离 Redis 的限流窗口键后，抽取一个仍存在的键重试得到 409；抽取一个已释放的键重试成功进入 handler 返回 204。日志 `idempotency-concurrent-stall-retry-20261104.txt` SHA-256 `2886be8a2f3b9ab35d8e91361d130e1720a7be91bf0f7265ad90458f94db06c8`，测试 SHA-256 `9a9d81ba6a1a68480b2cb4ca1f08951d8df44c6aba77d02cb7b14cdca53d7bff`。此前同一实验未做重试检查的日志 `idempotency-concurrent-stall-20261104.txt` 保留。

这说明修复在 Redis 恢复前未必能完成所有清理，且相同键可能仍被 5 分钟 TTL 挡住；不能宣称故障恢复后立即重试可靠。这里暂停被刻意安排在限流判定和清理之间，不是实际网络分区概率或全网关吞吐。测试只覆盖一个租户、单进程内 64 请求、Redis 进程暂停，不覆盖真实网络分区、不同 owner 并发恢复、billing/Outbox 或长期负载。要消除残留，需要权衡在占用幂等键前限流（会改变重复请求是否计入限额及 409/429 顺序）或设计可恢复的前置拒绝状态；不得无条件删除可能属于已执行请求的键。本次没有进一步修改生产代码。

## 测试候选：先限流再占用幂等键

`TestRateFirstConcurrentRedisStall` 只在测试中更换中间件顺序为 RateLimit → Idempotency，其余使用真实 middleware、真实隔离 Redis 和相同 64 请求屏障：限流器已判 429 后暂停 Redis 4 秒。两轮均 64 个 429、无下游业务调用，恢复后 64 个拒绝请求的幂等键均不存在；人为清除测试限流窗口后抽取一个键重试成功进入 handler。请求 P95 79.8/88.4ms，包括测试屏障和暂停容器操作；与前述原顺序另次运行的约 2.08 秒不可当作随机控制的生产性能收益。日志 `rate-first-concurrent-stall-20261104.txt`，测试 SHA-256 `b16d18804782f3a59f67aeb5dd5df387ba56914438936a99d29193df53177d38`。这是在限流判定完成后刻意暂停的时序，Redis 在判定之前或 EVAL 执行中不可用仍可能返回错误/结果不明；没有真实 gateway/billing、多实例或长时故障。

`TestAdmissionOrderChangesDuplicateRateSemantics` 的 miniredis 三轮显示顺序会改变对客户端的合同：限额 1 时，依次同键首次、同键重复、另一键，当前顺序返回 `[204,409,429]`，候选返回 `[204,429,429]`；限额 2 时当前 `[204,409,204]`，候选 `[204,409,429]`。候选先给重复请求计入限流，可能使后续新请求提前 429；限额耗尽时重复请求也不再优先返回 409。这是重要行为差异，不能将顺序调整当成无语义变化的修复。测试 SHA-256 `1397eaebf2149b825da875d8e6ee88caa4740eefe602c76a567f021698a1ba25`，日志 `idempotency-rate-order-20261104.txt`。
