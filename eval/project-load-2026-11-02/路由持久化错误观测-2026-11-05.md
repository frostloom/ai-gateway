# 路由持久化错误观测

当前路由在 provider 连续失败计数递增、成功清零、自动封禁的数据库写入返回错误时，仅记录日志且 `/report` 仍可返回 200。工作树新增低基数 Prometheus 计数 `router_persistence_errors_total{operation="increment|reset|ban"}`，只在对应 GORM 更新返回 error 时递增；router 的进程入口已挂载 `metrics.Handler()` 到 `/metrics`。不附渠道、租户、请求或错误文本标签。其含义是**调用报告错误次数**，不是确定未提交次数；连接故障可能导致提交结果未知。零行更新、无 DB 的单测路径、进程异常退出前的指标丢失与逻辑层不一致均不会由该指标完整覆盖。进程重启计数从零开始，需外部抓取及告警，不能作为持久账本。

真实隔离 MySQL + GORM 回调注入三类 UPDATE 失败的测试中，每轮 increment=2、reset=1、ban=1，数据库状态不变；修复前三轮预期失败，修复后三轮 race 通过。后者以实际杀停并重启脚本创建的隔离 MySQL 容器复测三轮：每轮故障中 `/report` 仍为 200，但 increment 错误计数增加 1；数据库恢复后再回报一次，内存失败数 2、数据库 1。这是经真实 Registry/HTTP handler 和同一 Prometheus handler 的进程内测试，HTTP 使用 recorder，没有启动生产 router 进程并通过网络抓取 `/metrics`；受控杀停不是所有网络故障或提交确认丢失。

**指标只是发现问题，不修复问题。** 当前依旧不能把 200 视为持久化确认；没有自动恢复、去重、回报身份、准确重试、多实例同步或长期故障测试。切勿根据错误指标为现有无身份协议直接重试：此前已验证同一失败重试会重复计数。也未开展指标开销或全网关压测。先前 overlay 生成的 router 源码不含此新增指标，旧结果按当时版本解释。

## 独立 router 进程与真实 HTTP 抓取

新增 `router_metric_process_test.go`：每轮编译当前 `cmd/router`、以独立子进程和 loopback 端口启动，只给该进程传入本轮容器 DSN 与测试控制令牌。强制杀停脚本创建的 MySQL，向真实 `/report` 发送一次失败回报，再经真实 HTTP `/metrics` 抓取 `router_persistence_errors_total{operation="increment"} 1`；重启同一容器后再回报一次并读取 `/breakers` 和数据库。三轮均为故障回报 200、错误计数 1，恢复回报 200、进程内失败数 2、数据库 1。测试只杀停本轮命名并匹配 loopback DSN 的 MySQL 容器，回收自己启动的 router，外层清理本轮容器。

测试本身用 `go test -race`，但它单独 `go build` 的 router 子进程**没有启用 race**。子进程真实 HTTP 抓取弥补前述 recorder 的边界；它仍只覆盖单实例、单次连接拒绝及手动恢复，不覆盖生产监控采集配置、告警、提交确认丢失或自动修复，也不改变 200 误确认及不一致现状。选取 loopback 临时端口后释放再由子进程绑定，存在端口竞争；冲突会使测试启动失败，并非生产场景。原记录保持，不能称错误已解决。
