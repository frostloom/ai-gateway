# 对账与在途请求竞争：隔离复现

**问题：**在请求仍等待上游期间，若 pending 账单超过对账宽限期，当前对账器只凭创建时间和无 usage marker 判断并冲正。上游稍后返回成功时，网关的用量上报因账单已冲正而失败，但非流式响应仍返回客户端 HTTP 200。若真实上游在这种时序下计费，则存在上游成本未计入本地账单的风险；本测试没有调用付费模型。

两轮隔离实测均以单个合成账户请求本地阻塞模拟模型：先看到一条 pending，等待对账器冲正后才释放模型；模型调用各 1 次，HTTP 均为 200，最终 reserve 均为 reversed、无 settle 记录。网关日志包含 `usage report failed` 和 `reserve is no longer pending`。账本和 Redis 余额一致，但这不代表已记下上游用量。每轮 Outbox 只有 reserve 和 reverse，relay 关闭，未测试投递。

复现：`python3 eval/project-load-2026-11-02/run_reconciler_race.py`。随机本地 MySQL/Redis 容器、模拟模型，测试对账扫描为 1 秒、宽限为 **5 秒**（正式命令默认 600 秒），关闭余额重建；这仅证明缩短时限下的竞争，不证明当前默认配置下正常请求会超过 600 秒。原始记录 `reconciler-race-runs/20261103-175903/` 和 `reconciler-race-runs/20261103-180019/` 含请求、三阶段账单、余额、日志和部分源码/二进制摘要。两轮 exit 0，专用容器已清理。

代码证据：`internal/billing/reconciler/reconciler.go` 的 `SweepOnce` 查询 pending 和 `created_at`，按读到的 usage 标记选择 Reverse；`internal/billing/store/mysql.go` 的 `ReportUsage` 拒绝首次向非 pending 账单记用量；`internal/gateway/handler/chat.go` 非流式成功路径在 `settleAndLog` 后仍返回上游 200，而该 helper 对上报失败只记录日志。

要保证安全，需要区分“确定未发送”与“已发送但结果未知”，以持久化状态及条件变更协调发送、心跳/租约、用量提交和对账。租约过期本身不能证明上游未执行；进程崩溃、慢请求、网络不确定及旧版本共存都必须纳入设计。简单缩短或延长超时、无条件冲正、仅在读时检查标记都不能证明消除竞态。本次未修改生产账务行为，亦未覆盖真实默认 600 秒、流式或真实模型供应商结果。
