# 状态守卫混版与数据库拦截实测

## 结论

仅部署实验状态守卫的新版 Store，不能与未接入守卫的 Store 安全共享账单：后者仍能将 `forwarding` 账单冲正。仅在 MySQL 使用触发器拒绝该状态变更也不是完整屏障：现有现金冲正在 MySQL 状态更新之前先修改 Redis，触发器拒绝时已经出现余额与账本不一致。不要将本实验触发器作为部署方案。

## 两进程复现

本地隔离容器 MySQL 8.0.40 / Redis 7，测试基于 HEAD `63b9d1ed4d64bb583d15fa884c37468e5c53044c` 的当前脏工作树；使用 `go test -race -c` 构造两个独立进程：一个使用当前 Store（称未接入守卫进程），另一个只对 Store 使用当前实验状态 overlay。二者共享同一个新建测试数据库和 Redis，并非历史版本的真实部署二进制；二进制 SHA、镜像 ID 和测试输出保存在日志中。

父进程预占 100 分后通过测试 SQL 将账单设置为 `forwarding`（用来模拟可能已发送，**并未实际调用上游**）。实验 Store 的冲正被拒绝；未接入守卫的子进程随后调用真实 Store `Reverse` 并成功。父进程再尝试记录 40 token 用量被拒，账单状态 reversed，有一条 reverse Outbox、没有 usage Outbox，余额和账本均为 500。三轮一致，见 `mixed-version-forwarding-verified.txt`。测试通过表示**成功复现风险**，不是安全通过。真实上游是否发生费用并未测试或推断。

## 触发器反例及有限恢复

测试专用触发器仅拒绝 `forwarding`、pending → reversed 的账单更新；它存在于新建隔离数据库，并在测试结束删除。未接入守卫进程返回的错误确认包含测试触发器的拒绝信息，但 Redis 此时已从预占后的 400 回到 500，MySQL 账单仍 pending，按账本计算余额为 400。三轮一致。参见 `mixed-version-trigger-recovery-verified.txt`。

随后测试进程上报准确的合成用量并结算：三轮均成功，现金链路重建/修复后 Redis 与账本均为 460。这只验证了一个**在用量后来可取得且正常结算**的受控恢复顺序；测试没有验证差异存在期间的并发查询或消费、服务崩溃、Redis 丢失、无用量或多种冲突。不能将这个受控恢复当作完整的故障恢复保证。

此结果要求切换策略在旧版本仍能操作 Redis/账务前阻断它们的写入，或经过验证地停止并隔离所有旧写入者；需要兼顾在途请求、旧凭据、异步任务和回滚。具体切换屏障、冻结时长、历史 pending 分类、租户可用性以及发生差异的核对步骤仍待实现和故障测试；本报告不宣称屏障已经完成。
