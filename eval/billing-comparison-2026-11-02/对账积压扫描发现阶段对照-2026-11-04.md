# 对账积压：扫描发现阶段对照

当前工作树 `reconciler.SweepOnce` 默认保留无 usage 的 pending，并按 ID 每页最多读取 256 行；一轮仍逐页读取所有到期 pending。已有 1 万条测试的三轮在同一数据库累积到 1、2、3 万条，不适合当作固定规模重复比较。

本实验在独立本地 MySQL 8.0.40、Redis 7，HEAD `63b9d1ed4d64bb583d15fa884c37468e5c53044c` 加未提交工作树，用 2 万条固定合成到期 pending，其中 20 条有 usage，其余 19980 条无 usage。对同一数据集按固定顺序交替重复五轮：

- 全量发现：模拟现有分页查询，客户端分类所有行。
- 筛选发现：只分页查询有 usage 的行，另做 SQL `COUNT` 统计无 usage 的行；不是正式实现。

| 轮次 | 全量发现耗时 ms | 筛选发现及 COUNT 耗时 ms |
|---|---:|---:|
| 1 | 1181.144 | 11.356 |
| 2 | 1244.006 | 13.036 |
| 3 | 1188.008 | 10.520 |
| 4 | 1311.175 | 10.407 |
| 5 | 1175.420 | 10.202 |

每轮两者都发现 20 条有 usage 和 19980 条无 usage；全量向 Go 返回 20000 行，筛选向 Go 返回 20 行，COUNT 返回聚合值。测试使用 `go test -race`，计时包含数据库查询、传输与 Go 处理；顺序固定、缓存预热和本机负载未控制。数字不是无 race 生产时延，也不是完整 SweepOnce 耗时或生产容量。没有测 MySQL 扫描行数、CPU、I/O、锁等待和并发负载，不推断其数量或优化倍数。

筛选发现值得进一步验证，但目前不应替换生产扫描：本实验数据静态，没有真实结算 RPC、余额、Outbox 或账务核对；没有测试扫描期间 usage 从空变为非空、不同 ID 的并发插入、同一轮统计与处理的快照差异、连续失败重试、取消、混版及旧式自动冲正。过滤后 `Scanned` 和 `Held` 指标语义必须明确；两个查询不是同一快照，并发时 COUNT 不能等同逐条处理结果。还需要测大积压下使用索引的实际执行计划、写入成本和与网关混合负载。旧式允许自动退款的模式也不能采用只扫描有 usage 的查询。

复现：`bash eval/billing-comparison-2026-11-02/run-reconciler-scan-compare.sh`。脚本随机创建并清理自己的隔离容器；不调用模型、服务端口或生产数据库。原始输出 `reconciler-scan-compare-20261104.txt`（SHA-256 `cbf66a2e0b0b2c52809916202593b2bcb14bccac091e02dd76c33e6880ec4fab`）；测试代码 `reconciler_scan_compare_test.go`（SHA-256 `d85b3c3a090b31fe8d41509064ba04eaf04dd28c519d6e60e926de7f6ecc29f5`）。实验仅给出下一步验证方向，不证明账务恢复协议已安全。

## 筛选扫描生命周期的受控验证

新增测试专用 `filteredSweepTest`，在独立 MySQL/Redis 中连接真实 Store，但不经过正式 reconciler 或真实 gRPC。三笔真实预占中，A 最初无 usage、B/C 有 usage。测试把页长设为 1，在读取 B 并将游标推进之后，先同步为较小 ID 的 A 上报 usage；接着对 B 注入调用 Store 前的失败，继续处理 C。第一轮仅结算 C；第二轮重新从头扫描并结算 A、B；第三轮无结算。三轮 `-race` 均符合预期，每笔 reserve、usage、settle Outbox 各一条、reverse 零条，Redis 余额与账本均 880（初始 1000）。日志 `reconciler-filtered-lifecycle-20261104.txt` SHA-256 `9f011c378d3fd7c79efb621d1cec563f5f2a285e84f2892375f818417ad6c479`；测试文件 `reconciler_filtered_lifecycle_test.go` SHA-256 `6c3c74f73b643bd076b5a3320356ec0896b15cee2edb6606abf83ae3f950330a`。

复现：`bash eval/billing-comparison-2026-11-02/run-reconciler-filtered-lifecycle.sh`。这个交错证明该测试候选在指定时序下将已越过游标的用量延至下一轮，并可重试调用前失败；不是实际并行 race 或真实网络失败，也不证明进程终止、提交确认丢失、多实例、统计指标及正式 scanner 的行为。测试候选没有实现 `Held`/`Scanned` 和旧版自动退款，不适合接入生产。长期 unknown、恢复授权及全链路安全问题仍未解决。

## 同进程并发扫描和计数边界

新增 `TestFilteredSweepConcurrentWorkers`，两条 goroutine 使用同一个 Store 和测试筛选扫描器，通过屏障保证均已读取同一笔 pending/已上报账单，然后并发结算。三轮 race 均得到：两个返回 `Settled=true`、工作者计数之和为 2，但 settle 账单和 settle Outbox 各一条，Redis 与账本余额均为 960（初始 1000、实际 40）。日志 `reconciler-filtered-workers-20261104.txt` SHA-256 `02102338fd8709490329d730168de3a1e23ce7645dd354b28826fa03e76e89fd`；新增测试后文件 `reconciler_filtered_lifecycle_test.go` SHA-256 `7bd677072ae6c5334edaec3c46256f9713d7371fdc08dcabcccbb8eee801667a`，上节所列文件 hash 是新增本测试前的版本。

复现：`bash eval/billing-comparison-2026-11-02/run-reconciler-filtered-workers.sh`。现有 `settleCash` 对已结算的幂等重放也返回 `Settled=true`；现有 reconciler 将此响应计入 `Stats.Settled`，因此多工作者的成功数不能相加作为唯一结算数。独立账单/事件数可用于本实验核对，但不等于已经设计好生产指标。该结果仅覆盖同进程 goroutine 的受控时序、同一账户一笔现金账单，不证明多进程、网络失败、崩溃恢复或订阅的安全性，也不改变候选未接正式服务的状态。

## 真实对账器的重复成功计数

`TestRealReconcilerConcurrentSettledCount` 改用两个真实 `reconciler.SweepOnce` 和真实 Store；测试适配器在两次 Settle 调用到达 Store 前设置屏障，保证两个扫描器都已选中同一账单。隔离 MySQL/Redis、三轮 race 均观测到两个扫描器的 `Stats.Settled` 之和为 2，实际 settle 账单与 Outbox 各 1，余额和账本均为 960。输出 `reconciler-real-workers-20261104.txt` SHA-256 `a62e87dc4c29e094ac62555ae7a60573ea757d75859dfb0a8bc20e94ea52a762`；测试文件 SHA-256 `85c816e03f65055524ea6bbb503bd489fa4e860478b82a61433dad8e92a384d3`。

复现：`bash eval/billing-comparison-2026-11-02/run-reconciler-real-workers.sh`。这是同进程两个 reconciler 实例、测试适配器替代 gRPC；没有验证独立进程、异常网络或崩溃。由于 Store 对已结算重放也返回 `Settled=true`，当前 `Stats.Settled` 计的是成功响应而非唯一状态转换；生产监控不能简单聚合为去重账务笔数。该实验没有修改指标或 RPC 契约，唯一结算计数的持久定义与跨实例聚合仍待设计。
