# 流式客户端写失败时已读取的用量

工作树 `internal/gateway/handler/chat.go` 原先读取上游 SSE 一行后先写客户端，写失败立即退出，再解析用量。受控测试让内容行成功写出、完整用量行已从本地模拟上游读入但写客户端失败：旧版估算模式实际向测试 billing 上报了估算 11/1，而上游帧为 4/2；这不是生产账单事故记录。另一个测试仅发送用量帧，首帧客户端写失败：即便先解析，原 `!wroteAny` 提前返回仍导致无用量上报。

工作树改为在尝试转发之前解析已经读到的用量；没有任何字节写出时仍尝试返回 502，但若已收到有效用量则继续上报和结算。无用量或发现无效用量仍保留原有未结算处理。测试用自定义 writer 注入指定写失败、使用本地 HTTP 模拟上游和 fake billing，验证先有内容时旧版估算模式与 conservative 模式均上报 4/2 并调用一次结算，以及首帧写失败时 conservative 模式上报和结算。测试不是实际 TCP 断线，也没有连接 MySQL、Redis 或真实上游；只确认 handler 对已完整读入的用量调用测试 billing，不能证明实际持久化、结算成功或客户端收到什么。

首次默认 SDK 的构建因 MacOSX 27 SDK 与链接器不兼容失败，随后使用本机 26.5 SDK：第一例修改前失败，上报 11/1；第二例修改前失败，无上报。修改后完整 handler 包 `-race` 通过。链接器 LC_DYSYMTAB 警告仍存在，全仓测试、真实连接故障和故障后的对账未在本次运行。仍无法解决在读到用量前断线、进程死亡、上报失败或记录丢失等情况，也未改变用户响应重放与账务幂等的边界。

```sh
SDKROOT=/Library/Developer/CommandLineTools/SDKs/MacOSX26.5.sdk \
  go test -race ./internal/gateway/handler -count=1
```

## 隔离真实账务验证

`stream_usage_write_failure_real_test.go` 使用真实 gateway handler、回环 billing gRPC、真实 Store、隔离 MySQL/Redis 及本地模拟 SSE 上游；测试 writer 对已读入的用量帧明确注入一次写失败，并断言该注入命中。三轮 race 中每轮 reserve 为 settled，记录的输入/输出用量为 4/2、provider 匹配，结算行恰有一条且实际收费 6 分；reserve、usage、settle Outbox 各一，reverse 为零，Redis 与 MySQL 账本均为 994 分。初版结果保留，最终测试额外断言失败次数及结算行数量后独立重跑。

此处 writer 是可控注入而非真实 TCP 断线；使用单个合成账户，强制严格 V2 和 conservative 模式，不覆盖其他模式的真实账务、多进程、并发、高负载、Redis/MySQL 故障、Outbox 投递或默认配置。上游已经送达用量、billing 正常可用，仍不能推断用量缺失或上报失败后能自动恢复。
