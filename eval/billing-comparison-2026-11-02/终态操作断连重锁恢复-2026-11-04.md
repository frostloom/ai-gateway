# 结算与冲正断连后的重锁恢复

## 问题和处理

上轮的锁内重建可处理 MySQL 明确回滚，但持有租户锁的 MySQL 连接丢失时，该连接无法执行账本查询或修复，返回错误后 Redis 仍可能与账本不一致。

现在 `internal/billing/store/mysql.go` 在结算或冲正的首次投影修复失败时，释放原会话并尝试以独立有界上下文重新获取租户锁；成功后检查该请求的 delta guard，按已提交账本重建并清理 guard。无论修复是否成功，原终态操作仍返回错误，不把不确定结果报告为成功；重锁或修复失败时，错误同时保留原错误及恢复错误。失败恢复期间的 Redis 写入仍受新会话的 fencing token 限制，清理使用既有的 guard 所有者检查。

## 隔离验证

本地 MySQL 8.0.40 / Redis 7、真实当前 Store，race 三轮。测试在 Redis delta 已应用、MySQL 事务插入 Outbox 的回调中，通过第二个连接执行实际 `KILL CONNECTION`，此时处于 **COMMIT 之前**。上轮代码的控制组 `terminal-connection-kill-first.txt` 显示：结算后 Redis 460、账本 400；冲正后 Redis 500、账本 400；显式重试后才收敛。期望立即恢复的 `terminal-fresh-recovery-red.txt` 因该差异失败。

当前代码的 `terminal-fresh-recovery-production.txt` 三轮：两路径都返回错误后已恢复 Redis/账本 400，reserve pending，终态 Outbox 为空且 delta guard 已清理；显式重试后结算余额/账本 460、冲正余额/账本 500，终态事件各一条。MySQL 驱动的 EOF 日志为注入连接中断的预期记录。测试不认为首次调用成功，也没有模拟真实上游。

明确 SQL 失败回归 `terminal-fresh-recovery-settle-regression.txt` 和 `terminal-fresh-recovery-reverse-regression.txt` 通过；完整 Store race 回归 `terminal-fresh-recovery-full-store.txt` 通过，包 58.183 秒，两个原 opt-in 性能测试跳过。当前 Store SHA256 `e4a53b0eaca810e385a7336c0ace3b05723313b362342b6094b822bee0d8f98c`，原先基于旧 Store 的实验 overlay 需重新生成并回归。

测试仅覆盖事务提交前连接被杀的一种顺序。尚未覆盖 COMMIT 已成功但确认丢失、数据库整体不可用或重锁超时、Redis 恢复时不可用、在 Redis 操作和恢复之间进程死亡、多个实例的全部交错。重锁/重建不能执行时仍会返回包含恢复失败的错误，余额可能保持不一致；普通查询不会校验已存在的陈旧 Redis key。不能据此断言全故障自动恢复，也不解决未知上游结果与旧实例混版。
