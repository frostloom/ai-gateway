# 跨账户幂等：真实账务链路与迁移风险

## 结论

当前全局幂等键会让不同账户的相同客户端键互相冲突。测试候选将键按账户隔离，在所测新数据场景下解决冲突，但直接切换会绕过历史账单；即使先查询旧账单，旧、新写入并存时仍有检查与写入之间的竞态。候选仅用于测试，**不能作为上线方案**。

测试针对 HEAD `42d8ef8e5ca2471b18800e50f8e7a57fbcfdd47f` 加当时未提交工作树，非纯 HEAD。使用隔离 MySQL、Redis、合成账户和本地模拟上游；鉴权、handler、billing gRPC 和 Store 为项目代码，HTTP 通过 recorder，模拟上游为本地 HTTP。MySQL 镜像 ID `sha256:d58ac93387f644e4e040c636b8f50494e78e5afc27ca0a87348b2f577da2b7ff`，Redis 镜像 ID `sha256:858f009f9709ce576febc734aa78b8f6d624b82571f9ddb6bda4377c833b3499`。不是实际供应商调用或真实收费。

## 实际路径及候选

当前 `internal/gateway/middleware/idempotency.go` 将客户端键用于全局 Redis `idem:<key>`，并将同一字符串作为 billing request ID；`internal/billing/store/mysql.go` 的账单以 `(request_id, phase)` 全局唯一。Redis 和账单两层都需要考虑命名空间。无客户端键的请求不受本文测试覆盖。

`build_tenant_idem_overlay.py` 仅构建测试 overlay：对 `tenant_id + NUL + key` 求 SHA-256 并编码成 `i2:` 前缀的 ID，同一 ID 用于 Redis 键和账单 request ID。它不是迁移方案，也不改变正式中间件。重放行为是拒绝重复请求，而非保存或重放模型回复。

## 三轮测试结果

| 场景 | 观察 |
| --- | --- |
| 原实现：不同账户相同客户端键 | 每轮 HTTP 200/409、模拟上游调用 1 次；正向测试按预期失败。 |
| 测试候选：不同账户相同键 | 每轮两账户各 200、各结算；同账户重复为 409，手动删除新 Redis 键后仍由 billing 拒绝重放；各账户 Redis 余额及账本均为 994，指定 Outbox 事件各一条。 |
| 历史账单迁移 | 先用测试辅助中间件模拟旧键及 request ID 写入，再运行候选；旧 Redis 键保留或删除两种情况下，每轮都是 200/200、模拟上游 2 次、2 笔 settled，余额及账本均 988，各账单有独立事件。这里测试通过表示成功复现重复执行风险。 |
| 查询旧账单后与旧写者竞争 | 候选查询旧 reserve 不存在后暂停，测试旧写者完成账单，再恢复候选；每轮模拟上游 2 次、2 笔 settled、余额及账本均 988。先查旧记录与新写入不是原子屏障。 |

旧写者由测试辅助中间件模拟旧 Redis/request ID 的核心行为并调用真实 handler 和 billing，并非运行旧版二进制；竞争测试也不是多进程混部。余额与账本一致只说明两笔均被记录，并不意味着业务幂等正确。测试未覆盖任意参数冲突、所有失败恢复、Redis 宕机、跨进程网络分区、真实滚动发布、回滚及历史数据完整迁移。

## 后续设计约束

正式方案需要先定义客户端键有效期限、同键异参处理及历史重试语义；设计所有版本共同遵守且无法绕过的数据库写入屏障，证明旧写者被排除后再切换命名空间，并处理历史记录和回滚。仅查一次 Redis 或 MySQL 都不能消除上述竞态。必须用实际新旧进程和数据库锁/事务交错、崩溃恢复、Redis 故障及高并发压力进一步验证；在此之前不部署测试候选，也不以此结论估计性能。

## 补充：pending 阶段 Redis 键丢失

新增 `idempotency_pending_redis_loss_test.go`：真实 gateway 鉴权、中间件和 handler 经本地 gRPC 连接真实 billing Store，测试服务显式启用 `RequireReserveV2()`。本地模拟上游在收到首个请求后暂停，此时账单已预占、未记录 usage；分别在同参数重试和不同请求内容重试之前删除 Redis 中间件键。恢复上游后，现有命名空间及测试候选分别三轮均为：首请求 200、两次重试各 409、上游 1 次、reserve 1 条并最终 settled、Redis 和账本余额 994、reserve/usage/settle Outbox 各一条。两组均采用 Go race 检测，进程 exit 0。

该实验只删除指定幂等键，Redis 服务和 billing 可用；不代表 Redis 全部故障、Redis 与 MySQL 分区、进程崩溃或任意旧版本组合也安全。严格 V2 测试条件尤其重要：`cmd/billing/main.go` 的 `BILLING_REQUIRE_RESERVE_V2` 默认是 `0`，而 Store 的旧兼容调用对匹配的 pending 账单仍可返回 `RESERVE_OK`（见 `strict_reserve_test.go`）；不能将本测试外推为旧网关混版安全。测试使用 HTTP recorder，不能证明客户端收到响应；并未保存或重放模型回复。
