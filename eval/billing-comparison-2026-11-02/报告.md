独立 MySQL 8.0.40 与 Redis 7 容器中，直接调用当前 `store.Store.Reserve`：租户 A 初始 1000 分，预占 100 分；租户 B 初始 1000 分，提交相同 request ID、不同租户及不同估算量。两次均返回 `RESERVE_OK` 和相同 bill ID，账单属于 A 且预占 100，Redis 余额分别为 900、1000。测试 PASS 表示复现了当前行为，不表示满足冲突拒绝要求。原始输出见 `conflict-output.txt`，测试是 `conflict_test.go`。

`internal/billing/store/mysql.go:278` 在找到 reserve 时直接返回，未比较租户及其他输入；`Bill`（同文件 104 行）也未保存原始估算 token，因此不能简单依靠现有行完整比较所有原始参数。网关 `internal/gateway/middleware/idempotency.go:23` 对客户端 key 使用全局 `idem:` 键，5 分钟后重新允许相同 key 并生成相同账务 request ID；`internal/gateway/handler/chat.go:113` 将其交给计费。此测试仅复现 Store 边界，未验证完整 HTTP 访问、上游响应或结算，不能据此断言线上实际损失。按用户要求，应将不同参数明确冲突作为后续候选设计和端到端测试的必测项。

## 已阅读的实际链路

`chat handler` → billing gRPC client → `server.Service` → `store.Store`。成功流为 Reserve → 上报用量 → Settle，失败路径调用 Reverse（`internal/gateway/handler/chat.go:113,432,441,480`）。网关的客户端提交去重与模型响应保存/重放是不同问题：中间件只在 Redis 中限期去重并返回 409，不保存响应。

- 现金 Reserve（`internal/billing/store/mysql.go:168,233`）先持有租户 MySQL named lock，Redis 写 owner token 并核验 SQL 会话；查模型价格、订阅和已有 bill，再取得请求 named lock；修复 orphan guard、根据 MySQL 账本重建并校验 Redis 投影，Lua 扣款后在 SQL 事务中写 reserve bill 和 Outbox。插入失败时重新持锁检查提交结果并从账本重建，不能直接假定失败意味着未提交（`cash.go:26,85`）。
- ReportUsage（`mysql.go:517`）事务内锁 reserve 行；重复的相同用量接受，不同值拒绝；用量 marker 与 Outbox 同事务。Settle（572）用价格快照计算，Redis delta 限制余额，账单记录实际收取和 shortfall，SQL 事务写 settle 行、状态及 Outbox；Reverse（733）退回 pending 预扣并事务更新状态及 Outbox；终态竞争由租户锁串行化。
- `plan.go:159` 的权威余额为初始额度加 topups，减 pending 预扣及已结算实际金额；`requireCashMatch`（966）会重建 Redis 投影并读回，不能仅凭 Redis 的存在推断 MySQL 写入更少。Outbox 持久化在账务事务内（`outbox.go:74`），异步 relay 另有重试/重复投递语义。
- 订阅模型额度路径、充值/退款、套餐及余额不足结算规则会影响候选一致性（`mysql.go:262,282,675`; `plan.go:636,700,757`）。它们尚未对候选实现或进行等价测试。应特别验证失败后 Redis 投影恢复和数据库提交结果不确定时的处理。
