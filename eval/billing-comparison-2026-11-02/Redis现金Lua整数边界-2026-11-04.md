# Redis 现金 Lua 整数边界

**发现真实超额预占反例：**HEAD `63b9d1ed4d64bb583d15fa884c37468e5c53044c` 加当时工作树（含受检 Go 计价），隔离 MySQL/Redis、真实 Store：初始余额 9007199254740992 分，计算出的预占比余额多 1 分。原 `reserve.lua` 对两者用 Lua `tonumber` 后舍入成同一个数，错误返回 `RESERVE_OK`，Redis 和账本均为 -1，且写入预占账单；三轮 `redis-precision-reserve-red.txt`。这是极端合成数据，不是生产事件，但证明原子操作不等于数值正确。

本次在现金 `reserve.lua`、`settle.lua` 和 `compensate.lua` 中验证十进制整数，在数值转换和任何 guard/余额变更之前拒绝负余额、无效格式及绝对值超过 **99999999999999 分（14 位）**的金额；结算退款或补偿会使余额超过该上限时也先拒绝。历史 delta guard 若已被旧 Lua 存为科学计数或超范围，也拒绝处理而非猜测。此上限是当前 Lua 5.1 双精度与 `tostring` 表达式下采用的保守应用边界，不是业务容量或对所有 Redis 版本的数学证明；超范围账户可能无法预占、结算或冲正，需人工核查，不应静默转成余额不足。对无法处理的 guard，补偿不会先删除它。

`bash eval/billing-comparison-2026-11-02/run-redis-precision-reserve.sh` 三轮 race：原超额反例返回 Unavailable、无预占行且余额/账本均保持 9007199254740992；真实 Redis 直接执行 Lua 的测试覆盖 14 位余额预占、补偿、正/负 delta、边界值退款、guard 重放，以及超上限退款、补偿和科学计数 guard 的拒绝；`redis-precision-boundaries-complete.txt`。额外计价溢出三个真实 Store case 三轮回归通过 `redis-precision-cost-regression.txt`。完整隔离 Store 包 race 通过 `redis-precision-full-store-race.txt`，两个 opt-in 性能测试 skip；复现 `BILLING_COMPARE_RUN_FULL_STORE=1 bash eval/billing-comparison-2026-11-02/run-subscription-full-store-race.sh`。

**范围和限制：**边界只落实于三个现金算术 Lua，不是所有金额写入的全系统上限；账本重建、充值/退款等 SQL 路径、外部管理接口或旧实例仍可能写入更大值，须进一步统一约束。旧版本已写入的负余额、超范围金额或科学计数 guard 不会自动修复，须隔离审计并设计兼容迁移；不应混版假定所有实例执行新 guard。未覆盖 Redis 多版本、真实故障重启下全部 guard、跨实例网络分区、大金额负载或 Outbox 投递。未知上游误冲正和订阅实际用量超估算仍未解决，不能据此上线。
