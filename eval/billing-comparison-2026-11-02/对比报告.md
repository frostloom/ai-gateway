# AI Gateway 计费核心方案对比：现金路径实验

## 结论与适用范围

本机隔离实验支持**继续研究 MySQL 余额表方案**：在当前测试的现金预占、用量、结算和余额查询负载下，候选 B 的三轮吞吐中位数在六组场景均高于现有 A；但存在单轮反例和明显波动。这不是两个完整产品的等价比较。候选缺少订阅、充值/退款、全量授权及线上迁移和故障恢复语义，不建议直接替换或部署。尤其是跨租户并发复用请求 ID，B 虽回滚且只预占一次，失败方目前得到 MySQL 1062 而非规范冲突响应。

一次 15 秒、8 账户/8 worker 的样本：A 为 94.4 完整周期/秒，平均 84.6 ms、P95 134.6 ms、P99 172.6 ms；B 为 166.0、48.2 ms、75.4 ms、107.0 ms。两者零错误、零超时，账本/余额与 Outbox 数量核对通过。这是各一次短期观测，不能外推生产容量或认为 B 必定更快。

## 代码版本与真实调用链

基准 HEAD `63b9d1ed4d64bb583d15fa884c37468e5c53044c`，分支 `codex/billing-mysql-comparison`；方案 A 包含本分支未提交的请求指纹冲突修复。测试时 `internal/billing/store/mysql.go` SHA-256 为 `71d5925e6d5824babac842559bdc6a0872c453f90904db261622bd2efe540299`。其他预存未提交 web 产物未参与测试。未访问生产数据库、调用模型 API、部署或提交。

`gateway/handler/chat.go` → `gateway/client/billing.go` → `billing/server/service.go` → `billing/store/mysql.go`。模型由上游调用，与此处 Store 计费核心分开；本测试直接用合成的模型目录和固定用量充当模型结果，**未启动模拟模型 HTTP 服务**。

A 的现金预占先持 MySQL 租户 named lock，发 Redis owner fence，再检查模型、订阅路径和请求；现金路径再取请求锁、根据账本重建 Redis、执行 Lua 预扣，然后事务写 reserve bill 和 Outbox（`mysql.go:168`、`cash.go:26`）。用量事务锁 reserve 行并写 marker 与 Outbox（`mysql.go:547` 附近）；结算/冲正持租户锁，先应用 Redis delta，再事务写终态和 Outbox（`mysql.go` 的 `Settle`、`Reverse`）。MySQL 的 `LedgerBalance` 将初始额度加 topup，减在途预扣和已结算实际费用（`plan.go:159`）；`requireCashMatch` 会重建 Redis 并读回。Outbox 只保证本地事务内与账单共同提交；relay/Kafka 投递另有重试和消费者去重（`outbox.go`）。因此不能假定 Redis 一定减少 MySQL 写入。

网关的 `Idempotency-Key` 是 Redis 限期提交去重，不保存或重放模型响应。五分钟窗口后的同参数账务重放与模型请求是否再次执行是独立问题，尚未完成端到端修复。

## 候选 B 与功能边界

`mysql_candidate_test_impl_test.go` 是测试专用代码，绝未接入生产：新增 `candidate_accounts` 余额行，现金预占事务锁账户行，读取模型及价格，检查余额和指纹，扣减余额并写原项目的 `bills` 和 `outbox_events`；用量在事务内锁 bill，更新 marker 与 Outbox；结算/冲正按账户、账单锁顺序在一个事务中写余额、状态、结算行和事件。唯一约束防止重复账单、事件。单事务失败回滚后无需 Redis 投影重建；提交结果未知时应查询持久账单，但此实验未实现完整客户端断线恢复策略。

已覆盖：现金模型价格快照、1.2 倍预占及最小 1 分、用量相同重放/不同冲突、短收封顶的基本实现、现金终态竞争及 Outbox 事务写入。**未证明完全等价**：订阅套餐窗口额度、订阅和充值退款对余额表的同步、禁用账户、历史余额初始化和迁移、旧账单与历史 guard、provider 错误映射和完整授权、Kafka relay/下游去重、断线后提交结果未知恢复、死锁重试及网关完整链路均未覆盖。短收仅实现而未专项对比验证。B 不使用 Redis 作为余额判断或扣减条件，但本实验没有删除其他 Redis 功能。

### 服务指标与解释

15 秒样本中 A 的 Redis `total_commands_processed` 增量为 34455，B 为 2；该统计包含测试自己的 INFO 探针，B 的 2 不表示候选扣款使用 Redis。该读数是全实例总量，非按请求精确归因。两边结束时 SQL 客户端池各有 8 个打开连接、池等待次数增量均为 0，不能推断服务器连接峰值。

同一 15 秒样本中 MySQL 全局 InnoDB 行锁等待增量 A 0 次、B 125 次/209 ms；A 使用的 MySQL named lock 不计入此指标，二者不能直接比较为总锁等待。`Innodb_data_writes` 增量分别为 18425 和 26638，是实例级后台计数，时间内完成周期数也不同，不能当作每笔逻辑写次数或磁盘字节。Redis used_memory 在 A 样本前后为 1,388,320/1,909,576 字节，在 B 样本前后为 1,910,600/1,807,216 字节；它是实例全局快照，受前一场景、key 过期和后台活动影响，不是每周期占用。MySQL CPU、字节级 I/O、Redis CPU 和连接峰值没有可靠采集，不估算。

瓶颈解释只能作假设：A 的路径包含账本聚合重建、named lock 和跨 Redis/MySQL 往返；B 用账户行维护余额，但事务与业务检查也更少。实验没有隔离这些因素，因此不能把差距单独归因于 Redis，或认定生产中删除 Redis 一定更快。下一步应先实现并测试订阅、充值、迁移、冲突规范化及提交未知恢复，再在稳定机器上增加多次长时、故障注入和实际资源指标测量。
