# 审计事件同 ID 内容冲突

## 当前行为

`internal/billing/store/audit.go` 的 `UpsertAudit` 对事件 ID 唯一键冲突执行 no-op，不比较载荷；`internal/billing/consumer/consumer.go` 的 `handle` 在该方法返回 nil 后计入成功并允许提交 offset。隔离 MySQL 中先写入事件金额 40，再以相同 ID、不同投递 offset 重放相同内容，随后提交金额 90 的事件；当前 Store 对第三次也返回 nil，安全断言三轮失败，日志 `audit-conflicting-event-red-20261104.txt`。这证明 Store 会静默吸收该人为冲突；没有在此轮发送真实 Kafka 消息，不推断生产已发生、余额已改变或 offset 已实际提交。旧实现的唯一行约束保证同 ID 一行，不证明不同内容一致。

## 测试候选

`audit_conflict_candidate.go.txt` 仅作为临时 Go overlay：普通插入成功则返回，MySQL 1062 后查询事件 ID，比较 ID、租户、请求、阶段、金额、模型、资金来源、token 指针以及完整 JSON 的解析值，忽略 offset、partition、source 和消费时间等投递元数据。测试在已有事件后顺序及 8 路并发提交相同内容，并分别提交不同金额、租户和 payload；隔离 MySQL/Redis、race 三轮通过（`audit-conflicting-event-concurrent-20261104.txt`）。测试没有 Kafka、首次并发插入竞争、跨进程或数据库故障；JSON 数值词法和时间字段的业务等价规则尚未确定，候选直接比较完整载荷可能拒绝语义兼容的版本差异。不要部署该候选。

**接入风险：**当前消费者 `Run` 对 `handle` 返回错误在当前消息上无限重试，整个消费者循环暂停；若直接把冲突转换为错误，虽然不再静默确认，会阻塞后续消息。需要设计持久隔离证据、可审计冲突告警、分区级顺序、合法重投及人工处置，再通过真实 Kafka 的提交/重启/重平衡、DB 故障、恶意和历史事件验证；不能简单跳过或无凭据重写账务记录。空事件 ID、key 与 payload 不一致、不同 schema、批量高并发与生产数据均未验证。

## 测试专用事务隔离原型

`audit_quarantine_test.go` 试验两张仅测试用表：按 topic、partition、offset 唯一记录合成消息身份指纹与处理结果，并在相同 MySQL 事务中写原始审计或冲突证据。相同坐标和内容重放返回既有结果，同坐标不同内容报错；同事件 ID 内容不同时保留原审计，并将冲突 payload 写入隔离表。这里的消息由测试直接传入函数，没有 Kafka、正式 consumer 或 offset 提交；topic/offset 只是测试输入。正常不同 offset 的重复事件可吸收，数据写入及隔离证据写入失败时事务返回错误。

`TEST_AUDIT_QUARANTINE=1 bash eval/billing-comparison-2026-11-02/run-audit-conflict.sh` 在隔离 MySQL/Redis、race 三轮通过：首次写、不同 offset 同内容、GORM 回调注入隔离写失败、重试保存唯一证据、同坐标重放和同坐标不同载荷拒绝，最后原审计金额保持 40。首次空 stub 三轮按预期失败（`audit-quarantine-red-20261104.txt`）；第一版实现因 MySQL 保留字 `partition` 和 `offset` 未引用，三轮 SQL 语法失败（`audit-quarantine-green-20261104.txt`，尽管文件名如此，该日志**不是通过**）；改为 GORM 字段引用后三轮通过（`audit-quarantine-final-20261104.txt`）。

## 同 ID 首次并发与提交确认丢失

`TestAuditQuarantineRaceAndCommitAck` 对测试事务原型用 12 个 goroutine 从屏障同时提交同一事件 ID 的 12 个不同合成消息坐标，其中六条金额 40、六条金额 90。未加重试的初版三轮均出现 MySQL 1213 deadlock、测试失败（`audit-quarantine-race-ack-20261104.txt`）；该失败只证明测试遇到死锁，不能据此断言消息已经丢失。

测试调用层随后只对 1213 做最多 20 次、短暂错峰的有限重试；不是正式消费者或事务原型内建策略，也没有对连接故障等不确定提交结果盲目重试。三轮均最终 1 accepted、5 duplicate、6 quarantined、12 delivery、6 条冲突证据；各轮发生 21、22、26 次死锁重试。最终原审计金额三轮分别为 90、40、40，**先提交者并不自动代表正确账务**；跨分区/生产者时序不可用来裁决真实金额。此热点下重试次数较高，未测性能或可持续性。

同次对两个独立冲突事件，测试驱动在真实 MySQL 提交成功后分别返回人为错误或 `driver.ErrBadConn`；随后用正常连接按相同坐标重试，均读取既有 quarantined 结果且各仅一条证据。每种三轮。`audit-quarantine-deadlock-retry-20261104.txt`。这是驱动包装模拟确认丢失，没有真实网络 COMMIT 响应丢失；并发与此注入是独立步骤。没有验证消费者在重试耗尽时的处理、正式 Kafka 分区或多进程，以及数据库故障和高吞吐。最终谁的内容为权威需要账本/Outbox 校验和人工或明确的业务规则；不能以先到为准自动消除冲突。当前正式 Store 及消费者未接入该原型。

## 测试原型：先按事件 ID 获取数据库锁

`guardedQuarantineAudit` 是测试专用包装器：在同一 MySQL 事务中先对事件 ID 的 SHA-256 对应 guard 行执行插入/冲突无操作，以获取行锁，再通过嵌套事务/savepoint 调用原消息坐标、审计和隔离逻辑。`TEST_AUDIT_LOCK_FIRST=1` 启用；不依赖 `RowsAffected` 判断插入。仅是为减少上节同 ID 死锁的候选，不改变正式消费者。

`TEST_AUDIT_QUARANTINE=1 TEST_AUDIT_LOCK_FIRST=1 bash eval/billing-comparison-2026-11-02/run-audit-conflict.sh`：12 路同 ID 不同坐标的首次竞争在**禁用测试死锁重试**时三轮全部成功，每轮 1 accepted、5 duplicate、6 quarantined、12 条 delivery，观察不到死锁错误；隔离写入错误回滚、同坐标冲突、普通重放及真实提交成功后驱动层注入两种确认错误的重试同次各三轮通过。日志 `audit-quarantine-lock-full-20261104.txt`。这里检查的是同进程、固定热点和单个本机 MySQL 的短测试，不能证明不发生任何死锁或性能提升。首次赢家仍可能是任一金额，不能据此确定正确账务。

附加大小写等价竞争：本次 `audit_events.event_id` 使用 `utf8mb4_0900_ai_ci`，而测试 guard 对原始 ID 字节哈希，大小写不同却被数据库视为同一审计键时会落到不同 guard。三轮 12 路测试均无错误、审计 1 条/冲突 6 条/delivery 12 条，见 `audit-quarantine-lock-case-20261104.txt`；这**不证明两个不同 guard 已经互斥**，也不能证明排序规则下其他等价字符串或更多调度无死锁。需要明确事件 ID 字符集和数据库二进制唯一性或使用一致的规范化规则，不能以此断言问题已消除。

限制：guard 一事件 ID 一行，当前无安全清理、存储上限或保留策略，额外写入会增加索引和热点锁成本；并未测试不同事件之间的吞吐、分区重平衡、多进程、长时负载或真实 Kafka。部分失败恢复依赖 savepoint/驱动语义，模拟确认丢失不是真实网络故障。key/header/cluster、业务内容真伪、历史冲突和正式 offset 提交/告警仍未解决；该原型不可部署。旧无锁测试的死锁红灯和有限重试结果保留。
