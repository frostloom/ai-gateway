# 鉴权缓存查询耗时与 TTL

测试目录原 `guardedAuthCache` 在权威查询完成后才计算完整缓存 TTL。测试构造查询先读到有效密钥、在返回前延迟超过 TTL；旧候选三轮均将旧结果写入一个全新 TTL 的 Redis 缓存，安全断言失败。正在进行中的查询可能返回先前结果这一点与新请求之后命中旧缓存是两件事。

新增仅供测试的 `guardedAgeCache`，其他逻辑复制原候选，期限从开始权威查询前计算：查询耗尽 TTL 则不回填，未耗尽仅缓存剩余时间，密钥本身过期时间仍可进一步缩短。miniredis 中三轮 race 验证超过 TTL 不回填、短查询使用剩余 TTL、缓存命中不刷新；旧候选原有测试同次运行，包括用于**复现缺陷**的长事务反例。它们是两个类型，原候选没有被替换。

真实隔离 MySQL/Redis 测试让真实 `Store.ValidateAPIKey` 读取旧值后在测试 wrapper 暂停，直接 SQL 禁用该密钥，等待超过测试的 100ms TTL 后释放查询。三轮均观察首次在途查询返回旧值但不写缓存，随后新查询由真实 Store 拒绝。暂停是在查询返回后由测试 wrapper 人为安排，不是实际 MySQL 长事务或网络延迟；100ms 是测试值，不是建议生产 TTL 或可保证撤销时限。

**本候选仍不可部署。** 查询耗时短于 TTL 时仍可能缓存旧值；围栏丢失、长写事务、租户多密钥失效、旧实例及绕过变更入口、Redis 故障/回填竞态、时钟和多进程等仍未闭合。若权威读取本身来自滞后副本或旧快照，查询开始时间也不能保证读取新数据；没有测试真实副本。用户选择参考的 New API 策略不等于此测试候选，参见 `鉴权短期围栏测试-2026-11-03.md`。没有声称严格立即吊销或性能收益。

## 补充：长写入与提交后再次失效

实际 MySQL/Redis + `guardedAgeCache`：测试先设置 150ms 围栏，把写回调停在数据库更新之前，围栏自然过期后通过真实 Store 读取旧密钥并缓存，随后提交禁用。三轮均观察真实 Store 拒绝、提交后的新候选查询仍接受旧值，等待测试缓存 TTL（1 秒）过期后才拒绝。`auth-age-long-mutation-20261105.txt` 的 PASS 表示复现风险，不是安全通过；人为阻塞写回调，并非实际长数据库事务。

增加仅测试用 `guardedPostCommitCache`：原变更返回成功后再次设置围栏并删除旧缓存。在上述指定顺序中，旧候选安全断言三轮失败（`auth-postcommit-red-20261105.txt`），新候选在第二次失效完成后拒绝旧值。**但它不能保证提交后立即生效**：在真实 MySQL 更新已提交后、测试回调返回和第二次 Redis 失效前插入屏障，三轮均观察提交后新请求仍命中旧值；释放后第二次失效，查询才拒绝。日志 `auth-postcommit-gap-20261105.txt` 中 gap 测试 PASS 表示成功复现这一间隙。两个系统没有原子提交，真实进程也可能在此间死亡。

miniredis 注入第二次 Redis EVAL 失败：三轮均为写回调已成功、变更方法返回错误，调用者不能把错误解释成数据库未变；`auth-postcommit-error-20261105.txt` 仅用内存布尔标记回调成功，不是真实数据库提交或网络故障。没有解决重试身份、提交确认未知、故障恢复、跨进程、多密钥失效或误用旧代码；候选不可部署。采用固定 150ms 和 1s 仅为实验，不是 New API 或生产时限。
