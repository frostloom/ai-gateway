# 预占已提交、回复超时：真实组件受控实验

## 目的与场景

此前完整网关 180 次/秒试验有两个 503 对应 pending，原记录没有逐请求上游接收信息，不能确定其成因。本实验验证其中一种**可能的**时序，不声称重现了那两笔请求。以下原有冲正结果使用显式 `WithAutoReverse()`；当前默认已改为保留无用量账单，见文末补充。

`gateway_reserve_timeout_test.go` 使用当前工作树的真实 gateway `handler.Chat`、真实 gateway billing 客户端、真实 billing gRPC 服务、Store、真实 `Reconciler.SweepOnce`、隔离 MySQL/Redis 和本地 mock HTTP 上游。Gateway 使用独立 loopback HTTP 服务，测试中间件直接设置合成 tenant/key/request ID，没有接入真实鉴权、限流或 HTTP 幂等中间件。billing 的测试 gRPC interceptor 等待真实 Reserve 返回成功、即预占事务已提交后，故意不返回回复，直到 handler 的 **3 秒** RPC deadline 到期；这是真实进程内 gRPC/HTTP 传输和应用层延迟注入，不是 TCP 丢包、进程崩溃或数据库故障。

## 结果

`bash eval/billing-comparison-2026-11-02/run-gateway-reserve-timeout.sh`，隔离环境、Go race 三轮，日志 `gateway-reserve-timeout-final.txt`：

1. 真实预占成功并落 reserve/Outbox 后回复超时；gateway 返回 503，模拟上游调用次数为 0；账单为 pending 且无 usage。
2. 同参数通过真实 gateway billing 客户端再次发起**计费预占 RPC**，返回 `RESERVE_DUPLICATE`，账单 ID 相同；这不表示模型回复被保存或重放。
3. 测试人为将账单时间改旧 11 分钟，再运行 grace 600 秒的真实对账器；对账扫描 1 笔并冲正，第二次扫描 0 笔。最终账本和 Redis 均为 1000，账单一条，指定 reserve/reverse 事件各一条，无 usage/settle 事件；整个过程模拟上游调用仍为 0。

早期 `gateway-reserve-timeout-recovery.txt` 没有重试断言，`gateway-reserve-timeout-replay-final.txt` 增加重试。`gateway-reserve-timeout-audited.txt` 的事件断言实际检查 2 条，但日志中 `outbox=1` 是计数变量随后被账单数覆盖造成的**标签错误**；已修正并重跑，最终日志为 2，原输出保留。

## 边界

这类明确在发送前就超时的测试中，显式旧模式最终冲正与没有上游调用的事实相符；**不能因此推断其他无 usage 账单也未发送**。上游已接收而用量丢失的已知反例在显式旧模式下仍可能被错误冲正。人工修改账单时间不是自然等待 600 秒；不覆盖业务端真实重试、HTTP 幂等中间件、原始两笔 pending、消息 relay、Redis/数据库异常、旧实例混版或真实付费供应商。测试没有生产部署或配置变更。

## 2026-11-05：当前默认保留的回归

针对后续 160 请求/秒测试产生的三个 503/pending，本实验仍只验证一种可能时序；当时没有逐请求上游接收证据，不证明那三笔的原因。当前真实 handler、billing gRPC、Store、对账器及隔离 MySQL/Redis 的受控实验三轮 race：预占已提交后测试拦截器延迟回复到 3 秒 deadline，HTTP 503、模拟上游 0 次；采用原请求参数和原内容摘要的计费 RPC 重试返回原账单 DUPLICATE。人工将账单创建时间前移 11 分钟后，**默认**对账器连续扫描两次均保留 pending、无结算或冲正，Redis 和账本均为 998，指定 Outbox 仅 reserve 一条。随后仅为对照，显式启用 `WithAutoReverse()`，冲正一次，Redis 和账本均恢复 1000，reserve/reverse 各一条。该显式模式不表示建议用于未知上游结果。
