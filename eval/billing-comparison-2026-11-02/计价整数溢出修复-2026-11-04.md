# 计价整数溢出与修复

**严重正确性问题：**原 `quota.CostCent` 在除以百万之前用 `int64` 相乘和相加，溢出可能得到负金额；现金结算把负差额作为退款。HEAD `63b9d1ed4d64bb583d15fa884c37468e5c53044c` 加修复前工作树，隔离 MySQL/Redis、真实 Store：初始余额 100000000 分，输入价 10000000000 分/百万 token，预占估算 1 token，合成实际上报 1000000000 token。数学价格为 10000000000000 分，现有短欠策略应至多收取可用余额。修复前三轮却把 Redis 余额错误增加到 8446844073709 分，而账本为 100000000 分，`cost-overflow-red.txt`。这是极端合成输入，不是生产损失或真实调用证据，但证明了可破坏账务一致性。

新增 `CostCentChecked` / `ReserveCostCentChecked` 以 128 位无符号乘加、除法及范围检查计算，拒绝负数和结果不能以 int64 表示的情况；保持原先先整除成本再乘 1.2 的取整规则。真实 Store 现金预占和结算改用受检函数：不可表示预占返回 InvalidArgument，不产生账单/Outbox；不可表示结算返回 FailedPrecondition，保留已报用量的 pending。旧 `CostCent` / `ReserveCostCent` 函数仍供 seed 和测试候选等使用，不应声称所有调用点已受保护。

`bash eval/billing-comparison-2026-11-02/run-cost-overflow.sh` 在隔离 MySQL/Redis 运行真实 Store，三轮 race：上述大用量按短欠策略收取全部 100000000、最终 Redis 与账本均 0；不可表示预占没有账单、Outbox 或余额扣减；不可表示结算保留 pending 与 usage、无 settle 行/事件，余额与账本一致。输出 `cost-overflow-all-final.txt`。这些 case 的输入均为合成值，未调用模型或运行 relay。

`go test -race ./eval/billing-comparison-2026-11-02 -run '^TestCostCheckedAgainstBigInt$' -count=3 -v` 将每轮 5000 组大范围随机输入和 5000 组可表示随机输入与 `math/big` 参考比较，并验证负数、范围溢出和已有取整；输出 `cost-checked-bigint-final.txt`。完整隔离 Store 包 race 回归通过，两个原 opt-in 性能测试 skip，输出 `cost-overflow-full-store-race.txt`；复现 `BILLING_COMPARE_RUN_FULL_STORE=1 bash eval/billing-comparison-2026-11-02/run-subscription-full-store-race.sh`。

**仍需处理：**Redis Lua 对余额和 delta 使用 `tonumber`，在很大整数上可能有浮点精度或字符串格式问题；本次没有建立整个余额链路的安全整数范围，也没有覆盖充值/退款的所有整数边界。不能以宽整数计价通过断言 Redis 大金额安全。不可表示的结算需要人工核查/恢复，不会自动结清；历史溢出账单或投影需单独核查，本次没有修复历史数据。订阅实际超估算、未知请求误冲正、旧实例及混版仍未解决，不宜部署。
