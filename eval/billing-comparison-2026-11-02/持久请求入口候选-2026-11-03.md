# 持久化请求入口候选（实验）

## 目的与范围

针对 Redis 无响应时 SETNX 结果不确定、失败请求恢复后仍被 409 阻断的实际复现，`idem_sql_gate_impl_test.go` 在独立测试表 `eval_idem_gate` 中构建最小状态机：请求 ID 唯一、参数指纹；`claimed` 状态记录 owner 和数据库时间的租约；过期后通过条件更新接管；在真正调用模型服务前，owner 必须用条件更新将状态置为 `forwarding`。一旦状态为 forwarding，即使租约时间过去，也视作上游结果不确定，不自动重发。旧 owner 的转发条件更新在接管之后返回 false。

这是安全性与可用性的取舍：如果在记录 forwarding 后、实际发包前崩溃，也会停止自动重试，需要额外人工或外部对账。仅靠网关无法证明上游是否处理过无响应的请求；不应声称模型请求端到端恰好一次。此实验没有真正调用网关、模型或账务，也没有实现最终完成态、响应保存与重放、usage/结算/冲正/Outbox 协调、请求 fingerprint 的生成和规范化、多租户密钥范围、历史迁移、过期数据清理、混部、告警或人工恢复。绝不能直接用于生产。

## 正确性实验

`run-idem-sql.sh` 在新建随机本地 MySQL/Redis 容器运行 `go test -race`；原始输出 `idem-sql-gate-results-v2.txt`。测试使用当前项目依赖版本和真实 MySQL，断言：同 ID 不同指纹冲突；未过期 claim 不可被其他 owner 接管；测试直接将租约设置为数据库过去时间后，24 个并发请求只有一个取得 ownership，旧 owner 无法转发；转发后即使将租约设为过去，仍不能自动重发；同一 owner 32 个并发 beginForward 仅一个成功；已取消 context 不授权。两项测试通过。它们不是进程 kill、MySQL 崩溃或网络不确定提交测试；人为修改租约用于可重复地观察条件分支，并非证明真实时钟与系统故障行为。参与者是同一测试进程通过连接池并发，并非真实多实例。

## 性能诊断（不等价）

`run-idem-sql-load.sh` 新建隔离数据库，64 workers 使用上限 40 的 SQL 连接池，16 或 64 个客户端，每轮 2 秒闭环并排空，重复 3 轮，奇偶轮调换先后，所有 ID 是合成唯一值。SQL 模式一次 claim INSERT 加一次状态 UPDATE；Redis 模式只执行一次 SETNX、无持久状态和恢复措施。两者语义不同，不能将数值解读为等价完整请求或计费性能差异。无 HTTP、鉴权、余额、上游、Outbox、故障及最终账务核对。

| 并发 | Redis SETNX 成功/秒（三轮） | SQL claim+forward 成功/秒（三轮） | SQL P95 ms（三轮） | SQL 池等待次数（三轮） |
|---:|---|---|---|---|
| 16 | 15233、15803、5447 | 1112、1266、1169 | 30.32、18.67、24.40 | 0、0、0 |
| 64 | 24999、27492、20474 | 1411、1854、1362 | 113.32、74.00、92.83 | 5651、7434、5492 |

各组测得操作错误为 0，池等待是累计次数，耗时相加跨 goroutine；测试机与其他工作负载共享，样本短且波动明显，不能当生产容量。输出为 `idem-sql-gate-load.txt`，源码哈希在测试后另记录 `idem-sql-source-postrun-sha256.txt`，不是运行前冻结证明。尚未测试历史状态持续增长、固定到达率和持久化故障。

此实验说明增加持久前置状态有实际额外成本和恢复语义，也暴露了 64 并发下的连接池竞争线索；不能据此选择最终数据库/Redis 方案。下一步需在现有账务与网关隔离副本接入、验证故障后的正确性与上游不确定语义，再做同条件完整流程测试；无这些证据不得声称更快、更安全或可部署。

## 独立进程被杀测试

随后补充 `TestSQLGateKilledOwner`（原始输出 `idem-sql-gate-process.txt`）：真正启动子测试进程连接随机隔离 MySQL，在它完成 claim 或完成 forwarding 状态写入并明确回报就绪后，由父进程 SIGKILL，使用数据库自然时间等待一秒租约过期，再以新 owner 尝试。两种场景都通过：claimed 可接管、forwarding 返回不确定并拒绝重发。该实验验证子进程死亡时持久行的这两个分支；子进程不发送上游、不执行账务，不证明数据库自身崩溃、网络中断、SQL 提交结果不确定或完整网关恢复。测试输出中的 load 和直接运行的 child 测试被明确 skip；实际 child 在父测试中单独执行并杀掉。更新后的源码涉及额外测试，先前 `idem-sql-source-postrun-sha256.txt` 为旧轮性能测试后的哈希，不能代表现源码。

## 与真实账务组合和反例

`TestSQLGateBillingRecovery` 使用真实隔离 Store：旧 owner 完成 reserve 后以测试 SQL 使租约过期，新 owner 接管，重复 reserve 返回同一账单，随后模拟已完成上游并上报 50 token、结算；断言一个 reserve、一个 settle、三个对应 Outbox 和余额/账本 950。候选没有真正接入网关或上游。

修复前 `idem-sql-reverse-gap.txt` 另复现：如果 reserve 在接管前已被冲正，原 Store 会重放 `RESERVE_OK`，单独的入口候选也会允许 forwarding，而 usage 被拒；不能部署该组合。现有 Store 已修复拒绝已终态及已报 usage 的重放；修复后的真实 Store 与相关定向测试见 `终态预占重试修复-2026-11-03.md`。这不消除状态检查之后与对账/上游发送的竞态，入口、账务和对账尚未组成统一状态机。
