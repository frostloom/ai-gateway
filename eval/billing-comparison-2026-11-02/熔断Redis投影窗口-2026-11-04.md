# 熔断 Redis 投影：提交窗口与阻断实验

这是一组独立测试函数，不接入项目路由。MySQL 使用 `持久熔断状态候选-2026-11-04.md` 的单渠道、阈值 1 简化状态机；Redis 使用测试 Lua 读写状态和版本。执行 `bash eval/billing-comparison-2026-11-02/run-router-breaker-projection.sh`，隔离 MySQL/Redis、race 三轮结果在 `router-breaker-redis-blocked-rollback.txt`；最初独立窗口实验 `router-breaker-redis-projection-gap.txt`、加入阻断但尚无回滚检查的 `router-breaker-redis-blocked.txt` 均保留。

1. **先提交后发布不够。** 起始 Redis closed/v0，MySQL 失败回报事务提交为 open/v1 后，测试控制流程暂停 Redis 发布。此时 Redis 仍放行（1）；发布 v1 后拒绝（0），再提交旧 v0 覆盖请求被版本比较拒绝。删除 key 后许可返回缺失（-1），不能当 closed。三轮一致。该 PASS 是成功复现不安全窗口，并非通过安全验收；没有实际杀进程或制造网络故障。
2. **先阻断可以封住受控窗口，但不完整。** 16 个 goroutine 竞争同一版本的 Redis 阻断，恰一人获取 owner；测试检查提交前和提交后、发布前都拒绝许可，错误 owner 不能发布；读取 MySQL 的 open/v1 并由正确 owner 发布后继续拒绝。阻断没有 TTL，避免过期自动放行，但失主会使渠道持续不可用，需要安全恢复。
3. **旧 Redis 状态恢复仍可失效。** 完成阻断和发布后，测试直接把 Redis key 写回旧的 closed/v0，以模拟 Redis 写入回滚或旧快照恢复；MySQL 仍为 open/v1，但 Redis 又放行（1）。三轮一致。直接覆盖只是故障模型，不是实际 Redis 故障转移、重启或持久化实验。该结果说明同一个 Redis 上的版本比较不能检测自身历史回滚，无法独立证明投影新鲜。

先阻断协议还假设所有写者遵循协议、owner 不被伪造、发布数据确实来自权威 MySQL；本测试没有实现这些授权或可信数据绑定，也未覆盖 MySQL 提交不确定、Redis 写入丢失/分区/切主、重建与旧写者竞争、跨节点恢复、探测与 AutoBan、正式路由接口、性能或长时间堵塞。Redis 在此可能提供快速原子判断和围栏，但不能把单个可回滚的投影当作权威安全状态。不能上线；继续研究必须明确不可绕过的权威入口、故障 epoch/信任边界、重建和可用性策略，并做真实故障测试。\nEOF
## 失主恢复与迟到写者

新增 `TestBreakerProjectionUnsafeRecoveryAllowsLateCommit`：测试先将 Redis 阻断，模拟恢复者读取 MySQL closed/v0 并使用旧 owner 令牌解除阻断；随后人为让原写者继续提交 open/v1，其迟到 Redis 发布被拒，但 Redis 已保持 closed 并放行。三轮结果一致（`router-breaker-redis-late-writer.txt`）。这是测试顺序控制的反例，不是已发生的生产事故；该“不安全恢复”是测试主动构造，并非现有生产恢复流程。

`TestBreakerProjectionFencedRecoveryRejectsLateWriter` 在测试表中增加 MySQL writer epoch：写事件时在同一外层事务先锁 epoch 行并核对；受控恢复先递增 epoch、再读快照并解除阻断。旧 epoch 的迟到事务被拒且不产生事件；随后新 epoch 受控写入 open/v1、发布后拒绝许可。隔离 MySQL/Redis、race 三轮通过，输出 `router-breaker-redis-fenced-recovery.txt`。这只证明上述先后顺序中旧代写者不能提交；增代、读快照和 Redis 发布尚不是原子操作，测试没有覆盖新代写者与恢复竞争，也未解决 Redis 回滚、认证、漏走 epoch 的旧实例或直接 SQL。绝不能仅凭本实验解除生产阻断或声称协议完整。\nEOF
## 正在执行的旧写者与恢复竞争

`TestBreakerProjectionRecoveryWaitsForActiveWriter` 将旧写者停在已持有 MySQL epoch 行锁的事务内，同时让另一个数据库连接提升 epoch；测试通过独立查询 `information_schema.innodb_trx`，实际观察该恢复连接处于 `LOCK WAIT`，而非仅依据等待时间猜测。Redis 此时保持 blocked；放行旧写者后，它在同一外层事务提交 open 事件，恢复更新获得锁并将 epoch 变为 2。随后测试读取到 open/v1、一条事件，发布该快照后 Redis 拒绝许可。隔离 MySQL/Redis、race 三轮通过，日志 `router-breaker-redis-lock-wait.txt`；早期仅用 150ms 等待的 `router-breaker-redis-active-writer.txt` 保留。

这验证的是旧写者**已取得同一 MySQL 围栏锁**的具体竞争；另一测试覆盖恢复先提升 epoch 后旧写者才尝试进入。两者都假设所有写者遵守锁协议。恢复之后的新写者与快照发布、Redis 回滚/切主、进程死亡和真实多节点仍未覆盖；没有正式恢复服务、权限或事件来源约束。观察到锁等待不证明系统无死锁，也不构成生产可用证明。\nEOF
## 实际 Redis 进程重启恢复旧 RDB

`bash eval/billing-comparison-2026-11-02/run-router-breaker-redis-restart.sh` 使用随机名称的专用 Redis 7 容器、固定 loopback 临时端口和隔离 MySQL；确认该容器 `appendonly=no`，先写 closed/v0 并执行真实 `SAVE` 固化旧 RDB，再阻断、提交 MySQL open/v1、发布 Redis open/v1，确认此时拒绝许可。随后实际 `docker kill` 并 `docker start` 同一容器、确认端口不变：三轮 race 均读到 Redis 恢复 closed/v0 并放行，而 MySQL 保持 open/v1。日志 `router-breaker-redis-real-restart.txt`。每轮使用新 key；测试后脚本清理自己创建的容器。

这是实际 Redis 进程终止和重启，不再只是手工覆盖 key；但旧 RDB 是测试**刻意**在新状态前保存，且 AOF 关闭，不能推断其他持久化配置、真实切主或项目生产环境的状态。测试中的 Redis 熔断投影并未接入生产路由；PASS 是复现旧状态导致错误放行，不是安全通过。验证了故障后需要可信的重建/epoch 和流量放行协调，单靠 Redis key 存在和版本单调性不够。\nEOF
补充读取 Redis `INFO server` 的 `run_id`：同一隔离容器每次强制重启后，该值三轮均变化，同时旧 RDB 的 closed/v0 被恢复并错误放行，日志 `router-breaker-redis-real-restart-runid.txt`。这提供了检测**本次进程重启**的一个信号，但测试没有建立检查与许可之间的原子绑定，也未覆盖切主、代理连接复用、网络分区和不同恢复拓扑；不能仅凭一次 run_id 检查宣称已安全防止旧值放行。\nEOF
## 连接身份检查与重连

扩展真实 Redis 重启测试：重启前通过一个 `go-redis` 专用 `Conn` 读取 `INFO server` 并确认其 run_id；重启后不在该 Conn 上重新核对身份，调用许可脚本最多三次。本次三个隔离容器轮次该专用 Conn 均报错（初次日志显示 `Conn is in a bad state: EOF`），没有在该 Conn 上取得许可；普通客户端连接池随后可以执行许可脚本，并读到旧 RDB 的 closed/v0 而放行。测试另通过连接池读取新 run_id 用于诊断，但**没有将该检查接入许可决策**。最终日志 `router-breaker-pinned-reconnect-final.txt`。

首次测试错误假定专用 Conn 会透明重连并返回许可，三轮实际上均为 EOF，因此测试失败；原始 `router-breaker-pinned-reconnect.txt` 保留，之后按观测行为修改断言。该结果仅针对当前 go-redis 版本、专用 Conn 和实际 kill/start 切点；不能外推所有客户端、自动重试、代理或连接池配置。专用 Conn 报错可以作为该连接的失败信号，但整个系统仍需确保连接重建后重新验证身份，并处理检查与许可之间的竞态、Redis 回滚/切主和故障恢复；本实验未实现这些保障。\nEOF
