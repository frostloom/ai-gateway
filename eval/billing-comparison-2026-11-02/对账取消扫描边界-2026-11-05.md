# 对账扫描取消边界

基于 HEAD `457dbfc3fee2e7b1575a29eab033439833985ce6` 加未提交工作树检查 `SweepOnce`：读取一页后逐笔调用结算；父 context 在第一笔中途取消时，原实现仍遍历后续行，若这已经是最后一页便返回 nil。隔离 MySQL 中两笔合成 pending 账单和可控模拟 billing client 连续三轮复现 `err=nil, calls=2`（`reconciler-cancel-page-red-20261105.txt`）。模拟 client 第二次忽略取消直接返回成功；这不等同于真实 gRPC 接受已取消请求，也没有真实结算或余额变化。

现对每行处理前及扫描结束前检查父 context，取消时返回部分统计和 context 错误。已有常驻 `Run` 将此错误记为 `SweepError`；已经发出的 RPC 仍可能完成或提交，取消不证明回滚，下一轮必须依赖原有幂等和账本确认。`Scanned` 是整页读到的行数，不代表逐行已执行。检查与下一次 RPC 之间仍可能发生取消，不能保证绝无新调用。

同一隔离环境三轮 race：取消时只观察到一笔模拟 RPC 且返回 `context.Canceled`；父 context 仍有效时，模拟单笔 10 秒超时后继续下一笔的原行为亦保持（`reconciler-cancel-page-green-20261105.txt`）。对账包 race 命令完成且显示 `[no test files]`，仅证明该包构建（`reconciler-cancel-package-20261105.txt`）。链接器警告留在日志中，`git diff --check` 通过。

测试没有证明真实 gRPC 提交中取消、进程关闭恢复或账务一致性；生产单次命令以 `context.Background()` 调用扫描，不因本改动获得整体超时。单笔 10 秒超时串行累积、扫描 SQL、Reverse 与 Rebuild 的等待边界及未知用量持久恢复仍待处理；不能据此宣称全链路稳定或性能达标。
