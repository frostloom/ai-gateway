# 订阅预占、Redis 重启与余额缺失

HEAD `63b9d1ed4d64bb583d15fa884c37468e5c53044c` 加未提交工作树和订阅预占修复。隔离 MySQL、Redis、真实 billing gRPC 与 Store：一笔订阅预占 100 后，实际 kill 并重启该脚本自己创建的 Redis 容器，确认余额 key 消失。重启后估算 250 的新订阅请求因 300 额度中已有 100 被拒，MySQL 中原预占仍 pending；但原 `GetBalance` 将 Redis 缺失当成真实 0，明明账本余额为 100000，三轮期望恢复余额的测试失败，见 `subscription-redis-restart-red.txt`。

现在余额查询在 key 不存在时通过现有租户现金锁重新检查并从账本重建，读取仍失败则返回错误；订阅新预占和重复预占的余额响应也使用该路径，不再忽略读取错误。Redis 中存在的值为 0 仍视为值，审计使用的低层 `getBalance` 未自动重建，仍可观察不一致。该改动使余额查询在缓存缺失时可能产生 Redis 写入，需要数据库与租户锁；调用者不可假定它始终只读。它不校验一个已存在但陈旧的 Redis 值。

`bash eval/billing-comparison-2026-11-02/run-subscription-redis-restart.sh` 三轮 race 通过：上面额度拒绝仍成立；再发可容纳的 50 token 订阅预占，其 `BalanceAfter` 为 100000；余额查询与账本均 100000，原预占仍有 100 token。输出 `subscription-redis-restart-green.txt`。测试 Redis 为随机隔离容器，重启确认该 key 消失，不使用生产数据。

`bash eval/billing-comparison-2026-11-02/run-balance-missing-concurrent.sh` 三轮 race：人工删除单个账户的余额 key 后，20 个查询与一笔现金预占并发；每次查询结果为预占前或后的合法余额，最终 Redis 与账本均 800，见 `balance-missing-concurrent.txt`。这是同进程有限竞争，不证明跨实例/所有重排序。

`BILLING_COMPARE_RUN_FULL_STORE=1 bash eval/billing-comparison-2026-11-02/run-subscription-full-store-race.sh` 在随机隔离数据库完成完整 Store 包 race 通过，两个原 opt-in 性能测试 skip，输出 `balance-missing-full-store-race.txt`。Go 测试 overlay 仅替换测试硬编码地址。
