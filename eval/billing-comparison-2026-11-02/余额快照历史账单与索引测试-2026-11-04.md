# 余额快照读取：历史账单和索引测试

## 范围

在独立 MySQL 8.0.40、Redis 7 上，用测试版 MySQL 快照 `GetBalance`（SHA `c610210bac0badbd639eba607f9017e0680a713a11092742a309f4c2c5dc325f`）与当前 Redis 热读分别测试。每个场景一个账户，8 个 worker 并发读取该账户，每轮 64 次、两轮；三个账户各有 0、5000、20000 条合成 settled 行，每条 actual=1，初始额度 100000。预置 Redis 余额与合成账本公式一致，每次读取都核对预期值。

这些是直接插入的**简化合成结算行**，没有对应 reserve、Outbox、充值和真实业务操作，不是端到端记账正确性测试。负载是单账户热读，不是用户关心的多账户整体网关容量；运行非随机、测试极短、数据缓存与机器状态未控制。结果仅说明该数据规模下的局部查询趋势，不应外推生产容量。

## 结果

`mysql-snapshot-history-analyzed-20261104.txt` 在原有索引下的快照查询，和独立容器中的 `redis-history-read-20261104.txt` 热读（每格为两轮范围）：

| 合成 settled 行/账户 | MySQL 快照 次/秒 | MySQL P95 ms | Redis 热读 次/秒 | Redis P95 ms |
|---:|---:|---:|---:|---:|
| 0 | 689–781 | 14.0–15.0 | 8099–13229 | 0.73–2.95 |
| 5000 | 362–398 | 26.1–30.9 | 11545–12753 | 0.86–0.92 |
| 20000 | 78–92 | 127.5–185.5 | 13156–13538 | 0.75–0.75 |

每次余额均与预设的合成账本公式一致，测试报告错误数均 0。Redis 每轮只约 5–8ms，计时和排程波动相对于测试长度很大；MySQL 的小样本 P95/P99 也不稳定。

## 索引观察

仅在隔离测试库创建 `(tenant_id, phase, status, actual_quota)` 索引，并执行 `ANALYZE TABLE`。当前查询没有强制索引：`mysql-snapshot-history-analyzed-20261104.txt` 的 `EXPLAIN FORMAT=JSON` 显示，优化器对 5000 行选 `idx_tenant_status_created`、对 20000 行选 `idx_recon`，没有自动选新索引；后者估计扫描约 12489 行。**这是优化器估计，不是实际扫描行数**。查询计划、缓存和执行时间可能随数据分布及统计信息变化。

`mysql-snapshot-history-forced-20261104.txt` 再对单条 settled 汇总 SQL 做 20 次顺序查询：20000 行场景默认计划平均 21.386ms，强制新覆盖索引平均 6.738ms；强制计划显示 `using_index=true`。这不代表完整 GetBalance 的速度：整个快照还有 pending、充值、租户等查询，也不测建索引后的写入、存储成本或混合负载，不能据此向生产添加索引或固定 `FORCE INDEX`。该报告保留早期未执行 ANALYZE 的 `mysql-snapshot-history-20261104.txt`，其运行条件不同。

这些证据支持继续比较事务维护的余额汇总与一致性快照：每次重算账本能绕过陈旧 Redis 读，但账户历史增长时可能成为瓶颈。汇总表仍须验证与所有记账、充值/退款、订阅、事务回滚、并发及迁移一致，不能假定天然更快或正确。
