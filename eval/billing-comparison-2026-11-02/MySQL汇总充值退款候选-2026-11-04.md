# MySQL 汇总余额：充值和按订单退款测试候选

## 目的与实现边界

之前将项目现有充值与汇总原型组合时，充值后账本 600 分而汇总仍 500，错误拒绝预占；`summary-recharge-red-20261104.txt` 以应一致的断言复现失败。这里新增的 `summary_money_candidate_test.go` 只在测试包实现两个候选方法：

- 模拟支付：先锁账户汇总行、再锁订单行，在同一 MySQL 事务写 recharge topup、增加汇总和将订单置 paid。
- 按订单退款：按相同锁顺序验证账户和订单，最多退当前余额，事务内写负 topup、减少汇总和标记 refunded；重复退款返回 0。

项目现有 `PayRecharge`/`RefundRecharge` 对应账务路径没有创建计费 Outbox，因此这个局部候选没有凭空添加事件；若后续业务要求充值事件，须在同一事务内明确加入并验证。测试使用现有订单创建与模拟支付规则，**没有真实支付**。

测试候选与正式 Store 没有集成：正式充值仍不会更新 `candidate_accounts`，两者混用仍会产生此前的不一致。该候选没有覆盖按金额退款、订阅、真实支付、现金所有变更入口、用户/服务权限、存量回填或旧版本屏障；不是可部署方案。

## 隔离测试

`summary-recharge-final-20261104.txt` 使用新建 MySQL 8.0.40/Redis 容器、Go race、每项三轮：

1. 一次支付在事务末注入失败，订单、topup 和余额回滚；16 个并发同订单支付均返回，最终汇总/账本 600、充值流水一条。按订单退款末尾注入失败后仍 paid、余额 600；正常退款 100，重复退款 0，最终汇总/账本 500、退款流水一条。
2. 每轮 8 次同账户 **600 分预占与 100 分退款竞争**。汇总行锁使两者按顺序决定：本次三轮预占分别赢 4/2/2 次、退款赢 4/6/6 次；每次只允许与实际剩余余额相容的结果，结束汇总和账本一致。不是跨进程或长期压力测试。
3. 初始 50 分、充值 100、预占 100 后，按订单最多退款 50；跨租户退款被拒、重复退款为 0，汇总和账本为 0。
4. 支付事务已更新汇总、尚未更新订单时，在测试回调中对该事务的真实 MySQL 连接执行 `KILL CONNECTION`，即 **COMMIT 前**。三轮均回滚订单/资金流水/汇总，余额和账本 500；随后显式重试得到 paid、一条充值流水、余额/账本 600。没有覆盖真实 COMMIT 已成功但确认丢失或数据库整体宕机。

每轮 race 通过是上述受控断言成立，不代表所有规则等价；候选仍可能发生原有账务状态机、Redis 投影以及权限问题。没有测审计事件消费、混合业务端到端性能或生产容量。
