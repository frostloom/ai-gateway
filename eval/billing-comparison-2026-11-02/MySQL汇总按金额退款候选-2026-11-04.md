# MySQL 汇总余额：按金额退款测试候选

## 实现与边界

本次仅在 `summary_money_candidate_test.go` 增加测试方法 `refundSummaryAmount`，不改变正式 Store：在 MySQL 事务内先锁候选账户行，检查退款幂等键和原请求金额，写负 topup 并减少汇总。请求超过可用余额时只退可用部分；同键同参数重试返回本次退款 0；不同金额、租户或不可验证历史流水返回冲突。空键在候选中生成随机键。两个账户同时使用相同新键时，依赖 topup 唯一约束，碰到 1062 后在事务外重新读取并校验归属。

该方法只接入测试候选；正式 `RefundAmount` 仍只更新原账本/Redis，不更新 `candidate_accounts`。账本和汇总尚不能混版、不能直接部署。现有按金额退款没有写计费 Outbox，因此本测试没有新增事件；支付渠道、业务鉴权、订阅和其他现金入口不在本次范围。

## 测试

`summary-refund-amount-red-20261104.txt` 以原 Store 退款与候选汇总组合：退款 200 后账本 300、汇总仍 500，一致性断言三轮按预期失败。最终 `summary-refund-amount-kill-20261104.txt` 在独立 MySQL 8.0.40/Redis 7 容器中运行 Go race，各项三轮通过：

1. 事务写入后注入失败并回滚；16 路同账户、同键、同金额调用累计退款仅 200，最终只有一条退款 topup，账本和汇总均 300；改金额重试被拒。
2. 余额 150、请求退 200 时实退 150，同键重试退 0；不同账户或不同金额重用该键被拒，零金额被拒，最终核对汇总和账本一致。
3. 两账户同用一个新键，在测试回调强制两个事务均到达 topup 插入前再同时放行；每轮仅一个退款 200，另一个返回幂等冲突，两账户余额合计 800 且与账本一致。这是同进程两个数据库事务的受控重叠，不是跨进程或长期并发证明。
4. 退款流水插入后、账户更新前，在事务回调对实际 MySQL 会话执行 `KILL CONNECTION`，处于 **COMMIT 前**。检查流水、汇总和账本回滚至 500；显式重试后恰有一条退款流水、汇总/账本 300。未覆盖提交成功但确认丢失、进程强杀或数据库整体故障。

新增方法后，既有按订单充值/退款候选回归也通过三轮，见 `summary-recharge-after-amount-20261104.txt`。此前的 `summary-refund-amount-barrier-20261104.txt` 保留了加入连接中断用例前的结果；不能将它当作覆盖新用例。

候选仍缺少冲正/用量未知结果的完整状态机、所有资金入口与迁移屏障、权限分离、跨进程死锁和重试策略、真实支付对账、提交确认丢失及性能验证。唯一约束冲突的补读只是测试实现，数据库不可用或死锁应明确失败并由上层处理，不能把错误当作已退款。
