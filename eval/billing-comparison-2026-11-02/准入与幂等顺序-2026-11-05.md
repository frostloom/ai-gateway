# 准入拒绝与幂等顺序：隔离账务实验

候选是在测试中创建的进程内非阻塞单槽 Gin gate，满时返回 503；**正式网关没有接入该 gate**。真实 `/v1` 目前按 APIKey → Idempotency → RateLimit → Chat 排列。现有 Idempotency 只在 RateLimit 的特定拒绝标志出现时尝试按 owner 清理 Redis 键，因此将其他拒绝机制直接插在它之后可能使未进入账务的请求留下幂等键。

实验构造真实 `middleware.Idempotency`、真实 `handler.Chat`、gateway billing 客户端、回环 billing gRPC、Store 与隔离 MySQL/Redis；上游是本机模拟 HTTP，路由与身份由测试替身提供，HTTP 为 Gin recorder。先由测试占满 gate，再用合成 Idempotency-Key 发起请求；确认 503、零账单后释放槽，立即用相同键重试，再次重试。严格 V2 和未知保留开启。

| 顺序 | 首次拒绝后 Redis 键 | 释放后首次重试 | 再次重试 | 最终余额/账本 | 指定 Outbox |
|---|---:|---:|---:|---:|---|
| Idempotency → gate | 存在 | 409 | 409 | 1000/1000 | 无 |
| gate → Idempotency | 不存在 | 200 | 409 | 994/994 | reserve/usage/settle 各一，无 reverse |

三轮 race 均如此，两种顺序合计的模拟上游每轮只收到一次请求。第一行的 PASS 是**复现潜在集成错误**，不代表正式项目已经安装该顺序；第二行只表明本次指定顺序和故障点可重试、无重复扣款。幂等 409 不是响应保存或重放。测试按事件键逐个核对；Kafka relay 未运行，不能证明事件交付。

这一结果支持在幂等键写入前拒绝未准入请求，但不决定实际 gate 应处于鉴权之前还是之后，也不能省略租户公平性、限流规则或容量保护。测试没有真实 API key/portal 中间件、RateLimit、真实 HTTP 网络或并发准入、排队取消、进程重启、Redis 故障、客户端重试风暴和多副本预算。测试中的槽位容量 1 仅用于构造时序，不是建议生产配置。真实项目中将新 gate 放在 Idempotency 后若要清理，必须先证明请求未进入任何计费或上游动作、正确处理 owner 和 Redis 部分失败；简单在任何 503 后删除键不安全。

## 补充：多账户并发、真实鉴权与限流

`admission_multiaccount_real_test.go` 在隔离 MySQL/Redis、真实 billing gRPC/Store、本地模拟上游下，按**真实 APIKey → 测试 gate → 真实 Idempotency → 真实 RateLimit → 真实 Chat** 构建进程内 Gin 处理链。4 个合成账户各有 4 个不同幂等键并发，共 16 个请求；测试 gate 有 4 槽，上游在收到前 4 个请求后由屏障暂时阻塞，确保其余 12 个在满载时作准入决定。真实身份通过合成 key 的 SHA-256 与真实 billing 校验；router 是测试替身、HTTP 为 recorder，测试限流为 1000/分钟，不代表推荐配置。

三轮 race 均为 4 个已准入、12 个 503；逐个检查 12 个拒绝请求在放行前没有幂等键或账单。期间对一个已准入的同键请求再次发起请求，因为 gate 位于幂等之前，**满载时得到 503 而非 409**；释放槽后 12 个被拒绝请求顺序以原键重试，均 200；随后所有 16 个同键请求均 409。上游每轮接收 16 次，逐笔为 settled 且 usage=4/2，reserve/usage/settle 事件各一、reverse 无；四个账户余额与账本均 976，限流 ZSET 各 4 条。已检查账本和事件，不包含 relay 投递。

这证明指定的同进程时序下，gate 前置未造成被拒绝请求的幂等残留或重复扣款，同时暴露过载时重复请求的可见状态码会变化。12 个重试是释放后**顺序**发出，不是并发重试风暴；准入公平性、热点账户隔离、取消和客户端断连释放、流式时长、多进程/多副本、Redis/MySQL/上游故障、真实 HTTP 监听、过载持续性能和实际部署配置均未验证。4 槽是人为实验参数，不代表容量；仅测试真实中间件的组合，gate 不在正式代码或配置中。

## 补充：真实 HTTP 流式断连释放测试槽

`admission_stream_cancel_test.go` 将真实 APIKey、测试单槽 gate、真实 Idempotency/RateLimit/Chat、回环 billing gRPC/Store 与隔离 MySQL/Redis 组合；gateway 和模拟上游均为本机真实 HTTP 监听，router 为测试替身。第一个合成账户收到一帧流式内容后，第二账户以另一幂等键请求，单槽满时得到 503 且 Redis 中无该幂等键；随后第一个客户端取消并关闭响应，模拟上游观察到请求 context 取消。测试等待 gate 槽释放，第二账户用原键重试，收到完整 `[DONE]` 并按 4/2 usage 结算。

三轮 race 均通过：模拟上游调用 2 次；第一笔 reserve 保持 pending 且无 usage，第二笔 settled；两个账户 Redis 余额与账本一致，第一笔仅 reserve 事件、第二笔 reserve/usage/settle 各一，均无 reverse。人为将第一笔账单时间前移 11 分钟并调用默认 `SweepOnce` 后仍 pending。对账通过直接 Store 测试桥，时间是人为修改，并未自然等待宽限期。首个请求已收到部分内容、但无持久 usage，保留并不意味着其供应商费用已解决。

这是测试 gate 的单进程、两账户、一个中途断连时序；不是正式准入实现，也未覆盖慢读但不断连、队列、公平性、崩溃、多实例、Redis 中断、长期积压或 Kafka 投递。不能依据槽位释放或当前余额一致推断上游未执行，不能把槽位容量 1 当作推荐值。

## 补充：单账户占满与测试用租户配额

`admission_fairness_test.go` 比较两个**测试专用、单进程非阻塞 gate**：A 仅总计 4 槽；B 总计 4 槽、每租户 1 槽。两组均使用真实 APIKey → gate → Idempotency → RateLimit → Chat、真实 billing gRPC/Store、隔离 MySQL/Redis；router 为替身、HTTP 为进程内 recorder，上游为本机模拟 HTTP。测试让热点账户 4 个不同请求同时开始，并让已到上游的热点请求在屏障处等待，再发另一个账户的请求。B 的计数仅存在进程内并在请求退出时删除，不是多副本全局配额或生产实现。

三轮 race 均为：A 接受 4 个热点请求，冷账户首次 503；B 接受 1 个热点请求、拒绝 3 个热点请求，冷账户首次 200。释放屏障后，A 的冷账户和 B 被拒绝的 3 个热点请求使用原幂等键顺序重试成功。每组上游 5 次、5 笔 settled，每笔 reserve/usage/settle 各一且无 reverse；两个账户余额与账本分别 976 和 994。A 被拒冷账户在重试前确认没有幂等键；B 的被拒热点请求同键重试成功。Kafka relay 未运行。

这说明在这个受控时序下，每租户上限能给另一账户留出机会，但代价是热点账户 3 个请求被拒；**不是公平性或低错误率的全面证明**。四个不同账户仍可占满全局槽；限制值 4/1 是刻意制造竞争的参数，不是建议配置。未测试排队、优先级、多个网关进程、身份伪造/租户变更、客户端断连、Redis 故障、长流、真实 HTTP 监听、并发重试风暴、容量或公平调度。采用配额前需定义允许单账户的并发、多账户保留策略和过载响应。
