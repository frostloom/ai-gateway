# 预占请求内容指纹与版本协商

基准 HEAD `63b9d1ed4d64bb583d15fa884c37468e5c53044c` 加未提交工作树。原 reserve 指纹只绑定账务参数和 prompt token 估算；同一 request ID 的不同正文只要估算相同便被视为同一预占。现在 gateway 对实际 `chatRequest` 规范化 JSON 算 SHA-256，随 Reserve 的 v2 gRPC metadata 传送；billing 显式校验单个小写 64 位摘要，使用带版本域的账务参数和摘要计算数据库原 `reserve_fingerprint`。不增加数据库列，不保存正文；摘要不是加密或保密凭据，低熵输入仍可能被猜测。未改 proto 生成文件。

新 gateway 的 billing client 要求服务端确切确认 `replay-v2` 才认为预占成功；新 billing 对无效、重复或未知协商参数在触碰 Store 前拒绝。老客户端无新摘要时继续使用 v1，v1 与 v2 指纹不同，不能相互验证已有账单；历史 v1 pending 被新 v2 请求重放时保守拒绝。旧 billing 可能在拒绝确认前已执行旧预占，新 gateway 会拒绝转发但该账单可能留下待核查，不能将协商称作无副作用的混版。未建立阻断所有旧客户端创建新 v1 预占的迁移屏障，也未解决其他入口或直接 Store 调用。

绑定范围是 gateway 当前解析和转发的 `chatRequest`（model、messages、max_tokens、stream），规范化 JSON；不包含被现有 handler 忽略的未知字段、客户端 header、原始 JSON 表达顺序或后续渠道选择等上下文。原有账务参数（含 provider、账户和估算）仍进入最终指纹；渠道发生变化可能使同正文重试冲突。相同 ID 的响应不保存/重放，也不能阻止使用新 ID 的重复请求。该摘要无签名，依赖现有共享控制面身份及传输环境，不能视为供应商执行证明或权限控制。

## 验证

- 真实本地 gateway/billing/router/reconciler、MySQL/Redis、模拟上游，保守选项开启。相同 ID、不同正文但相同估算的安全期望在修改前失败（`../project-load-2026-11-02/content-fingerprint-e2e-red.txt`）；修改后两轮通过（`unknown-hold-fingerprint-runs/20261104-023601/`、`20261104-023728/`），最终校验增加异常协议检查后再通过一轮（`20261104-024003/`）。相同正文 Redis 键过期模拟后为 duplicate，不同正文为 conflict；均无第二次模拟上游调用、pending 保持。复现 `python3 eval/project-load-2026-11-02/run_unknown_hold_fingerprint.py --current`。Redis 键人工删除，非自然等待，grace 5 秒测试用途。
- 真实 Store 和隔离 MySQL/Redis：一次新预占后同 ID 20 个并发调用，同摘要十个 duplicate、不同摘要十个 conflict，v1 重放 v2 拒绝，仅一条 reserve 和一条 reserve Outbox、余额/账本 900；race 三轮 `content-fingerprint-concurrency.txt`，复现 `bash eval/billing-comparison-2026-11-02/run-content-fingerprint-store.sh`。同进程竞争，不证明跨进程故障和所有执行顺序。
- store 单元测试涵盖 v1/v2 交叉拒绝，gRPC bufconn 客户端验证缺失或错误确认拒绝，三轮 race `content-fingerprint-unit-final.txt`；九种异常 metadata 在 Store 前拒绝，三轮 race `content-fingerprint-contract-errors.txt`。gateway 四包隔离 race 回归 `../project-load-2026-11-02/content-fingerprint-gateway-regression.txt`。未进行全项目回归或性能测量。

未知上游结果、自动冲正、双开关、旧实例、订阅和充值全链路、实际网络确认丢失及未来数据迁移/回滚仍未完整解决。不能据此认定安全或部署；本地测试不使用生产数据、付费模型，不提交代码。

## 订阅与旧预占回归补充

`bash eval/billing-comparison-2026-11-02/run-content-fingerprint-subscription.sh` 在隔离 MySQL/Redis 中使用真实 billing gRPC、订阅套餐和 Store；race 三轮均确认 v2 订阅预占成功、同摘要重复、不同摘要冲突、v1 对 v2 重放拒绝，写入用量后结算、终态重放拒绝，reserve/usage/settle Outbox 各一条且 Redis 余额与账本均为 100000。输出 `content-fingerprint-subscription.txt`。这是单账户正常订阅，不覆盖额度满、窗口滚动、并发订阅竞争、重启或充值退款。

`bash eval/billing-comparison-2026-11-02/run-strict-reserve.sh` 在隔离数据库、race 下通过既有 SQL gate 恢复、终态拒绝与 v1 严格预占三项回归，输出 `content-fingerprint-strict-regression.txt`。这些结果不证明 v1 与 v2 可以无中断混版：历史 v1 账单被 v2 重放时会拒绝，旧 gateway 仍能创建 v1 新账单，旧 billing 可能先执行再让 v2 gateway 因缺少确认而拒绝。实际新旧进程混跑、数据库故障、迁移/回滚和生产拓扑仍需验证。

## 可选服务端 v2 屏障

新增 billing 进程配置 `BILLING_REQUIRE_RESERVE_V2=1`：该服务实例在任何预占写入前拒绝未协商 v2 的 Reserve；默认 `0` 保留旧兼容。配置只接受 `0` 或 `1`，其他值启动失败；启动日志记录模式。本次未修改生产配置或部署。已创建账单的 usage、settle、reverse 接口不受此设置影响，因此它只约束新 Reserve 入口，不是未知账单退款保护。

在真实 billing gRPC、订阅 Store、隔离 MySQL/Redis 的定向测试中，修改前 v1 新预占成功，三轮期望失败 `content-fingerprint-required-red.txt`；启用服务选项后三轮 race 通过：v1 在写账单/Outbox 前被拒绝，v2 正常预占、重复与内容冲突符合预期，余额与账本一致，见 `content-fingerprint-required-green.txt`；复现 `bash eval/billing-comparison-2026-11-02/run-content-fingerprint-required.sh`。

另两轮 `python3 eval/project-load-2026-11-02/run_unknown_hold_require_v2.py --current` 启动独立真实 billing 进程并设置该环境变量，v1 gRPC 探针被拒绝且按请求 ID 检查账单与 Outbox 均为 0；真实新 gateway v2 预占与请求内容冲突测试成功。证据目录 `../project-load-2026-11-02/unknown-hold-require-v2-runs/20261104-024447/`、`20261104-024608/`。脚本显式配置保守网关和对账选项、mock 503，5 秒测试 grace，不涉及付费服务。默认未开启该屏障时，既有 v1 严格预占回归仍通过 `content-fingerprint-required-default-regression.txt`。

该屏障仅约束开启它的新 billing 实例；旧实例、直接 Store/SQL、另一路旧服务或未开启选项仍可绕过。它会拒绝旧 gateway 的新预占而影响可用性，不能解决历史 v1 重放无法验证、旧 billing 先写再被新网关拒绝、上下游结果未知、退款或混版切换。需要全实例身份与部署屏障、迁移/回滚和压力验证，不能单凭此选项上线。
