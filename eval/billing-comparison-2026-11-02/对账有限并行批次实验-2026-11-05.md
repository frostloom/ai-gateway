# 对账有限并行批次：隔离原型

## 范围及正确性

`reconciler_parallel_batch_test.go` 定义测试专用固定工作者队列，对给定账单列表通过真实 loopback gRPC、真实 billing Service 和隔离 MySQL/Redis 结算；每个 RPC 期限 10 秒。它不是正式 `SweepOnce`：没有扫描、分页、状态统计、故障恢复调度或旧版冲正，不改正式代码。比较的是**结算批次完成数/秒**，不是完整网关请求吞吐。

`TestParallelBatchBlockedAndDuplicateRealLedger` 以同一合成账户的两笔真实预占/usage，拦截第一笔第一次 gRPC 在 handler 之前挂起；并发执行第一笔、第二笔及第一笔重复请求。三轮均在释放第一笔前看到第二笔真实结算返回，释放后两笔各一条 settle 账单和 settle Outbox，Redis 与账本均 920。三轮 Go race 通过，日志 `reconciler-parallel-stall-final-20261105.txt`。重复的第一笔可能先于被阻塞的同 ID 调用执行；该实验验证指定交错下不重复结算，不证明所有顺序或真实网络故障。

随后每组 32 笔先构造真实预占和 usage，再按 1 或 4 工作者结算；结束后重复所有结算并逐笔核对 reserve 状态、settle 账单、reserve/usage/settle/reverse Outbox 以及所有账户 Redis/账本余额。各组均成功、无超时或错误。1 个账户与 8 个账户分开；每账户均允许多个请求。同一测试容器各组使用不同新账户，按固定顺序执行，数据不断累积；三轮 race、共机、未随机化，样本少、可能受宿主其他进程和缓存影响，不是生产容量。初始两组测试在正确性实验并行运行，保留 `reconciler-parallel-batch-20261105.txt`，不作主要对照。正确性后另有一次不重叠实验 `reconciler-parallel-batch-after-correctness-20261105.txt`，当时无锁指标；下表为之后补采指标的独立三轮，HEAD 版本不同但计费源及测试对象以各日志/源码为准。

所有组错误/超时均为 0。隔离 MySQL 的 `Innodb_row_lock_waits` 与 `Innodb_row_lock_time` 每组增量均为 0；本进程 database/sql 连接池等待增量均为 0。Redis `total_commands_processed` 每组增量：1/1 为 386、385、385；1/4 为 385、385、385；8/1 为 385、385、385；8/4 为 391、394、394。含一次用于读取结束计数的 INFO 命令；这是整个隔离 Redis 的计数，不是逐命令归因。未采可靠 CPU、I/O 或 Redis 锁等待，不能据此指定瓶颈。原始输出 `reconciler-parallel-batch-metrics-20261105.txt`。

四工作者在这组三轮分散账户批次中完成更快，但每组只有 32 笔，单账户延迟增加且吞吐一轮下降，数值波动很大；该数据仅支持进一步评估，不能推断因果、生产容量或适当工作者数。状态统计在并发扫描或重试时可能重复计数；既有真实扫描器实验已复现两个扫描器同时返回 Settled=true 但账单只一条，不能将返回次数直接当唯一结算数。

## 下一步和复现

在接入前需要覆盖真实扫描分页/快照、取消和退出时全部任务回收、有界排队与过载、stats 聚合及多实例、同账户与余额重建/充值/冲正竞争、提交不确定与重试、MySQL/Redis 故障、unknown hold、旧版自动冲正、实际负载和全网关混合性能。原型不可部署，也不能把其测试结果视作这些条件已满足。
