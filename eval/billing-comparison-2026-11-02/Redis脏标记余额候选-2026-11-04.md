# Redis 脏标记余额读取候选

## 设计与已知限制

只在测试 overlay 中试验：获得租户 MySQL advisory lock 后，通过同一 Redis Lua 同时发布 cash owner token 和 tenant dirty 标记，随后才允许该会话修改 Redis 余额；干净读取通过单次 Lua 原子检查标记并读取余额。若 dirty 存在，读取拿租户锁、按 MySQL 账本重建。会话正常释放前再次按账本重建，再以 owner token 比对后清除 dirty；恢复失败保留 dirty。该设计每次金融操作都额外重建，代码仅为实验，并非完整协议或生产实现。不同 Redis key 在 Cluster 模式可能不在同一 hash slot，尚未适配。

`build-dirty-balance-candidate.py` 从固定 SHA 的当前 `cash.go`/`mysql.go` 生成 overlay，SHA 分别 `7c203c28b7a1f34d01e17946234db10c7018a3d6e890f4e3f63ba6e2bb88e453` 和 `f989027318888ae700ab4ccfb042bc052b7fb5d03973ca67e92f50d76cec94ba`。仅修改公开 `GetBalance` 的读取路径，不代表项目所有内部 Redis 读均安全；旧实例、直接 Redis 写者和混版可绕开标记。清理时重建失败不会让原操作返回新错误，只会留下标记，故运维可见性也未解决。

## 故障与并发证据

- `terminal-dirty-candidate-20261104.txt`：真实子进程在 Redis delta 后、MySQL COMMIT 前 SIGKILL，结算与冲正各三轮；候选查询返回账本 400，随后另一预占和原终态重试均与账本一致。基线差异、切点及限制见 [终态进程崩溃与余额读取](终态进程崩溃与余额读取-2026-11-04.md)。
- `dirty-concurrent-baseline-20261104.txt`：真实结算事务在 Redis 修改后暂停，三轮并发 GetBalance 均直接返回未提交的 460，期望不能读取时测试失败。`dirty-concurrent-candidate-20261104.txt`：候选读取等待租户锁并在 200ms 截止时返回错误，事务继续提交后读取 460，race 三轮通过。这验证的仅是一个结算切点，不覆盖全部写入口和锁交错。
- `dirty-marker-loss-red-20261104.txt`：在相同 SIGKILL 后，测试**手动删除** dirty 标记、保留已变化的余额，候选又返回 460 或 500、账本为 400，一致性断言三轮失败。这是对标记丢失状态的模拟，不是实际 Redis 重启、故障转移或 RDB/AOF 实验；它证明单靠 Redis 标记不足以保证安全。不能把该候选用于生产或作为完整崩溃恢复方案。
- `balance-disabled-dirty-20261104.txt`：停用租户已有 Redis 余额的干净读取通过；未覆盖停用租户 dirty 恢复的所有业务语义。候选未提供有可信持久性保证的数据库 epoch、混版栅栏或标记丢失检测。

## 局部热读及完整网关短测

局部读取按 [此前余额测试](终态进程崩溃与余额读取-2026-11-04.md) 的 64 个空账本账户、32 worker、每轮 1280 次执行两轮，候选 `balance-read-dirty-candidate-20261104.txt` 为 24327 / 21527 次/秒，P95 1.659 / 2.340ms、P99 5.227 / 3.733ms，错误 0。它只测无 dirty 的热读，两个运行顺序不同，每轮极短，不能代表混合负载或生产容量。

完整链路以 64 个账户、开放到达率 100/140/180 请求每秒各两轮、每轮 10 秒、本地 15ms 模拟模型执行；Kafka relay 和 Agent 关闭。基线 `eval/project-load-2026-11-02/gateway-open-load-runs/20261104-060908/`，候选 `eval/project-load-2026-11-02/gateway-open-load-runs/20261104-062728/`。两组源码清单、MySQL/Redis 镜像、发压器与非 billing 二进制 SHA 相同；billing 二进制不同。运行器因新增候选开关而 SHA 不同，两组非交错、时间和机器负载不同，不能只凭差异判定因果。延迟为所有请求，吞吐分母含排空。
