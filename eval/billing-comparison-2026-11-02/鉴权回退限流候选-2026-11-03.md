# 鉴权回退并发闸门（测试候选）

先以测试实现 `auth_bulkhead_impl_test.go` 对回退 MySQL 的鉴权操作设置单进程最多 16 个并发许可；无许可直接返回 `errAuthBusy`。它只存在测试目录；并不限制 Redis 缓存命中、其他数据库业务、其他进程，也不是集群级上限。定向 race 测试覆盖并发许可、释放及过载错误。

`auth-bulkhead-load-20261103.txt` 在独立 MySQL 和本地黑洞 Redis 假端点上运行 16/64 并发、每组 3 秒、两轮，64 个合成 Key；发压与服务及其他进程共享宿主机。与该运行的无闸门故障组相比：

| 并发 | 轮次 | 无闸门成功/秒，错误 | 16 许可、立即拒绝成功/秒，错误 | 闸门拒绝占请求比例 | MySQL 池等待次数（无 / 有闸门） |
|---:|---:|---:|---:|---:|---:|
| 16 | 1 | 448.83，0/1360 | 438.54，0/1359 | 0% | 0 / 0 |
| 16 | 2 | 431.41，0/1297 | 351.01，0/1089 | 0% | 0 / 0 |
| 64 | 1 | 1695.57，0/5143 | 1158.96，1937/5452 | 35.5% | 204 / 0 |
| 64 | 2 | 1395.81，0/4232 | 953.40，2114/5333 | 39.6% | 424 / 0 |

闭环客户端在快速拒绝后继续发请求，不代表真实客户端重试行为；分组顺序固定、短时间且宿主负载变化，不能把差值完全归因闸门。该场景下无等待策略牺牲大量成功请求，不能推荐为低错误率的默认方案。等待次数为测试池统计，非数据库总负载；无闸门 0 错误也不能证明长期或多进程下安全。所有故障组为每次鉴权先等待人工无响应 Redis 再回退；普通客户端重试、完整 gateway 的其他 Redis 依赖、真实 Redis 恢复和总容量均未测。

后续候选给本地闸门增加最多 50 ms 的等待，仍限制 16 个回退并发并在等待到期时拒绝；定向 race 测试覆盖限额、许可释放、取消及到期。它也仅为实验，会增加尾延迟且等待 goroutine 数未被独立限制；后续必须比较排队上限、过载时的失败率、重试及多实例预算，不能只看成功吞吐。

## 加入最多 50 ms 等待后的对照

`auth-wait-load-20261103.txt` 采用同样的 16 许可、两个账户并发档、3 秒/轮和两轮；64 并发两轮：无等待分别拒绝 2423/5355 和 2817/4884；50 ms 等待分别出错 587/2774（其中 582 为闸门过载，其余 5 未分类）和 77/4474（全部为闸门过载）。完整结果及 P95/P99 见原始文件。两组均为固定顺序、主机负载变化明显的闭环实验，不能解释为等待必然降低拒绝，也不能忽略五个未分类错误。等待组并没有严格限制等待者数量；短测结果既不满足先前暂定的 1% 错误率，也不足以选择安全参数。继续补充错误分类、记录实际最大并发及更长、更均衡的负载，验证取消、队列上限和多实例预算。

## 有界队列的三轮探针

新增测试候选将回退并发限制在 16、等待者最多 32、等待最长 50 ms；超过队列或时间返回过载错误。排队名额在获得执行许可时立即释放，定向 race 测试覆盖执行许可、等待名额、取消和超时；发现并修复了最初错误地把排队名额持有到执行结束的候选错误。无 FIFO 公平保证，限额仍仅为单进程。

`auth-bounded-queue-20261103.txt` 使用与前文相同的 MySQL 和黑洞模拟，16/64 并发、每组 3 秒、三轮，第二轮反转顺序。64 并发的有界队列分别处理 3961、4945、2175 个请求，其中过载拒绝 376、53、1056（约 9.5%、1.1%、48.6%）；对应成功请求每秒 1180.47、1613.89、363.09，P95 87.90、56.92、172.77 ms。均未达到暂定 1% 错误率。无闸门故障组分别为 0/1392、9/1151、0/2176 错误，9 个错误类型为 `*net.OpError`；无等待闸门一轮另有 2 个 `*net.OpError`，未记录底层原因，不能臆断是数据库、网络或超时。各组请求数不同，拒绝后发压器立即继续，统计为全请求包含拒绝的延迟；由于系统负载变化剧烈以及顺序和速率不完全可控，不能据此证明等待策略的普遍收益。

该样本否定了在本实验条件下把 16/32/50ms 直接当作低错误率默认配置；不是生产容量，也不是其他负载与参数的定论。下一步需要更稳定环境、固定到达率、实际网关与完整账务、真实 Redis 故障、多进程预算及客户端退避，才可讨论生产限流与熔断设置。相关命令仍是 `run-auth-outage.sh`；脚本现已更新为三轮含队列版本，旧实验原始输出保留但脚本不再逐字复现旧顺序。

## 2026-11-05：真实 Redis 停止与有界回退

`auth_bounded_redis_crash_test.go` 使用真实隔离 MySQL、真实 Redis 和测试候选 `guardedAgeCache` + 单进程回退闸门；脚本核验自建容器名称与 loopback 端口后实际终止 Redis。32 个并发鉴权使用两个合成密钥，闸门配置 8 个执行许可、8 个等待位置、最多等待 50ms；测试**人为阻塞回退入口 400ms**，然后释放并调用真实 `Store.ValidateAPIKey`。三轮 Go race 均得到 8 成功、24 过载拒绝、其他错误 0，测试 wrapper 观察最大在途回退 8。执行数和拒绝数受这个人为屏障、等待期限和调度影响，不代表自然数据库故障或生产参数。这里的最大在途是进入 wrapper 的鉴权操作数，不是 MySQL 的连接数或 SQL 并发指标。

随后以直接 SQL 禁用一个密钥，启动同一 Redis 容器并等待 ping 成功；两密钥没有在崩溃前预热，恢复后禁用密钥拒绝、有效密钥接受。该检查不覆盖 Redis 持久化旧缓存、围栏丢失、恢复期间并发、密钥变更入口或多个进程。候选只用于测试，当前网关还在幂等、限流和计费路径依赖 Redis，鉴权回退成功不代表整网关可在 Redis 停机时服务。

日志中的大量连接拒绝和 go-redis `failed to dial after 5 attempts` 由真实 Redis 中断触发；虽然测试将命令 `MaxRetries` 设为 -1，连接池日志仍显示拨号重试，不能把配置解释成每请求只有一次拨号。没有测量错误风暴对 CPU、日志或生产网络的影响。三轮的 75% 拒绝率是该强制屏障实验结果，不应作为吞吐容量或推荐配置，也没有比较真实客户端退避、长时间负载和集群级上限。
