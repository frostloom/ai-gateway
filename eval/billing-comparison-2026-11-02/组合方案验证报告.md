# MySQL 事务记账 + Redis 余额读缓存：隔离原型验证

## 结论

测试原型**不能提供余额读取的强一致性，也不能直接用于生产**。模拟 MySQL 成功提交、进程在 Redis 失效之前中断时，MySQL 余额已变为 850 分，缓存仍返回 950 分；因此不应将该缓存用于余额判断或扣减。测试中 MySQL 仍是预占和结算的权威，缓存仅用于读取。

事务 Outbox 可以为失效提供可恢复的事件来源：本实验人工读取已经与账单同事务提交的事件，再执行一次失效，缓存随后读到 850 分。但这只验证了一次受控恢复，不证明实时一致，也没有实现可上线的消费者、重放进度、幂等、顺序、积压监控或失败恢复。将陈旧余额展示给用户是否可接受仍需产品规则；在此决定前不应把原型当作方案定稿。

本次读多写少的短时测试也**没有证明加缓存后的完整周期稳定快于纯 MySQL**。例如 8 账户/8 并发，三次 MySQL 候选为 64.7、121.3、100.6 个周期/秒，组合原型为 62.7、83.0、138.9；波动很大，不能据此下生产性能结论。测试环境仍为本机隔离容器、非等价完整业务实现。

## 原型及一致性边界

测试专用 `hybrid_impl_test.go` 基于上一轮现金候选：MySQL 事务承担余额判断、预占、用量、结算和 Outbox；Redis 仅缓存余额，预占和结算后执行 Redis 脚本递增代数并删除缓存。缓存未命中时读 MySQL，通过另一 Lua 脚本仅在代数仍相同时填充；Redis 读异常时退回 MySQL。这里的代数仅存在 Redis，不具备持久不可回退性。

受控测试 `hybrid_test.go` 使用 1 秒缓存 TTL；负载测试使用 10 秒 TTL。测试复现并验证：

1. 正常完成失效后，旧代数的延迟填充会被拒绝；随后读取新余额。
2. 如果 Redis 的代数键丢失，代数可能回到初始值，旧读取持有的相同代数可以通过检查并填入旧值（ABA）。该测试直接删除代数键模拟这一条件，不声称执行了真实 Redis 故障切换。
3. 人工跳过提交后的失效步骤，读到了旧值；从真实事务 Outbox 读取那一条 reserve 事件，人工执行失效后恢复。这里没有真正杀进程或运行常驻 relay。
4. 另一次跳过失效仅等 TTL，测试在 1.2 秒后重新从 MySQL 读取正确余额。这不是对所有故障的严格陈旧上限：例如失效失败、在途慢读取、Redis 键丢失以及持续写入会改变边界。
5. 客户端关闭造成失效失败时，MySQL 事务已提交而原型返回错误，缓存仍是旧值；同请求重试后候选账务幂等不重复扣款，并重新执行失效。返回错误不能理解成交易未提交，需明确未知结果处理协议。

测试对账使用实际 bills 与 `LedgerBalance`，最终通过。候选仍没有完成订阅、充值、退款、迁移和全部故障恢复；跨租户并发同请求 ID 仍可能暴露 MySQL 1062。此前方案比较及 Redis 的其他作用分别见 `对比报告.md`、`Redis价值补充报告.md`。

## 混合负载

## 复现

从仓库根目录，使用 Docker、Go 及脚本指定的本地镜像。脚本创建全新隔离容器，退出时移除，不访问现有数据库。

```sh
# 缓存异常、人工 Outbox 失效和 TTL 恢复
BILLING_COMPARE_HYBRID=1 ./eval/billing-comparison-2026-11-02/run-conflict.sh
# 三方案混合短负载与正确性测试
BILLING_COMPARE_HYBRID=1 BILLING_COMPARE_HYBRID_LOAD=1 ./eval/billing-comparison-2026-11-02/run-conflict.sh
```

`hybrid-recovery-final.txt` 为最终受控正确性和人工 Outbox 恢复日志，`hybrid-final-output.txt` 为混合负载日志。输出目录也保留早期日志；这些实验没有修改生产配置、使用生产数据、调用模型 API、部署或提交。
