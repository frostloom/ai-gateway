# 计费链路高并发与稳定性判断

> 后续更新：下文“短期继续使用现有路径”仅表示**不凭当前对比直接切换测试版 MySQL 候选**，不表示当前网关已达到安全上线标准。后续隔离实验发现上游结果未知时可能重复发送、在途请求可能被对账冲正，以及旧版本可绕过测试 gate；另有压测 pending 未观察到最终恢复。整网关决策和证据见 `../project-load-2026-11-02/高并发稳定性综合决策-2026-11-03.md`。

## 建议

**短期继续使用现有已验证路径；中期优先把“计费核心由 MySQL 事务维护权威余额”做成完整候选，完成等价、故障和容量验证后再决定切换。现在不应直接从正式计费链路移除 Redis。**

理由是：本机现金路径测试中 MySQL 候选在两组较长压力测试的吞吐更高、热点账户的 P99 更低；Redis 故障时独立 MySQL 候选仍可完成现金流程。但候选目前并非完整生产实现，真实故障恢复、订阅和充值等业务尚无等价证明。高并发与稳定性不能仅由本机吞吐决定。MySQL 仍是两种方案的共同依赖：单账户行锁、连接池、数据库故障和提交结果未知均要处理。Redis 仍负责网关限流、去重、会话等其他功能。

是否保留 Redis **余额读取缓存**应单独决定：此前热读微基准 Redis 更快，但测试版缓存复现了提交后缓存失效前的旧值及代数重置竞争。即使未来保留缓存，也不能用测试版原型的缓存值作为扣款条件；若展示允许短暂陈旧，需明确期限、告警和恢复策略后再实现。该判断不等于建议删除整个 Redis 服务。

## 新增压力测试

基准 HEAD `63b9d1ed4d64bb583d15fa884c37468e5c53044c` 加当前分支未提交的请求冲突修复；当前生产 Store 源码 SHA-256 `71d5925e6d5824babac842559bdc6a0872c453f90904db261622bd2efe540299`。Darwin arm64，Go 1.25.12，隔离本机 Docker MySQL 8.0.40 和 Redis 7.4.11，新建合成账户；MySQL 客户端池最多 40 连接。其他机器服务继续运行，A/B 固定顺序，非专用机器。

每个周期为预占 100 分、上报 50 token、结算 50 分；每四个周期另读一次余额。按组持续发起 20 秒，再等待在途操作结束，因此实际墙钟略长。每组两次。测试直接调用真实 A Store 或测试专用 B，使用 15 秒上下文，**不是 HTTP 端到端测试，不包含模型服务、不等于现有网关的 3 秒预占超时**。延迟为完整周期墙钟；每轮结束核对余额与 MySQL 账本、pending、settle 和 Outbox 数量。原始数据 `stability-output.txt`。

64 worker 超过客户端 40 连接上限，池等待计数 A 两次 7413/7133、B 两次 13657/16324；它们是客户端获取连接的累计等待事件，B 完成了更多周期，不能直接当作每次请求的等待率。B 的 InnoDB 行锁等待计数显示存在热点竞争；A 的 MySQL named lock 不计入该计数，不能直接与 B 的行锁等待相比较。两个方案的 Redis 命令量、MySQL 全局计数、连接池值保存在原始 JSON；CPU、字节级 I/O 和连接峰值未采集，不估算。

## 故障证据与尚未覆盖

- 新增 `disconnect_test.go`：在测试候选事务中写入余额、账单与 Outbox 后、提交前，用 MySQL `KILL CONNECTION` 强制断开该事务连接；三者回滚，重试一次产生一笔预占。日志 `stability-output.txt`。这是提交前断连，不是进程在提交成功后断连。
- 此前实停隔离 Redis：A 余额读和新预占失败，B 独立现金流程可完成；Redis 恢复后 A 从账本重建。MySQL 停止时 A 的缓存命中读可返回，但不证明其新鲜或可继续预占。详见 `Redis价值补充报告.md`。
- 未覆盖提交成功但响应丢失、MySQL 主从切换、跨可用区网络分区、Redis 高可用切换、长时负载、线上迁移、线上容量或全链路故障；也未证明 B 的订阅/充值/退款等与 A 等价。B 在并发跨租户复用同 ID 时可能返回数据库 1062，需规范冲突及死锁重试。
- 测试版 MySQL+Redis 缓存在提交后失效前可读到旧余额，代数丢失存在旧值回填风险，详见 `组合方案验证报告.md`；目前不应把它视为强一致实现。

## 切换前的判断条件

1. 明确实际峰值账户分布、读写比例、可接受 P95/P99、超时/错误率和单账户热点要求；本报告无法凭空认定当前样本满足业务 SLO。
2. 实现完整候选：订阅、充值/退款、短收、历史初始化、请求冲突/死锁处理、Outbox 和恢复，保证余额、账本及事件事务一致；测试旧数据和迁移/回退。
3. 在真实拓扑的隔离环境以业务峰值及突发量反复长测，验证 3 秒预占和 10 秒终态预算、余额账本一致、CPU/I/O、连接与锁等待；覆盖提交前后中断、服务切换、重放和对账。
4. 只有业务规则、故障恢复和容量目标均达标，才选择分阶段切换计费核心；需保留已验证回退路径。余额展示缓存和其他 Redis 功能分别决策。

## 复现

```sh
# 现有回归、候选正确性、提交前连接中断，以及两轮 20 秒压力场景
BILLING_COMPARE_RUN_CANDIDATE=1 BILLING_COMPARE_STABILITY_RUN=1 ./eval/billing-comparison-2026-11-02/run-conflict.sh
# 参照网关 3 秒/10 秒预算的 Store 边界样本
BILLING_COMPARE_GATEWAY_BUDGET=1 ./eval/billing-comparison-2026-11-02/run-conflict.sh
```

脚本启动新容器、随机 loopback 端口并在退出时清理。`KILL CONNECTION` 仅针对该脚本新建容器中的测试事务。未连接生产数据库、使用生产数据、调用付费模型、部署或提交。
