# 路由无效权重保护

## 问题与修复

`internal/router/registry.go` 原先在选择渠道时直接对所有候选权重求和，然后调用 `rand.Intn(total)`。当前 provider 表的 `weight` 是有符号整数，`internal/billing/store/provider.go` 的写入路径没有正数检查；数据库约束也未要求正数。测试使用真实隔离 MySQL 写入一个 0 和一个 -1 的 active 渠道，直接调用真实 `RouteExcludeContext`，发生 `panic: invalid argument to Intn`，见 `router-invalid-weight-red-20261105.txt`。这是受控输入下的直接调用结果；没有声称生产发生或整个 HTTP 服务必然退出，实际 `net/http` 对 handler panic 的恢复方式取决于服务边界。

当前工作树的 `RouteExcludeContext` 只将权重大于 0 的渠道交给加权选择。无有效候选时返回已有的无渠道结果（HTTP `/route` 返回 503）；`pickWeighted` 另对空输入、无效权重及 int 求和溢出返回 nil，由调用方处理。该策略将非正权重视为不参与路由，正权重的正常加权逻辑未改变；现有渠道缓存仍按原 TTL 刷新，不保证管理端修改立即生效。管理写入口仍可能保存非正权重，当前修改是在读取侧防御，不构成写入校验或历史数据迁移。

## 验证

`router-invalid-weight-final-20261105.txt`：真实隔离 MySQL + Redis、race 三轮，非正权重单独存在时不 panic 且 HTTP 503；加入一个权重为 2 的渠道后，64 并发及随后 100 次选路均选中该有效渠道。回报顺序和开启阈值计数的两个已有定向测试也各三轮通过。没有直接覆盖 int 求和溢出的分支、所有权重分布、缓存失效竞态或跨实例配置同步；不能据此宣称全面验证路由。

`router-invalid-weight-packages-20261105.txt`：`go test -race ./internal/router ./internal/gateway/client` 通过，客户端包使用 Go 测试缓存；日志保留系统链接器警告。
