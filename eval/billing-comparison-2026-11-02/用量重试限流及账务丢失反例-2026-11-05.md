# 用量重试限流与账务恢复反例

## 核心结论

**不要采用本次简单限流候选。**在真实隔离账本的受控突发中，当首次用量上报在发送前失败，限流拒绝了 48 个重试；这 48 笔均返回 HTTP 200，却没有持久 usage、仍为 pending。当前对账器无法从缺失的 usage 推导实际用量。重试限流不能与持久记录、可信用量恢复和未知状态处置分开设计。

## 测试候选

`build_usage_bounded_overlay.py` 仅在测试 handler overlay 上叠加 50–150ms 随机等待、单进程最多 16 个活跃重试和最多 64 个排队重试；等待队列满时直接停止重试，等待过程受原 10 秒总 context 限制。正常首次 ReportUsage 不受此限制；没有持久队列、跨实例协调、公平性、资源指标或告警。这只是用于检验一个具体假设，16/64 为实验参数，不是配置建议。客户端成功响应策略不变，限流拒绝只记录错误并保留 pending。

## 同步替身验证限流

`TestUsageRetryAdmissionBound` 同步释放 128 个首次上报的合成 Unavailable，第二次调用替身在返回成功前停留 200ms；没有实际 SQL、Redis 或远程 billing。原随机退避候选三轮均为重试并发峰值 128，未达到希望的 16 上限，预期断言失败 `usage-retry-admission-red-20261105.txt`。限流候选三轮峰值 16、重试 80、未进入重试 48、模拟 settled 80，均返回模拟 HTTP 200，`usage-retry-admission-green-20261105.txt`。此处 settled 是替身计数，不是账本结果；强制同时失败是极端受控场景。

## 真实账本中的后果

`TestUsageRetryRealAdmissionBurst` 使用真实 gateway handler、回环 billing gRPC、独立 MySQL/Redis、16 合成账户和本地模拟上游；HTTP 使用 recorder。128 请求同时发起，测试 bridge 人为在所有首次上报到齐后同步返回 Unavailable；被允许的第二次上报先人为延迟 200ms 再调用真实 gRPC。各组先后独立容器运行三轮 race。失败注入并非真实网络中断或数据库持续故障，固定同时释放与 200ms 延迟用于暴露过载边界，不能当作自然流量。

| 首次故障与候选 | 每轮 HTTP 200 | 每轮第二次上报 | 每轮 settled | 每轮 pending 有 usage / 无 usage | 每轮 P95 / P99 ms |
|---|---:|---:|---:|---|---|
|发送前失败；限流|128|80|80|0 / 48|2068 / 2113；1945 / 1978；2129 / 2150|
|实际上报提交后人为丢响应；限流|128|80|80|48 / 0|2318 / 2340；3228 / 3241；2120 / 2133|
|发送前失败；随机等待但无并发限流|128|128|128|0 / 0|1809 / 1815；1663 / 1686；2082 / 2127|

每笔账单的 usage marker 与 usage Outbox 事件一致，已结算账单有且仅有一条 settle/usage 事件，pending 无 settle，均无 reverse；每账户 Redis 与账本余额一致。限流组 48 个等待区外的请求没有进行第二次上报；有 usage 的 48 笔可供对账器后续补结算，但实验没有启动对账器或等待真实 600 秒宽限期。**无 usage 的 48 笔没有用量依据**，不能通过普通补结算恢复。随机无界重试在此合成场景完成，但并发上报压力较大；它同样不构成安全生产方案。

结论不是“关掉限流即可安全”：首次上报仍无限流；无界重试可能加重真实数据库故障，而拒绝重试又会丢失当前进程唯一的用量。需要先为成功响应后的用量提供可信、持久、可核对的恢复路径，并明确返回语义、超载控制和容量，再评估任何限流策略。固定比例未验证多网关全局限制、请求取消与进程死亡、外部存储故障、真实网络分区、上游费用、流式或 Kafka；候选保留测试目录，不能部署。

限流 overlay 下先前单笔暂时性/永久故障、32 请求多账户和首次事务仍在执行的竞态均各三轮 race 通过（`usage-retry-bounded-correctness-20261105.txt`），但这些通过不覆盖上面的拒绝恢复问题，也不代表项目全量回归。
