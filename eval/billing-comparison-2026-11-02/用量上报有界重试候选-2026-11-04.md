# 用量上报有界重试：测试候选

## 背景与方案

上轮完整网关短测出现 HTTP 200 而无持久 usage 的样本：gateway `settleAndLog` 使用 10 秒后台 context 发送一次 ReportUsage，超时后直接保留 pending 并返回模型响应；没有 usage 的账单不能由当前对账器按实际用量结算。`Store.ReportUsage` 对已存在相同 request/bill、provider 和 token 的用量幂等，对不同内容返回 FailedPrecondition，记录与 usage Outbox 同事务。

本实验仅用 `build_usage_retry_overlay.py` 生成 handler overlay，不修改正式 gateway：保留 10 秒总后台预算，ReportUsage 最多两次，每次最多 3 秒；仅对 gRPC Unavailable 或 DeadlineExceeded 且总 context 未结束的情况等待 100ms 后重试，其他错误停止；nil 或 `accepted=false` 视为失败，不进入 Settle。成功上报后才使用原 Settle。该固定延迟没有 jitter 或全局限流，且第一次被取消的实际服务端事务可能仍在运行；故障风暴、真实超时后并发提交、老版本 billing 和结果不确定时序仍需验证，**不可部署**。新增重试可能加重拥塞，缩短首次超时也改变了系统行为。

## 正确性实验

真实 gateway handler、billing gRPC Service 和 Store，隔离 MySQL/Redis、本地模拟上游，测试 billing client bridge 在 ReportUsage 注入故障；HTTP 使用 recorder。基线无重试时，`before`（发送 RPC 前返回 Unavailable）和 `after`（真实 gRPC 上报成功后人为返回 Unavailable）各三轮均 pending；后者已持久 usage 但未 settle。预期失败 `usage-retry-gateway-red-20261104.txt`，永久错误分支通过。响应丢失是调用方包装器注入，不是真实 TCP 断线或数据库 COMMIT 确认丢失。

候选 `usage-retry-gateway-final-20261104.txt` 三轮 race：

- 首次发送前 Unavailable、提交成功后模拟响应丢失、以及首次调用被 3 秒 context 人为超时：均上报两次、最终 settled，一条 usage 和一条 settle Outbox、无 reverse，Redis 与账本 994。
- FailedPrecondition 不重试；连续 Unavailable 最多两次；返回 `accepted=false` 不重试、不结算。三者仍对模拟模型响应返回 HTTP 200，账单 pending、无 usage/settle/reverse；这是明确未解决的用量丢失/人工核查风险，不能称已恢复。
- 32 个并发请求分散到 8 个账户，每请求先实际提交 usage 再人为丢弃首次成功响应；每请求重报一次，各有一条 reserve、usage、settle 事件，每账户 Redis 与账本均为 976。三轮通过；这是单进程并发和真实本地 gRPC，不是跨进程竞争或性能容量。

候选 overlay 下现有 gateway handler 包 race exit 0，日志 `usage-retry-handler-regression-20261104.txt`；不代表全项目测试。未验证 SSE 实际网络客户端、首次调用与重试交错的所有情况、进程或节点在持久化前死亡、订阅、支付、真实 Kafka、错误来源可信度、旧实例混版及异常负载。没有真实模型或费用。没有证据证明该重试能保证持久化，更不能自动冲正未知状态。

## 补充：128 请求同时丢弃用量响应

`usage_retry_storm_test.go` 在同一进程通过真实 handler、本地 billing gRPC、隔离 MySQL/Redis、本地模拟模型并发运行 128 个请求分散至 16 个账户。测试 bridge 对**每个**上报先等待真实 gRPC 成功，再人为返回一次 Unavailable；并非真实网络故障或数据库持续不可用。基线与候选先后使用独立容器各三轮 Go race；每轮是一次同时起跑的有界突发，P95/P99 为请求端到端耗时，包括故障注入和结算，不是持续吞吐或网关容量。

各轮均有 128 条 usage 事件；逐请求 reserve/usage/settle/reverse 事件数量及状态、每账户 Redis 余额与账本一致性检查通过。基线 pending 均**已报告用量**，默认对账器理论上可按配置宽限期补结算；实验没有运行对账器或等待 600 秒，不能称已补结算。候选用量上报调用翻倍且本轮耗时更长；因为候选额外执行结算、负载顺序固定和宿主共享，不能把耗时差简单归因于重试本身。
