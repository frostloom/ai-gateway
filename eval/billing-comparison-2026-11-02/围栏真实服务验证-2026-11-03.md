## 接入面核查

本项目 `internal/billing/server/service.go` 的鉴权服务调用 `Store.ValidateAPIKey`；返回给 gateway 的 gRPC response 不含类型及到期时间。将候选放在 billing Store/服务侧可读取必要字段，但仍须独立设计和测试并发及故障行为，不应在网关盲目缓存现有 response。浏览器 session 是 APIKey 特殊名称，验证还关联 portal_sessions、portal_users、tenants；登出使用 `RevokePortalSession` 改状态，浏览器路径还经过独立 `/auth/me`。候选仅允许普通 key 缓存、浏览器 session 始终权威查询，避免缓存跳过关联状态检查。

源码搜索在生产路径中发现 portal session 创建与撤销，以及脚本生成测试/初始 Key，但未找到普通 API Key 的完整管理 API。不能据此排除直接 SQL、其他外部工具或未来写入路径。若普通 Key 能被绕过应用协议直接更新，则即使接入应用层围栏也不会触发失效，可能延迟吊销；在落实、约束和验证所有写入入口前，不应把候选当作可部署方案。普通 key 当前验证未联查 tenant 状态；引入额外 tenant 验证会改变现有语义，须分开评估。

**测量口径补充**：本次原始基准未统计 Redis 命中、超时或回退 MySQL 的次数；表中“缓存命中”指预热后的缓存候选调用，不能证明每次都命中 Redis。后续脚本已增加权威查询计数，原始输出不变。
