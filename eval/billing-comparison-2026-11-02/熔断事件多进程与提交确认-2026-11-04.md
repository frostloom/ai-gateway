# 熔断事件多进程与提交确认测试

## 范围

测试对象是 `router_durable_breaker_impl_test.go` 中的单渠道 MySQL 状态机原型，SHA256 `cc62ab11b0facfc86b3c381356fe15db82e107e5eb121351d1ef465c48fb4678`；不是生产 Router，也不是上一轮的缩锁 overlay。使用随机隔离 MySQL 8.0.40 / Redis 7、Go race。原型将事件与熔断状态放在同一 MySQL 事务，锁定单条状态行并检查事件 ID。

## 多进程事件竞争

`router-breaker-multiprocess-verified.txt`：每轮启动六个独立测试进程，全部准备后释放屏障并向同一 MySQL 发送相同事件 ID，三轮结果：

- 六个相同失败事件：一次应用、五次幂等重复，状态 open、失败数 1、版本 1、事件一条。
- 三个成功和三个失败使用同一 ID：一次应用、同参数重复两次、冲突三次；最终事件、状态及失败数与实际获胜结果一致，版本 1、事件一条。测试中成功或失败均可能获胜，未规定提交顺序。

屏障仅使六个进程在都就绪后开始，不证明所有事务在数据库同时等待行锁。测试只涉及一个渠道、一个固定 ID 和一个数据库；不证明正常不同事件的业务顺序、多 provider 权重、AutoBan、生产身份授权或高负载下的公平性。

## 提交确认丢失模拟

`router-breaker-ack-verified.txt` 与 `router-breaker-ack-badconn-verified.txt` 各三轮：驱动包装器先让真实 MySQL `Commit()` 成功，再分别返回模拟确认丢失错误或 `driver.ErrBadConn`。首次调用报错，再以同 ID 相同参数重试不再应用；状态 open、失败数 1、版本 1、事件一条；相同 ID 改成成功被拒绝。这里是驱动层注入，不是实际 TCP 丢包或 MySQL 故障切换。

## 决策和剩余工作

结果支持在此单渠道候选中使用事件唯一约束与同事务状态更新处理上述重复，但并未建立端到端可靠回报：正式网关还没有可靠地产生、保存和重试事件 ID；真实 Router 的 `/report`、内存熔断/AutoBan、跨实例顺序、旧实例兼容、Redis 投影、消息积压和认证都没有接入。原型每次许可要锁同一 MySQL 行，既有局部压测显示明显热点，不能用来声称它与当前路由功能或性能等价。缩锁候选的写入失败丢失风险也没有因为本次测试而消失，二者尚未整合，不宜部署。
