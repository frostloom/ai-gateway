# 订阅额度预占并发缺口与修复

基准 HEAD `63b9d1ed4d64bb583d15fa884c37468e5c53044c` 加未提交工作树。原 `subscriptionConsumed` 只汇总 reserve 行中已上报的 prompt/completion；新 pending 预占无 token，因此即使租户现金锁串行化，每次检查也看不到前面尚未上报用量的订阅请求。隔离 MySQL/Redis、真实 billing gRPC，订阅窗口额度 300，每次估算 100，8 个并发不同请求，修复前三轮均 8 个预占成功，期望只有 3 个成功的测试失败，见 `content-fingerprint-subscription-concurrency.txt`。这与 v2 指纹无关，不代表真实供应商费用。

## 修改

- 订阅 reserve 行增加 nullable `reserved_tokens` 和 `reserved_tier`，与预占账单及 reserve Outbox 同事务保存；现金预占不使用这两列。租户锁下检查订阅余额：未上报用量时占用估算，上报后按实际用量，冲正后不占额度。检查 token 非负、加法溢出及比较溢出；预占时档次作为快照，避免后续模型标签调整改变这些新账单的归属。
- 未上报用量的 pending 即使超过滚动窗口也继续占用预占；上报后沿用原始按账单创建时间的滚动窗口规则。修复前将待处理账单时间人工设为 6 小时前会错误释放额度（三轮 `subscription-aged-pending-red.txt`），修复后三轮通过。
- 新 schema 更新 `scripts/schema.sql`，独立迁移 `scripts/migrations/20261104_subscription_reservation.sql`；**没有在生产执行迁移**。旧的无用量未终态订阅账单无法从现有行推导原估算，nullable 字段保留 NULL，此时相关租户订阅额度查询/新预占保守报错，需先核查/处理历史数据。旧已上报记录按原模型当前档次回退；找不到模型/档次时失败而不猜测。

## 验证

- `bash eval/billing-comparison-2026-11-02/run-content-fingerprint-subscription-concurrency.sh`：修复后三轮 race 均为 3 个成功、5 个额度不足，成功账单均为订阅、各一个预占事件，之后 3 个实际用量上报并结算，余额与账本一致；`subscription-reservation-concurrency-green.txt`。同一进程经真实 gRPC，非跨进程崩溃或长时间负载。
- `bash eval/billing-comparison-2026-11-02/run-subscription-reservation-lifecycle.sh`：三轮 race 覆盖先占 200、拒绝 150、实际用量 50 后允许 150、冲正释放、再占 250、原模型变更档次、人工回拨超过窗口仍占用、模拟历史 NULL 时拒绝；余额与账本一致。`subscription-reservation-lifecycle-final.txt`。这没有验证自然等待 5 小时或所有套餐变化。
- `BILLING_COMPARE_RUN_FULL_STORE=1 bash eval/billing-comparison-2026-11-02/run-subscription-full-store-race.sh` 通过隔离数据库完整 Store 包 race；原有两个 opt-in 性能测试 skip，输出 `subscription-reservation-full-store-race.txt`。脚本用 overlay 只改测试硬编码地址，实际创建随机容器。
- `bash eval/billing-comparison-2026-11-02/run-subscription-reservation-migration.sh` 对随机隔离数据库构造旧表、执行迁移并确认旧 pending 的两列仍 NULL；race 一轮 `subscription-reservation-migration.txt`。未验证大表锁时长、回滚或混版。

## 边界

此改动防止在**估算之和**已达到额度时继续预占，无法保证实际用量不超估算：客户端 `max_tokens=0` 或上游实际 token 超出估计时仍可能超出窗口额度；要给严格上限，必须明确输出上限及超限策略。旧账单若已上报用量但没有档次快照，仍依赖当前模型标签；旧版本仍可创建没有预占字段的行，混版需要停写/兼容屏障。老 pending 无法自动恢复，可能长期阻止订阅请求；实际迁移、可用性、SQL 计划与高并发吞吐、Redis/MySQL 失联、租户禁用、订阅购买退款和审计事件投递均需进一步验证。旧对账器仍可能错误冲正未知请求，本修复不等于完整计费安全，不应仅凭这些结果部署。
