# MySQL 一致性快照余额读取候选

## 真实 Redis 快照回退

`dirty-real-redis-restart-fixedport-20261104.txt` 对 Redis 脏标记候选进行三轮 race 测试：在 500 分余额预占 100 分后，明确关闭 Redis 自动 RDB 保存、确认 AOF 关闭并执行 `SAVE`；之后正常结算至 MySQL 账本 460。对**测试脚本自己创建的** Redis 容器发送 SIGKILL 并启动同一容器，恢复旧 RDB 后原始 Redis 值为 400，dirty 不存在，候选 GetBalance 也返回 400，而 MySQL 账本为 460；显式重建后为 460。测试 PASS 表示成功复现陈旧读，不表示安全通过。这是刻意制造的旧 RDB、单节点配置，不能外推其他 AOF、复制或故障切换拓扑。

首次执行 `dirty-real-redis-restart-20261104.txt` 在重启后无法连接原随机端口并超时；修订脚本固定本轮随机选取的宿主端口后成功。原失败保留，不把它计作通过，也不确定端口变化是否是唯一原因。

## 快照读取原型

`build-mysql-balance-read-candidate.py` 基于当前 Store 构造测试 overlay：仅将公开 `GetBalance` 改为 MySQL 只读 REPEATABLE READ 事务，先检查租户存在，再在同一快照内汇总现有账本。它不修改 Redis，不改变预占/结算/冲正，故**不是 MySQL-only 计费方案**，也不会修复 Redis 余额投影。生产写入仍依赖 Redis 和现有锁；账本本身如果有缺失或错误，该读取不能修正账务。

不加事务的对照在 `mysql-read-unsafe-red2-20261104.txt` 受控三轮复现：预占 100 的 pending 求和后暂停，另一事务结算实际 40，继续汇总时把结算前的 pending 和结算后的 actual 同时扣减，错误返回 360；真实一致结果应为此前 400 或此后 460。初次测试 `mysql-read-unsafe-red-20261104.txt` 因测试钩子没有命中而失败，不能作为行为证据。

初版快照 overlay 对不存在的租户错误返回零，见 `balance-missing-snapshot-20261104.txt`；原实现对应测试通过。增加同一快照中的租户存在检查后，当前 v2 SHA `c610210bac0badbd639eba607f9017e0680a713a11092742a309f4c2c5dc325f`，初版保留在 `mysql_balance_snapshot_v1.go.txt`。以下均使用 v2：

- `mysql-read-snapshot-v2-concurrent-20261104.txt`：上述受控竞争 race 三轮都返回结算前 400，之后返回 460。
- `mysql-read-snapshot-v2-process-crash-20261104.txt`：终态进程在 Redis delta 后、SQL COMMIT 前实际 SIGKILL，结算/冲正各三轮，查询返回已提交账本 400；后续另一预占和原终态重试的受控账本核对通过。
- `mysql-read-snapshot-v2-redis-restart-20261104.txt`：真实 Redis 从上述旧 RDB 重启，Redis 原始余额 400，而快照查询与账本为 460；之后测试显式重建 Redis。这不证明项目会自动重建。
- `mysql-read-snapshot-v2-missing-20261104.txt`、`mysql-read-snapshot-v2-disabled-20261104.txt`：不存在租户返回错误、停用租户可读取，分别在隔离环境通过。
- `mysql-snapshot-redis-down-20261104.txt`：完成预占后实际 SIGKILL 隔离 Redis，MySQL 仍可用时查询返回 400；仅一轮，未证明 Redis 故障时预占或结算可用。

## 局部读取代价

独立新容器、64 合成空账本账户、32 worker、每轮 1280 次查询、两轮，错误均 0；非随机先后运行、每轮约 1 秒，仅为局部 Store 查询。MySQL 快照每次检查租户并汇总账本，实际账单增长后的扫描成本未测。

| 方案 | 次/秒 | 平均 ms | P95 ms | P99 ms |
|---|---|---|---|---|
| Redis 原热读 | 17793 / 22652 | 1.730 / 1.359 | 1.781 / 2.020 | 25.949 / 8.325 |
| MySQL 快照 v2 | 1287 / 1707 | 24.331 / 18.366 | 45.136 / 29.664 | 101.613 / 40.187 |

原始输出 `balance-read-baseline-20261104.txt`、`mysql-read-snapshot-v2-load-20261104.txt`。该结果表明安全读取可能有显著成本，不是生产容量或完整网关性能；未测 MySQL 断连、读副本延迟、长事务、混合负载、存量大账本及所有充值/订阅语义。`LedgerBalance` 的账本规则与实际系统是否在所有历史状态一致仍须审计。当前候选不应直接上线。
