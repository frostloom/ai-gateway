# 终态进程崩溃与余额读取

## 当前工作树的实际崩溃结果

使用隔离 MySQL 8.0.40、Redis 7 和真实 Store。先对 500 分余额预占 100 分；结算场景再上报 40 分用量。独立 Go 子进程执行 Settle 或 Reverse，在 Redis delta 已应用、MySQL 事务内准备插入终态 Outbox、COMMIT 前的 GORM 回调里向**该子进程自身**发送 SIGKILL。父进程验证实际 SIGKILL 及切点标记，再读取状态；并非仅模拟函数返回错误。

`terminal-process-crash-20261104.txt` 的 race 三轮中，结算崩溃后的普通 GetBalance 为 460、账本为 400；冲正崩溃后分别为 500 和 400。此时账单仍 pending、delta guard 存在。说明现有 `GetBalance` 对已存在 Redis key 直接返回，可能暴露尚未提交账本的旧投影。测试结果 PASS 是对该差异的复现，**不是一致性通过**。

之后同账户另一笔真实预占触发租户锁内按账本重建，再扣 100，余额变为 300；再重试原结算或冲正，Redis 和账本分别一致为 360 或 400，终态 Outbox 各一条。这是单一顺序、隔离账户的受控恢复：测试没有测差异窗口内并行查询/预占、服务自动重启、真实 Redis/MySQL 同时故障、提交确认丢失或全部进程交错；不能据此承诺自动恢复。原有更早的 SQL 连接中断测试不是进程被杀。

## 一律重建的测试候选

`build-consistent-balance-candidate.py` 从当前 `mysql.go` SHA `e4a53b0eaca810e385a7336c0ace3b05723313b362342b6094b822bee0d8f98c` 生成测试 overlay SHA `633c165c28467a2dedf1d8925649dc7cebd7bd33a5531d925779b3c258823cd1`：每次 GetBalance 都调用现有 `RebuildBalance`，持租户锁读取账本并写 Redis。原代码按查询应等于账本的断言在两个崩溃场景下三轮失败（`terminal-consistent-read-red-20261104.txt`）；候选三轮通过（`terminal-consistent-read-green-20261104.txt`），随后两笔操作和 Outbox 仍按上述受控顺序一致。

这不是纯读取：它会拿 MySQL 会话锁、查询账本、更新 Redis 投影。更重要的是候选改变现有行为：已停用租户、余额 key 存在时，原实现仍返回 500；候选返回 `tenant disabled`，对应 `balance-disabled-baseline-20261104.txt` 通过、`balance-disabled-candidate-20261104.txt` 预期失败。该候选未接生产，不应直接上线。

## 余额查询局部性能

独立新容器、64 个合成空账本账户、32 个闭环 worker、每轮 1280 次 GetBalance、各两轮。仅测 Store 查询，不是网关 HTTP 或持续混合负载；组别先后运行，非随机、共享机器。错误均 0。

| 组别 | 次/秒 | 平均 ms | P95 ms | P99 ms |
|---|---|---|---|---|
| 原 Redis 热读 | 17793 / 22652 | 1.730 / 1.359 | 1.781 / 2.020 | 25.949 / 8.325 |
| 一律重建候选 | 1019 / 991 | 30.600 / 31.371 | 49.106 / 42.967 | 165.740 / 46.840 |

原始输出 `balance-read-baseline-20261104.txt` 和 `balance-read-candidate-20261104.txt`。每轮不到约 1.3 秒、账户无账单，采样与运行先后波动大；不能外推生产容量或推断真实账本越大时的性能。测试文件随后只追加了停用租户用例，原性能用例未修改，但这些性能日志没有记录测试文件 SHA。

结论是两种简单选择都不充分：直接热读可能在崩溃后显示不一致；每次重建在本实验中明显更慢且破坏现有停用租户读取行为。需要进一步验证只对有可信脏状态的账户进行恢复、数据库权威版本/投影协议或显式“余额待核对”语义，同时处理 Redis 回滚、并发读写、旧实例、锁顺序及故障期间可用性，不能靠 key 存在判断投影正确。

## 复现

```sh
bash eval/billing-comparison-2026-11-02/run-terminal-process-crash.sh
python3 eval/billing-comparison-2026-11-02/build-consistent-balance-candidate.py
TEST_EXPECT_CONSISTENT_READ=1 bash eval/billing-comparison-2026-11-02/run-terminal-process-crash.sh
TEST_EXPECT_CONSISTENT_READ=1 GOFLAGS="-overlay=$PWD/eval/billing-comparison-2026-11-02/consistent-balance-overlay.json" bash eval/billing-comparison-2026-11-02/run-terminal-process-crash.sh
bash eval/billing-comparison-2026-11-02/run-balance-read-load.sh
GOFLAGS="-overlay=$PWD/eval/billing-comparison-2026-11-02/consistent-balance-overlay.json" bash eval/billing-comparison-2026-11-02/run-balance-read-load.sh
bash eval/billing-comparison-2026-11-02/run-balance-disabled.sh
GOFLAGS="-overlay=$PWD/eval/billing-comparison-2026-11-02/consistent-balance-overlay.json" bash eval/billing-comparison-2026-11-02/run-balance-disabled.sh
```

两条基线一致性断言和候选停用租户用例预期失败；脚本只创建并清理各自的隔离容器，不连接生产数据库或模型。
