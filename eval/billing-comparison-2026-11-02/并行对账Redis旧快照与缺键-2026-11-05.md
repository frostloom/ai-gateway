# 并行对账：Redis 旧快照与余额键缺失

## 重要发现：余额接口可返回旧值

在随机隔离 Redis 上先创建三个合成账户各 1000，关闭自动 RDB 保存、确认 AOF 关闭并手动 `SAVE`；然后每账户做两笔预占（各 100）并记录实际用量，Redis 与 MySQL 账本均为 800。对本测试的 Redis 容器 SIGKILL 并重启，恢复故意保存的旧 RDB；通过真实 `Store.GetBalance` 读取，每账户仍返回 **1000**，而 MySQL 账本为 **800**。串行和测试版四工作者对账器各三轮都复现；PASS 代表指定不一致被观察到，不是读取一致性通过。旧快照场景针对单节点本地 Redis，不代表所有 AOF/复制/故障切换配置。

当前实现的 `balanceOrEnsure` 在键缺失时重建，但键存在时直接返回 Redis 值；本次故障表明键存在不能证明它是最新的。这个窗口会影响使用该 Store/gRPC 读取路径的调用方，不能因为最终账本一致就忽略。此处未验证页面；门户总览是另一条路径，见后续路径测试。

## 预占和后续结算的受控对照

在三账户读出旧值后，对其中一账户尝试预占 900（账本只有 800，旧 Redis 值 1000）。真实 `Store.Reserve` 三轮均返回余额不足，没有新增该请求账单或 reserve Outbox，该账户投影此时为 800。代码路径在持有账户锁时执行 `requireCashMatch`；这项测试只验证这一种单次请求和金额，不证明所有并发、订阅、旧实例或 Redis/MySQL 故障下均不超额。

随后两种扫描器分别处理六笔已报告用量的账单，三轮均各有一条 settle 账单及 reserve/usage/settle Outbox、无 reverse，最终三个账户 Redis 与账本均为 920。第一个账户在预占尝试时已被校正，另两个仍从旧值开始；因此不能把三个账户的校正都归给扫描器。事件未通过 Kafka 投递。

## Redis 键确实缺失的恢复

另一组隔离 Redis 中断实验每轮六笔已上报账单、三个账户；Redis 实际停止时六笔均 pending 且结算报错。重启后逐账户检查，三轮均为 **0/3 余额键存在**，测试随后仅对这三个测试账户执行 DEL 并再次确认键缺失，再使用测试版四工作者扫描。每轮六笔各一次结算及对应事件，无 reverse，三个 Redis 余额与账本均为 920。这次验证了给定条件下缺失余额键可恢复；不覆盖任意 guard 丢失、旧快照、集群、故障转移、充值竞争或实际用户流量。

旧快照实验显示：**缺键恢复和旧值识别是不同问题**。按账本读取的测试候选及其性能成本已在 [MySQL 一致性快照余额读取候选](MySQL快照余额读取候选-2026-11-04.md) 记录；尚未证明完整生产方案，不建议简单移除 Redis 或直接采用该候选。仍需权威数据一致性、缓存版本/故障转移、所有现金与订阅入口、混版和性能综合验证。
