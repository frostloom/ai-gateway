# 鉴权单查询候选：隔离实验

当前 `Store.ValidateAPIKey` 对普通密钥查询一次 MySQL，再在 Go 中判断状态与到期；浏览器会话还查询一次关联会话、用户和租户的数量。测试专用 `auth_single_query_test.go` 将关联数量放在首条语句的条件子查询，继续在 Go 判断密钥状态和过期，未引入 Redis、TTL 或负缓存。候选没有接入服务、没有修改生产代码。浏览器会话在同一个 SQL 语句读取状态，和原先两次查询在并发更新时可能观察到不同时间点的状态，因此不能声称全部时序完全等价。

隔离 MySQL 8.0.40 中与真实 Store 比较，普通密钥、禁用密钥、禁用租户、过期、缺失会话、有效浏览器会话、禁用用户、用户属于其他租户、删除会话九种状态相符；另验证不存在的密钥被候选拒绝。三轮 `-race` 全通过。每个状态顺序修改并读取，不覆盖并发提交、不同数据库隔离级别、异常 schema 或故障；到期点附近的两个顺序调用可能自然跨过截止时间。不存在密钥只检查了候选，未在该例重复检查原实现。

延迟实验与正确性同用隔离 MySQL，单进程串行、相同连接池、真实 GORM/Store，顺序基线→候选→候选→基线；每组 200 次，三轮、`-race`。表中为六组平均值和各组 P95 的范围（毫秒），不是将各组样本合并后的分位数；原始每组 P99 在日志。此测试包含 Go race 插桩与本机容器网络开销。

| 密钥 | 方案 | 组均值范围 ms | 各组 P95 范围 ms |
|---|---|---:|---:|
| 普通 | 当前 Store | 0.983–1.678 | 1.285–3.731 |
| 普通 | 候选 | 1.446–1.670 | 1.888–3.500 |
| 浏览器 | 当前 Store | 2.408–3.466 | 3.377–9.916 |
| 浏览器 | 候选 | 1.391–2.010 | 1.913–3.870 |

浏览器单次查询在这组短时串行实验中有较低延迟；普通密钥没有稳定收益，不能因此推断网关吞吐提升。真实生产比例、热点/多用户并发、读写竞争、连接占用、MySQL CPU/I/O 和 SQL 执行计划未测，尤其候选额外子查询可能改变数据库负载。两次查询缩为一次不是引入缓存的替代论证，也没有支持删除其他 Redis 功能。需要在浏览器请求占比真实或明确合成的完整网关中测量，并测试并发状态变更及完整会话规则，再考虑生产改动。

## 补充：多租户混合并发和提交后失效

新增 `auth_single_query_concurrency_test.go`：16 个合成租户，各有一个普通密钥与一个浏览器会话密钥；32 个 goroutine 轮流发出共 1280 次真实 Store/候选鉴权，每组各自闭环，相同 MySQL 连接池上限 16，按基线→候选→候选→基线的顺序执行，三轮共 12 组。每个结果校验返回的密钥 ID。每轮随后先提交禁用一个普通密钥和该租户浏览器用户，再启动 64 次并发请求，由两个方案各处理 32 次；三轮全部拒绝。状态变更在请求启动**之前**完成，不证明变更期间在途请求的线性化或事务隔离。

| 指标 | 当前 Store，6 组范围 | 单查询候选，6 组范围 |
|---|---:|---:|
| 已完成鉴权/秒 | 1474.1–3763.3 | 4376.3–5125.4 |
| 均值 ms | 8.089–21.135 | 5.839–6.839 |
| P95 ms | 16.021–73.759 | 11.310–15.238 |
| P99 ms | 21.383–103.468 | 15.864–24.613 |
| 每组连接池等待次数 | 1836–1873 | 1208–1242 |
| 错误 / 超时 | 每组均 0 / 0 | 每组均 0 / 0 |

每组 1ms 采样观察到最大打开及使用连接数均为 16；采样不能证明瞬时峰值。连接池等待次数是 SQL 连接获取次数，浏览器基线一次鉴权需要两次查询，不能当作等待的请求数。各组 1280 次的延迟分位数独立计算，吞吐为该组完成数除以发放到全部完成的时间。首轮基线明显偏慢，原因未定位；组顺序固定、没有预热控制，实验规模短且本机共用资源，不能把差距全部归因于 SQL。各组 50% 浏览器会话是人为构造，不代表真实流量。测试并未同时运行计费或完整网关，未采集数据库 CPU、I/O、锁、真实网络和集群指标，也未验证连接池扩大或多副本条件。

## 补充：名称比较的排序规则差异

`auth_single_query_collation_test.go` 在隔离 MySQL 对真实 Store 和测试候选比较精确会话名称、两种大小写变化及末尾空格。原候选的 SQL `name = ?` 使用数据库排序规则，而 Store 的 Go 字符串比较区分字节；三轮均出现 `__BROWSER_SESSION` 和 `__browser_sessioN` 被 Store 作为普通密钥接受、候选却当作浏览器会话拒绝。该测试未为这些名称建立浏览器 session。末尾空格在本次配置未造成差异。失败日志 `auth-single-query-collation-red-20261105.txt`，exit 1；这是测试候选问题，不是正式 Store 的故障。

仅将测试候选改为 MySQL 二进制比较后，名称对照、原九种状态和原 32 goroutine 多租户混合测试同次 `-race -count=3` 通过，日志 `auth-single-query-collation-green-20261105.txt`。每轮 1280 次一组、50% 浏览器、16 条连接的短时鉴权测试中，修正后候选六组 4738–5734 次/秒、P95 9.665–14.081ms，基线六组 2280–4316 次/秒、P95 14.383–35.824ms，均零错误；组顺序固定、非整网关、不同组共机资源未控制，不能推断生产容量或因果收益。前文性能测的是修改前候选，不能当作修改后性能结果。这里没有覆盖全部 Unicode、排序规则和 schema，未接入生产代码，也没有消除前述故障和并发更新的限制。
