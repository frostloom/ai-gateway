# 未知用量人工核查：测试原型

## 目的与边界

上游已收到并回复、handler 在保存用量之前死亡时，网关本地可能没有足够证据判断上游是否执行和收费。测试状态机将该账单保留为 forwarding/pending，不依靠租约过期自动退款或重发。本实验只探索：**如果外部核查已经可信地确认具体用量**，如何保留可核对的处置记录并通过既有接口幂等结算。

`manual_usage_resolution_test.go` 是隔离测试候选，使用合成 request/tenant/bill/provider、token 数、证据 SHA-256 和合成 actor；在同一个 MySQL 事务内先锁 reserve 账单，检查 tenant/request/bill/provider、pending、forwarding 和未报 usage，再同时写测试人工记录 `eval_manual_usage` 与测试收件箱 `eval_usage_inbox`。相同处置可重放，不同参数或不同 actor 返回冲突。后续通过已有测试恢复器调用真实 Store 的 `ReportUsage` 和 `Settle`；收件箱写入和最终结算不是同一事务，依赖既有账务幂等。

## 故障与并发测试

`TEST_KILL_BEFORE_LOCAL=1 TEST_MANUAL_RESOLUTION=1 bash eval/billing-comparison-2026-11-02/run-handler-journal-process.sh --candidate`：本地模拟上游完整响应后实际终止隔离 MySQL；handler 所在子进程在本地日志写入前被杀并回收。重启数据库后测试人为将账单及 lease 设为过去，真实 `SweepOnce` 经测试 bridge 不冲正，发送及退款许可均拒绝。随后测试使用**预先知道的模拟用量 40+2** 作为合成人工核查输入：8 个 goroutine 并发提交，同值均幂等，变更用量或 actor 冲突；一个测试核查记录、一条收件箱记录，重复恢复后有一条 settle、指定 reserve/usage/settle 事件各一条，Redis 与账本均为 458。

在写测试人工记录前用 GORM 应用回调注入错误，三轮均验证收件箱和人工记录一并回滚；跨租户、错误 provider、缺失证据摘要被拒。完整 race 三轮输出 `manual-resolution-atomic-final.txt`；未实现时预期失败 `manual-resolution-red.txt`，初次实现输出 `manual-resolution-green.txt`。注入为应用层错误，不是真实数据库提交中断；账单时间是人工修改，没有自然等待 600 秒。测试状态的授权和 RPC 均为测试替身，没有生产客户端响应。

## 不可部署与未覆盖

- **没有实际人工审批或供应商证明。** actor 只是调用者提供的字符串，摘要仅校验格式，不能证明操作者身份、权限、证据真实性或供应商支持查询。实际实现需要身份认证、明确的处置权限、审计及证据保管；不可自动信任此测试记录。
- 不对“查不到用量”推断零费用或自动退款。没有可信核查结果时继续保留未知，并需要实际监控、告警和人工处理流程。
- 旧服务、旧对账器和直接数据库访问可绕过状态机，混版、回退、历史账单和订阅未解决。测试按最初账单 provider 匹配，未覆盖合法渠道切换后的 provider 归属。
- 本节未覆盖人工记录事务中数据库或 Redis 故障、COMMIT 确认丢失、不同进程竞争、消息 relay/消费、真实调用及长时性能；后续补充实验的覆盖范围见下文。本测试非完整服务或生产安全验收。

该原型仅证明合成证据先被明确接受时，指定失败与并发路径中可以保留测试核查记录并补结算；它不能消除用量丢失，也不能授予自动收费或部署权限。

## 补充：人工记录与迟到用量竞争

发现测试候选中的具体冲突：人工记录和收件箱已提交但尚未重放时，V4 测试 Store 的普通 `ReportUsage` 仍可写入不同 token。`TEST_KILL_BEFORE_LOCAL=1 TEST_MANUAL_RESOLUTION=1 TEST_MANUAL_LATE_USAGE=1 bash eval/billing-comparison-2026-11-02/run-handler-journal-process.sh --candidate` 三轮均出现矛盾用量被接受，安全断言失败，见 `manual-late-usage-red.txt`。这是测试候选缺陷，并非已发生的生产事故。

新 overlay `billing_manual_guard_candidate.go.txt` 在真实 Store 用量事务持有账单行锁后，查询测试人工记录；有记录时 provider、prompt、completion 必须相同才能继续。人工记录写入同样先锁该账单，因此遵守协议的两个写入路径以该行串行化。`TEST_STORE_MANUAL_GUARD=1 TEST_KILL_BEFORE_LOCAL=1 TEST_MANUAL_RESOLUTION=1 TEST_MANUAL_LATE_USAGE=1 bash eval/billing-comparison-2026-11-02/run-handler-journal-process.sh --candidate` 三轮 race：人工记录先提交，矛盾迟到用量被拒，原用量重放后结算一次，输出 `manual-late-usage-green.txt`。将末变量替换为 `TEST_MANUAL_USAGE_FIRST=1`：正常用量先提交时矛盾人工记录被拒，三轮各按先提交用量结算，输出 `manual-usage-first-green.txt`。

再替换末变量为 `TEST_MANUAL_USAGE_RACE=1`，两个 goroutine 同时开始提交不同用量；race 三轮中恰有一方成功、一条结算及指定三条事件、账本和 Redis 一致。**三轮恰好均为人工记录先获胜**；正常用量先获胜由前述固定顺序测试覆盖，不能声称此次竞争随机覆盖了两种调度。输出 `manual-usage-race-green.txt`。

新 Store overlay 只供测试，每次 `ReportUsage` 查询测试人工表；表不存在会令用量上报失败，尚无正式迁移或兼容路径。旧 billing 实例、旧协议、其他入口仍可绕过该检查；没有真实授权、证据来源、跨进程/断连和性能验证，也没有解决人工凭据可信度。上述结果不证明可上线或完全等价。

## 补充：人工记录提交的三个故障切点

以下均在上述测试 handler 已死、模拟上游已响应且账单保守 pending 后执行；账单时间人工改旧，actor 和证据全为合成。三组均以 `TEST_STORE_MANUAL_GUARD=1 TEST_KILL_BEFORE_LOCAL=1 TEST_MANUAL_RESOLUTION=1 TEST_MANUAL_LATE_USAGE=1` 加下列变量运行 `bash eval/billing-comparison-2026-11-02/run-handler-journal-process.sh --candidate`，各三轮 race：

- `TEST_MANUAL_PROCESS_KILL=1`：独立测试处置进程收到记录事务提交成功后被实际杀死并回收，父进程用相同内容并发重试、拒绝矛盾用量并结算；一条测试人工记录、一条收件箱和一条 settle，余额与账本 458。输出 `manual-resolution-worker-kill.txt`。
- `TEST_MANUAL_ACK_UNKNOWN=1`：测试驱动等待真实 MySQL COMMIT 成功后返回 EOF；独立连接确认人工记录及收件箱均存在，随后同值重试、拒绝冲突并结算一次。输出 `manual-resolution-ack-unknown.txt`；这是驱动注入，不是实际 TCP 确认丢包。
- `TEST_MANUAL_KILL_SQL=1`：在同一事务中收件箱及人工记录 INSERT 后、提交前，通过独立连接执行 MySQL `KILL CONNECTION`；三轮均确认两条记录一起回滚，随后正常重试、冲突拒绝和结算一次。输出 `manual-resolution-kill-sql.txt`；unexpected EOF 为主动断开测试会话。

这些测试没有实际人工审批、可信供应商证据或生产身份认证。第二项仅模拟已提交一侧，不覆盖事务结果未知时所有网络行为；第三项是单个提交前切点。未覆盖跨节点竞争、旧实例绕过、审计不可篡改、订阅和性能，不能部署。

## 补充：人工记录提交后 Redis 进程中断

执行 `TEST_STORE_MANUAL_GUARD=1 TEST_KILL_BEFORE_LOCAL=1 TEST_MANUAL_RESOLUTION=1 TEST_MANUAL_REDIS_CRASH=1 TEST_MANUAL_LATE_USAGE=1 bash eval/billing-comparison-2026-11-02/run-handler-journal-process.sh --candidate`，日志 `manual-resolution-redis-crash-final.txt`，Go race 三轮通过。测试先在模拟上游回复后终止隔离 MySQL 和 handler，再恢复 MySQL 并提交合成人工记录及收件箱；随后实际 `docker kill` 本次脚本创建的隔离 Redis 容器。故障期间用量及其一条 Outbox 事件已持久化，结算失败，账单与收件箱保持 pending，没有结算或冲正。日志中的 Redis connection refused 是主动终止容器的结果。

重启同一容器并确认端口不变后，三轮均观察到余额 key 不存在（`key_exists_after_restart=0`）。测试在隔离、无业务流量条件下**显式调用**真实 `Store.RebuildBalance`，重建余额为 499；随后重放收件箱并重复重放，最终 Redis 余额与账本均为 458，指定 reserve、usage、settle 事件各一条，结算记录一条。此处的重建是测试主动调用，未验证生产自动恢复机制。

故障切点是人工记录提交后、结算尚未发生；未覆盖结算 Lua 已执行但确认丢失、Redis 复制故障或网络分区、持久文件彻底损坏，也未覆盖并发流量下重建。仅覆盖测试 Store、合成人工输入、单账户现金链路，没有 Kafka relay、真实授权或旧版本混部；不能据此认定生产可自动恢复或可安全部署。

脚本改用固定 loopback 端口后，另执行默认候选回归 `bash eval/billing-comparison-2026-11-02/run-handler-journal-process.sh --candidate`，race 三轮通过：模拟上游各调用一次，handler 在本地日志写入后被终止，扫描恢复后各有一次结算、三条指定事件，余额与账本均为 458；此回归覆盖的是日志写入后的进程死亡路径。
