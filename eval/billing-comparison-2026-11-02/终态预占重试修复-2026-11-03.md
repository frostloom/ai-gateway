# 已终态预占重试的账务缺口与修复

## 重现

`idem-sql-reverse-gap.txt` 保留修复前的真实隔离 MySQL/Redis Store 实验：请求已预占、随后被冲正并恢复余额，新 owner 重新调用相同请求 ID 和参数的 `Reserve`，返回原 bill ID 和 `RESERVE_OK`；实验性入口 gate 随后允许进入 forwarding。对该 reversed 行的 `ReportUsage` 返回 FailedPrecondition。这个顺序说明如果调用方把该重放视作可发模型请求，可能产生无法按该 reserve 正常记录用量的调用；测试没有调用模型，不声称已经发生真实资金损失。当前 gateway 有独立 5 分钟幂等键，但它有期限；不能把它当作账单终态安全保证。

## 修复和验证

在 `internal/billing/store/mysql.go` 的 `verifyReserveReplay` 中保留原参数指纹检查，并只允许 status 为 pending 且未上报 usage 的相同参数重放。reversed、settled、未知状态或已有 usage 返回 FailedPrecondition；现有 gateway `Chat` 将此错误映射为 409。修改贯穿所有调用该函数的 replay 分支，包括余额路径和订阅路径，无 schema 变更。已存在的历史无指纹行依旧拒绝。语义变化：调用方不能再通过再次 Reserve 得到已终态账单的成功响应，部署时需检查依赖旧行为的消费者与版本混用；旧版 billing 实例仍有原行为。

`TestReserveReplayRejectsFinalizedOrReported` 修复前四个状态断言失败，修复后与原指纹测试的 race 检查通过。`idem-sql-terminal-fixed.txt` 使用真实隔离数据库与 Redis：原预占复用、用量已报/已结算/已冲正的重试拒绝、余额/账本及 3 个预期 Outbox 事件验证通过；同时运行持久入口候选测试。`terminal-reserve-regression.txt` 在随机容器和 Go overlay 中运行请求冲突、并发预占、重复预占、结算/冲正、Outbox、重建与订阅等既有定向测试，通过；gateway `TestChatReserveConflictReturns409` race 定向通过。没有执行全部项目测试或真实上游。

## 未解决的关键边界

状态判断和上游发送不是跨系统原子操作：即使 Reserve 检查时为 pending，之后对账线程仍可能冲正，或者先前执行者仍在调用上游；仅靠此修复不能证明任何重试都不会重复模型调用或漏计。入口候选也没有和账单状态、对账任务、上游发送组成经过验证的统一状态机，因此仍不可上线。Redis SETNX 失败后残留幂等键并导致 409 的可用性问题尚未修复；模型回复重放仍未实现。

## 补充：真实 gRPC 服务和 Store 的并发协商

`replay_protocol_real_integration_test.go` 使用真实 gateway billing 客户端、真实 billing gRPC service、控制面令牌拦截器、真实 Store，以及独立 MySQL/Redis；不启动 HTTP 网关或模型。16 个 goroutine 对同一请求 ID 和参数并发调用 Reserve，三轮各得到 1 个 OK、15 个 DUPLICATE、0 错误；更改估算参数后的请求得到 FailedPrecondition。每轮核对 1 条 reserve Outbox 及 Redis/账本余额均为 900。复现：`bash eval/billing-comparison-2026-11-02/run-replay-protocol-real.sh`；Go race 模式三次，输出 `replay-protocol-real-corrected-output.txt`。

首次输出 `replay-protocol-real-output.txt` 的冲突断言已检查 FailedPrecondition，但日志错误地打印后续操作覆盖的 err，显示 `conflict=OK`；已修正日志并重新运行，原记录保留。测试只证明单 billing 服务实例和此并发规模下的预占协商，未覆盖网关真实请求、Redis 失效、混版、进程死亡、自然 TTL、不同账户或最终结算。它不改变本文所列混版及在途冲正风险，也不是完整网关容量测量。
