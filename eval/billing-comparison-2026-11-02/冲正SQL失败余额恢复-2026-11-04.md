# 冲正 SQL 失败后的余额恢复

## 问题和修改

当前现金 `Reverse` 在 Redis Lua 退款后，才以 MySQL 事务推进账单状态并写 Outbox。如果该事务失败，Redis 的已有余额 key 不会因为查询而自动重建，`GetBalance` 可能返回偏高余额，直到后续重建或重试。这个问题不依赖实验状态机。新旧状态守卫混版测试还通过真实账务 gRPC 确认过 500 分投影、400 分账本的差异（`mixed-version-trigger-grpc-read.txt`）。

`internal/billing/store/mysql.go` 在冲正事务报错时，仍持有租户锁的情况下调用既有 `repairOrphanGuard`：读取账本重建 Redis 余额，并在同一 Redis 脚本内清理该请求的 delta guard。原冲正仍返回错误；修复失败则同时报告原 SQL 错误和恢复错误。正常路径无新增操作。此补救不阻断旧实例冲正 forwarding 账单，也不解决上游结果未知或混版安全。

## 证据

隔离 MySQL 8.0.40 / Redis 7，真实当前 Store，race 三轮每组：

- 初始余额 500、预占 100 后，以 MySQL 触发器拒绝账单状态更新。修复前 `reverse-projection-repair-red.txt` 三轮为余额 500、账本 400，未达到所期望的恢复；此前 `reverse-sql-failure-balance-current.txt` 验证移除故障后重试可完成。
- 修复后 `reverse-projection-production-update-verified.txt` 三轮均在失败返回后读取余额 400、账本 400，reserve 保持 pending，reverse Outbox 为零、delta guard 被清理；移除触发器后重试及重复冲正，余额和账本均为 500，reverse Outbox 恰好一条。
- `reverse-projection-production-outbox-verified.txt` 以 Outbox 插入触发器使事务回滚，三轮同样通过上述账单、余额、guard、事件和重试核对。
- 现有完整 Store race 测试通过（`reverse-projection-full-store-final.txt`，包 59.713 秒；原有 opt-in 性能测试仍跳过）。

这些触发器只存在于测试新建数据库，模拟的是 SQL 明确失败，不是连接断开或 COMMIT 已提交但确认丢失。测试没有覆盖 Redis 在修复中不可用、锁会话丢失、进程在 Lua 和修复之间崩溃、真实供应商或连续负载。若修复自身失败，错误会暴露，但余额仍可能暂时不一致；普通查询只在 key 缺失时重建。修复也没有覆盖结算事务失败后的对应窗口，不能声称完全解决 Redis/MySQL 故障一致性。

修复后 Store SHA256 `842d5aba9a3ee6d0f9850ac6f89ecea8257e109264cb56a66d0585578ede1ae9`；之前生成的状态机 overlay 基于修改前 Store，不能用于当前组合结论，需重新生成并验证。所有测试均为本地隔离环境。
