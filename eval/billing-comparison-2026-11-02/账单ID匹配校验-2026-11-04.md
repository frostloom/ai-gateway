# 用量和终态操作的账单 ID 一致性

## 问题和修复

`billing.proto` 的 ReportUsage、Settle、Reverse 同时包含 request_id 和 bill_id。当前代码原先只以 request_id 查询预占，忽略传入的 bill_id；即使正数 ID 指向另一笔真实预占，仍对 request_id 指向的账单执行操作。ID 不匹配意味着调用方可能组合了错误身份；本实验未证明用户可调用内部 RPC，也不把它说成已发生的越权或真实损失。

工作树中的 `internal/billing/store/mysql.go` 对三个入口检查：非零 bill_id 必须为正且等于 request_id 对应预占行 ID，否则返回 FailedPrecondition；检查发生在用量写入前和结算/冲正获取账户锁前，也适用于终态重放。零值按现有测试和调用惯例继续视作省略，兼容旧客户端。因此此修改只是防止明确的不匹配，不是权限认证，不保证调用方对 request_id 的操作权，也不保护零值客户端；混部旧实例仍可忽略此字段。未改变对账未知用量、显式冲正或上游执行状态的策略。

## 验证

- 修改前在隔离真实 MySQL/Redis 中生成三个合成预占 A/B/C，分别以 A 请求 ID + B 账单 ID 报用量及结算，以 B 请求 ID + C 账单 ID 冲正：三次均被接受，实际 A 已结算、B 已冲正、C 保持 pending，Redis 与账本均 860。`bill-id-mismatch-20261104.txt` 是现象复现；通过表示缺口被重现。
- 修复前要求不匹配拒绝的安全断言三轮失败（`bill-id-mismatch-red-20261104.txt`），明确出现用量/结算/冲正均未返回错误及实际终态和事件变化；原始日志保留。
- 修复后目标测试 race 三轮通过（`bill-id-mismatch-final-20261104.txt`），覆盖正数错配、负数 ID、无用量写入、无终态账单/事件、余额核对，以及匹配 ID 正常执行、终态与用量重放错配、零值兼容冲正。仅测试当前进程和 Store，不是完整 RPC、并发混版或网络故障测试。
- 隔离容器下现有 Store 包完整 race 退出 0（`bill-id-full-store-20261104.txt`），两个 opt-in 负载测试跳过；不代表整个项目全量测试通过。没有运行全项目测试或完整网关回归。

## 真实 gRPC 与对账补结算（补充）

`bill_id_grpc_recovery_test.go` 在本机回环启动真实 billing gRPC 服务与控制令牌拦截器，使用项目真实 gateway billing 客户端、真实 Store、隔离 MySQL/Redis；A、B 两个合成预占分别经历用量、结算、冲正错配拒绝。随后 A 的正确用量已记录，测试人为将 A 的创建时间调旧 11 分钟，真实 `SweepOnce` 用扫描得到的账单 ID 经 gRPC 补结算；B 使用正确 ID 冲正。三轮 race 均通过，最终 Redis 和账本均 960，A 的 reserve/usage/settle 与 B 的 reserve/reverse 事件各一条，A reverse、B usage/settle 事件均不存在。`bill-id-grpc-recovery-final-20261104.txt` 是当前测试的最终日志；前一轮初始版本 `bill-id-grpc-recovery-20261104.txt` 同样通过，但没有额外事件缺失断言。
