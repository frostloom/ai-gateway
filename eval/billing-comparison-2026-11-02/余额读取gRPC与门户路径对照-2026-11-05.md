# 余额读取：billing gRPC 与门户路径对照

## 路径和旧 RDB 正确性

上一次旧 RDB 测试直接调用 `Store.GetBalance`，不能证明门户展示出错。代码实际路径不同：billing `GetBalance` gRPC 调用 `Store.GetBalance`；gateway `/portal/me` 的 API Key 认证后转发 billing `/admin/me`，调用 `MeOverview`，后者持账户锁比对账本并在不一致时尝试重建。其他调用方和浏览器会话路径未在此覆盖。

独立 Redis 中关闭自动 RDB 保存、确认 AOF 关闭，在三个合成账户余额各 1000 时执行 `SAVE`；之后每账户两笔预占，余额与账本各 800；杀停并重启本测试 Redis 以恢复旧 RDB。真实 loopback billing gRPC、真实 billing admin HTTP、真实 gateway API Key 中间件和 `/portal/me` 路由，网关以 `httptest` recorder 调用、代理经 loopback HTTP，三轮 race：

| 读取路径 | 当前实现 | 测试版 MySQL 快照 GetBalance |
|---|---|---|
| 内部 `GetBalance` gRPC | 返回旧 Redis 值 1000；账本 800 | 返回账本快照 800；Redis 原值仍为 1000 |
| 另一个账户的 `/portal/me` | 返回余额及账本 800，并将该账户 Redis 投影修复为 800 | 同左；此候选不改变 `MeOverview` |
| 无 API Key 的门户请求 | 401 | 401 |

门户请求刻意携带其他账户的 `tenant_id` 查询参数；结果应是经 API Key 派生账户的 800，并由测试核查该账户的 Redis 投影被修复。三账户金额相同，单凭金额不能区分租户；测试的实际 tenant 参数与修复的账户 key 对应，仍未覆盖恶意会话、跨租户写请求或浏览器 Cookie。随后一个账户对真实 800 余额尝试预占 900，被拒绝且无账单/事件；最后六笔已有预占各一次结算、事件及最终 Redis/账本 920。试验没有实际页面渲染、真实用户、真实模型或资金，不能推断用户实际损失。PASS 表示按表中指定行为完成，包括旧值复现。

快照 overlay 每次 `GetBalance` 在 MySQL 主库使用只读 REPEATABLE READ 事务，先校验租户存在、再汇总账本；不改变 Redis，也不改变预占/结算/门户总览，Redis 仍是计费写路径所需依赖。当前源码基础上另做三轮受控并发结算：快照读取获得结算前一致余额 400、结算后为 460；不存在租户报错、停用租户可读取，`balance-current-snapshot-correctness-20261105.txt`。不覆盖所有历史账本、充值订阅、真实网络分区或 MySQL 提交/主从故障。候选仍仅为测试，不推荐直接上线。

## 小样本路径开销

本地 MySQL/Redis 容器、真实 billing gRPC 和 admin HTTP、通过 loopback HTTP 的 gateway `/portal/me` 与真实 API Key 中间件；16 个合成空账本账户、8 个闭环工作者、每种路径每轮 128 次、Go race 三轮。gRPC 查询与门户查询分别执行；每次检查返回余额 1000，门户同时检查账本 1000。延迟为一次请求从发起到返回，吞吐为完成数/墙钟时间；P95/P99 各 128 样本。串行先运行 Redis 基线，再在新容器运行候选，未随机、共机且短时，GORM 日志及同机服务有开销；不是生产容量或整个网关的模型请求吞吐。

| 方案 / 路径 | 次/秒（三轮） | 平均 ms（三轮） | P95 ms（三轮） | P99 ms（三轮） |
|---|---|---|---|---|
| Redis / GetBalance gRPC | 4130.9、4150.7、4438.3 | 1.88、1.84、1.75 | 8.37、6.86、5.17 | 8.97、7.34、6.18 |
| MySQL 快照 / GetBalance gRPC | 564.6、436.8、612.2 | 13.88、18.02、12.83 | 20.14、33.64、17.69 | 21.34、34.86、20.36 |
| Redis 基线 / portal | 217.1、222.6、257.2 | 36.57、35.66、30.11 | 76.34、70.78、35.70 | 78.19、81.08、40.99 |
| 快照 overlay / portal | 189.1、196.2、208.8 | 41.71、39.87、38.09 | 64.77、55.21、52.29 | 71.86、59.41、57.01 |

所有组错误/超时为零，进程内 database/sql 连接池等待增量为零；未采可归因的 CPU、I/O 或 Redis 命令量。门户并不调用替换的公开 `GetBalance`，两组差异不能归因于该改动。上述 gRPC 差异提示直接每次重算账本有成本；它未覆盖真实历史增长、混合读写和大规模用户，不能以此决定生产架构。

## Redis 停止和重启

分别在两个随机隔离 Redis 容器中，使用真实 billing gRPC、billing admin HTTP、实际 gateway API Key 中间件和通过 loopback HTTP 的 `/portal/me`，在 MySQL 保持可用时真正杀停 Redis，三轮 race：当前 Redis 读取的 `GetBalance` gRPC 每轮报错；MySQL 快照 overlay 的同一 gRPC 每轮返回账本 1000。**两组门户均返回 HTTP 500**；重启各自 Redis 并确认端口和连接后，门户均返回 HTTP 200、余额与账本均 1000。账本为空且只覆盖一个账户，测试不包含预占、结算、浏览器 Cookie、多进程、真实网络分区或数据库失联；不能说整个网关或计费写路径在 Redis 故障中可用。两个独立环境可并行运行，因此该测试不是性能对照。

首次基线测试的断言正确检查门户非 200，但日志错误使用重启后的状态变量，造成“中断 HTTP=200”的误导；原日志 `balance-path-outage-baseline-20261105.txt` 保留、不能作为中断状态证据。修正记录后基线/快照日志 `balance-path-outage-baseline-fixed-20261105.txt` / `balance-path-outage-snapshot-20261105.txt` 三轮均输出上述结果；每次只停止自己创建的 Redis，连接拒绝是主动故障。测试源 SHA-256 `520528c64e4f60e0698a490012123045c17d6375283fa983fcd13c3c6d0445c1`，原错误日志 `2d9e315ba62585cffd8f7d9a24be91d7d67cc5b06ecac638a83011fabc08bfcd`，修正基线/候选日志 `e6a5ee73967e0a879f17e38270fa271673844bff36250929a1a955691521da5e` / `94f4e44702357778f5cffc6784eba53e222dea9b9550d040cf9dd5de8f857cd4`。
