# 鉴权 Redis 无响应并发试验

隔离 MySQL 8.0.40、64 合成普通 API Key、实际 `Store.ValidateAPIKey`，Go 测试直接调用鉴权，不包含 gRPC、网关、计费或模型上游；使用 16 和 64 个并发 worker，每组闭环发压 3 秒并排空，重复两轮，顺序固定先直查 MySQL 后测试候选。数据库连接池最大 40；发压和数据库容器与其他工作负载共享主机。测试候选 Redis 客户端设置 `ContextTimeoutEnabled=true`、30ms 上下文、禁用命令重试；Redis 故障用本机监听、接受连接但不响应的 TCP 替身模拟，不操作任何已有服务。该模拟并不等价于 Redis 崩溃、分区恢复、主从切换或真实客户端所有超时状态。正常项目当前 Redis 工厂没有上述 context 选项。

每组权威查询次数等于该组请求数；故障组均回退，没有使用陈旧缓存。超时数只统计 Go `errors.Is(context.DeadlineExceeded)` 识别的错误；本次无其他错误。连接池等待次数是测试客户端 sql.DB 的累积增量，等待总时长是并发请求等待时间之和，不是墙钟时长；原始 `AUTH_POOL` 同时提供该增量、排空后连接数。故障组的较少等待次数不代表数据库压力更小：Redis 等待降低了送往 MySQL 的请求速率，这是一个可能的解释，不能由该非随机短测证明因果。未单独记录 Redis CPU、MySQL CPU/I/O 与查询服务端分位数。

这两轮故障组没有错误，但只有 3 秒，不能说明更高并发、持续流量或数据库同时故障时稳定；32 连接 Redis 池、每次缓存预算及两次组次序都会影响结果，不能用结果作为生产容量。该候选仍有围栏超时、丢失、直接 SQL 写入等已验证风险，不应上线。

实际 `/v1` 请求除鉴权外，还依赖 Redis 的幂等键（客户端提供时）、限流及现金余额/锁；鉴权回退成功不保证 Redis 故障时完整请求可用。进一步测试必须覆盖这些步骤和账务恢复，并为故障回退设置数据库容量隔离和明确的过载行为，避免把高峰全部转嫁给 MySQL。
