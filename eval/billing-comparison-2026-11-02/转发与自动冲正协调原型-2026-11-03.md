# 转发与自动冲正协调原型（测试专用）

本原型针对“模型调用还在途、无用量却被自动冲正”的问题，扩展已有 SQL 请求入口测试：发送前在 gate 行锁内检查预占仍为 pending、没有用量，再标记 forwarding；自动冲正也先锁相同 gate 行，只有 claimed 才可触发真实 Store 的 Reverse，forwarding 状态既不自动冲正也不自动重发。为保持实验清晰，forwarding 标记与执行 HTTP 之间存在一个故意保守的窗口：即使尚未实际发包，遇到故障也须按不确定结果处理，不能凭本地租约推定上游未执行。

`idem_billing_coordination_test.go` 在隔离 MySQL/Redis 中使用真实 Store、测试 gate 和本地 `httptest` 模型，24 对转发/冲正竞争，race 模式重复三次。第二轮测试输出 `coordinated-gate-output-v2.txt`：各次实际转发/冲正为 13/11、11/13、9/15；模拟模型调用分别与转发数一致。每个请求核对账单及 Outbox 条数，全部账本与 Redis 余额一致、无 pending。在 forwarding 标记之后、发送 HTTP 之前，测试调用协调冲正和重复转发，均被拒绝；随后模拟正常响应、用量上报及结算。首轮结果保留 `coordinated-gate-output.txt`。复现：`bash eval/billing-comparison-2026-11-02/run-coordinated-gate.sh`。结果只覆盖单进程并发、无真实故障时序和正常本地模型；未启动 Outbox relay。

**不能部署：**原型在持有 gate 数据库事务时调用另一数据库连接和 Redis 完成 Reverse；gate 连接失效时行锁可释放，而 Reverse 可能仍在运行，另一发送者可能进入，故本次测试不能证明断连或崩溃安全。它也没有接入真实 gateway/reconciler，没有处理旧版本或绕过 gate 的直接冲正、提交结果不确定、状态恢复、账单与 gate 的原子持久化、异常结果查询、管理员处置、订阅、历史数据迁移和过期清理。未验证分布式死锁、连接池耗尽、高并发开销或长时间 unknown 的用户体验。SQL 行锁跨外部操作尤其需要重新设计，而不能仅凭此原型声称安全。

可能的后续方向是统一权威状态和账务状态的持久化事务/明确幂等协议，使发送许可与终态竞争有可验证的原子边界；发包后的不确定状态需要上游可查询凭据、保守保留及可审计的人工处理路径。该方向尚无实现证明。

## 补充：先持久化冲正意图的原型

测试专用 `idem_reversing_test.go` 将 claimed→reversing 作为单独 MySQL 事务提交，事务结束后才调用真实 Store Reverse，再将 intent 标为 reversed。发送侧只允许 claimed，因此 reversing 期间不会重新发送；重复恢复调用可复用 Store 的冲正幂等。这样测试设计不再需要将 gate 行锁跨 Redis 和另一连接持有。

测试先用未实现的 stub 得到预期失败 `reversing-red-output.txt`，然后实现并验证。`bash eval/billing-comparison-2026-11-02/run-reversing-gate.sh` 在隔离 MySQL/Redis 下以 race 运行三轮：每轮 24 次发送与冲正竞争，模拟模型调用与获准发送数相同，逐请求账单、Outbox 条数及 Redis/账本余额核对一致；三轮发送/冲正分别为 14/10、16/8、12/12。另模拟持久化 reversing 后停止、财务冲正完成但 intent 尚未更新后停止，验证禁止发送与重复恢复；完整输出 `reversing-extended-output.txt`。这些“停止”由测试控制流程模拟，没有杀进程或数据库。

该状态机仍是局部实验：必须保证所有发送、冲正和用量写入入口遵守协议，旧版本或直接 Store 调用可绕过；未测真实进程死亡、提交确认丢失、gate 表状态损坏、订阅及 Redis 故障、遗留数据迁移、消息投递、池耗尽和性能。尤其不能把标记 forwarding 当成已实际发包证明；未知结果仍需可查询凭据或保守留存与人工处理。它尚未接入生产网关或对账器，也不是分布式端到端恰好一次的证明。

## 补充：真实终止冲正工作进程

`bash eval/billing-comparison-2026-11-02/run-reversing-process.sh` 采用新隔离 MySQL/Redis 和子测试进程：子进程分别在 (1) reversing 意图提交后、尚未执行退款，以及 (2) Store 退款完成后、intent 仍为 reversing 时，输出就绪信号；父进程收到信号后实际强制杀死并回收子进程。随后父进程确认转发被拒，8 个并发恢复调用同一账单并重复恢复，核对最终 intent、reserve 状态、两条指定 Outbox、余额和账本。两个切点各重复三次，race 模式通过，最终输出 `reversing-process-final-output.txt`；先前单恢复和并发恢复输出分别保留 `reversing-process-output.txt`、`reversing-process-concurrent-output.txt`。模型服务未调用，relay 未启动。

这是真实子进程死亡，但不是 MySQL 或 Redis 进程死亡，也不覆盖正在执行 SQL/Redis 命令时被杀、网络分区、提交确认丢失及恢复者自身故障。实验仍依赖所有相关入口遵守 gate，且未接入真实网关、对账器或历史/混版流程，不能直接部署。

## 补充：避免抢占有效租约

先前 `markReversing` 在 claimed 状态不检查租约，因此可能在正常 owner 仍活动时启动冲正。新增测试先针对该行为得到预期失败 `lease-reverse-red.txt`，再在单独的测试候选 `markExpiredReversing` 中于 gate 行锁内用数据库时间判断租约到期，确认 pending 且无 usage 后才条件更新到 reversing。`bash eval/billing-comparison-2026-11-02/run-lease-reverse.sh` 以 race 模式运行三轮：有效租约不能被标记；等待数据库时钟自然过期后，16 个并发标记者恰有一个成功；旧 owner 无法转发；恢复冲正后 Redis 与账本余额一致。输出 `lease-reverse-green.txt`。未修改先前 `markReversing` 或生产链路，故之前阶段化原型不能自动继承此保障。

租约到期只说明 owner 的许可已经过期，不证明旧进程停止，也不证明已经发出的上游调用不存在；发送前的数据库条件检查及 forwarding 永不自动回滚仍不可缺。新候选假设 reserve 已存在，尚未覆盖 claim 后、reserve 前进程失联或旧进程迟到执行 reserve；尚未验证租约续期、转发与过期边界、混版、数据库时钟变化及真正的进程崩溃，不能部署。

## 补充：预占前后的不确定状态

测试专用 `idem_reserving_test.go` 尝试在调用真实 Store Reserve 前将 claimed 原子改为 reserving，只有当前 owner 且数据库时间下租约有效可进入；正在预占时禁止转发和自动冲正。预占成功且 owner 租约仍有效时改为 reserved，才可进一步标记 forwarding。如果预占已完成但 owner 的租约过期，状态保留 reserving、账单保持 pending，需要后续核查，不自动退款或重发。

测试先以空 stub 得到预期失败 `reserving-red.txt`。第一版在预占后退回 claimed，新增重放断言暴露同一 owner 能再次进入 reserving（`reserving-replay-red.txt`）；随后改为单独 reserved 状态。`bash eval/billing-comparison-2026-11-02/run-reserving-gate.sh` 在隔离 MySQL/Redis、race 下三轮通过：16 个同 owner 并发进入仅一人成功；正常路径预占、转发授权、用量上报、结算；自然过期的迟到 owner 不能完成转发准备，账单及对应预扣保留，Redis 与账本一致。原始输出 `reserving-replay-green.txt`。未实际调用模型，过期后的保留金额是有意的未知状态，不等于已结算或自动恢复。

该新增状态机仍是局部候选，尚未与前面的恢复原型统一：reserved 超时后的恢复未实现；reserving 无账单时无法区分尚未调用、调用正在进行或提交结果不确定；旧 owner 和绕过入口的调用仍可能直接执行 Store；账单参数绑定、恢复者权限、人工处置、进程死亡、重启及全链路性能尚未覆盖。不能靠本次测试认定可自动恢复或安全上线。

## 补充：预占完成、发送前 owner 失联

`idem_reserved_recovery_test.go` 新增测试专用 `markExpiredReserved`：同一个 gate 行锁内，只有 reserved、预占仍 pending 且无 usage、数据库时间确认租约到期时才改为 reversing；复用测试原型的幂等冲正。先用旧版仅支持 claimed 的候选运行，得到预期失败 `reserved-recovery-red.txt`；再实现 reserved 分支。`bash eval/billing-comparison-2026-11-02/run-reserved-recovery.sh` 以隔离 MySQL/Redis 和 race 运行三轮：有效租约不可冲正，数据库时间自然到期后 16 个竞争者中仅一个取得冲正意图，旧 owner 不能转发，最终账单、两条指定 Outbox、余额和账本核对一致。

另外，测试在已提交 forwarding 后**人为将租约设为过去**，确认该分支仍拒绝自动冲正；随后模拟用量上报和结算。最终记录 `reserved-recovery-final.txt`。这些步骤未调用模型，也没有实际杀进程或测试 DB/Redis 故障。

此结果依赖 reserved 准确表示尚未发包，且发送与状态变更都遵守同一 gate。代码仍分散在测试辅助函数中，未与生产入口/对账器集成；旧版本、绕过 gate、reserving 结果不确定、实际网关故障、消息投递和性能仍未验证。不能根据此实验自动退款已经 forwarding 或身份不明的请求。

## 补充：现有对账器绕过测试 gate

`reconciler_gate_bypass_test.go` 将测试 gate 的请求推进到 `forwarding`，使用真实 Store 预占，再将账单创建时间**人工提前 11 分钟**。真实 `reconciler.SweepOnce` 以 600 秒宽限扫描，测试适配器直接调用真实 Store Reverse，替代 gRPC 传输。隔离 MySQL 8.0.40 和 Redis 7 环境中，race 模式三次均观察到 `scanned=1 reversed=1 gate=forwarding bill=reversed balance=1000 ledger=1000 events=2`，见 `reconciler-gate-bypass-output.txt`。运行 `bash eval/billing-comparison-2026-11-02/run-reconciler-gate-bypass.sh` 可复现。

此实验直接证明：保留当前对账器与 Store，而只在新网关加入测试 gate，会绕开该 gate 并冲正测试中的 forwarding 账单。实验没有真正等待 600 秒、没有发送模型请求、没有运行 gRPC 服务或 Outbox relay，也没有证明任何真实供应商执行或收费。账单时间仅用于触发扫描，不应将模拟结果当作自然故障发生率。要安全引入状态机，冲正权威入口和所有旧版本/旁路均须协调，且仍需验证提交不确定、Redis 失败与混版部署；单靠调整扫描器或超时时间不足以建立这一保证。

同一隔离测试进一步在冲正后提交一条合成迟到 usage，并尝试结算：三次均得到 `FailedPrecondition`、`settled=false`、usage Outbox 数为 0，见 `reconciler-gate-bypass-late-usage-output.txt`。这说明一旦该时序发生，事后直接调用现有用量/结算接口无法按正常路径补账；合成用量不是实际供应商记录，测试亦不代表已发生真实损失。

实际 `Store.Reverse` 在账户锁下先执行 Redis delta，再以 MySQL 事务推进账单及写 reverse Outbox；`ReportUsage` 使用账单行事务。要把 `forwarding` 和冲正安全地统一，必须考虑这两个存储的边界、锁连接丢失及所有调用者，而非仅在 Redis 更新之前查询一次 gate。前述 `reversing` 意图原型仍需整合到权威入口并进行真实进程中断、混版和完整网关验证。

## 补充：真实对账器与测试状态适配器

新增 `reconciler_guarded_prototype_test.go`：真实 `SweepOnce` 通过测试用 billing 适配器与现有 gate 原型、真实 Store 协作。两个合成请求都将创建时间人工提前 11 分钟、租约人为设为过期：一个进入 forwarding，另一个仅到 reserved。适配器对 forwarding 返回 FailedPrecondition；对于 reserved，先持久化 reversing，首次故意返回 Unavailable 模拟中断，第二次扫描完成真实冲正。之后测试向 forwarding 请求提交合成 usage 并结算，核对余额、账本和 5 个指定 Outbox 事件。

`bash eval/billing-comparison-2026-11-02/run-reconciler-guarded-prototype.sh` 以隔离 MySQL/Redis、race 模式运行三次，全部通过；各次第一轮扫描 2、冲正 0，第二轮扫描 2、冲正 1；合成迟到 usage 得以结算，Redis 与账本余额均为 904。原始输出 `reconciler-guarded-prototype-output.txt`。该实验没有调用模型，人工设定时间，不是自然等待 600 秒；模拟中断为返回错误，非实际杀进程。它验证的是受控路径下的组件组合，不证明端到端安全。

## 补充：终止后并发扫描与统计重复

`bash eval/billing-comparison-2026-11-02/run-reconciler-intent-concurrent.sh` 在两个前述真实子进程终止切点后，同时运行 8 个测试版扫描器；隔离 MySQL/Redis、race 三轮各两个切点均通过账务检查：最终 reserve 状态 reversed、余额及账本为 1000、指定 reserve/reverse Outbox 各一条，再扫描处理零条。输出 `reconciler-intent-concurrent-output.txt`。
