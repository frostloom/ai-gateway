# 账本汇总单 SQL 候选：隔离成对测试（2026-11-04）

本次只改变 LedgerBalance 的查询形态，候选仍使用 Redis + MySQL，**不是** Redis 对纯 MySQL 的对比。生产 `plan.go` 未采用候选。当前数据不足以证明多账户整体性能改善，也不足以上线。

## 方法

基线分别查询充值、待结算预占、已结算和初始额度；候选用单条 SELECT 的四个标量子查询获取同样四项，再复用现有 checkedLedgerBalance。Go overlay 临时替换代码；各组隔离账户及合成数据。MySQL 8.0.40、Redis 7-alpine 均为随机名称与回环端口的临时容器；同一容器依次执行 A/B、B/A、A/B 三轮。每组 2 秒发起闭环请求后排空，Go race 开启；每账户初始历史为零，含预热；这不是完整网关或生产容量测试。吞吐为完成的预占、用量、结算完整现金周期数除以含排空的耗时。无完整周期平均延迟采集。

宿主共享且负载高，测试后 uptime 显示 1/5/15 分钟负载 48.15/38.25/41.59；不能视为压测期独占资源。各组只有 48–222 次完成，P95/P99 不稳定。未可靠采集 MySQL CPU、I/O、服务端锁等待、Redis 资源、独立超时数。

## 正确性与限制

单 SQL 专项测试覆盖充值、退款、预占、结算、账户隔离、缺失账户、上下文取消和金额溢出；基线与候选各三轮 race 日志见 `ledger-single-baseline-overflow-20261104.txt` 和 `ledger-single-candidate-overflow-20261104.txt`。候选 Store 全包 race 运行日志 `ledger-single-full-store-profile-20261104.txt` 显示 PASS，124 个 PASS 行、2 个显式 opt-in 跳过（负载探针、行计时探针）；不能称整个项目测试通过。

首次全包运行 `ledger-single-full-store-20261104.txt` 因既有查询次数探针固定期待三条汇总和一条初始查询而 panic，原始失败保留。重跑只在临时 overlay 中严格改成断言一条汇总且无独立初始查询，探针通过；没有修改生产测试或跳过该断言。候选一条语句与原四条语句的快照边界不同，尚须确认非同租户锁读取、事务隔离、NULL/SUM 及并发更新语义；不同历史量、执行计划、长时间运行、真实故障和端到端网关性能均未覆盖。

## 复现

在具备 Docker、Go 和对应 SDK 的本机，从项目根目录运行；脚本创建并清理自身临时容器：

```sh
SDKROOT=/Library/Developer/CommandLineTools/SDKs/MacOSX26.5.sdk \
GOPROXY=off GOTOOLCHAIN=local \
BILLING_COMPARE_LEDGER_SINGLE=1 BILLING_COMPARE_LEDGER_AB=1 \
bash eval/billing-comparison-2026-11-02/run-subscription-full-store-race.sh
```

完整 Store 测试使用相同命令，将 `BILLING_COMPARE_LEDGER_AB=1` 改为 `BILLING_COMPARE_RUN_FULL_STORE=1`。原始负载日志 `ledger-single-paired-load-20261104.txt` 中的 `CASH_LOAD` JSON 包含各项及阶段 profile。候选由 `build_ledger_single_overlay.py` 生成；负载与核对逻辑见 `internal/billing/store/cash_load_test.go`。
