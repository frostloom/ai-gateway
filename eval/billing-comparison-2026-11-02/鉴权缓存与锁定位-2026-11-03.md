# 鉴权缓存候选与计费定位（2026-11-03）

## 适用范围

HEAD `63b9d1ed4d64bb583d15fa884c37468e5c53044c`，分支 `codex/billing-mysql-comparison`，含未提交改动。仅在测试代码构建候选，不接入网关；Redis 和 MySQL 均为随机命名的一次性本地容器，数据均合成，结束自动清理。脚本输出 `auth-cache-run.txt` 包含镜像摘要及原始数据。

## 语义与正确性

候选缓存命中返回存储的 Key，设置 TTL，且单独检查 Key 的 `ExpiresAt`；只缓存有效 Key，浏览器会话 `__browser_session` 绕过缓存。Redis 请求预算 30 ms，失效时回退权威验证；权威验证失败返回错误。测试未接入网关，也未实现状态变化时的可靠失效、持久事件、版本栅栏或故障恢复。

- `TestAuthCacheBoundaries`（内存 Redis 模拟）覆盖有效命中、过期、禁用后的 TTL 内过期数据、TTL 后拒绝、浏览器会话绕过、Redis 停止时回退及权威验证报错。
- `TestAuthCacheStaleRefill` 控制并发时序：旧查询开始后执行 DEL，再让旧查询返回，验证旧值能够重新填入缓存。测试通过表示成功重现风险，不是安全通过。
- `TestAuthCacheRealStoreLoad` 中先用真实 MySQL 的 `Store.ValidateAPIKey` 验证 Key，再实际将数据库 `status` 改为禁用。候选在 TTL 内仍接受，等待 TTL 后拒绝；这证明了当前候选不能满足立即吊销。
- 浏览器会话是否有效取决于关联用户、租户和 session：绕过缓存只是此候选的保守处理。生产 gRPC 响应当前只含 valid、API Key ID 和 tenant ID，不含过期时间及 key 类型；候选直接使用 Store 对象，不能直接放入当前网关。需另设计接口及权限变更的可靠传播。

不能声称 TTL 即严格吊销时间：旧查询在变更之前读取、变化之后填入，可在查询完成后重新开始 TTL。Redis 故障下所有请求回落 MySQL 也可能放大数据库压力；未在高并发故障期间验证降级稳定性。绝不将该候选部署生产。

## 计费 Store 分段探针

独立随机 MySQL/Redis，Go 测试通过 overlay 将测试固定 MySQL 端口改为该临时容器，Redis DB 1 也指向该容器；没有访问固定端口既有服务。每组一次 2 秒闭环加排空，32 workers，单账户与 8 账户，完整周期 reserve + usage + settle。源为现有 `cash_profile_test.go` 和 `cash_load_test.go`，非 HTTP/gRPC 网关压测；主机仍有其他工作负载。原始输出 `cash-profile-20261103.txt`；两个场景请求错误、pending、重复 phase、余额不变量错误均为 0，不能替代长期及故障测试。

命名锁测量包含客户端网络往返及排队，并非纯 MySQL 内部等待；阶段百分位分布不能相减。其与长 reserve/settle 耗时吻合，是热点竞争的定位线索，不代表多账户完整网关的唯一瓶颈。预占和结算各持有账户锁的正确性依赖余额投影核对和 Redis/MySQL 故障恢复，不可直接删除锁；应先按阶段跟踪持锁内的查询、Redis 和提交时序，再在保留串行化与账务不变量的条件下寻找缩短持锁的方法。短测未复测，无法衡量波动，不能声明改造收益或生产容量。

**测量口径补充**：本次原始基准未统计 Redis 命中、超时或回退 MySQL 的次数；表中“缓存命中”指预热后的缓存候选调用，不能证明每次都命中 Redis。后续脚本已增加权威查询计数，原始输出不变。
