# MySQL 汇总余额：历史账单读取与混合验证

## 候选范围和关键缺口

现有测试原型 `mysql_candidate_test_impl_test.go` 使用独立 `candidate_accounts` 行保存余额：现金预占、用量、结算、冲正通过 MySQL 事务写余额/账单/Outbox，并对账户行加锁；它不经 Redis 判断余额。该原型不等价于完整项目，未实现现有订阅额度、充值退款、授权、混版迁移、未知上游结果等规则；它允许对已上报用量的 pending 账单冲正，不可作为安全生产方案。

新增诊断在隔离环境把它与项目现有**模拟充值**入口组合：余额初始 500 分，现有充值 1 元后 MySQL 账本和 Redis 投影变为 600，而候选汇总行仍为 500；一笔需预占 600 的候选请求被错误判为余额不足。`summary-history-recharge-20261104.txt` 中该诊断 PASS 表示成功复现不等价，不是业务通过，也没有发生真实支付。这个结果证明不能仅切换余额读取或只改预占/结算而忽略其他资金入口。

## 受限混合正确性

同一日志中，4 个账户各预置 1000 条直接插入的合成历史结算行及相符汇总余额；8 个 worker 完成 80 个候选请求，每次预占和用量各重试一次，再结算或冲正并重试终态。40 个结算、40 个冲正、80 个 reserve 和 240 个 Outbox 行，最终汇总与账本公式一致；并发读取使用 MySQL 只读一致性快照，对汇总行与账本进行了 72 次核对，未发现差异。测试启用 race 检测。此处历史行没有真实 reserve/Outbox，是构造性能数据；请求使用本地候选，不代表完整网关、真实上游或上述遗漏入口。

原型已有独立测试覆盖部分并发预占、幂等、终态竞争和事务回滚，不能将那些结果外推到充值、订阅或当前正式 Store；见 `mysql_candidate_test.go` 与既有对比报告。

## 读取成本对照

`summary-vs-snapshot-history-20261104.txt` 使用同一隔离 MySQL、同一个账户的预造 0/5000/20000 条合成结算行，8 个 worker、每轮 64 次读，两轮；先快照、后汇总。汇总行是**测试手工按合成账本预置**，没有验证历史迁移。各次余额与预期公式一致、错误 0。下表为原索引阶段，两轮范围：

| 历史 settled 行 | MySQL 账本快照 次/秒 | 快照 P95 ms | MySQL 汇总行 次/秒 | 汇总 P95 ms |
|---:|---:|---:|---:|---:|
| 0 | 816–868 | 12.2–14.4 | 5306–5343 | 1.67–1.72 |
| 5000 | 313–454 | 26.8–38.7 | 5713–5758 | 1.53–1.85 |
| 20000 | 100–110 | 86.8–94.0 | 5584–5668 | 1.59–1.73 |

汇总组每轮约 11–12ms、样本很小且固定顺序，读写负载、网络延迟和机器噪声都未控制；只能说明在这组数据和查询下单行读取更省时间，不能作为生产容量、完整链路收益或写入性能结论。覆盖索引阶段及全部平均/P99/计划在原始文件；索引对写入的影响未测。

## 后续门槛

需要在**同一权威事务**覆盖充值/退款、所有订阅及现金变动、账户初始化、状态迁移和 Outbox；在多进程竞争、提交确认丢失和崩溃时逐事件核对，并设计存量账本一致快照回填、旧写入者隔离、差异修复与回滚。尤其不能因汇总读快就假设它不会出现过期或重复扣款，也不能把当前可被其他冲正入口绕过的未知结果保护称为完成。
