# 鉴权短期围栏测试

参考 QuantumNous/new-api `45746eee4de25ab1eb75d4b7fbb8de2199483ea3` 的 `model/token_cache.go`、`model/token.go`：写数据库前先设置 10 秒 Redis 围栏、删除缓存，回填 Lua 检查围栏。测试目录的 `auth_fence_impl_test.go` 是围绕本项目测试接口建立的简化模型，仅复现关键时序，既不是 New API 源码的测试，也没有接入生产。候选回填遇到已存在缓存不会刷新 TTL；其他细节亦未声称完全一致。

运行 `TestFenceBlocksStaleRefill`、`TestFenceRedisFailure`、`TestFenceStateLossAllowsStaleRefill` 及先前缓存边界测试，启用 Go race。原始输出 `auth-fence-results.txt`：全通过。这里部分测试通过表示成功重现设计缺口，并非证明安全；miniredis 运行于内存，状态丢失使用 FlushAll 模拟，不等同真实 Redis 重启/主从切换。

- 围栏有效时：数据库旧查询先取得旧快照，随后执行围栏与删除，旧快照无法重新填入缓存。
- 围栏过期：控制旧查询晚于围栏过期才返回，旧快照仍可回填。
- 围栏状态丢失：模拟 Redis 清空后，旧快照也可回填。
- 旧查询自身即使发生在围栏期，仍可能向该次正在进行的请求返回旧权限；阻止缓存回填不等于取消已在途请求。
- Redis 不可用时，本模型的失效操作返回错误，读取回退权威验证；模拟未覆盖网络分区、部分成功、重连、写库先后、多个网关实例及缓存读取与写入的所有竞态。New API 相应写入路径在失效失败时记录错误并继续数据库更新；不能把本测试模型的错误传播当成 New API 行为。

固定时间围栏依赖旧查询、事务及消息传播具有可靠上界；缓存状态丢失同样可能破坏该假设。若业务需要立即吊销，应先明确对已在途请求、已完成鉴权的请求、变更提交后的新请求分别提供什么保证。再设计权威版本、原子状态变更/事件持久化、缓存失效与回填条件、Redis 丢失及不可用时的行为，并验证实现；单独加版本字段或 Outbox 本身不自动保证立即一致。当前候选不建议上生产。

## 失效操作部分失败（补充）

`TestFenceBestEffortDeleteFailure` 对测试候选注入 Redis `SET` 围栏成功、`DEL` 缓存失败；模拟调用方忽略失败并提交吊销后，后续缓存读取仍返回旧 Key。该模型的 `GET` 不检查围栏，因此证实这种组合存在风险；测试通过表示缺口被重现。New API 已核实的 Token 更新路径在失效失败后记录错误并继续写库，而其 Token 缓存读取不检查围栏；本例是对该失败组合的隔离模拟，不是对 New API 自身运行结果。需区分“返回更新失败/拒绝敏感更新”、降级权威查询及允许短暂旧权限等策略，并评估 Redis 不可用对可用性的影响。补充测试 `-race` 输出 `auth-fence-results-v2.txt`。
