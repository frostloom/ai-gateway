# 鉴权原子围栏测试候选

在用户选择的 New API 有限期围栏方向上，`auth_guarded_impl_test.go` 是仅供比较的加强候选：单条 Redis Lua 同时设置围栏并删除缓存；命中读取时通过 Lua 同时检查围栏；若失效操作返回错误，测试中的变更回调不执行；在围栏期间回退权威查询。该选择可能降低 Redis 故障期间的权限变更可用性，与 New API 失效失败仅记录并继续写库的行为不同，不能称两者等价。还没有生产路由、数据库事务或集群集成。

`auth_guarded_tests-v2.txt` 中 race 测试覆盖：Redis 操作报错时不执行变更、围栏和旧缓存同时存在时不直接命中，以及长事务跨越围栏有效期导致旧状态回填；第三项通过意味着已复现缺陷。锁定围栏与数据库提交不是一个分布式事务，Redis 状态丢失、失效确认丢失、并发写入、提交不确定以及进程中断仍未完整验证。单纯 Lua 不保证数据库与 Redis 跨系统原子性；Redis Cluster 多 key 同槽、写入口约束、旧版本混部、绕过应用的 SQL 更新、恢复与监控均待解决。该测试候选仍不可用于生产，也不能宣称立即吊销。

原始命令：

```sh
SDKROOT=/Library/Developer/CommandLineTools/SDKs/MacOSX26.5.sdk GOPROXY=off GOTOOLCHAIN=local \
  go test -race ./eval/billing-comparison-2026-11-02 -run '^(TestGuarded|TestFence)' -count=1 -v
./eval/billing-comparison-2026-11-02/run-auth-cache.sh
```

真实隔离 MySQL/Redis 的两测试实例以同一个 Redis 客户端共享缓存；完成预热后通过原子围栏执行 SQL 禁用，两实例均拒绝，`TestGuardedActualStoreMultiInstance` 通过，原始输出 `auth-guarded-real-20261103.txt`。该测试既不代表真实多进程，也不测试异常提交。该次 32 并发鉴权微基准每档 2 秒、3 次，零操作错误，但未统计权威回退次数，且负载不稳，不能称纯缓存命中或稳定性能对比：guarded 约 873–1570 次/秒、P95 64–122 ms，MySQL 约 439–737 次/秒、P95 105–204 ms。进一步记录权威回退的实验进行中；这些数字不用于完整网关容量。

## Redis 上下文超时核查

带权威回退计数的后续基准 `auth-guarded-counted-20261103.txt`：缓存候选模式各轮未发生权威回退（直接 MySQL 模式不经此计数器，显示 0 并不代表没有查询）；但普通缓存第三轮 33 个请求 P95 约 4016 ms。此前说明中的“30 ms Redis 超时”仅是候选设置的 context 截止时间，并非已验证上限。

`TestRedisContextTimeoutObservation` 用本机监听但永不响应的合成 TCP 服务，go-redis v9.22.0 的 context 30ms、socket read 300ms 条件下：默认 `ContextTimeoutEnabled=false` 一次约 302 ms，显式 true 一次约 31 ms（`redis-timeout-observation.txt`，Go race 通过）。这是局部故障注入，不能证明此前 4 秒延迟的直接原因或任何严格实时上限；连接池等待、重试、调度和数据库回退均会影响总时间。

本项目 `internal/pkg/redisx/redisx.go` 也未设置该选项，配置了 3 秒 socket 读写超时。该工厂同时用于计费等其他功能，不能贸然全局改动：需要测试请求取消时 Redis Lua 是否已执行、MySQL 提交/补偿和锁 fencing 的一致性，以及超时对其他路径的影响。当前不将此设置视为已优化。

## 失败回退的额外一次访问

合成无响应 TCP 测试中，启用 context timeout 的候选原先在读取超时、回退权威查询成功后又尝试一次缓存回填，单次测得 65.3 ms（含两次约 30 ms 等待，权威为内存替身）。先编写 `TestGuardedUnavailableSkipsRefill`，旧候选失败（访问两次）；随后仅在测试候选中调整：读取出现非 miss 错误时直接返回权威结果，不再尝试回填；race 检查通过，黑洞测试一次测得 33.8 ms。原始 `auth-guarded-tests-v3.txt` 中旧日志措辞仍写“includes attempted cache fill”，该句未及时更新，实际由 `TestGuardedUnavailableSkipsRefill` 验证无第二次尝试；日志措辞随后修正。数字为单次本机注入，不是时间上限，实际数据库可能慢或不可用。候选仍未接入生产，也未解决 TTL、失效传播等已列缺口。

## 租户禁用与多个密钥的失效缺口

当前真实 `Store.ValidateAPIKey` 同时校验密钥状态、过期时间及租户状态；浏览器会话还校验关联用户和会话。网关和 Agent 都通过 billing 的验证接口，浏览器身份接口还会直接调用 Store。测试候选只按单个 key hash 设置围栏，并明确不缓存浏览器会话；尚无租户级失效机制。当前计费预占另行检查租户状态，但其他使用鉴权结果的接口不应假定得到同样保护。

新增 `TestGuardedTenantDisableLeavesCachedKeys`：真实隔离 MySQL/Redis 中为一个租户预热两个普通密钥；通过直接 SQL 禁用该租户，真实 Store 立刻拒绝两个密钥，而候选仍返回两个缓存结果；测试 TTL 600ms 过后两者均被拒绝。三轮 race 均复现，PASS 表示缺口已复现，而非方案通过；真实代码当前没有接入此缓存，这也不是对 New API 自身行为的运行测试。直接 SQL 用于模拟未接入失效机制的状态变更，不证明项目已有租户禁用 API。600ms 仅为测试参数，不是生产策略或可保证的最大撤销延迟；长事务、Redis 数据丢失与旧查询回填可能进一步影响边界。

复现：`bash eval/billing-comparison-2026-11-02/run-auth-tenant-invalidation.sh`。脚本仅创建和删除自身随机命名的容器，日志 `auth-tenant-invalidation-20261104.txt` SHA-256 `40e758959484187498139ef3e17d3d9435f4a6de6cf399e63acec445d985df7e`，测试文件 SHA-256 `317a9b547e1ff0f58fee7dfd4f5cfbb70e61531b306c89d76c18ef12e65d873a`。接入前需要设计租户及密钥依赖的失效、所有写入口与外部 SQL 的约束，并验证失效失败、并发回填、混版、Redis 重启及具体可接受的过期窗口；不能仅对单个 key 加围栏就宣称覆盖租户禁用。

## 围栏状态丢失后旧值回填

`TestGuardedFenceLossBeforeCommit` 使用真实隔离 MySQL/Redis：先预热普通密钥，候选设置围栏并清除缓存；数据库状态更新之前，精确删除该测试围栏，随后通过候选读取旧数据库状态并回填，再禁用密钥。三轮均观察到真实 Store 拒绝该密钥、候选仍接受缓存。测试 PASS 表示复现缺陷。手动删除模拟围栏丢失这一状态，不是 Redis 重启、驱逐、故障切换或网络分区的完整模拟；测试也没有验证实际服务的权限变更 API 或 New API 本身。该缺口说明单靠易失的 Redis 围栏不能证明跨 Redis/MySQL 的安全失效，候选维持测试专用。

运行 `bash eval/billing-comparison-2026-11-02/run-auth-fence-loss.sh`；同脚本也重跑租户禁用两密钥测试，两个测试各三轮、race 通过。日志 `auth-fence-loss-20261104.txt` SHA-256 `e36fa4bb8efcd6d7f759a1ecb0e3b599a7bff19838a3b3d0cafd149a4c3fa28e`；当前测试源码 SHA-256 `e5884e7b0c936f1b4e799d2ff41a22be7dbec322cd474d681f1ce8c20052bcf4`。上一节测试文件 SHA 是追加本测试前的历史版本。
