# 对账分页有限并行扫描候选

## 范围

仅通过 `build_reconciler_parallel_overlay.py` 在测试构建中替换 `SweepOnce`，正式扫描器未改。默认保留未知账单时，仍固定本轮 upper ID、按 ID 每页最多 256 条；每页无 usage 的账单保留并统计，有 usage 的账单最多四个并发 Settle，等待本页任务结束后读取下一页。结算沿用每次 10 秒子 context；取消后停止领取任务并等待在途调用返回。显式旧版自动冲正复用现有串行实现。测试候选不是跨实例限流，四个工作者是每次扫描的上限；多个扫描器会叠加。已读入但取消后未处理的记录仅留待后续扫描，`Scanned` 仍是读取数，`Settled` 是成功响应数。

## 正确性与故障边界

隔离 MySQL/Redis、真实 billing Service、loopback gRPC，Go race 三轮：

- 顺序实现让第一笔在进入服务前挂住，第二笔在释放前未执行，三轮预期失败 `reconciler-parallel-sweep-red-20261105.txt`。候选三轮中第二笔先完成、释放后两笔各一条 settle 账单及事件，同账户余额与账本均 920；`reconciler-parallel-sweep-core-20261105.txt`。
- 取消用测试替身阻塞四个 RPC，取消后四个调用结束、扫描 join，队列中六笔未发送，十笔合成账单均 pending。原串行扫描不能在屏障前到达四个调用，三轮预期失败 `reconciler-parallel-cancel-red-20261105.txt`；候选三轮通过，见 core 日志。替身主动遵循 context；不证明不遵循取消的自定义客户端或真实网络故障一定结束。
- 已有真实 Store 测试在候选下三轮通过：每轮至少 1025 条无 usage 的待核查记录、分页读取不超过 256、已知 usage 补结算；后插入 ID 推迟至下轮；默认和显式保留未知账单。它们在同一容器多轮累积数据，实际 scanned 数递增，见 `reconciler-parallel-sweep-green-20261105.txt`。该组合中的空响应测试第一轮通过、后两轮因前面测试遗留的过期账单及租户而失败，不将该整组称通过。空响应在独立容器另三轮通过 `reconciler-parallel-sweep-nil-20261105.txt`；其中显式旧版 Reverse 走原串行路径。
- 真实 gRPC 进入 handler 前挂起和 handler 成功提交后延迟响应两组，各三轮均超时后可继续、按原有账单身份重试且各一条结算账单及事件、余额等于账本，`reconciler-parallel-sweep-timeout-20261105.txt`。属于受控服务端拦截，不是真实网络或数据库故障。
- 两个真实扫描器经屏障选到同一账单时，三轮响应统计之和均为 2，实际 settle 账单/Outbox 各 1、余额及账本 960；`reconciler-parallel-sweep-two-scanners-final-20261105.txt`。最初遗漏 `TEST_REAL_RECON_WORKERS=1` 的日志 `reconciler-parallel-sweep-two-scanners-20261105.txt` 三次均 skip，不能算通过。重复扫描的业务写入在该交错下幂等，但 `Settled` 不能视为跨扫描器唯一结算数。

上述首轮测试当时尚未覆盖取消时数据库扫描本身、服务器无视取消、进程终止、重启恢复、真实分区、混版、充值/冲正/重建并发、不同租户的大积压及长期运行；进程与单次服务重启补充见文末。四个 worker 每页 join，任何不返回的客户端调用仍可阻塞，且旧版 Reverse 保持原期限行为。未接入生产。

## 补充：进程与依赖故障恢复

以下仅对测试 overlay，隔离容器及合成账单；每项外层 Go race 三轮通过。子进程自身以普通 `go build` 构建，不是 race 二进制。

- **对账进程中断：**真实独立 `cmd/reconciler` 子进程使用 overlay，对同一账户 6 笔已上报 usage 和 1 笔无 usage 的预占扫描。测试拦截器保证四个 RPC 到达；第一笔真实 billing Store 完成提交后不给响应，其余三个在 handler 之前等待。父进程收到提交信号后杀死并回收子进程，并等待四个服务端调用结束。此时首笔 settled、其余六笔 pending；重启独立对账进程后六笔已知 usage 各有且仅有一条 settle 账单和 settle 事件，无 usage 保持 pending、无 reverse，Redis 余额与账本均 660。该切点是服务器已返回 Store 成功、客户端未收到回复，不是数据库提交确认丢失；没有模拟整机或数据库崩溃。日志 `reconciler-parallel-process-20261105.txt`。
- **Redis 停止与重启：**六笔已报 usage 分布三个账户，同账户有两笔。扫描前真正杀停本次专用 Redis，候选报告六个 Settle 错误，六笔仍 pending 且有 usage；重启同一容器并确认端口/响应后，第二轮六笔 settled，逐项核对一条 settle 账单与对应 reserve/usage/settle Outbox、无 reverse，三账户 Redis/账本均 920。日志 `reconciler-parallel-redis-outage-20261105.txt`。未单独检查重启后 key 丢失情况，不能单凭最终余额声明冷重建已被验证；故障是扫描前断开，非操作中途丢确认。
- **MySQL 停止与重启：**扫描前杀停本次专用 MySQL，扫描查询返回错误；重启并确认端口/连接后，六笔仍 pending 且有 usage，随后第二轮结算六笔、逐项事件和三账户余额/账本均核对通过。日志 `reconciler-parallel-mysql-outage-20261105.txt`。数据库在扫描开始前已停止，不覆盖事务中崩溃、主从切换或提交不确定。日志中的 EOF 和连接拒绝来自主动故障。

这些结果补充指定故障和重启，不覆盖故障与实际高负载同时发生、多进程竞争、Redis 旧快照、长积压或真实网络分区，不能改变候选暂不部署的判断。
