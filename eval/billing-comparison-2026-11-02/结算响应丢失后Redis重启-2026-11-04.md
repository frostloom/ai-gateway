# 结算响应丢失后 Redis 重启：隔离故障实验

在当前工作树（HEAD `63b9d1ed4d64bb583d15fa884c37468e5c53044c`，包含未提交变更）的真实 billing Store 上，将两个故障组合：先由测试客户端 hook 在 Redis 结算 Lua 实际执行成功后丢弃返回值，再在 MySQL 结算账单写入前实际 `docker kill` 本次脚本创建的隔离 Redis 容器并重启。客户端 hook 是应用层注入，不是实际网络丢包。账单在 Redis 重启前确认 pending 且有 usage、没有 settle 行；重启后检查该账户余额 key 和该请求 delta guard 均不存在。重试调用真实 `Store.Settle`，没有在测试中手动调用重建；其现有 `requireCashMatch` 路径在持有账户锁时按账本重建投影，然后重新执行结算。再重复调用一次并核对账务。

使用隔离 MySQL 8.0.40 和 Redis 7，`go test -race` 三轮，三类情况各三次通过：

| 场景 | 初始余额 | 预占 | 使用量对应金额 | 最终余额 / 账本 | 入账金额 | 不足额标记 |
| --- | ---: | ---: | ---: | ---: | ---: | --- |
| 退回多预占 | 1000 | 100 | 40 | 960 / 960 | 40 | 无 |
| 追加扣款 | 1000 | 100 | 150 | 850 / 850 | 150 | 无 |
| 余额不足 | 150 | 100 | 250 | 0 / 0 | 150 | `shortfall:100` |

每次都核对一条结算行及指定 reserve、usage、settle Outbox 事件各一条；重复结算返回成功且余额与账本一致。测试代码 `redis_settlement_restart_test.go`，日志 `redis-settlement-restart-final.txt` 包含镜像摘要和三轮结果。复现：

```sh
bash eval/billing-comparison-2026-11-02/run-redis-settlement-restart.sh
```

脚本使用随机命名容器和仅 loopback 的临时端口，退出时只清理自身容器，无生产数据或模型调用。以上仅覆盖**现金单账户、Redis Lua 已成功但客户端丢弃结果、随后 Redis 重启且余额和 guard 都消失、重试串行进行**的切点。未验证 Redis 复制或持久化的其他恢复状态、网络分区、订阅、跨节点故障、实际网络确认丢失或 Outbox relay；并发范围见下方补充；不能据此认定整个计费链路或生产自动恢复安全。尤其该实验已有可信 usage，不能解决上游执行后用量未持久化造成的未知结果，也不改变无 usage 自动冲正的风险。

## 同账户并发恢复补充

使用 `TEST_RESTART_CONCURRENT=1 bash eval/billing-comparison-2026-11-02/run-redis-settlement-restart.sh`，同一故障切点在 Redis 重启后同时启动 12 个针对原账单的结算请求；退款和追加扣款两种情况下，再同时对同一账户的另一请求发起预占。所有并发请求成功后，该另一请求按合成用量 20 结算。余额不足分支只启动 12 个原账单结算重试，不发起额外预占。

隔离 MySQL/Redis 下 race 三轮通过：退款场景最终余额和账本均为 940，追加扣款场景均为 830，余额不足场景均为 0。两笔请求分别核对结算金额、各一条结算行和各三条指定 Outbox 事件；原请求额外核对不足额标记。原始输出 `redis-settlement-restart-concurrent-final.txt`，旧版断言的初次通过输出 `redis-settlement-restart-concurrent.txt` 保留。

这是同一进程内的有限竞争测试；启动屏障不保证覆盖所有锁获取顺序，也不是高并发容量测试。没有覆盖跨进程、多节点、Redis 重启期间就有并发写入、持续流量、网络分区或订阅，更不能证明未知用量场景安全。

## 终态 SQL 回滚时 Redis 实际停止

当前工作树的现金终态恢复改动后，重新执行上节 `TEST_RESTART_CONCURRENT=1` 真实 Redis 重启与并发重试回归，三轮通过，日志 `redis-settlement-restart-after-terminal-fix-20261104.txt`；其故障点仍是 Lua 回复被测试 hook 丢弃、SQL 终态写入前，不直接测试下述 SQL 回滚路径。

新增 `TestTerminalRollbackRedisOutage`：实际 Store 的现金 settle/reverse 完成 Redis delta 后，在 Outbox 写入前的 GORM 回调中用 `docker kill --signal KILL` 终止脚本自己创建的隔离 Redis，并由回调注入 SQL 错误令事务回滚。终态调用返回错误，测试在 MySQL 中确认预占仍 pending、目标终态 Outbox 为零；随后启动同一 Redis 容器，等待可连接后，直接重试真实 Store 操作。三轮 race 的结算和冲正各三次通过：重试后结算余额/账本 460、冲正 500，目标终态事件各一条。日志 `terminal-rollback-redis-outage-20261104.txt` 的 connection refused 为 Redis 被主动杀死期间的预期记录。

Redis 的停止和启动是真实容器操作，SQL 失败则由应用回调模拟；测试没有记录 Redis 重启后 key 的持久化状态或断言首次错误的具体码，不应称所有状态都已丢失或确认哪一步修复执行。它没有验证真实数据库断连、提交成功但响应丢失、Redis AOF/复制、网络分区、同账户并发、进程崩溃、Kafka 或订阅；也不能解决上游已执行但 usage 未知的问题。当前正式改动仍需其他故障和整体验证。
