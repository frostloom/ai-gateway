# 账单发送许可与退款许可：隔离状态竞争原型

在 HEAD `63b9d1ed4d64bb583d15fa884c37468e5c53044c` 加当前未提交工作树的基础上，`../project-load-2026-11-02/billing_execution_state_candidate.go.txt` 为测试 overlay：真实预占事务将账单 `execution_state` 设为 reserved；测试代码以 MySQL 条件 UPDATE 让 reserved→forwarding 与 reserved→reversing 竞争；候选 Store 在真正操作 Redis 退款前要求 reversing，并在退款账单状态及 Outbox 事务中写 reversed。账单及状态在同一行，候选未改生产文件或配置。

`bash eval/billing-comparison-2026-11-02/run-execution-state-test.sh --candidate` 在新建隔离 MySQL/Redis、race 下运行三轮，每轮 12 笔不同账户请求：两个 goroutine 同时竞争条件更新，各请求恰有一个胜者；forwarding 胜出时测试直接 Reverse 被拒，随后合成 usage 正常结算；reversing 胜出时调用真实 Store Reverse 两次并拒绝再次发送许可。逐请求核对余额、账本和指定 Outbox 均一致。三轮 forwarding/reversing 分别为 7/5、9/3、5/7，原始输出 `execution-state-green-fixed.txt`。

**不能部署，也不证明整体方案安全：**许可由测试直接执行 SQL，无认证、owner、租约、实际 gRPC 或网关接入；任何有 DB 写权限的调用都可伪造 reversing。测试不检查何时可以认定上游未发送，不能凭超时/理由字符串提供退款许可。保守 legacy 默认拒绝退款并破坏既有接口；旧 billing 实例可绕过状态，状态迁移、混版、回滚未解决。候选没有协调 ReportUsage/Settle 与 reversing 的所有竞争，也没有处理 Redis 变更后 MySQL 提交不确定、数据库会话中断、跨进程崩溃、扫描与恢复、订阅/充值、长时负载和 Outbox relay。条件更新只建立此局部互斥，不是外部服务恰好一次执行的证明。必须补齐服务端授权、真实网关/对账集成和故障恢复后再做性能对比。
