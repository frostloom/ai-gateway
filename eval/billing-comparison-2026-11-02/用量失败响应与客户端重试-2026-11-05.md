# 用量持久化失败时返回错误的重试边界

## 发现

不能只把用量上报失败时的 HTTP 200 改成 503，就宣称避免了账务风险。测试中，同一幂等键的重试被阻止再次调用上游，但调用方也拿不到首个模型响应；不带幂等键的相同请求重试生成新请求 ID，模拟上游被调用两次。流式内容和 `[DONE]` 已写出时，后续用量上报失败无法将已发送的 HTTP 状态改成 503。

## 候选和非流实验

`build_usage_failure_http_overlay.py` 只构造测试 handler：非流式 ReportUsage 返回错误时不返回模型正文，改返回 503；实际 usage 已成功记录而 Settle 失败仍保持原有响应语义。流式路径仍沿用已写出的响应。未接入生产；该候选未处理 `accepted=false`、响应重放、老版本混部、未知上游状态或完整账务协议。

`TestUsageFailureErrorResponseRetrySemantics` 使用真实 gateway Idempotency 中间件、handler、billing client、回环 gRPC Service 和 Store、隔离 MySQL/Redis、本地模拟上游；billing client bridge 在 ReportUsage **发送前**人为返回 Unavailable。billing 强制 v2。HTTP 使用 `httptest.ResponseRecorder`，同一请求正文：

| 场景 | HTTP 顺序 | 模拟上游调用 | reserve / 无 usage pending |
|---|---|---:|---|
|相同幂等键：首次、立即重试、手动删除该 Redis 键后再次重试|503、409、409|1|1 / 1|
|不带幂等键：首次、再次发送相同正文|503、503|2|2 / 2|

三轮 race 均重现，验证三个 pending 均无 usage/settle/reverse Outbox，两个账户的 Redis 余额与账本一致。手动删除模拟 Redis 记录失效，不是自然等待五分钟，也不是 Redis 完整故障；删除后同键被 billing 的严格预占重放拒绝，不能推广到旧网关/旧 billing 混部、重复请求改变键、没有持久预占或其他故障。无键第二次是客户端再次发起请求，并非网关自动重试；两次均为本机模拟上游，不能断言真实供应商收费或实际损失。

原 handler 保留 200，基线要求 503 的断言三轮失败（`usage-failure-error-response-red-20261105.txt`）。测试候选及流式用例最终合并三轮通过（`usage-failure-http-final-20261105.txt`）。测试通过说明指定行为被复现，**不代表账务安全或恢复成功**。

## 流式边界

`TestUsageFailureAfterStreamSentKeepsHTTP200` 使用真实 handler、回环 billing gRPC、隔离账本与本地 SSE 模拟上游；bridge 在 ReportUsage 发送前人为失败。三轮均观察 recorder 为 200、包含正文和 `[DONE]`，账单 pending 且无 usage，usage/settle/reverse 事件均无、余额与账本一致。候选未改变流式处理；这说明在该实现里内容已写出后，非流式 503 策略不解决流式账务失败。recorders 不代表真实网络客户端已完整收到数据，也未模拟断网、客户端取消或发送时间竞态。

用户侧要可恢复地重试，必须先有可靠请求/attempt 身份、明确的已发送或未知状态、可信持久用量与对账；是否保存/重放模型响应是独立能力，账务幂等不自动提供响应重放。强制客户端提供和保留幂等键、错误返回、流式事件协议及旧客户端兼容都需要设计和验证；本实验不决定这些产品语义。候选仅用于故障理解，**不可部署**。
