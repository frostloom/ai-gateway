# 正式账务状态协议的接入约束

本文件是工作树设计约束，不是已实现功能或上线批准。基准 HEAD `63b9d1ed4d64bb583d15fa884c37468e5c53044c`，有未提交修改。依据当前源码和测试候选，不连接实际服务。

## 现有权威路径与协议差异

- `internal/proto/billing/v1/billing.proto` 只有 Reserve、ReportUsage、Settle、Reverse 等现有 RPC；无申请发送许可、渠道 attempt、可恢复冲正意图或人工核查接口。`internal/billing/server/service.go` 的 Reverse 直接调用 Store。
- `cmd/billing/main.go` 用 `controlplane.UnaryServer` 对全部 unary RPC 校验同一个共享令牌；`cmd/reconciler/main.go` 和 gateway billing client 通过 `controlplane.Dial` 使用该机制。`internal/pkg/controlplane/token.go` 的客户端使用 gRPC insecure transport。源码没有按调用方角色区分发送者和恢复者；实际部署网络、代理及传输保护未在此次验证，不能据此推断服务是否对外暴露。
- `billing_execution_state_v4_candidate.go.txt` 给账单增加测试状态、在 Reverse 和 ReportUsage 中检查状态。状态转换由 `execution_capability_rpc_test.go` 的测试服务提供，恢复密钥和桥接不是正式服务，也不能用共享控制令牌自行推导最小权限。
- `reserve` 当前兼容旧客户端：服务按 metadata 选择新旧语义；因此升级部署时旧调用者或旧 billing 实例仍可能使用未经新状态协议保护的路径。仅增加列、部署网关或修改对账器均不能证明所有写入口被约束。

## 可实施的设计门槛

1. 在 billing 权威入口定义版本化状态转换与持久字段：新预占、发送许可、用量记录、冲正意图、终态及 Outbox 的事务边界必须明确。每个渠道 attempt 有稳定身份；发送后结果不确定时保留未知，不以租约过期或无 usage 证明未执行。跨 Redis/SQL 修改须定义中断恢复及重建顺序。
2. 引入可鉴别的服务身份和方法级权限，区分 gateway 发送许可、reconciler 恢复与人工处置；不得用客户端自由文本 reason 授权退款。能力或凭据应绑定账单、请求、租户、动作、有效期和重放规则，并在权威服务验证。TLS/mTLS 与网络隔离方案需按实际拓扑验证，不能从源码猜测现有部署。
3. 先确定兼容矩阵与切换屏障：旧实例可以绕过新逻辑时禁止宣称已启用保护。历史 pending 标记为需核查而非推断未发送；数据库迁移须明确字段默认值、索引、回填及回退后不可安全释放的状态。切换、回滚要确保旧服务无法写入受保护账单；需要实际混版、崩溃和回滚测试才能确认方案。
4. 对每个步骤制定可观测恢复：有界扫描、分批、公平性、逐条失败隔离、重复处理、长期 unknown 告警及审计。每条状态转换与余额、账单、用量、Outbox 核对，并测试数据库/Redis 故障、提交确认不确定、进程死亡和多实例。
5. 完整规则和同等负载通过后才比较性能：覆盖现金和订阅、充值退款、禁用租户、重放参数冲突、所有上游失败路径；旧/新 RPC、跨进程和整个网关同时压测。尚未达成等价前，任何测试原型都不是生产方案。

本次只做源码与测试原型核对，没有新增正式 RPC、数据库迁移、授权系统或部署。现有对账扫描后 usage 已提交仍退款的反例，以及测试桥在受控路径阻止退款的结果，见 `对账扫描后用量先提交竞争-2026-11-04.md`。
