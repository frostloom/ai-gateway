# 对账结算 RPC 的有界等待

## 改动及边界

`SweepOnce` 对每笔有 usage 的账单顺序调用 billing Settle。原调用直接使用长期运行的父 context，单笔无法返回会挡住后续账单。现在仅对每次 Settle 创建最多 10 秒的子 context；父 context 更早取消时仍以父期限为准。超时记入既有 `SettleErrors`，继续处理后续账单；它表示结果未确认，不表示事务未提交，也不触发冲正。账单若仍 pending，后续扫描按已有幂等 Settle 再试。10 秒与现有 gateway 结算等待量级相同，是初始护栏而非经生产负载调优的 SLA。

此改动不并行化扫描或提高模型调用容量；许多慢账单仍可能使一轮耗时达到逐笔期限之和。扫描 SQL、旧版主动 Reverse 和余额 Rebuild RPC 本次没有增加期限，不能宣称整轮有界。无 usage 的账单仍按现有默认保留策略处理；持久化可恢复用量、路由多实例和全网关性能问题不由此解决。

## 验证

- 原实现中，隔离 MySQL 上人为挂起第一笔 Settle，12 秒后第二笔仍未到达，三轮预期失败，`reconciler-rpc-timeout-red-20261105.txt`。
- 修改后相同场景三轮中第一笔记录错误，第二笔得以继续；原先 500ms 阻塞确认及默认/显式保留未知账单的测试也通过。`reconciler-settle-timeout-green-20261105.txt`。
- 测试桥先调用真实 Store 完成第一笔结算，再故意让响应等到 context 到期；第二笔随后结算，重复调用两笔后，每笔 settle 账单和 settle Outbox 各一条，Redis 和账本均 920。原实现因为父 context 先到期而两笔均报错，红灯 `reconciler-timeout-commit-red-20261105.txt`；修复后三轮通过，同上绿灯日志。这是测试桥制造的延迟，不是真实网络故障。
- 独立 loopback gRPC、真实 billing Service、隔离 MySQL/Redis 中，拦截器在真实第一笔结算返回成功后延迟响应到 context 取消；三轮中第二笔继续，重复结算仍各一条账单和事件、余额/账本 920，日志 `reconciler-settle-timeout-grpc-20261105.txt`。拦截器模拟延迟，不是物理网络分区或数据库提交确认丢失。
- `go test -race -count=1 ./internal/billing/reconciler ./internal/billing/store ./cmd/reconciler` 通过，包日志 `reconciler-settle-timeout-packages-20261105.txt`。旧的独立 `-once` 恢复、空响应、状态错误测试在各自隔离容器中通过。把 `-once` 和空响应合并运行时，第 2/3 轮由于前者留下测试租户导致后者统计到额外租户而失败，原始失败 `reconciler-settle-timeout-regression-20261105.txt` 保留；不把该组合运行说成通过。测试隔离后分别通过的日志为 `reconciler-timeout-once-isolated-20261105.txt`、`reconciler-timeout-nil-isolated-20261105.txt`、`reconciler-timeout-status-isolated-20261105.txt`。未运行全仓库套件。

每个数据库实验为独立随机本地容器，Go race 各三轮；真实账务测试不调用模型。链接器警告、故障注入产生的错误及日志中的慢 SQL 保留。未验证真实网络分区、多实例、billing 服务器在客户端超时后长时间继续执行、长时间积压、公平性或故障期间吞吐，不应根据局部测试宣布整体目标完成。
