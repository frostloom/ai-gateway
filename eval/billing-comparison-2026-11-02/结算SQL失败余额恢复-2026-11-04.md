# 结算 SQL 失败后的余额恢复

## 缺陷与改动

现金结算先通过 Redis Lua 按实际用量与预扣的差额补扣或退款，再在 MySQL 事务内写结算行、更新 reserve 状态并插入 Outbox。该事务明确失败时，原实现直接返回，Redis 已改变而 MySQL 仍为 pending，`GetBalance` 可读到不一致的余额。

在初始 500 分、预扣 100 分的隔离测试中，实际费用 40 分时失败后的 Redis 为 460、账本为 400；实际费用 150 分时 Redis 为 350、账本为 400。`settle-projection-red.txt` 三轮重现，均未满足余额恢复断言。

当前 `internal/billing/store/mysql.go` 对现金与订阅结算的事务失败，仍持租户锁时调用既有 `repairOrphanGuard`，按已提交账本重建余额并原子清理该请求的 delta guard；原结算返回错误，修复也失败则同时报告两个错误。正常结算路径未增加重建步骤。订阅结算的 delta 为零，但仍会生成 guard，故同样处理其失败路径。

## 验证

各组新建本地 MySQL 8.0.40 和 Redis 7，race 三轮，均使用当前正式 Store 和合成数据：

- `settle-projection-verified.txt`：MySQL 触发器拒绝写结算账单。实际用量 40 和 150 两个方向，失败返回后余额与账本均为 400，reserve 保持 pending、原 usage 保留、无结算行和结算事件、delta guard 清理；移除故障后重试和重复结算，余额分别为 460 与 350，账本相等且结算事件各一条。
- `settle-projection-outbox-verified.txt`：触发器拒绝插入结算 Outbox，事务回滚后同样验证上述两种用量、guard 与重试。
- `settle-projection-subscription-green.txt`：订阅结算 Outbox 失败后 guard 清理、账单 pending；重试和重复结算后余额与账本相等且结算事件一条。
- `settle-change-reverse-regression.txt`：此前冲正事务失败后的恢复与重复冲正回归通过。`settle-projection-full-store.txt`：现有完整 Store race 通过，包 55.496 秒，两个原 opt-in 性能测试跳过。

数据库触发器测试的是明确回滚，并非真实 MySQL 断连或 COMMIT 成功但确认丢失；未覆盖 Redis 恢复时不可用、持锁连接丢失、Lua 后进程死亡及多实例故障切换。恢复本身失败时仍可能有暂时不一致，错误会同时包含恢复失败；普通余额读取对已存在的陈旧值不会自动核对。这项修改不解决未知上游结果、混版屏障或生产容量。当前 Store SHA256 `92e396051efb293b6aea38c76655f5c8ae0f5276b9f8d0acd7f8ce78ff80257a`，旧状态机 overlay 需基于当前代码重新生成并验证。
