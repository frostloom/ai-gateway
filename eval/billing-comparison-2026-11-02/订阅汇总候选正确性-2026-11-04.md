# MySQL 汇总候选：订阅计费正确性验证

## 范围与结论

基于 HEAD `63b9d1ed4d64bb583d15fa884c37468e5c53044c` 和当时未提交工作树，在本机临时 MySQL 8.0.40、Redis 7 容器中测试。现金汇总候选不能直接替换当前实现：有效订阅且现金为零时，当前 Store 接受符合套餐的请求，现金候选返回余额不足。原现金终态入口也会将订阅用量当成现金扣减。下面的订阅入口仅存在于测试代码，没有接入正式服务或自动选择现金与订阅；不能据此宣称方案已等价或可上线。

现有规则及调用以 `internal/billing/store/mysql.go` 的 Reserve、订阅额度计算和终态实现为准：符合条件的有效定期订阅走 subscription，预占现金为零；未上报的 pending 预留按估算计入，即使已早于窗口；已上报按实际用量计入，已结算且超出窗口的用量不再计入；无法确定预留 token 的旧 pending 失败关闭。

## 测试结果

三轮 `go test -race` 均通过，PASS 中有两项是**成功复现差异或边界**，不是表示两方案完全相同：

| 测试 | 观察 |
|---|---|
| 订阅差异复现 | 零现金账户当前 Store 接受订阅预占，现金汇总候选拒绝。 |
| 订阅并发预占 | 配额 300、每次估算 100、并发 8 次：测试候选接受 3 次、拒绝 5 次；3 条预占和 Outbox，现金不变；另检查重放、参数冲突及事务回滚。 |
| 订阅结算与冲正 | 测试专用终态入口保持现金不变，检查重复、相反终态、事件唯一性及注入回滚。原现金终态入口的误扣已在独立红灯日志保留。 |
| 窗口和旧记录 | 过窗口的未知 pending 仍计入；旧已结算用量过窗口后不再计入；缺预留 token 的旧 pending 拒绝新预占。 |
| 用量与预占交错 | 当前 Store 与测试候选均在受控交错中接受第二个估算 100 的预占，最终第一请求实际 300 加第二请求预估 100，超过配额 300。 |

最后一项中，第二次预占的额度求和与第一次 usage 更新重叠，可按预占先于 usage 的顺序解释；它本身不能证明锁实现错误。即使串行，实际用量超过预估也可能导致超额。需要决定超估时是否允许超额、如何限制后续请求及如何记账；不能丢弃已经发生的用量。测试未覆盖多实例滚动升级、真实网络故障、全部套餐/充值组合与生产性能。
