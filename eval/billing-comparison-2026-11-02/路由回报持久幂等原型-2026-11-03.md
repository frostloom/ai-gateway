# 路由回报持久幂等原型（测试专用）

目的：可靠区分重复回报，避免提交成功但响应丢失后重试失败回报导致计数重复。`router_event_idempotency_test.go` 在隔离测试表中给每条回报唯一 event ID，将事件插入和 provider 失败数更新放在同一 MySQL 事务；provider 行锁串行化同一 provider 的事务。相同 ID、相同参数视为重复，参数冲突拒绝；允许同 provider 连续成功批次合并一次清零，失败事件逐条处理。测试表使用二进制事件 ID 键。此原型不修改项目生产 schema 或路由代码。

`bash eval/billing-comparison-2026-11-02/run-router-event.sh` 在随机隔离 MySQL/Redis 上以 race 模式各运行三轮，结果 `router-event-final-v2.txt`：

- 16 个并发同 ID 失败回报仅一次增加失败数；相同 ID 不同结果拒绝。包含新 ID 的成功批次遇到已有 ID 参数冲突时，整批回滚且失败数不变。
- 16 个不同成功事件合并清零，重复批次不再应用；注入 provider 更新失败时，事件插入回滚，移除故障后重试成功。
- 子进程在事务提交后、给调用方返回结果前输出信号并被父进程实际强制杀死；父进程用同 ID 重试，事件仍一条且失败计数仍为 1。这是进程死亡的明确切点，不是对真实网络丢包或提交确认丢失的模拟证明。

stub 的预期失败保留 `router-event-red.txt`，早期输出保留 `router-event-green.txt`、`router-event-final.txt`。测试容器已清理，未调用模型或使用生产数据。

**不能直接部署：**当前 gateway/router 协议没有稳定回报事件 ID 或该事务，原实现的熔断状态在内存中、AutoBan 条件与计数路径并非简单的每条事件加一；本原型仅模型化计数，未实现半开探测、AutoBan、禁用、跨实例内存一致性、多个 provider 事件死锁、DB/网络中断或未知提交恢复。已成功事件的保留期限与去重清理、认证和恶意重复、队列满、批次内失败顺序、迁移以及成本/吞吐也尚未验证。事件表每条都要写，不能假设批量一定比现状快。实际网关接入需要定义稳定 ID 如何覆盖同一请求的多次 provider 尝试及重试，并做完整功能与性能对照。

## 补充：持久事件成本的 SQL 局部压测

`bash eval/billing-comparison-2026-11-02/run-router-event-load.sh` 对同一合成 provider、全成功回报进行闭环 2 秒并排空，32/128 worker，各三轮、第二轮反转顺序；比较当前式互斥串行清零（baseline，无事件持久化）、逐事件事务、单 worker 最多 32 条成功事件的事务批次。每条持久事件仍逐条 SELECT/INSERT；每组先清空测试事件表，MySQL 连接池上限 40。固定唯一合成 ID、无重试；每组校验事件行数与成功数相等。运行未启用 race，所有组 errors=0；原始每组平均、P95、P99、事务数和事件数在 `router-event-load-output.txt`。

| worker | 方式 | 成功回报/秒（三轮） | P95 ms（三轮） |
|---:|---|---|---|
| 32 | 无事件基线 | 504、523、512 | 102.5、131.0、116.3 |
| 32 | 单事件事务 | 215、188、207 | 191.0、251.7、197.1 |
| 32 | 最多 32 条一批 | 467、530、437 | 91.3、73.4、108.1 |
| 128 | 无事件基线 | 564、430、548 | 320.4、558.6、323.7 |
| 128 | 单事件事务 | 206、214、219 | 1301.5、1223.0、1216.9 |
| 128 | 最多 32 条一批 | 498、462、468 | 350.2、348.4、420.4 |

示例：128 worker 第一轮批次写入 1089 条事件，使用 35 个事务；逐条事务写 546 条使用 546 个事务。与无持久事件的基线相比，单事件事务在本机该短测明显更慢；合并事务减少开销，但语义比基线更强且实现仍是原型，不可据此断言等价或生产收益。

此测试没有真实 router、gateway、模型、混合失败、多个 provider、未知提交、事件保留增长、网络及故障，未采集独立超时分类、数据库 CPU/I/O 或池等待时间；二秒闭环、同一记录和本机负载波动不能作为容量上限。原先不持久化事件的纯内存回报合并测试结果不能直接套用于这里。

## 补充：批量读取和插入事件

测试专用 `applyReportEventsBulk` 对同一 provider 的连续成功批次，在 provider 行锁和同一事务内批量读取已有 ID、检查参数、一次批量插入新事件并清零；相同 ID 同参数去重，冲突整批回滚。不同 provider 并发使用相同 ID 时，唯一键保证至多一个插入，失败方重试后得到冲突；首次竞争失败可能是数据库错误，不能假设总是同一错误码。仍然不支持批量失败事件或真实熔断/AutoBan。

`bash eval/billing-comparison-2026-11-02/run-router-event-bulk.sh` 在隔离 MySQL/Redis 上 race 三轮通过并发重复、批次重放、冲突回滚、故障回滚和跨 provider ID 冲突，日志 `router-event-bulk-final.txt`；预期的 stub 失败保留 `router-event-bulk-red.txt`。这不覆盖网络/数据库崩溃、提交确认丢失、批量边界和所有竞争。

更新后的 `run-router-event-load.sh` 在相同 SQL 局部设置中新增 `event_bulk`，每组 2 秒、最大 32 事件一批、三轮反转顺序，完整数据 `router-event-bulk-load.txt`；各组错误 0，持久事件组的行数与请求数逐组一致。示例结果如下，P95 含排空期间完成的请求：

| worker | 逐事件读写的事务批次，回报/秒 | 批量查询/插入事务，回报/秒 | 前者 P95 ms | 后者 P95 ms |
|---:|---|---|---|---|
| 32 | 438、481、481 | 2574、2701、2305 | 151.0、115.2、83.3 | 19.7、17.7、29.8 |
| 128 | 553、447、436 | 4297、4243、4871 | 292.7、393.6、466.4 | 67.1、57.4、39.0 |

同一运行的无事件基线和单事件事务也在原始 JSON 中；它们不具相同保障。批量版本这组局部测试减少往返且较快，但只有单 provider、全成功、短时闭环，事件表在每组前清空；未测长期表增长、混合失败、死锁、CPU/I/O、超时分类、真实网络或完整 gateway。不能将其当作整网关容量或上线依据。生产路由协议、稳定事件 ID、内存熔断与持久状态的协调、故障恢复及保留策略仍未实现。

## 补充：混合回报、等待锁超时及进程终止

对批量 SQL 原型追加三轮 race 回归，输出 `router-event-bulk-crash-v2.txt`：先成功、后失败时，重放旧成功不会清除后来失败；新成功清零后重放旧失败不会重新加一。测试持有 provider 行锁并使另一个请求在获取锁前超时，确认没有事件残留；解除锁后同 ID 重试成功，再重试不重复加一。

另让独立子进程调用批量实现写入**一条失败事件**，事务提交后、模拟返回结果前实际强制终止，父进程以相同 ID 重试；三轮均保持单条事件和一次失败计数。这证明该明确切点的去重行为，不是批量多事件进程崩溃、MySQL 进程死亡、提交确认丢失或真实网络中断证明。首次添加该测试有变量重复声明，在编译阶段失败、未运行注入，保留 `router-event-bulk-crash.txt`；修复后运行 `bash eval/billing-comparison-2026-11-02/run-router-event-bulk.sh` 成功。

上述混合顺序是按已完成事务的顺序验证，并不保证跨实例实际到达顺序或内存熔断与数据库原子一致。该批量原型仍未接入路由和网关，先前单 provider 全成功的 SQL 性能数据不能外推到真实故障混合流量。

## 补充：持久去重不能单独恢复内存熔断

`bash eval/billing-comparison-2026-11-02/run-router-event-memory-gap.sh` 用隔离 MySQL 的测试事件/渠道计数表、真实 `router.Registry` 和模拟消费者，race 三轮。先提交一个失败事件及计数，再**通过测试控制流程跳过**内存状态更新，模拟消费者在提交后、内存更新前停止；同事件重试被去重（新增 0），假设消费者仅对新插入事件更新内存，则事件有一条、测试数据库失败数为 1，而真实 Registry 仍 closed 并继续选中该渠道。阈值为测试设定的 1；对照 Registry 收到同一失败后为 open。输出 `router-event-memory-gap-route.txt`。测试使用真实 Registry 和测试用独立 SQL 表，未杀实际进程，未接真实 router 事件 API；`router-event-memory-gap.txt` 是只核对状态的早期版本。测试 PASS 是复现不安全组合，不是安全通过。

这排除了“给 Report 加唯一 ID、提交后只在新增时修改本机内存”作为完整恢复方案。需要统一事件的持久顺序、内存投影版本与启动/断连后恢复，并明确每个实例如何同步和处理重复；仅把数据库当前失败计数读进内存也不能自动重建 cooldown、半开探测、探测归属等状态。恢复和并发写入之间还要有明确的版本或锁协议。上述测试没有给出已验证的恢复实现，不能证明生产事故，也不能将该原型部署。\nEOF
