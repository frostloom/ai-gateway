# 路由恢复发现分页：测试原型

当前正式 router 的 `Report` 持全局互斥锁执行 MySQL 写入，写入失败只记录日志，`/report` 仍返回 200；同一回报重试也没有事件 ID 去重。先前缩锁候选没有解决这些问题。现有单渠道测试原型将事件和状态放在同一事务，并在受控多进程测试中对同 ID 回报去重；但之前的测试发现器只按 ID 左连接，可能把同 ID 不同内容视为已处理。它们均未接入正式网关。

新增仅在测试文件中使用的 `scanProbeOutbox`：在单条 SQL 中比较 attempt、Outbox 与已处理事件的身份字段，以 `conflict` 暴露不一致，以 `pending` 表示合法但未应用；采用测试表的二进制 ID 排序及 keyset 游标，每页限定 1–100 行。正常匹配的已处理事件不返回。它不修改状态、不消费事件、不保存游标、不隔离冲突，也不是正式 relay。

真实隔离 MySQL/Redis、Go race 各三轮测试：

- `TestProbeDiscoveryClassifiesConflictAndAdvances` 构造一个冲突、一个正确完成和两个待处理记录，每页一行读取；顺序观察到冲突及两条待处理，正确完成被过滤。跨当前游标插入更小 ID 后，重新从头扫描能发现新记录。
- 第一版只比较 Outbox 和已处理事件时，`TestProbeDiscoveryDetectsAttemptMismatch` 以匹配的事件及不同 token 的尝试记录复现遗漏，三轮红灯，原日志 `router-discovery-attempt-red-20261105.txt`。修正后再检查缺少 attempt 和 outcome 为 NULL 的情形，三轮均显示冲突。
- 既有冲突复现与双进程重复发现测试同次各三轮通过；后者仍调用旧的一次性发现 SQL，不是新扫描器的多进程测试。旧冲突测试 PASS 表示风险复现，而非旧发现器正确。

**限制：**构造的冲突是人为损坏的测试数据，未证明正常事务自然生成；游标只在调用者内存，必须推进并周期性回到开头，扫描过程没有跨页快照，进程重启或只反复读取第一页仍可能被冲突占满。未验证持续流入时的公平性、扫描代价、索引/大表性能、持久隔离与告警、消息重试、实际 relay、认证、混版、数据库故障或网络分区。NULL 安全比较针对测试表，不代表已经覆盖正式 schema。此原型不保证完整恢复、生产安全或性能收益，也不解决缩锁的状态一致性；不可部署。
