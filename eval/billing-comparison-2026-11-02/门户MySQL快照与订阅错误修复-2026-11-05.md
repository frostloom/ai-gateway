# 门户 MySQL 快照实验与订阅查询错误修复

## 已修复：订阅查询错误不能当成无订阅

当前 `MeOverview` 曾忽略 `GetActiveSubscription` 返回的错误。隔离 MySQL 中真实创建活跃订阅，用 GORM 回调在订阅查询前注入错误；原实现三轮都返回成功，但 `Subscription=nil`、额度空，红灯 `portal-subscription-error-red-20261105.txt`。这是应用层故障注入，不代表真实数据库网络故障，不能从中推断资金损失。

现正式 `meOverviewCash` 将该查询错误向调用方返回。相同注入三轮通过，且经真实 billing gRPC/API Key 中间件、billing admin HTTP 和 gateway 门户代理观察到 HTTP 500，不再返回伪造的无订阅总览；`portal-subscription-error-green-20261105.txt`。真实充值 100 分、定期订阅额度 300、上报用量 40、退订后本期权益保持的正常字段三轮通过 `portal-subscription-business-after-fix-20261105.txt`。`go test -race -count=1 ./internal/billing/store ./internal/billing/admin ./internal/gateway/handler` 通过，日志 `portal-subscription-error-packages-20261105.txt`；链接器 warning 保留。测试尚未覆盖所有数据库故障、所有订阅状态或全仓库回归。

## 仅测试：门户直接读取 MySQL 快照

`build_portal_snapshot_overlay.py` 从当前 `plan.go` 生成测试 overlay：对每次 `MeOverview` 使用同一只读 REPEATABLE READ 事务，校验租户存在，读取账本余额、订阅/额度、套餐、充值和消费；查询错误返回失败。它**每次**都直接读 MySQL，不是仅当 Redis 出错时回退，不读取或修复 Redis。它将 `balance` 和 `ledger_balance` 设为账本值，`consistent=false` 且附加 `projection_checked=false`，明确没有确认投影状态；内部 `GetBalance` gRPC、鉴权、预占、结算和充值写路径没有改变。

现有接口 `consistent` 是布尔值，前端没有识别 `projection_checked`：`web/src/dashboard/views/SubscriptionView.vue` 对 false 显示“不一致”，`web/src/portal/views/HomeView.vue` 则显示账本口径。未核验并不等于投影不一致，因此**此候选与现有 UI/调用方语义不兼容，不可直接上线**。它还放弃了正常门户读取时修复 Redis 的副作用；尚无经过验证的回填、故障切换和旧客户端迁移方案。候选严格处理订阅/套餐查询错误，也与原来某些被忽略的错误行为不同。

## 功能验证

`portal-snapshot-final-correctness-20261105.txt` 在最新正式修复基础上、隔离 MySQL/Redis、Go race 三轮通过以下四项：

- 实际杀停本次 Redis 时，真实 billing gRPC/API Key 鉴权和 loopback gateway `/portal/me` 返回 MySQL 账本 1000，明确标记未核验投影；原本 `GetBalance` gRPC 仍失败。Redis 重启后总览仍可读，但测试确认缺失的 Redis 余额键没有被该候选重建。原实现对同一实验三轮 HTTP 500，`portal-snapshot-outage-red-20261105.txt`；测试使用合成数据和本机网络，不是断网/主从切换。
- 人为暂停快照读的 pending 汇总，在另一真实 Store 结算完成后继续：快照仍返回结算前余额 400、消费 0，后续新快照返回余额 460、消费 40。该测试验证一个指定交错，不代表所有事务/历史/故障一致性。
- 真实充值 100 分、活跃订阅额度 300、用量 40 和退订后当期剩余额度 260，候选字段与当前正常路径相符。
- 不同余额的两个账户中，API Key 属于 600 账户而 query 参数伪造为 1000 账户；gateway 返回 600，非法 key 返回 401。它覆盖 API Key 路径，不覆盖浏览器 Cookie、所有授权或跨租户写入。

数据库故障、真正多实例、真实供应商、账本历史完整性、长事务资源占用、消息投递、过期/换套餐竞争和生产迁移尚未覆盖。实验不证明 Redis 失联时其他门户操作或计费写入可用。

## 门户短负载与失败保留

16 合成空账本账户、8 闭环工作者，每组 128 次 `/portal/me`，真实 billing gRPC/HTTP 与 gateway loopback HTTP，Go race，各三轮；查询结果含余额和账本检查。延迟含成功和失败响应，吞吐为成功响应除批次时间。先基线后候选、不同隔离容器、宿主共享且未随机化，不是整网关容量。

基线失败轮次错误率 6.25% 和 3.91%，均不满足 ≤1% 标准。客户端可见 timeout 均为 0，不代表 gateway 内部没有超时。两组原始日志为 `portal-snapshot-load-counts-baseline-20261105.txt` 与 `portal-snapshot-load-counts-candidate-20261105.txt`；进程内数据库池等待增量为 0，未采可归因 CPU/I/O 或 Redis 操作量。

此前新版正式修复后的另一次候选对照 `portal-snapshot-load-candidate-final-20261105.txt` 前两轮成功，第三轮至少出现一个 HTTP 502、测试退出 1；旧测试只打印第一个失败，无法计算该轮完整错误率。其日志还显示其他鉴权查询 deadline exceeded，但没有逐请求关联，不能把 502 物理归因于它们。该轮后宿主 load average 为 25.02/26.03/19.79，仅是事后单点。后续改进测试统计所有错误后才得到表中数据；不删除或覆盖失败。前面另一组低负载数据见 `portal-snapshot-load-baseline-20261105.txt`、`portal-snapshot-load-candidate-20261105.txt`，源代码当时尚未包含订阅错误修复。

因此不能以表中某次零错误宣称候选更稳定，也不能将测试结果当生产容量；未覆盖慢模型、真实网关完整路径、高历史数据或长时间负载。
