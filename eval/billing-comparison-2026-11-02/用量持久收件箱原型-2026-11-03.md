# 用量持久收件箱：隔离恢复原型

目的：探索成功响应的用量不能只保存在网关内存时，如何在已持久化后恢复上报和结算。`usage_inbox_test.go` 仅为测试代码，使用 V4 账单状态 overlay：测试 MySQL 表 `eval_usage_inbox` 以 request ID 为主键，保存租户、账单、provider、两种 token 和 pending/done 状态。写入先锁住对应 reserve 账单并要求 forwarding；相同参数重放无副作用，不同参数返回冲突。测试恢复器读出记录，调用现有 Store `ReportUsage` 和 `Settle`，两者成功后标记 done。账单、用量事件和结算事件仍由现有 Store 负责；收件箱状态与最终结算不在同一个事务内，重启重试依赖账务操作本身的幂等。

`bash eval/billing-comparison-2026-11-02/run-usage-inbox-test.sh --candidate` 创建随机隔离 MySQL 8.0.40/Redis 7，Go race 三轮。先保留未实现的预期失败 `usage-inbox-red.txt`；随后先后强制终止并回收三个真实测试子进程，切点分别为：收件箱提交后、usage 已提交但未结算、结算已提交但收件箱仍 pending。父进程以 8 个 goroutine 并发重放并再重放一次；每轮均检查相同用量接受、不同用量冲突、最终账单 settled、用量为 40+2、收件箱 done、指定 reserve/usage/settle Outbox 共三条，Redis 和账本均 458。最终日志 `usage-inbox-three-kills.txt`；此前只覆盖前一/前两个切点的 `usage-inbox-green.txt`、`usage-inbox-two-kills.txt` 与 `usage-inbox-concurrent-replay.txt` 保留。子进程均在收到相应 Store 成功之后才被杀，不是提交确认丢失。

## 重要边界

- 测试直接构造用量并写入收件箱，**没有接入真实 gateway 或 billing RPC**，也没有实际模型调用；不能证明响应与收件箱写入的顺序或安全性。
- 收件箱和账单都依赖 MySQL。MySQL 不可用时无法保存；模型响应已收到而记录未提交前进程死亡仍会丢用量。单纯增加 MySQL 表不能解决这个窗口，必须把未知状态保留下来并设计可信外部查询或人工处置。
- `forwarding` 仅是测试状态，旧实例、直接调用及旧对账器可以绕过；provider 和用量来自测试调用者，缺正式身份、租户及 attempt 授权，不能防止伪造。该原型不可上线或用于自动退款。
- 未验证不同进程并发恢复、真实 Redis/MySQL 重启、网络分区、COMMIT 确认丢失、消息 relay/消费、订阅/充值、迁移、清理、速率、吞吐和长期积压。失败任务隔离、扫描分页、退避、监控、持久工作调度也未实现。

本实验仅证明**已经落库**的合成用量在三个指定进程死亡切点及同进程并发重放下可以重新进入现有账务接口；不证明网关与供应商端到端恰好一次，也不证明已经解决此前五个 HTTP 200 最终冲正的问题。

## 补充：真实 handler 与收件箱组合

测试 bridge `inboxFailureBridge` 在真实 handler 调用 `ReportUsage` 时，先将合成用量写测试收件箱，再返回注入的 Unavailable；该 bridge 不是正式 RPC。`TEST_HANDLER_INBOX=1 TEST_HANDLER_INBOX_KILL=1 bash eval/billing-comparison-2026-11-02/run-execution-gateway-test.sh --candidate` 使用 V4 Store overlay、真实 handler、隔离 MySQL/Redis、本地模拟上游与测试 gRPC 状态转换。测试人为把账单时间和 lease 改旧后，通过测试 bridge 的真实对账扫描拒绝冲正；然后实际终止已写入 usage、尚未结算的恢复子进程，再用收件箱重放结算。非流和完整流各三轮 race 通过，记录器均为 HTTP 200，最终账单 settled，指定 reserve/usage/settle 事件各一条、无 reverse，Redis/账本分别为 960 和 958。日志 `handler-inbox-worker-kill.txt`。无实现收件箱的测试桥先得到预期失败 `handler-inbox-red.txt`；不杀恢复者的组合测试为 `handler-inbox-green.txt`。

反例：`TEST_HANDLER_INBOX=1 TEST_HANDLER_INBOX_WRITE_FAIL=1 bash eval/billing-comparison-2026-11-02/run-execution-gateway-test.sh --candidate` 用 GORM 应用回调在测试收件箱创建时注入错误；三轮中流/非流 handler 记录器仍为 200，收件箱为零行，账单保留 pending，无 usage/settle 事件，余额与账本均 999。日志 `handler-inbox-write-failure.txt`。测试通过表示**成功重现收件箱失败后的证据缺失**，不是安全通过；注入不是实际 MySQL 停机，记录器也不是网络客户端。

此组合增加了 handler 链路证据，但上节限制继续成立：写入前进程崩溃或 MySQL 故障仍无持久用量；流式响应可能已发送，非流式当前 handler 也会返回 200。旧服务与真实对账入口未强制状态机、正式权限和真实 billing RPC 不存在，故不能部署。需要可信用量来源、保存失败时的业务响应与人工核查策略，不能把一个额外 MySQL 表当成完整解决方案。

改动后不设置上述实验变量运行 `bash eval/billing-comparison-2026-11-02/run-execution-gateway-test.sh --candidate`，原五种 handler 模式 race 三轮通过，日志 `handler-inbox-final-regression.txt`；不代表全仓库测试通过。

## 补充：MySQL 进程在收件箱写入前被终止

`TEST_HANDLER_INBOX=1 TEST_HANDLER_INBOX_DB_KILL=1 bash eval/billing-comparison-2026-11-02/run-execution-gateway-test.sh --candidate` 在真实 handler 调用测试收件箱时，于测试 GORM 的 INSERT 执行前对脚本本次创建的专用 MySQL 容器执行 `docker kill`，handler 返回后重启同一容器，确认端口未变并等待 MySQL 就绪；仅随后读取账单并执行人为改旧时间的测试对账。隔离 MySQL/Redis、race 三轮，流/非流各一次共六次：记录器均显示 HTTP 200、收件箱零行、用量/结算事件零条；测试状态机阻止自动冲正，账单 pending、Redis 与账本均 999、仅 reserve 事件。日志 `handler-inbox-mysql-crash-fixed.txt` 中 unexpected EOF 对应主动杀死 MySQL。该测试通过表示**成功重现证据缺失与保守保留**，不是账务自动恢复通过；未向 MySQL 重启后重新提供用量，因此不能结算。

首次测试 `handler-inbox-mysql-crash.txt` 在 MySQL 容器重启后客户端连接旧端口被拒，后续两轮也未执行完整测试，原始失败保留；初始使用 Docker 自动随机端口，测试时未记录重启后的映射，因此端口变更只是可能原因，未单独证实。修订后的脚本为本次专用容器显式选择 loopback 端口，并在重启前后核对映射；端口选择与绑定之间仍存在常规竞争窗口，绑定失败会使脚本退出而非连接其他数据库。

故障只发生于收件箱 INSERT **之前**，不覆盖提交成功但确认丢失、磁盘损坏、主从切换或网络分区。模型为本地模拟，测试 bridge 和 status 转换并非生产接口，账单时间人工调整，HTTP 200 只由进程内 recorder 观察。旧对账/旧实例仍能绕过保护，且进程退出后没有可信用量来源，不能部署或声称已经实现恢复。

固定端口脚本不启用故障变量时的原 handler 五模式 race 回归三轮通过，记录 `handler-inbox-fixed-port-regression.txt`；并非全仓库回归。
