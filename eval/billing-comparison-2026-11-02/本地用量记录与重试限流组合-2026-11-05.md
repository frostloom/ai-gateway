# 本地用量记录与重试限流组合实验

## 结果与边界

本实验将已有**测试专用**本地用量文件与测试专用有界重试组合，探索限流拒绝后是否还存在可重放的信息；不修改正式 gateway/billing、不构成生产方案。在可写临时目录的受控场景中，128 个合成请求的用量均已写入并调用文件和目录 `Sync`，80 笔即时结算、48 笔因重试未获准而 pending 且无 MySQL usage；测试随后在**同一进程人工**读取文件并重复重放两遍，三轮均得到 128 笔 settled，每账户 Redis 和账本均 952，指定 reserve/usage/settle Outbox 各一条、无 reverse。

反例同样重要：将测试目录设为不存在后，128 次记录均失败，handler 仍向 recorder 返回 HTTP 200，128 笔均无 usage 且 pending，无 usage/settle/reverse Outbox，Redis 与账本一致。三轮复现。该失败是不存在目录，不是真实磁盘满、权限改变或掉电；通过表示反例被观察到，不是安全通过。**因此本地文件加限流仍无法保证成功响应有可恢复用量。**

## 方法

`usage_retry_journal_admission_test.go` 以真实 gateway handler、回环 billing gRPC、真实 Store、隔离 MySQL/Redis、16 合成账户和本地模拟模型同时发起 128 请求；HTTP 是 `httptest.ResponseRecorder`。测试 bridge 在首次 ReportUsage 时先调用已有 `saveLocalUsage` 将用量写临时文件，文件内容包括合成 request/tenant/bill/provider 和 token；函数写临时文件、文件 sync、硬链接不覆盖既有目标并 sync 目录。成功时等 128 条记录均写入后统一注入上报发送前 Unavailable；限流 overlay 最多 16 个活跃、64 个等待重试，第二次由 bridge 等待 200ms 再调用真实 gRPC。

| 场景 | 每轮 HTTP 200 | 同步文件 / 写失败 | 即时 settled / pending | 即时 pending 无 usage | 人工重放后 |
|---|---:|---|---|---:|---|
|临时目录可写|128|128 / 0|80 / 48|48|128 settled，重放两遍，余额每账户 952|
|目录不存在|128|0 / 128|0 / 128|128|无可读用量文件，未执行重放|

可写场景三轮 handler 完成时间分别为 2397 / 2280 / 2294 ms；失败场景 691 / 555 / 854 ms。含测试同步屏障和 200ms 人为等待，不是服务延迟或性能对照；未测磁盘 I/O、吞吐或真实持久卷。文件 fsync 成功只说明本机调用返回成功，不证明硬件断电、节点永久损坏或容器迁移后记录仍存在。

人工重放前，测试按记录的 request、tenant、bill 和 provider 查询本次合成账单，再调用真实 Store `ReportUsage` 和 `Settle`；重复整批两遍后核对每个账单、指定事件与余额。此测试信任测试目录和 bridge，不包含真实身份授权、节点间共享、文件清理、自动扫描调度、恶意篡改、接入版本或人工操作协议。上一轮独立子进程死亡实验是不同实验；本次没有杀进程，不能把两者相加称为端到端崩溃恢复。

写文件之前仍有上游已响应而进程死亡的窗口；本地卷不可用或丢失也不可恢复。仅在文件落下后重放，不能证明模型侧恰好一次或真实供应商费用。为防止错误再次调用，任何进一步设计需同时考虑未发送/已发送未知状态、权威身份、可恢复存储、容量上限和写入失败时的响应语义；直接返回错误也可能促使客户端重试并重复调用上游，须验证完整幂等协议。候选不可部署。
