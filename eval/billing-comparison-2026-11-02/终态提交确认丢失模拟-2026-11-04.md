# 结算和冲正提交确认丢失模拟

## 测试方法

在独立的本地 MySQL 8.0.40 和 Redis 7 使用当前 Store（SHA256 `e4a53b0eaca810e385a7336c0ace3b05723313b362342b6094b822bee0d8f98c`）。测试通过包装数据库驱动：调用真实底层 `Commit()` 并等待其成功后，向 Store 人为返回错误。分别使用普通人工错误和 `driver.ErrBadConn`，确认错误确实由注入产生。**这不是丢弃真实网络 COMMIT 响应包，也不证明服务端和客户端所有断网时序。**

## 结果

`terminal-commit-ack-verified.txt` 和 `terminal-commit-ack-badconn-verified.txt` 分别三轮，两个场景均通过：

- 现金结算：预扣 100 分，实际 40 分；提交实际成功但调用返回 `Unavailable`，账单 settled，余额/账本均 460 分，结算 Outbox 一条；再次结算余额和事件数不变。
- 现金冲正：预扣 100 分；提交实际成功但调用返回 `Unavailable`，账单 reversed，余额/账本均 500 分，冲正 Outbox 一条；再次冲正余额和事件数不变。

两组都检查首次返回后的 delta guard 已清理，并以账单状态与指定 Outbox 核对提交确实发生。测试不模拟全数据库不可达、Redis 丢失、实际进程崩溃、并发重放或消息投递；`ErrBadConn` 为驱动包装层返回，不宣称真实 TCP 在该处断开。此前实际 `KILL CONNECTION` 测试发生在提交前，不能与本测试合称真实网络提交确认丢失全覆盖。未知上游结果与状态守卫混版仍未解决。

## 独立终态恢复候选与 guard 丢失组合

在上节测试基础上，使用 `build_terminal_repair_overlay.py` 的测试候选：现金终态 SQL 错误后及重新持锁恢复时强制按账本重建投影，不改变显式冲正规则。测试在 Outbox 写入后、提交前主动删除 delta guard，并确认删除了一条键；驱动包装器随后等待真实 MySQL COMMIT 成功，再人为返回普通错误或 `driver.ErrBadConn`。每种错误下现金结算与冲正各三轮 race 通过：调用方收到 Unavailable，数据库分别已 settled/reversed，结算余额及账本 460、冲正 500；重放后每个终态 Outbox 仍一条。日志为 `terminal-ack-loss-guard-repair-20261104.txt` 和 `terminal-ack-badconn-guard-repair-20261104.txt`。

这验证的是**真实提交成功后的驱动层人为错误**，不是捕获真实网络 COMMIT 回复丢失；删除单个 Redis 键也不是 Redis 宕机。测试未注入回滚、并发重复调用、真实服务重启或 Kafka 投递；此前真实 KILL 在提交前，覆盖不同切点。强制重建候选还缺完整回归、锁交接及恢复失败验证，不可部署。
