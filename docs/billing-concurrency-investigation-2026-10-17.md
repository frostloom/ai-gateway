# 余额重建并发风险：调查与基线

## 范围

基于远程 main 提交 `5054b583d3cf8462224942bc5445d2dab84ae573`，核对新增在线余额重建及充值、退款恢复逻辑。本记录是调查结果，不代表并发缺陷已复现或修复，不授权模型或 JEV 付费评测。

## 已核对的执行顺序

- `Reserve` 先执行 Redis 预扣，再提交 MySQL reserve 行；现有 MySQL 会话锁只按 request ID 串行化同一请求。
- `Settle`、`Reverse` 也存在 Redis 变动与 MySQL 状态提交之间的间隙。
- `RebuildBalance` 从 MySQL 聚合余额后直接 SET Redis，没有与这些间隙协调。
- 新增的 `MeOverview` 不一致修复，以及充值、退款后的 `requireCashMatch`，会在线调用重建。
- 新增恢复函数会删除已经提交的 topup 流水并恢复订单状态；需要核验并发、提交结果不确定和请求取消时的所有权与可恢复性。

## 待复现的假设

当 Redis 已预扣而 reserve 行尚未提交时，在线重建可能把旧账本余额写回 Redis，覆盖在途预扣。应通过测试屏障固定这个执行顺序，分别核验预扣成功和插入失败补偿后的余额及账本。结算、冲正、不同订单退款的并发以及故障重试也应覆盖。

这些是代码路径推导出的风险；当前尚无新增确定性失败测试，不能把它们称为已复现缺陷。

## 2026-10-18：批准方案与实现

用户已批准上述短设计，并要求沿用工作区、保留 `plate_sim.py`，每个验收目标完成后提交推送。前文是调查时的历史快照；本节记录后续修复。

- `Reserve`、`Settle`、`Reverse`、充值、两种退款、在线重建和概览修复共用按租户的 MySQL 会话锁；嵌套 request 锁复用同一固定连接，避免连接池只有一个连接时自锁。
- Redis 余额 Lua 校验租户 owner token。先发布 token，再核验 MySQL 锁所有权，防止失联旧会话恢复后覆盖新持有者的余额。
- 预扣落库失败后重新取得租户及 request 锁，确认持久账本，再绝对重建投影并清除匹配 guard；不做可能重复退款的累加补偿。
- 结算重放以持久终态为准，避免 Redis guard 过期后再次扣款。pending 请求残留 delta guard 时先按账本恢复，再重新应用。
- 充值或退款已提交、投影更新失败时保留订单及流水；同一幂等操作重试负责恢复投影。新预扣、结算、冲正也必须先对齐账本，恢复失败即停止，不能使用退款前的旧余额。
- 启动补建缺失余额时，在租户锁内重新检查存在性，并从账本恢复；已有 key 保持原状。
- 固定会话的 SQL 写入使用有界、脱离调用取消的上下文；开始新财务写入前检查原调用取消。订阅消费聚合先物化结果，再查询模型，避免同一固定连接上嵌套未关闭的结果集。

## 确定性失败与修复证据

新增 `cash_concurrency_test.go`，使用 SQL 回调、Redis hook、MySQL 实际锁等待和会话终止固定交错顺序。

修复前已观察到的失败包括：

- 预扣落库间隙重建覆盖预扣；插入失败后重建与累加补偿重复归还。
- 结算、冲正落库间隙重建恢复旧 pending 余额。
- guard 过期后重复结算再次扣费；旧会话延迟重建覆盖新请求余额。
- 投影失败时删除已提交充值或退款流水。
- 启动恢复把应为 1950 的账本余额写成初始 1000；启动并发把预扣后的 900 覆盖成 1000。
- 原调用在写入前取消仍提交财务变动。
- 独立审查发现：退款已提交而投影失败后，新预扣可消费已退款金额；结算、冲正出现 live/ledger 分别为 950/50、1000/100。补充测试先复现，再加入扣费前账本对齐。

回归另覆盖并发独立退款不能共享同一余额、单连接运行，以及终态 SQL 失败后重建再重试。首次全量回归暴露订阅结果集与固定连接的死锁，堆栈定位后改用物化查询，相关订阅和客服真实 Store 分支已通过后续回归。

独立只读审查已复核最终实现，确认上述退款后陈旧余额的 P1 已解决，未发现其他确认的 P1/P2 阻断。审查未与主线程并发执行数据库清理测试。
