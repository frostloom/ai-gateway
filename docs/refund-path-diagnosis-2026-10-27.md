# 退款失败路径的离线诊断

源于真实范围v5-repeated-receiver-20261027第六对selective失败。原始LLM文本/完整tool_calls未保存，故本次是路径替身实验，不是历史输出回放，也没有修复产品或重新测评。

在8fe1857源码的私密test overlay中复用真实Handler、现有假admin/脚本LLM/FakeJEV及审计store，model和jev_selective各测试四条替代路径，8条全部通过，agent包12.880秒。生产源码、原测试文件、原Go回归断言均未改。新测试代码和原始输出SHA在同日公开档案；Go SDK26.5，与原全量回归相同。当前假admin余额20000元，不冒称复现真实余额25元/退款cap全流程；原cap25真实成功与失败的业务核对仍以原journal为准。

| 输入的脚本路径 | 观测结果 |
| --- | --- |
| 直接调用refund_recharge(amount_money=100) | 1次脚本模型调用，生成退款待确认预览，无业务POST |
| get_balance后再调用refund_recharge | 2次，读取后仍生成待确认预览，无业务POST |
| get_balance后连续两次虚报退款成功 | 3次，一次reply repair后诚实无操作，无pending；后续确认空pending、无写 |
| 首响应同时提出get_balance和refund，后轮再次提出refund | 原实现保留首工具，第二轮退款仍生成预览，无业务POST |

四条路径分别证明对应受控输入的处理结果。第三条与真实运行的3模型/1纠正/仅get_balance/无pending等可见结果相容，但不证明真实上游就是该文本或顺序。第四条说明裁剪不必然导致退款失败；它也不能排除真实一次响应含被裁剪的退款工具。LLM原始数组缺失仍是归因边界。脚本次数不是实际提供方调用/质量或计费证明。

源码核对：chat.go的工具分支仅处理首个tool_call，读结果回填后继续模型循环；合法写工具先preview再挂起，不在这轮执行；无工具回复由replyRepairReason和现金新读边界检查，最多一次纠正，耗尽后返回诚实限制。空pending确认直接no-op。reply_boundary.go的退款正则接受原明确申请；当前不能据此推断每个模型输出一定能触发预览。

当前证据支持：任务完成失败必须保留，防止虚报/越权写入的边界在已观察路径和这些替身输入下起效。没有证据证明执行器收到合法退款工具后错误拒绝或执行失败，也不能把负例完全归给供应商或JEV。原错误中的组合终态断言不等于无关订阅/订单真的被改动，独立状态核对保持原结论。

后续若要改善模型任务完成率，应先增加有界、脱敏的模型决策观测（例如每轮工具数量、首工具类别、裁剪数、修复原因类别），再以独立版本/范围验证；禁止把自动退款、放宽任务成功定义、增大原循环上限或续旧claim当修复。本轮不实施这些行为变化。Langfuse真实接收、停止运行和全部评分读回已在receiver-repeated-live-result文档完成交付；不能把本替身诊断升级成完整24对测评通过或历史根因已确认。
