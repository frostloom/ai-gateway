## 0. 这个里程碑在干什么（30 秒版本）

给「AI 模型网关」加一张**不可能超支的钱包**：

- 多租户网关，每个租户有充值额度，每次大模型调用按 token 数扣费。
- 调用**开始前先预占（Reserve）**一笔额度；调用结束后按实际用量多退少补（M3）。
- 必须成立的两个不变量：
  1. **并发下绝不超卖**——100 个并发请求同时扣，最多把余额扣到 0，绝不能扣成负数。
  2. **同一笔请求绝不重复扣**——网关崩溃重试、客户端重试，同一个 `request_id` 只能扣一次。

M1 只做「预占」这一个动作。为什么单独做一个里程碑？因为**预占是一切计费正确性的根**：预占错了，后面结算、退款、对账全错。

## 1. 概念层（先懂概念，再看代码）

### 1.1 定点整数额度，不用浮点

金额/额度进浮点 = 灾难。`0.1 + 0.2 = 0.30000000000000004`，逐笔漂移累积，对账永远对不平。

做法：所有比率用 **×1000 定点整数**存 `int64`：

```
model_ratio = 1.0  →  存 1000
group_ratio = 1.0  →  存 1000
quota = tokens × model_ratio × group_ratio / 1_000_000
```

例：1000 tokens × 1000 × 1000 / 1e6 = **1000 quota**（即 1 token = 1 quota，数字很干净）。

落点：[internal/pkg/quota/quota.go](../../internal/pkg/quota/quota.go) 的 `Compute` / `ReserveAmount`。

**面试话术**：「额度走定点整数全链路 int64，杜绝浮点漂移，这是金融类系统的基础工程决策。」

### 1.2 预占的三件套（两个存储 + 一个守卫）

| 组件 | key / 表 | 角色 |
|---|---|---|
| Redis 余额 | `billing:balance:{tenant_id}` | **热投影**，扣减走内存，快 |
| MySQL 账本 | `bills` 表（reserve 行） | **权威账本**，可审计、可重建 |
| guard key | `billing:req:{request_id}` | 幂等守卫，「这单扣过没」 |

关键心智模型：**Redis 余额是缓存投影，MySQL 账单是权威账本**。面试官问「Redis 和 MySQL 不一致怎么办」，答案在 M4 对账（以账本重建投影）。

### 1.3 check-then-act 竞态——本项目要消灭的 bug

错误写法（**new-api 的真实缺陷**）：

```
bal = GET balance
if bal >= pre:
    DECRBY balance pre    # 这两步之间，另一个并发请求也读到了 bal=1000
```

100 个并发都读到余额 1000 ≥ 100，全部通过检查，全部扣减 → 余额 -9000，超卖。

修复思路：把「**判余额** + **扣减**」合进**单条 Lua 脚本**。Redis 是单线程执行脚本，脚本中间不会被其他命令插进来 → **原子**。这是 Lua 脚本存在的唯一理由。

### 1.4 幂等：同一 request_id 只扣一次

三层保障，一层比一层兜底：

1. **DB 唯一索引** `uk_request_phase (request_id, phase)`——两个并发 insert 同时落，一个成功、另一个撞 1062；
2. **Redis guard key**（`SET NX`）——第二个请求看到 guard 已存在，就不再做扣减；
3. **DB 快速查重**——已存在该 request_id 的 reserve 行，直接幂等返回原 bill。

### 2.2 reserve.lua 逐行讲（必须能背）

[internal/billing/store/lua/reserve.lua](../../internal/billing/store/lua/reserve.lua)

```lua
local bal = tonumber(redis.call('GET', KEYS[1]) or '0')
if redis.call('EXISTS', KEYS[2]) == 1 then        -- guard 已存在 → 已扣过
  return {2, bal}                                  -- 幂等重放，不重复扣
end
if bal < tonumber(ARGV[1]) then
  return {-1, bal}                                 -- 余额不足
end
redis.call('SET', KEYS[2], ARGV[2], 'EX', 86400)  -- 写 guard（NX 语义，TTL 24h）
redis.call('DECRBY', KEYS[1], ARGV[1])            -- 扣减
return {1, bal - tonumber(ARGV[1])}
```

- `KEYS[1]` = 余额 key，`KEYS[2]` = guard key，`ARGV[1]` = 预扣额，`ARGV[2]` = request_id。
- 返回 `{code, balance}`：`1` 扣成、`2` 已扣过、`-1` 不足。
- 为什么 `EXISTS` 放最前面？先挡幂等重放，省一次无谓检查。
- `SET ... NX` 写法是 `SET key val EX 86400` + 前置 `EXISTS` 判断，在单条 Lua 里天然无竞态（不需要真正 `NX` 选项也能保证，因为脚本原子）。

### 2.3 mysql.go 的 Reserve：三层顺序为什么安全

[internal/billing/store/mysql.go](../../internal/billing/store/mysql.go) 的 `Reserve`（约 132 行）：

```
① DB 快速查重   → 命中则幂等返回（不扣）
② Redis Lua 扣减 → guard 幂等，余额不足返回 INSUFFICIENT
③ 落 reserve 行  → 撞唯一索引 1062 → 读回原行幂等返回
```

为什么 ① 在 ② 之前？绝大多数幂等重试在 ① 就被挡下，不浪费一次 Redis 往返。

**崩溃自愈**（面试亮点）：假设 ② 扣减成功、③ 落库前进程崩溃。重试时：
- ① 没查到行；
- ② guard 已存在 → Lua 返回「已扣」**不再扣**；
- ③ 这次 insert 成功 → 落一行、扣一次 → **自愈**。

那 guard 存在但行永远没落呢？（调用方永不重试）→ Redis 多扣了，少一行。这是 M4「从账本重建 balance」job 兜底的场景，注释写在 `Reserve` 上方。

## 3. 数据流：一次 Reserve 调用

```
调用方（未来是 gateway）
   │ gRPC Reserve{request_id, tenant_id, model, est_prompt_tokens}
   ▼
billing server ──► store.Reserve
   │
   ├─①  SELECT bills WHERE request_id=? AND phase='reserve'   ──命中→ 直接返回 OK(bill_id, balance)
   │
   ├─②  EVAL reserve.lua  余额 key / guard key
   │       ├─ guard 在 → 返回已扣
   │       ├─ 余额不足 → 返回 INSUFFICIENT
   │       └─ 扣减成功 → 返回新余额
   │
   └─③  INSERT INTO bills (request_id,'reserve',pre_quota=est_prompt×1.2)
           ├─ 成功 → 返回 OK
           └─ 1062 重复 → 读回原行 → 返回 OK
```

## 4. 面试 Q&A（附参考回答）

### Q1：为什么用 Redis Lua 而不是 MySQL 事务（`SELECT ... FOR UPDATE`）？

计费是**热点路径**，Redis 单线程内存扣减吞吐是几十万 ops/s，MySQL 行锁一个量级都追不上。而且我们的状态跨 MySQL + Redis 两个存储，MySQL 行锁锁不住 Redis 那一次扣减——**分布式系统没有全局原子，只能分层兜底**：Lua 保证 Redis 侧原子，唯一索引保证 DB 侧幂等。

### Q2：并发预占怎么保证不超卖？给我证据。

两件事：
1. **机制**：判余额和扣减合进单条 Lua，Redis 单线程执行脚本 → 两个请求不可能同时通过检查。这是把「check-then-act」改成「act-in-one-step」。
2. **证据**：`TestReserveConcurrentNoOversell`——100 个协程从 1000 余额各预占 100，断言恰好 10 个成功、90 个 INSUFFICIENT、最终余额 0、**成功数==10 就是没超卖的直接证明**（超卖会 >10）。跑在真 Redis 上（miniredis 单线程串行，测不出竞态）。

### Q3：幂等怎么做的？为什么需要三层？

- 唯一索引管「**两个并发同时落库**」（数据库层面的最后防线）；
- guard key 管「**重试/并发不重复扣**」（Redis 侧的快速判断）；
- DB 查重管「**幂等重放直接返回原结果**」（省一次 Redis 往返）。
- 三层是不同故障场景的兜底，缺一不可：guard 没设上就崩溃 → 靠唯一索引；唯一索引被删 → 靠 guard。

### Q4：Redis 余额和 MySQL 账单不一致怎么办？

Redis 是投影、MySQL 是权威。不一致最终靠对账收敛（M4：低频 job 从账单重算余额）。M1 的弱兜底是 `EnsureBalanceKeys`：启动时为活跃租户补建余额 key（用 `tenants.initial_quota` 初始化）——解决「Redis 被清空/新租户」场景。

### Q5：扣款成功但落库失败怎么办？

- 调用方**会重试** → guard 让 Lua 变 no-op，insert 补上 → 自愈（详见 2.3）。
- 调用方**永不重试** → 孤儿状态，M4 重建 job 收敛。

### Q6：为什么预扣要 ×1.2？为什么不用精确值？

预占时只知道 prompt 的估算 token 数，**输出 token 还没发生**。预留 20% 裕量，避免大输出调用在中途把余额扣成负数。真正的扣费是 M3 的 settle：按实际 token「多退少补」。预扣带裕量、结算按实际，是「预占-结算」模式的标准做法。

### Q7：guard key 为什么要 TTL 24h？不带 TTL 行不行？

不带 TTL 会在 Redis 里堆垃圾（每个 request 一条，永远不删）。24h 远超一次请求的正常生命周期；万一真超过，DB 唯一索引照样兜幂等，代价只是多扣一次再被对账纠回来——可接受。

### Q8：为什么 request_id 不用自增 ID，而用 `crypto/rand` 生成的？

`request_id` 要满足「**全局唯一 + 调用方可控**」：网关在发起时生成，重试时复用同一个，这样幂等才有意义。自增 ID 只能在服务端生成，客户端无法在重试时带上同一个值。`crypto/rand` 而非 `math/rand` 是为了不可预测（防撞号/防猜号）。
