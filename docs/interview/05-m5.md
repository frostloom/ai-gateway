# M5 里程碑文档：路由熔断 + 可观测 + 压测（稳定性收尾）

> 前置：[04-m4.md](./04-m4.md)（对账收敛）
> 本篇回答「网关的稳定性怎么保证、怎么证明」：多 provider 故障切换、熔断状态机、
> AutoBan、Prometheus 可观测，以及用压测把整个计费系统的正确性「打到边界」。
> 压测顺带揪出了两个真实 bug（连接池风暴、rebuild 竞态）——这是全项目最强的面试素材。

## 0. 这个里程碑在干什么（30 秒版本）

前面 M1-M4 解决了「扣费不丢不重、崩溃自愈」。M5 回答三个新问题：

1. **一个模型背后有多个 provider，选谁？坏了一个怎么办？**
   → 权重随机选 + **failover（故障切换）** + **熔断**（连败 N 次自动断开，冷却后探测恢复）
   + **AutoBan**（累计连败太多，写库永久踢出候选集）。
2. **系统跑得好不好，怎么看到？**
   → Prometheus 指标（请求量/延迟/在途）+ `/breakers` 熔断观测端点。
3. **到底扛不扛得住？**
   → 压测：100 并发 × 30s，P99、错误率、余额==账本三项断言。

验收（已达成）：故障注入验证熔断 **OPEN→HALF-OPEN→CLOSED** 全链路、AutoBan 移除候选集、
压测报告三断言全 PASS。

## 1. 概念层

### 1.1 权重路由：为什么不是轮询，而是加权随机？

`providers.weight`：mock-a=5 / mock-b=3 / mock-c=1，权重越高被选中的概率越大。
这是 **加权随机** 而非严格轮询：

- 轮询是「确定性的」，同一时刻所有请求会均匀打满每个节点——如果某个节点慢了，轮询
  不会把流量挪开，反而可能排队；
- 加权随机是「概率性的」，权重表示容量，天然把流量按容量分配；配合下面的 failover，
  一个节点出错后流量会概率性地避开它。

面试可补：真实生产还有一致性哈希（session 亲和）、least-loaded（动态感知负载）等策略，
本项目用加权随机 + 熔断过滤，是「静态容量 + 动态健康」的组合。

### 1.2 failover：只在「首个字节前失败」重试（M3 规则延伸到多 provider）

转发上游失败时，网关重试**另一个** provider。但**重试有严格边界**：

| 失败时机 | 能否重试 | 原因 |
|---|---|---|
| 建连失败 / 上游返回 5xx（首个字节前） | ✅ 重试另一节点 | 客户端啥都没收到，重试不重复计费（Reserve 幂等） |
| 流式传输中途断开 | ❌ 绝不重发上游 | 上游可能已经跑了一半、可能已经计费，重发 = 双扣上游 |
| 4xx | ❌ 透传退款 | provider 正常，只是拒绝请求，重试没用 |

**核心：重试必须换一个节点。** 如果 failover 还是纯加权随机，可能连续 3 次都选到同一个
坏 provider——这是压测真实验出来的 bug（`(5/9)³ ≈ 17%` 概率把一个请求白白打到坏节点上）。
修复：网关记录本请求**已试过的 provider**（`tried` set），重路由时用 `exclude` 参数排除。

### 1.3 熔断状态机：CLOSED → OPEN → HALF-OPEN → CLOSED

每个 provider 一个熔断器（进程内存）：

```
CLOSED（正常）
  │  连续失败 ≥ FailThreshold（默认 5）
  ▼
OPEN（断开，被移出候选集）
  │  冷却 Cooldown（默认 10s）后
  ▼
HALF-OPEN（放 1 个探测请求）
  │  探测成功 → 回 CLOSED（恢复全量流量）
  │  探测失败 → 回 OPEN（再冷却一轮）
  ▼
（AutoBan：跨周期累计失败 ≥ AutobanAfter（默认 20）→ 写库 status=banned，彻底移出）
```

**为什么熔断是「内存态」，AutoBan 是「持久态」？** 熔断快（5 连败就断开，兜住瞬时抖动，
provider 恢复了自然回 CLOSED，不用人工）；AutoBan 狠（累计 20 连败说明这节点持续不稳定，
写进 MySQL 让**所有**网关实例都不再选它——即使网关进程重启、内存熔断态清空，AutoBan 依然生效，
直到人工解除）。

### 1.4 HALF-OPEN 探测位：为什么「只在选中时占位」？

探测的语义是「一次只放 1 个请求试水」。朴素实现会在「候选集包含该 provider」时就置
`probeInFlight=true`——但加权随机不一定选中它，探测位就**永久卡死**，provider 被静默下线。
修复：

1. `available()` 只判断「放不放行」，**不**消耗探测位；
2. 真正选中（`Route` 返回该 provider）时才 `markProbe` 占位；
3. 探测发出后超时（`probeTimeout=30s`）仍无回报 → 释放探测位（网关可能崩了）。

面试价值：这就是「状态机里每个状态转移都要有**兜底超时**」的活例子——探测请求发出去，
网关崩了，`Report` 永远不来，探测位必须自己超时释放，否则一个 bug 让节点永久掉线。

### 1.5 可观测：Prometheus 指标 + /breakers

- `gateway_http_requests_total`（counter，按 service/method/status）
- `gateway_http_request_duration_seconds`（histogram，算 P50/P95/P99）
- `gateway_http_in_flight_requests`（gauge，当前在途数）
- gateway（gin 中间件）和 router（net/http 中间件）**共用一套指标**，用 `service` label 区分
- `/breakers`：导出每个 provider 的熔断状态 + 连续失败数，场景脚本断言用

### 1.6 压测为什么敢断言「余额 == 账本」？

压测不是只报吞吐。三项断言：

1. **无错误**：全部 200（限流阈值已调高，所以不该有 429/402/5xx）
2. **余额守恒**：`Redis 余额 == initial - Σsettled actual - Σpending pre`（独立 SQL 计算，
   不是程序自说自话）——并发 100 下既不超卖、也不丢钱
3. **无重复 settle**：同一 request_id 的 settle 行 ≤ 1（幂等唯一索引兜底）

并且压测期间**对账常驻并发跑**（见 2.6 的发现），证明对账任务和在线事务共存不冲突。

## 2. 代码导读

### 2.1 熔断核心：[internal/router/registry.go](../../internal/router/registry.go)

- `Registry.RouteExclude(model, exclude)`：快照 → 熔断过滤 → **排除已试过的** → 加权随机选中 → `markProbe`
- `Report(providerID, ok)`：状态机推进（成功：HALF-OPEN→CLOSED；失败：连败计数，达阈值→OPEN，达 AutoBan→ban）
- `available(ps)`：按状态过滤 + 探测位判定 + 探测超时释放
- `markProbe(pick)`：**选中才占探测位**（1.4 的修复）
- `ban()`：写库 `status=2` + 失效路由缓存，`nextClosedAt=24h` 兜底自动恢复
- `States()`：导出观测快照

关键代码（Report 的失败分支）——注意 **AutoBan 检查在 OPEN 检查之前**，而且连败计数在
HALF-OPEN 探测失败时**不清零**（跨周期累计，才能攒到 AutoBan 阈值）：

```go
b.consecutiveFail++
if b.consecutiveFail >= r.AutobanAfter {
    r.ban(providerID, b)            // 持久层：写库踢出
    return
}
if b.consecutiveFail >= r.FailThreshold && b.state != breakerOpen {
    b.state = breakerOpen           // 内存层：快速熔断
    b.nextClosedAt = now.Add(r.Cooldown)
}
```

### 2.2 网关 failover：[internal/gateway/handler/chat.go](../../internal/gateway/handler/chat.go) 的 `forwardNonStream`

```go
tried := map[uint64]bool{}
failover := func(providerID uint64) bool {
    tried[providerID] = true                       // 本请求试过了，下次排除
    r.Report(ctx, providerID, false)               // 回报 router，驱动熔断
    if next, err := r.Route(ctx, model, triedSlice(tried)...); err == nil && next != nil {
        prov = next                                // 换一个没试过的节点
        return true
    }
    return false
}
```

重试上限 3 次；所有节点都失败 → 退款 + 502。4xx 透传不重试（provider 正常）。

### 2.3 故障注入：[cmd/mock-provider/main.go](../../cmd/mock-provider/main.go)

`MOCK_FAIL_RATE`（0-100，命中返回 500）+ `MOCK_LATENCY_MS`（模拟慢节点），环境变量注入，
场景脚本重启 mock-a 来「打挂/治愈」它。

### 2.4 可观测：[internal/pkg/metrics/metrics.go](../../internal/pkg/metrics/metrics.go) + [cmd/router/main.go](../../cmd/router/main.go)

三个指标 + `/metrics` 端点 + `/breakers` 端点（`reg.States()` 转 JSON）。

### 2.5 连接池修复：[cmd/billing/main.go](../../cmd/billing/main.go)（压测揪出的 bug）

压测第一轮崩出大量 `dial tcp 127.0.0.1:3307: connectex: Only one usage of each socket address`。
根因两处：

1. **gateway 每次请求 new 一个 `http.Client`**：每个 client 带自己的 Transport/连接池，
   高并发下疯狂新建 TCP 连接，把 Windows 临时端口（TIME_WAIT）占满。
   修复：共享包级 `upstreamClient` / `streamClient`（Transport 连接池复用）。
2. **billing/reconciler 的 gorm 池无限流**：默认 MaxOpenConns 无上限，压测下连接数暴涨。
   修复：`SetMaxOpenConns(50)` / `SetMaxIdleConns(20)` + 连接生存期。

**面试点：Go 的 `http.Client` 必须复用。** `http.Client` 是并发安全的，连接池在 Transport 里；
每次 new Client = 每次新建连接池 = 连接风暴。这是 Go 新手最常见的生产事故之一。

### 2.6 rebuild 竞态修复：对账的两个 job 并发特性不同（压测揪出的第二个 bug）

压测发现：**RebuildAll 与在途 Reserve/Settle 竞态，会漏掉 pre 预占**。

Reserve 是「Redis 先扣 pre → 再插 DB 行」。若 RebuildAll 恰在这两步之间读到账本：看不到该行
→ 算出「这笔不该扣」→ `SET` 覆盖 Redis → 这笔 pre 永久漏掉（之后 Settle 只补扣 delta，不补 pre）。
压测里余额比账本高 +628（6 笔 pre 泄漏）。

**设计取舍**：对账的两个 job 并发安全性不同——

- **SweepOnce（真正的对账）**：只扫 `created_at < now-grace` 的**超龄** pending 行，走 billing
  幂等 RPC，和在线事务天然不冲突，**压测期间可以放心跑**；
- **RebuildAll（重建投影）**：是「用账本覆盖 Redis」的维护操作，**不能和高峰在途事务并发**。
  修复：压测期间只跑 sweep（`-no-rebuild`），流量停止后再跑一次 rebuild 收敛投影
  （loadtest 断言前自动执行）。

面试答案：重建余额是**低频维护操作**，正确姿势是流量低峰执行，或用分布式锁把 rebuild
和 reserve/settle 串行化——本项目选择了「低峰执行 + 事后收敛」，并在文档里讲清了为什么。

## 3. 数据流：一次故障切换

```
客户端 POST /v1/chat/completions
  → gateway 中间件（鉴权/幂等/限流）
  → router.Route("mock-model")          # 加权随机 → mock-a
  → billing.Reserve                     # 预扣，生成 bill pending
  → 转发 mock-a → 返回 500（注入故障）
  → Report(a, false)                    # 熔断计数 +1
  → Route("mock-model", exclude=[a])    # 排除后 → mock-b
  → 转发 mock-b → 200
  → Report(b, true)                     # 熔断清零
  → ReportUsage + Settle                # 按实际结算，bill settled
  → 客户端收到 200
# mock-a 连续 5 次被打到 → OPEN，从候选集移除 → 后续请求直接走 b/c
# 冷却后 HALF-OPEN 放 1 个探测 → 治愈则 CLOSED，仍坏则 OPEN
# 累计 20 连败 → providers.status=2（AutoBan，持久），人工解除
```

## 4. 面试 Q&A（附参考回答）

### Q1：熔断为什么有两个层（内存熔断 + 持久 AutoBan）？一个不行吗？

熔断快：5 连败就 OPEN，兜住**瞬时抖动**，provider 自愈后自动回 CLOSED，无需人工。
但它只活在进程内存里——网关重启就清零，且不同实例各自独立。AutoBan 是持久层：累计 20
连败说明**持续不稳定**，写进 MySQL 的 `status=2`，任何实例（哪怕刚重启）都不再选它，
直到人工解除。两层的阈值一个「快」一个「狠」，是「快速自愈」和「长期隔离」的分工。

### Q2：HALF-OPEN 探测失败为什么会回 OPEN，而不是再放一个探测？

探测的意义是「用最少的代价验证节点是否恢复」。放一个探测已经能得出结论：没恢复。
如果探测成功才回 CLOSED。否则每次冷却都放一个探测，OPEN 状态形同虚设（等于一直在试）。
探测失败回 OPEN 后再冷却一轮，才允许下一个探测——避免一个坏节点被反复试探浪费流量。

### Q3：探测请求发出去，网关崩了没人回报，会不会永久卡在探测中？

会——所以有**探测超时**：`probeInFlight` 记录了 `probeSince`，30s 无回报就释放探测位，
放行下一个探测。任何「等外部回报」的状态机状态都必须有超时兜底，这是通用原则。

### Q4：failover 为什么不能重试同一个 provider？

纯加权随机重试，可能连续 3 次都选到坏节点（`(5/9)³≈17%`，压测实测触发 502）。
failover 的语义是「换一个没试过的节点」：网关维护 `tried` 集合，重路由带 `exclude` 参数。
这也是「失败后重试」的一般性正确姿势——重试目标要有**去重/排除**，否则白重试。

### Q5：流式传输中途断了，为什么绝不重发上游？

流中途断开，分不清是「客户端断的」还是「上游断的」；如果是上游已经跑了一半并可能已经计费，
重发另一个 provider = **同一请求被两个 provider 执行 = 双扣上游**。这是 M3 的规则：
**只有首个字节前失败才重试**。流中途失败的处理是「保持 pending，交给对账收敛」。

### Q6：压测为什么会炸出「端口耗尽」？怎么定位的？

错误 `Only one usage of each socket address` 是 Windows 下临时端口（TIME_WAIT）耗尽的典型表现。
定位靠日志：billing 连 MySQL 全在报这个错。根因不是 MySQL 本身，而是**调用方疯狂建连接**：
gateway 每次请求 new `http.Client`（新 Transport=新连接池），加上 billing 的 gorm 池无上限，
几百 RPS 就把临时端口挤爆。修复就是复用 `http.Client` + 限连接池。

### Q7：为什么压测要断言「Redis 余额 == 账本求和」，而不是只报吞吐？

吞吐高但钱算错 = 事故。余额守恒断言：`Redis == initial - Σsettled - Σpending`，用**独立 SQL**
从 bills 表重算一遍，跟 Redis 对比。它一次性验证三件事：不超卖（余额没变负）、不丢钱
（没多扣）、幂等（没重复结算）。这是「计费系统正确性」的最终裁决，比任何单测都硬。

### Q8：压测期间跑对账，为什么不会干扰压测？

对账 sweep 只处理超龄（`created_at < now-grace`）的 pending 行，压测 30s 内的账单都远不够
宽限期，所以 sweep 是 no-op；它用 billing 幂等 RPC 写库，重复执行安全。真正的坑在 RebuildAll——
它会覆盖 Redis，和在途事务竞态漏钱（2.6）。所以压测只跑 sweep，rebuild 在流量停止后跑。
**这也说明：对账任务要按「并发特性」分开设计，不能一刀切。**

### Q9：AutoBan 之后怎么恢复？

人工 SQL：`UPDATE providers SET status=0, consecutive_fail=0 WHERE id=1`，然后重启 router
（清内存熔断态）。场景脚本演示了完整闭环：打挂 → AutoBan → SQL 解除 → 重启 router →
mock-a 回归候选集（20 次 /route 选中 14 次）。
