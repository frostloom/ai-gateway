> 上一篇：[02-m2.md](02-m2.md)（非流式全链路）· 下一篇：[04-m4.md](04-m4.md)（对账收敛）
> 看完这篇，你应当能讲清楚：SSE 流式怎么逐帧透传、**流式计费难在哪**、客户端断连后钱怎么办。

## 0. 这个里程碑在干什么（30 秒版本）

大模型调用是**流式**的（token 一个接一个吐出来）。M3 把网关升级成 SSE 中继：

```
客户端 ←── text/event-stream ── 网关 ←── text/event-stream ── mock-provider
         逐帧透传 + 每帧 Flush            增量内容帧 → usage 帧 → [DONE]
```

**计费规则一句话**：只有「上游产出了完整结果（网关拿到 usage 帧）」才结算按实际扣；其余情况一律不结算，**账单保持 pending，交给 M4 对账冲正**。

---

## 1. 概念层（先懂概念，再看代码）

### 1.1 SSE 协议是什么

Server-Sent Events：服务端**持续**往一个 HTTP 连接里推文本，`Content-Type: text/event-stream`。格式按行：

```
data: {"choices":[{"delta":{"content":"你"}}]}\n\n   ← 每帧以空行分隔
data: {"choices":[],"usage":{...}}\n\n              ← 终帧：带实际用量
data: [DONE]\n\n                                     ← 结束哨兵
```

- 每个 `data:` 行 + 空行 = 一帧；
- 客户端（curl -N / EventSource / OpenAI SDK）按帧消费；
- 普通 HTTP 响应是「一次给完」，SSE 是「一段一段给」。

### 1.2 流式计费为什么难？（核心考点）

非流式：请求完 → 拿到 usage → 一次结算，边界清晰。

流式：**没有明确的「请求结束」时刻**，只有状态序列：

| 状态 | 含义 | 计费决策 |
|---|---|---|
| 客户端断连 | 客户端走了 | 上游可能还在跑 |
| 上游中断 | provider 挂了/网络断 | 流没跑完 |
| 网关崩溃 | 网关自己挂了 | 谁都不知道发生了什么 |
| 正常完成 | 网关收到 usage 帧 + `[DONE]` | **按实际结算** |

**难点**：网关在「客户端断连」和「上游中断」发生时，**无法可靠区分**——可能是上游根本没跑完（不该收），也可能是跑完了只是客户端先走了（该收）。

### 1.3 本项目的解法：以「完整终态」为准 + 对账兜底

```
结算 ⟺ 网关收到了 usage 帧（上游确实产出了完整结果）
其他任何情况 → 账单保持 pending → M4 对账统一收敛
```

- **拿到 usage → 结算**，哪怕此刻客户端已经断连（「上游跑完就算数」）；
- **没拿到 usage → 保持 pending**，不猜、不冲正，交给对账用 `usage_reported_at` marker 一锤定音（M4）。

为什么网关不自己冲正？因为流式中断的边界太模糊（谁先断？有没有 half-usage？网关自己猜会误判）。统一交给对账，逻辑只有一处、可审计。

### 1.4 逐帧 Flush：客户端「增量可见」的关键

`http.ResponseWriter.Write()` 默认把数据**缓冲**，响应结束后才一次性发出。SSE 必须每写一帧就 `Flush()`，客户端才能看到「正在生成」。

```
w.Write(line); flusher.Flush()   ← 每个 data 行后都 Flush
```

没 Flush → curl -N 会一直等，像死了一样。

### 1.5 流式上游的 HTTP client 不能设总超时

非流式给 `http.Client` 设 `Timeout: 2min`。流式不行——一个正常的流可以持续几分钟到几十分钟，总超时会**误杀长请求**。所以流式用无超时的 client，靠 `context`（客户端断连）和每行读取来管控生命周期。

## 2. 代码导读（文件 → 关键函数 → 数据流）

### 2.1 核心：relayStream（[internal/gateway/handler/chat.go](../../internal/gateway/handler/chat.go)）

```
① 设置 SSE 响应头：Content-Type: text/event-stream
② 转发上游（Accept: text/event-stream），无总超时的 http.Client
③ 循环：
     line, err := reader.ReadBytes('\n')      // 逐行读上游
     w.Write(line); flusher.Flush()           // 逐行透传 + Flush
     if 写失败 → 客户端断连 → break            // 不结算，保持 pending
     if parseUsageFrame(line) → 记录 usage
     if line == [DONE] → break                // 正常结束
④ 循环结束：
     usage != nil → ReportUsage + Settle（按实际）   // 上游跑完就算数
     usage == nil → 保持 pending（M4 冲正）
```

### 2.2 parseUsageFrame：怎么识别「这是 usage 帧」

[internal/gateway/handler/chat.go](../../internal/gateway/handler/chat.go) 的 `parseUsageFrame`：

```go
// 只有当 choices 为空数组 + usage 非空才返回
// 这是防误判的关键：内容增量帧也带 choices，但它们没有 usage
```

OpenAI 的流式协议里，**终帧**长这样：

```json
{"id":"...","choices":[],"usage":{"prompt_tokens":7,"completion_tokens":100}}
```

而内容帧是 `choices:[{delta:{content}}]`。所以判断条件「`len(choices)==0 && usage != nil`」精确命中终帧，不会把内容帧误当成结算依据。

### 2.3 mock-provider 的流式（[cmd/mock-provider/main.go](../../cmd/mock-provider/main.go)）

```
role 帧 → 内容增量帧（分 8 块，每块间隔 50ms，让流可观察）→ usage 帧 → [DONE]
```

间隔 50ms 很重要：**让「增量可见」和「kill 客户端测试」可复现**。

### 2.4 结算收尾与 M2 相同的原则

`settleAndLog` 复用 M2 的 `BackgroundCtx(10s)`——**绝不复用请求 ctx**。客户端断连时请求 ctx 被 cancel，结算用它就丢了。

## 3. 数据流：一次流式请求的时序

```
客户端              gateway            mock-provider
  │ POST stream=true │                  │
  │─────────────────>│  鉴权/限流/幂等   │
  │                  │──Reserve───────>│
  │                  │<──OK(bill_id)────│
  │                  │──POST stream────>│
  │                  │<─ role 帧 ───────│
  │<─ data: role ────│  Flush           │
  │                  │<─ content 帧 1 ──│
  │<─ data: 内容 1 ──│  Flush           │
  │                  │<─ content 帧 2 ──│
  │<─ data: 内容 2 ──│  Flush           │
  │      ...（增量）   ...               │
  │                  │<─ usage 帧 ──────│
  │<─ data: usage ───│  Flush           │
  │                  │<─ [DONE] ────────│
  │<─ data: [DONE] ──│                  │
  │                  │──ReportUsage────>│
  │                  │──Settle─────────>│
  │                  │<──delta──────────│
```

**kill 客户端路径**（在 content 帧 2 后掐断）：
```
  │<─ data: 内容 2 ──│  Flush           │
  ✂ 客户端断开连接
  │                  │<─ content 帧 3 ──│
  │   写 w.Write 失败 → break            │
  │   没有 usage → 保持 pending ────────>│  (M4 会冲正)
```

## 4. 面试 Q&A（附参考回答）

### Q1：SSE 和普通 HTTP 响应有什么区别？

普通响应「一次给完」，SSE 是「一条连接持续推帧」。SSE 是单向的（服务端→客户端），适合流式生成；WebSocket 是双向的，适合聊天/实时协作。大模型流式用 SSE 就够了，不需要 WebSocket 的双向能力。

### Q2：为什么必须逐帧 Flush？不 Flush 会怎样？

HTTP 写缓冲默认攒着，响应结束才一次性发。逐帧 Flush 才让客户端看到「正在生成」的增量。**没 Flush = 客户端干等，看起来像卡死**。这是流式网关最容易翻车的地方之一。

### Q3：怎么判断流「跑完了」？

收到 usage 帧（`choices:[]` + `usage`）或 `[DONE]`。本项目以 **usage 帧**为结算依据（它有实际 token 数）；`[DONE]` 是协议层结束哨兵，可作辅助。

### Q4：客户端断连了，钱怎么办？

**不结算，账单保持 pending，交给 M4 对账冲正（全退）**。为什么不立即退款？因为「断连」和「上游跑完」在网关侧难以可靠区分——与其猜，不如留个明确状态（pending + 无 marker），让对账用同一套规则处理「网关崩溃/客户端断连/上游中断」三种情况。**逻辑只写一处，可审计、不误判**。

### Q5：那「客户端断连但上游跑完 → 照收」怎么实现？

如果网关在客户端断连**之前**已经读到 usage 帧，循环结束时会结算（usage 已到手）。规则是「**以 usage 是否到手为准，不以其后续能否送达客户端为准**」——计费依据是上游有没有产出完整结果，跟客户端在不在无关。

### Q6：为什么流式失败不立即退款，而非流式要？

非流式：一次请求一发响应，「首个字节前失败」边界清晰（建连失败/HTTP 错误），网关能确定上游没产出 → 直接退款。流式：边界的判断发生在**连接存活期间**，断连可能是客户端先走、也可能是上游先挂，网关无法知道「这是不是一次完整请求」→ 不猜，留给对账。**「边界清晰的立刻处理，边界模糊的交对账」是分布式系统的一条通用原则**。

### Q7：为什么 usage 帧必须要求 choices 为空？

内容增量帧也带 `choices` 但没 usage。如果不检查 `choices` 为空，会把内容帧误当成结算依据（usage 是 nil，跳过还算好；一旦协议变动就危险）。**用「choices 空 + usage 非空」精确定位终帧**，是防御性解析。

### Q8：流式为什么不能给 http.Client 设总超时？

一个正常流式生成可以持续几分钟。总超时会误杀正常的长请求。生命周期靠 `context`（客户端断连取消）和逐行读取管控。**超时的粒度要和语义匹配**：非流式用请求级总超时，流式用连接级取消。

## 5. 验证结果（本机真实跑过）

```
$ bash scripts/m3/scenario.sh
  stream -> deltas=8 done=1 usage={'prompt_tokens': 7, 'completion_tokens': 100}
PASS  流式有增量帧
PASS  收到 [DONE]
PASS  usage 帧带 completion>0
  latest settle row: 107	99	7	100
PASS  结算按实际（actual=prompt+completion）
  killed -> killed after 2 frames ; new bill id=13 status=pending
PASS  掐断后 reserve 行保持 pending
M3 scenario: 5 项全部 PASS
```

数据库证据：
- 流式完整跑完 → `actual=107, delta=99`（**按实际 7+100，不是按预占 8**）；
- 掐断连接 → 该请求 reserve 行 `status=pending`，无结算——等 M4 冲正。

**对照 M3 验收**：curl -N 看到增量与 `[DONE]` ✓ · 按实际扣不按预占 ✓ · kill 客户端后账单保持 pending ✓
