## 先练一段一分钟介绍

> 这是一个 Go 多租户 AI 模型网关，对外提供 OpenAI 兼容接口。请求经过鉴权和限流后，网关先选择上游，再向计费服务申请预扣，接着转发模型请求并按用量结算。当前默认批量模式用 Redis 维护实时余额，账单和余额变动先暂存在进程内，后台默认每 5 秒批量写入 MySQL；Kafka 异步承载事件明细。项目还包含基于工具调用的智能客服，租户身份和工具权限由服务端控制，写操作需要用户确认。

## 一次请求如何走完

1. 请求经过网关鉴权与限流。`Chat` 读取并解析请求，从上下文取得 tenant、API key 和 request ID，估算输入 token。
2. 网关先通过 router 为模型选择 provider；没有可用上游时直接返回，尚未发生预扣。
3. 网关带 request ID、租户、模型、估算 token、最大输出 token 等调用 billing `Reserve`。余额或订阅额度不足会拒绝。
4. 预扣成功后转发到上游；非流式与 SSE 分不同路径。正常结束后依据获取到的用量走结算；异常是否冲正或保留要看具体失败位置和配置。
5. 默认批量模式下，余额由 Redis 路径调整；账单和余额变化进入内存批次并周期性写 MySQL。事件可以异步发往 Kafka。

从 [gateway Chat](../../internal/gateway/handler/chat.go) 开始，跟到 [billing Reserve/Settle/Reverse](../../internal/billing/store/mysql.go)，再看 [批量刷账](../../internal/billing/store/ledger_batch.go)。不要只看函数名：订阅额度、余额、流式和非流式是不同分支。

## 高频追问与参考回答

### 为什么要预扣，不能请求结束后直接扣吗？

模型调用之前不知道最终用量，但需要先限制余额不足用户的消费。系统根据估算输入和最大输出等信息预扣，结束后按实际用量结算。这样能控制并发消费风险，但估算、失败处理和最终结算仍需分别设计。

### Redis 为什么是当前实时余额的依据？MySQL 做什么？

默认批量模式在 Redis 上完成实时余额检查与调整，MySQL 保存批量写入的账单及余额变化。MySQL 在刷盘前可能滞后；它不是每个时刻都能直接代表最新余额。配置 `BILLING_LEDGER_BATCH_SECONDS=0` 会关闭批量，不能把这套说明套到所有模式。

### 假设余额 100，两次请求都想预扣 80，会发生什么？

同一余额检查与扣减放进 Redis Lua 原子执行：一次扣成功后余额变为 20，另一次因不足被拒。还要结合请求 ID 幂等和具体业务分支看重放；Lua 原子性只覆盖 Redis 脚本执行，不代表跨 Redis、内存、MySQL 的操作整体原子。

### 每 5 秒刷一次，是否意味着最多丢 5 秒数据？

不能这么保证。5 秒是默认调度间隔，不是持久化完成的硬时限；数据库故障、排队或重试可能更久。刷盘前批次在进程内，进程异常退出存在未落盘窗口。要结合部署持久化、事件及故障记录判断，不能保证所有故障都自动恢复。

### Redis 与 MySQL 不一致，为什么不直接用 MySQL 覆盖 Redis？

批量模式下 MySQL 可能还没收到已经发生的 Redis 扣款。直接用旧值覆盖可能把扣过的钱加回去。应先检查在途批次、账单与事件，再根据具体恢复流程处理；相关敏感路径在有未处理变动或差异时会拒绝继续。

### Kafka 是账本吗？它参与扣钱吗？

当前默认方案中 Kafka 用于异步传递计费明细，余额仍通过 Redis 处理，MySQL 由批次写入。Kafka 没有和 Redis 扣款组成一个跨系统原子事务。代码里存在消费者写账的其他实现，但当前 billing 启动入口拒绝开启 `BILLING_LEDGER_VIA_KAFKA=1`，不能把它说成默认运行路径。

### 同一个 request ID 重试，如何避免重复扣费？

系统使用 request ID、Redis guard、请求内容指纹、账单状态及数据库约束等机制处理不同阶段的重放；不同内容复用同一个 ID 还需要识别冲突。面试中应按具体阶段解释，不能只说“加了唯一索引就实现全链路恰好一次”。

### 什么时候能切换上游？为什么流中途通常不能重试？

代码在特定的首字节前失败场景下尝试其他 provider，已试节点会排除。若流已经向客户端输出，重发可能造成内容重复，也可能带来上游重复费用，因此不能直接重放。客户端没有收到内容也不必然证明上游没有执行，实际处理要看失败类型和保守配置。

### 用户说“帮我退款”，怎么防止模型越权？

模型输出只是候选工具及参数，不是授权。服务端从已验证的身份得到租户，独立校验参数和权限；涉及写操作先生成预览并等待确认。JEV 是选择性判断与快速路径的一部分，不能替代服务端的鉴权、校验和确认。

### 1220 条评测是不是都通过了？

不能这么说。本地一批双臂采集状态是 1220 完成、0 失败，这不是任务全部通过的结论；另一批 Langfuse 相关运行状态是 1218 完成、2 失败，2436 个本地 grade 文件均为 `{}`，不能证明有效评分或平台读回。不同实验的模型、分母、评分规则和失败处理应分开描述。

### 你们的吞吐量是多少？

可以说：2026-11-10 一次资源受限的隔离环境测试，用模拟上游，64 并发约 772 请求/秒；256 并发复测约 804 请求/秒、2 万请求零失败。512 并发突发触发连接超时保护。不能将这些数字说成真实模型推理吞吐、稳定生产容量或对其他产品的公平对比。详见[压测记录](../online-load-test-2026-11-10.md)。

## 两小时练习

- 20 分钟：不看文档画请求链路，核对路由和预扣的顺序。
- 35 分钟：在代码里追一次 `Reserve` → `reserveBatched` → 批次刷账，解释 Redis 与 MySQL 各自保存什么。
- 20 分钟：看 gateway 的非流式与 SSE 分支，解释何时重试及何时保留未知状态。
- 20 分钟：看客服身份和写工具确认，自己举一个越权请求说明会在哪里被拦。
- 25 分钟：脱稿讲项目一分钟，回答上面的问题；对不确定的地方回到代码或记录，不编数字。
