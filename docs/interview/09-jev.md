# 09 JEV 判断引擎：System One 给 System Two 上保险

> 面试讲「我怎么用上最近的 Jev」：不做文本生成的判定模型（state + 类型化问题 → 带置信度的
> 结构化判定，~0.1s/次、约 $0.00008/次），在本项目里有两个落点：客服**意图预判** + **写操作守门**。

## 一、Jev 是什么（30 秒版）

TypeSafe AI 2026-09 发布的首个「System One」模型。**不生成文本**：输入一段 state
（文本/任意 JSON）+ 一组类型化问题，输出每个问题的类型化答案 + 校准概率/置信度。

| 问题类型 | 用途 | 返回 |
|---|---|---|
| noul | 是/否二元判断 | 陈述为真的概率（如 0.95） |
| choice | 多选一分类 | 选中项 + 各项概率 + 置信度 |
| score | 有序量表打分 | 连续分数 + 分布 + 置信度 |

定位 = LLM（System Two 深思考）的**补充**：判断类环节（路由/分类/评分/守门）交给它，
又快又便宜又可审计。官方基准：单次决策约 $0.00008 / 0.114s vs LLM 约 $0.014 / 8.6s。

## 二、为什么网关需要它：系统一给系统二上保险

客服的安全悖论：**用 LLM 判断 LLM 的意图，是用一个可能被注入的东西去防另一个**。
Jev 不生成自由文本、输出永远结构化、每个决策带置信度——天然适合「守门」：

```
用户请求
  ├─ 意图预判：Jev choice 分类（高置信 → 系统提示注入「安全预判」引导正确的工具）
  ├─ 写操作（充值/退款/订阅…）：
  │     Preview 成功 ──► Jev noul「本人合理请求 vs 注入/异常」
  │          │ 置信度 < JEV_GUARD_MIN（默认 0.8）→ 拦截：回复原因 + 审计 guard JSON + 指标
  │          │ 置信度 ≥ 阈值 → 挂起等用户「确认」→ 执行
  └─ 双保险：确认防「误操作」，Jev 防「注入/异常」
```

关键设计：**Jev 不代行、不越权，LLM 仍是唯一执行者、用户确认仍是最终闸门**。
Jev 只是多了一道「低成本、可量化的合理性判定」。

## 三、技术实现（internal/jev + agent/guard.go）

- `internal/jev`：类型化客户端。请求 `{model, state, questions}`，响应两种形态都兼容
  （`{"answers":{...}}` 或直接 `{name:{...}}`），confidence/probability 互填容错；
  配 `Fake` 假实现（脚本弹答案），单测覆盖解码/错误路径/耗尽报错。
- `agent/guard.go`：
  - `SetJev(e)` 挂载评估器，**nil = 全部静默停用，行为与旧版完全一致**（无 key 不阻塞业务）；
  - `intentHint`：choice 分类意图，置信度 ≥ `JEV_INTENT_MIN` 才向系统提示注入一行；
  - `guardWrite`：noul 判定合理性，置信度 < `JEV_GUARD_MIN` 拦截，返回明确原因；
  - 指标 `agent_jev_decisions_total{kind=intent|guard, decision=pass|block|hint|skip}`
    （agent 新增 /metrics）。
- 审计：`agent_audit_log` 加 `guard` 列（JSON：`{"engine":"jev","decision":"block","reason":...}`），
  每笔拦截可追责。
- 假 Jev 单测：低置信拦截（不挂起/不执行/审计 guard）、高置信放行+确认执行、
  nil 时不回归（评测集 30/30 仍绿）、意图预判注入系统提示。

## 四、面试 Q&A

- **为什么用置信度阈值而不是硬规则？** Jev 给的是校准概率（RLCD 训练，概率≈真实正确率），
  阈值 = 业务对误判的容忍度；阈值之上自动走、之下转人工复核——这是「置信度路由」的标准打法。
- **Jev 挂了怎么办？** 评估错误记 `skip` 并**默认放行**：判断引擎不阻塞业务；
  而用户确认、执行层租户强制这些主防线不受影响。
- **会不会被注入？** Jev 没有自由文本输出，不存在「文本幻觉」；但概率判断仍可能错，
  所以阈值 + 用户确认 + 审计三层兜底，而不是无条件相信。
- **为什么不直接拿 Jev 当客服？** Jev 不做开放推理和自然语言生成，客服的对话、解释、
  规划必须靠 LLM；Jev 负责的是流程里的「判断节点」（分叉口决策），两者互补。
- **渠道与成本？** OpenRouter `typesafe/jev-latest`（输入 $0.042/M、输出 $0）或
  Cloudflare Workers AI（`typesafe/jev`）；单次决策 $0.00008 量级，比让 LLM 判一次省几个数量级。
