# M4 里程碑文档：对账收敛（Reconciliation）

> 上一篇：[03-m3.md](03-m3.md)（SSE 流式）· 下一篇：[05-m5.md](05-m5.md)（路由熔断+可观测+压测）
> 看完这篇，你应当能讲清楚：**网关崩溃后「预扣已扣、结算没落」的账由谁来收、怎么收、为什么收不错**。

---

## 0. 这个里程碑在干什么（30 秒版本）

网关可能在**任意时刻**崩溃——钱已经预扣了（Redis 减了、MySQL 落了 reserve 行），但结算还没做。这笔账挂在 `pending` 状态没人管，额度被卡死。

M4 加了一个独立的 **reconciler（对账）服务**，定期把滞留的 pending 账单收敛掉：

```
pending + 无 marker（usage_reported_at 为空）→ 流没跑完 → 冲正全退
pending + 有 marker                → 流已跑完 → 补结算（按实际扣）
```

以及最后一道保险：**从 MySQL 账本重建 Redis 余额**（`RebuildBalance`），把任何脏投影洗回来。

---

## 1. 概念层

### 1.1 为什么需要对账？（核心考点）

任何「先扣钱、后结算」的系统，都有个天然窗口：**预扣成功 → 结算失败/进程崩溃**。此时：

- Redis 里钱已经扣了；
- MySQL 里 reserve 行是 `pending`；
- 没有任何人会把钱退回来或结算掉 → **额度永久卡死**（用户少额度，公司多记应收，两边都不对）。

**为什么不能让网关自己冲正？** M3 说过：流式中断的边界太模糊（客户端断连 / 上游中断 / 网关崩溃，三者无法可靠区分）。网关自己猜会误判（可能把「跑完了只是没来得及结算」的钱退了，也可能把「没跑完」的钱收了）。所以：

> **网关不做最终裁决，只留一个明确的中间状态（pending + marker），交给对账用统一规则裁决。**

规则只写一处 → 可审计、可推演、不会出现"这个网关这么判、那个网关那么判"。

### 1.2 marker：对账的「分水岭」

M2 设计时就留了这个伏笔：`ReportUsage` RPC 把 `usage_reported_at` 写进 reserve 行——这是**持久化 marker**，证明「上游确实产出了完整结果」。

对账就靠它一锤定音：

| reserve 行状态 | 含义 | 对账动作 |
|---|---|---|
| `pending` + 无 marker | 流从未产出完整结果（网关死在 ReportUsage 前 / 客户端断连 / 上游中断） | **Reverse 全退** |
| `pending` + 有 marker | 流已跑完（ReportUsage 成功了），但 Settle 没落（网关死在 Settle 前） | **补 Settle**（按记录的 actual） |

没有这个 marker，对账就只能瞎猜「这笔是退还是收」。有了它，退和收**只由一次幂等写操作决定**。

### 1.3 宽限期（grace）：别碰在途请求

对账不能扫到 pending 就处理——那会把**正在正常流式**的请求（此刻也是 pending，钱刚预扣）给冲正掉，灾难。

所以只扫 `created_at < now - 宽限期` 的行。宽限期 > 最大流式时长，保证正常请求在宽限期内必然完成（或 settle 或 reverse）。只有超过宽限期还挂着 pending 的，才可能是崩溃残留。

> 面试答「对账会不会误伤正常请求」就靠这一条：**宽限期 + marker 双重保护**。

### 1.4 对账本身幂等：可以反复跑

对账调用的 Reverse / Settle 都是幂等 RPC（M2/M3 已建）：

- 同一 request_id 只退一次、只结一次（`billing:delta:{request_id}` guard + 唯一索引）；
- 已 settled 的再冲正 → no-op；已 reversed 的再结算 → no-op。

所以对账**不需要分布式锁、不需要精确一次**——两个 reconciler 同时跑、跑重复了，结果一样。这是幂等设计带来的最大工程红利：**把「恰好一次」的难题降级成「至少一次 + 幂等消费」**。

### 1.5 重建投影：权威账本 vs 缓存投影

系统里有**两份余额**：

- **MySQL bills = 权威账本**（谁欠多少、收了多少，全部有行可查）；
- **Redis `billing:balance` = 热投影**（供并发扣减，快）。

平时以 Redis 为准（快），Redis 挂了/脏了怎么办？**从账本重建**：

```
balance = tenants.initial_quota
        - Σ(pending reserve 行的 pre_quota)     // 在途预扣：钱已从投影扣走，必须继续扣着
        - Σ(settled settle 行的 actual_quota)    // 已结算的净消耗
```

> **面试点**：为什么重建要减 pending 预扣？因为预扣的钱在 Redis 里已经扣了，如果不减，重建后余额虚高，等补结算时会把实际 150 的账按「余额充足」多退 → 超扣。**投影必须和「扣减动作已发生的事实」一致。**

## 2. 代码导读

### 2.1 对账服务：[internal/billing/reconciler/reconciler.go](../../internal/billing/reconciler/reconciler.go)

```
SweepOnce(ctx):
  ① SELECT * FROM bills
     WHERE phase='reserve' AND status='pending' AND created_at < now-grace
  ② 对每行：
       无 marker → billing.Reverse(request_id, reason="recon:no_usage")
       有 marker → billing.Settle(request_id)
  ③ 全部走幂等 RPC，可安全重复执行
```

**架构决策**：reconciler **只读 MySQL 扫描**（它不写账），写操作一律走 billing 的 gRPC。这样「写账的入口始终只有 billing 一家」，对账只是「发现 + 触发」。写账逻辑不重复，就不会出现两个版本互相矛盾。

### 2.2 入口：[cmd/reconciler/main.go](../../cmd/reconciler/main.go)

- 默认常驻，每 `-interval`（默认 30s）跑一轮；
- `-once` 只跑一轮就退出（场景脚本 / 手动验证用）；
- `-grace` 宽限期可配（生产 600s，场景测试设 1s 模拟「早过了宽限期」）。

### 2.3 重建投影：[internal/billing/store/mysql.go](../../internal/billing/store/mysql.go) 的 `RebuildBalance`

```go
bal := tenant.InitialQuota - pendingPre - settledActual
rdb.Set(BalanceKey(tenantID), bal, 0)
```

三个数都是 SQL 聚合，权威、可审计。`reconciler.RebuildAll` 每轮对每个活跃租户调一次。

### 2.4 M4 意外收获：settle.lua 的三个真 bug

写 M4 测试时，**第一次真正走到退款路径**（之前 M2/M3 场景都只测正常结算和 pending），立刻暴露了 [settle.lua](../../internal/billing/store/lua/settle.lua) 的潜伏 bug，已修复：

| bug | 现象 | 修复 |
|---|---|---|
| 返回余额算错 | 正 delta（补扣）时返回 `bal+delta`，实际余额是 `bal-delta`（返回比实际高） | `return {1, bal - delta}` |
| 透支守卫判错 | `bal+delta<0` 挡不住透支（bal=50, delta=99 → 50+99≥0 放行 → DECRBY → -49） | 只有补扣才查：`delta>0 && bal<delta` |
| Reverse 符号传反 | 退款传 `+pre`，被当作「再补扣」→ **二次扣款** | 传 `-pre`（delta 语义统一为「新余额 = 旧余额 - delta」） |

**这也是个很好的面试故事**：修复 new-api 的缺陷时，自己也差点在同样的地方踩坑——「**退款的方向搞反**」是计费系统最经典、最贵的 bug（直接扣错钱）。被真测试 + 真 Redis 逮住，而不是上线后被投诉。

## 3. 数据流：一次对账收敛

```
场景：网关在 ReportUsage 之后、Settle 之前被杀。

gateway(已死)           billing              reconciler
  │ 预扣(pre=100) ──────>│   Redis: -100        │
  │<─ bill_id ───────────│   MySQL: reserve(pending) │
  │ ReportUsage(50,100)─>│   MySQL: usage_reported_at=now  ← 持久 marker
  ✂ 网关崩溃（Settle 没发）
                        │                     │  每 30s 扫描
                        │                     │→ 发现 pending+marker，已过宽限期
                        │<── Settle(补结算) ────│
                        │   actual=150, delta=50
                        │   Redis: -50  │  MySQL: reserve→settled, 写 settle 行
```

对账前 Redis 被扣了 `100+50=150`，账本显示 `actual=150` → **一分不差**。

## 4. 面试 Q&A（附参考回答）

### Q1：网关崩溃了，凭什么对账能「知道」这笔该退还是该收？

靠 M2 就埋好的持久 marker：`usage_reported_at`。**有 marker = 上游已经产出完整结果**（ReportUsage 在流结束后才调用），只差结算 → 补结算。**无 marker = 流从未产出完整结果** → 全退。这是设计层就决定的「分水岭」，对账只是读它做裁决。

### Q2：对账会不会误伤正在正常进行的请求？

不会，两层保护：①**宽限期**——只扫 `created_at` 早于「最大流时长+宽限期」的行，正常请求在宽限期内必然结束；②**marker + 幂等**——就算极端并发误扫，Reverse/Settle 幂等，已在跑的请求的结算不受影响（结算发生在流结束后，对账最多碰到状态冲突，也是 no-op）。

### Q3：为什么对账不用分布式锁？两个 reconciler 同时跑会怎样？

因为对账调用的 Reverse/Settle 都是**幂等**的：delta guard + 唯一索引保证「同一 request_id 恰好冲正一次」。两个 reconciler 同时跑同一笔，只有一个真正生效，另一个 no-op。**这是把「恰好一次」的难题降级成「至少一次 + 幂等消费」，工程上便宜得多。**

### Q4：Redis 余额和 MySQL 账本哪个是权威？不一致了怎么办？

**MySQL bills 是权威账本，Redis 是热投影**。平时并发扣减用 Redis（快、原子）；Redis 脏了/丢了，`RebuildBalance` 从账本重算投影覆盖。投影坏掉的唯一后果是「余额显示不对」，不会造成账目混乱——因为**每笔扣减都有 MySQL 行可追溯**。这就是「账本为主、缓存投影为辅」的经典分层。

### Q5：重建余额为什么还要减掉 pending 的预扣？

因为预扣的钱**已经在 Redis 投影里扣掉了**（这是"钱已扣"的事实）。如果重建时不减，投影虚高 → 后续补结算按「余额充足」处理 → 超扣。投影必须反映「扣减动作已发生」这个事实，哪怕该请求还没结算。

### Q6：对账多久跑一次？宽限期设多少？

本项目：每 30s 扫一轮，宽限期 10 分钟（大于 mock-provider 的最大流式时长）。生产上宽限期 = 你承诺的「最长一次流式调用时长」+ 安全余量。对账是低频兜底，不需要秒级。

### Q7：为什么对账写操作走 billing gRPC，而不直接写库？

**写账入口只有一家**。如果 reconciler 直接 UPDATE bills，就会有「billing 写账」「reconciler 写账」两套逻辑，将来改状态机容易漏改一处，出现两个版本互相矛盾。对账只做「发现 + 触发」，把裁决交给 billing 幂等 RPC——职责单一、可审计。

### Q8：你们怎么证明对账「收对了钱」？

验收脚本独立断言，不用程序自说自话：
1. 构造三种崩溃残留（Reserve 后无 marker / ReportUsage 后有 marker / 真 kill 网关中途）；
2. 跑对账后查 MySQL：无 marker → `reversed`，有 marker → `settled` 且 delta 正确；
3. **用独立 SQL 从账本算出应剩余额**（initial − Σ已结算 actual − Σ在途 pre），和 Redis 余额比对，必须相等。

### Q9：对账发现 Reverse 又失败了怎么办？

对账每轮都会重扫，**失败的留在 pending，下一轮再试**（对账天然自带重试）。直到成功或有人工介入。因为写操作幂等，重试永远安全。
