# M2 里程碑文档：非流式全链路

> 上一篇：[01-m1.md](01-m1.md)（原子预占）· 下一篇：[03-m3.md](03-m3.md)（SSE 流式）
> 看完这篇，你应当能讲清楚：一次 `curl` 请求在 4 个服务里是怎么流转的、为什么这么拆、计费为什么「先预扣后结算」。

---

## 0. 这个里程碑在干什么（30 秒版本）

M1 只有 billing 一个服务、一个「预占」动作。M2 把整条链路打通：

```
curl -X POST /v1/chat/completions
  gateway（鉴权·限流·幂等·编排）
    ├─ gRPC 问 billing：预占额度
    ├─ HTTP 问 router：该模型用哪个 provider
    ├─ HTTP 转发给 mock-provider（假 LLM）
    ├─ gRPC 告诉 billing：实际用量 + 结算（多退少补）
    └─ 把 provider 的响应原样还给客户端
```

**4 个服务，各自只干一件事。** 这就是微服务拆分。

---

## 1. 概念层（先懂概念，再看代码）

### 1.1 为什么拆成 4 个服务？（微服务拆分原则）

| 服务 | 职责 | 为什么单独拆 |
|---|---|---|
| **gateway** | 对外 HTTP 入口：鉴权/限流/编排 | 所有外部流量都从它过，是「门面」 |
| **billing** | 计费：预占/结算/退款/对账 | 账务是**独立生命周期**（请求结束了账还要对），且是正确性核心 |
| **router** | 选 provider：权重/熔断/容灾 | provider 上下线、故障切换是**独立运维域** |
| **mock-provider** | 上游假 LLM | 真实上游是第三方，天然独立 |

拆分的判断标准（面试要讲）：**是否独立变化、独立伸缩、独立故障**。billing 可以单独加节点抗压测；router 故障不该拖垮已建立的连接；gateway 重启不该影响计费正确性。

### 1.2 控制面 vs 数据面（本项目最值钱的架构概念）

- **控制面（gateway→billing）**：gRPC。一次请求只调用 2~3 次，低频、但必须正确（计费）。
- **数据面（gateway→router→provider）**：HTTP/SSE。高频、大流量、必须快（token 流）。

**为什么 gateway 不直接连 MySQL/Redis？** 因为「谁碰账」必须是**唯一入口**——如果 gateway 和 billing 都写 bills 表，幂等、事务、对账就全乱套。gateway 通过 gRPC 问 billing「给我扣 100」，billing 自己保证不超卖、不重复。**服务边界 = 数据所有权边界**。

### 1.3 API Key 为什么存 SHA-256？

明文 `sk-xxx` 一旦落库/落日志，泄露就是灾难。做法：

- 落库只存 `SHA-256(key)`（64 位 hex），校验时把请求里的 key 哈希后查表；
- 明文 key 只在 gateway 内存里算一次哈希，**永不跨服务传递**；
- 表里额外存明文前 8 位（`key_prefix`）用于人工排查（看日志知道是哪个 key，但拼不出完整 key）。

### 1.4 限流：滑动窗口（ZSET）为什么比固定窗口好

- **固定窗口**：按分钟分桶，桶内计数。缺陷——第 59 秒和第 61 秒各发 100 个请求，都通过（跨了两个桶），实际 2 秒内发了 200 个。
- **滑动窗口**：ZSET 记录每个请求的时间戳，统计「最近 N 秒内」有多少个。第 59 秒的请求会滑出第 61 秒的窗口，精准。

本项目用 **Lua 脚本**把「清过期 + 计数 + 插入」合成一步，原子执行（和 M1 reserve.lua 同思想）。

### 1.5 幂等键：409 挡住重复提交

客户端带 `Idempotency-Key: k-001` 提交请求。gateway 用 `SET idem:k-001 <req> NX EX 300s` 原子占位：

- 第一次：SET 成功 → 放行；
- 重复提交（300s 内同键）：SET 返回 nil → **409**，不重复计费、不重复出结果。

**取舍点（面试主动讲）**：我们选「409 拒绝」而不是「缓存上次响应重放 200」。重放需要存完整响应体（可能几 MB），只换来自动重试的体验。对 demo 场景，409 更简单也更诚实。真正的**幂等兜底**在 billing——`request_id` 重复时 Reserve/Settle 是 no-op（M1 的三层幂等）。

### 1.6 预扣 ×1.2 + 结算 delta：为什么不是直接扣实际？

调用开始时**只知道 prompt 估算，不知道实际用量**（输出还没生成）。所以：

1. **Reserve** 按 `est_prompt × 1.2` 预扣（留裕量，防大输出中途余额变负）；
2. provider 返回实际 `usage`（prompt + completion）后，**ReportUsage** 上报；
3. **Settle** 算 `actual = (prompt+completion) × ratio`，`delta = actual − pre`：
   - delta > 0 → 补扣（输出超出预扣裕量）；
   - delta < 0 → 退回（用得多估了）。

这就是 **TCC 里的「Try → Confirm」** 思路（预占对应 Try，结算对应 Confirm）——面试可以把这个模式说出来。

### 1.7 最容易踩的坑：结算绝不复用请求 ctx（本项目反复强调）

`context.Context` 是 Go 的标准「取消信号」机制。**客户端断开连接 → 请求 ctx 被 cancel**。

如果结算/退款用这个 ctx 调 billing：
- 客户端在收到响应前断网；
- 请求 ctx 被 cancel → gRPC 调用直接失败；
- **钱没扣，但用户拿到了结果 → 白嫖 bug**。

所以结算/退款必须用 `context.Background()` 派生出的独立 ctx：

```go
settleCtx, cancel := context.WithTimeout(context.Background(), 10*time.Second)
```

「**用请求 ctx 做对外转发（取消即止损），用后台 ctx 做计费收尾（必须做完）**」——这是本项目的核心工程决策之一。

### 2.2 chat.go 编排（面试必背的数据流）

[internal/gateway/handler/chat.go](../../internal/gateway/handler/chat.go) 的 `Chat`：

```
① 路由：router.Route(model)         → 选 provider（失败/无可用 → 503，没产生计费）
② 预占：billing.Reserve(...)        → 余额不足 → 402；成功 → 拿到 bill_id
③ 转发：POST {provider}/v1/chat/completions
       ├─ 用「请求 ctx」→ 客户端断连即取消上游，不浪费 provider
       ├─ 建连/HTTP 错误 → billing.Reverse 退款 → 502
       └─ 非 2xx → 透传上游错误体 + Reverse → 502
④ 收尾：billing.ReportUsage(实际用量)
        billing.Settle(delta)   ← 用「后台 ctx」，客户端断连也不丢
⑤ 返回：原样透传 provider 的 JSON
```

**每个错误分支都问一句「钱怎么办」**：
- 路由失败 → 没预占，不用退；
- 余额不足 → 预占被拒，不用退；
- 上游失败 → 已预占，必须 **Reverse 全退**；
- 上游成功 → 已预占，必须 **Settle 按实际**（或多退少补）。

这就是「**有借必有还，借还必相等**」的账务闭环。

### 2.3 settle.lua：为什么「结算」和「退款」共用一个 guard

[internal/billing/store/lua/settle.lua](../../internal/billing/store/lua/settle.lua)

- Reserve 之后，一条请求的终态**二选一**：要么 Settle（按实际结清），要么 Reverse（全退）。
- 两者都要在 Redis 余额上「应用一次」修正：settle 应用 `delta`，reverse 应用 `+pre`。
- 共用 `billing:delta:{request_id}` guard → **谁先拿到 guard，另一个就变 no-op**，天然互斥。防止「结算后又退款」或「退款后又结算」的双重修改。

### 2.4 ReportUsage 为什么单独一个 RPC？（埋 M4 的伏笔）

结算前先 `ReportUsage`，把实际用量写进 reserve 行（`usage_reported_at` 时间戳 + token 数）。

这是**对账的分水岭**（M4 的核心）：对账扫描 pending 账单时——
- 没有 `usage_reported_at` → 说明流根本没跑完（gateway 崩溃/上游故障/客户端断连）→ **全退**；
- 有 marker 但没有 settle 行 → 流跑完了但结算丢了 → **补结算**（用记录的 actual）。

把一个 RPC 拆成 ReportUsage + Settle 两个幂等 RPC，就是为对账留的「可区分状态」。

## 3. 数据流：一次完整请求的时序

```
客户端                gateway              billing              router           mock-provider
  │ POST /chat        │                     │                    │                    │
  │──────────────────>│ ① APIKey 校验        │                    │                    │
  │                   │──ValidateAPIKey────>│                    │                    │
  │                   │ ② 限流/幂等          │                    │                    │
  │                   │──Route?model───────>│                    │                    │
  │                   │<──────provider──────│                    │                    │
  │                   │──Reserve──────────>│                    │                    │
  │                   │<──OK(bill_id)───────│                    │                    │
  │                   │──POST /chat─────────│───────────────────>│                    │
  │                   │<──────────200+usage──────────────────────│                    │
  │                   │──ReportUsage──────>│                    │                    │
  │                   │──Settle────────────>│                    │                    │
  │                   │<──delta─────────────│                    │                    │
  │<─────────200(usage)────────────────────│                    │                    │
```

失败分支（上游 500）：
```
  │──POST /chat──────>│ ... Reserve 成功 ...
  │                   │──POST /chat─────────>│ 500
  │                   │──Reverse───────────>│   ← 退款
  │                   │<──refund─────────────│
  │<──502─────────────│
```

## 4. 面试 Q&A（附参考回答）

### Q1：为什么拆 4 个服务？一个单体不行吗？

单体当然能跑。但拆分的收益在「**独立变化、独立伸缩、独立故障**」：billing 是正确性核心，需要单独压测、单独上机器、单独做对账；router 管 provider 故障切换，不该被计费拖累；gateway 重启不影响已建立的计费状态。面试加分点：说出「**服务边界 = 数据所有权边界**，谁碰 bills 表谁说了算」。

### Q2：gateway 为什么不直接连 MySQL/Redis？

如果 gateway 和 billing 都写数据库，幂等和事务就没人能保证了。gateway 通过 gRPC 把「扣款」交给 billing，**billing 是唯一写账的进程**，它内部保证不超卖（Lua）、不重复（唯一索引）。这是「防腐层/所有权」思想：**外部只能通过服务接口动数据，不能绕过服务直接摸数据**。

### Q3：API Key 为什么存哈希？

明文泄露即灾难。存 `SHA-256(key)`，校验时哈希后查表；明文只在内存出现一次。参考 GitHub API 的做法：密钥只在创建时显示一次，之后永远无法找回，只能重置。**密钥可重置但不可反推**。

### Q4：限流为什么用滑动窗口？固定窗口有什么问题？

固定窗口按分钟分桶，跨桶瞬间能打两倍流量（59s+61s）。滑动窗口用 ZSET 精确统计「最近 N 秒」，更准。代价是 ZSET 每条请求存一个成员（内存略高），但对租户级限流足够。加 Lua 是因为「清过期+计数+插入」必须原子，否则并发会超限（和超卖同理）。

### Q5：幂等键重复为什么返回 409 而不是重放 200？

重放需要缓存完整响应体，成本和收益不成比例（demo 场景）。409 是「提交去重」语义，够用。真正的兜底在 billing 的 request_id 幂等——网关内部重试永远不会双扣。面试主动讲取舍：「409 vs 200-replay 是产品决策，我选了简单诚实的 409，计费正确性由下层幂等保证」。

### Q6：为什么预扣 ×1.2 而不是等实际用量出来直接扣？

因为请求开始时**不知道实际用量**（输出没生成）。预占带裕量保证「钱不够时在调用前就拒绝」（防白嫖），调用后按实际多退少补。这是**先授信后结算**的通用模式，支付宝/微信支付扣款前的「预授权」也是这个思路。

### Q7：为什么结算用 context.Background()，不用请求的 ctx？

请求 ctx 在**客户端断开连接时被 cancel**。如果结算复用请求 ctx，客户端断连 = 结算静默丢失 = 用户拿到了结果却没扣钱。结算/退款是「必须完成」的账务收尾，必须和请求生命周期解耦。**对外转发用请求 ctx（取消即止损），账务收尾用后台 ctx（必须做完）**。

### Q8：结算失败怎么办？钱会不会丢？

分两层兜底：
1. **网关层**：用后台 ctx 重试几次（计划里是 10s 超时）；
2. **系统层**：结算失败 → 该 request 留下 `pending + 有 marker` 状态 → **M4 对账任务**扫描到它自动补结算。**钱永远不会丢，只是晚一点结**。

### Q9：router 选 provider 的依据？挂了怎么办？

M2 是「**权重随机**」：从 providers 表筛出 `status=active` 且支持该模型的，按 weight 随机。provider 挂了的场景（重试、熔断、failover）是 **M5** 的内容——M2 只保证「有 provider 可选且选得均匀」。

## 5. 验证结果（本机真实跑过）

```
$ bash scripts/m2/scenario.sh
  normal -> status=200 prompt=5 completion=100
PASS  正常请求 200 且带 usage
  idempotency -> first=200 second=409
PASS  第二次同键 409
  rows for idem:scenario-key-1 = 2
PASS  重复幂等键只一行请求（2 条账目）
  insufficient -> status=402
PASS  余额不足返回 402
M2 scenario: 4 项全部 PASS
```

数据库检查（一发请求产生两行账目，余额正确）：

```
SELECT request_id,phase,status,pre_quota,actual_quota,delta_quota FROM bills;
  req_xxx  reserve  settled   12   NULL   NULL
  req_xxx  settle   settled   12   110    98     ← delta=actual-pre=110-12
Redis: GET billing:balance:1 → 999890  (= 1,000,000 − 110，恰好等于实际用量)
```

**对照 M2 验收**：一发请求产生 reserve+settle 两行、余额正确 ✓ · 重复 Idempotency-Key 返回 409 且只一行 ✓
