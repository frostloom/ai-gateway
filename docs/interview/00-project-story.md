# 00 项目故事：30 秒电梯版 → 3 分钟答辩版

> 面试的开场最重要。这一篇给你三档长度的版本，以及贯穿全程的叙事主线：
> **「对标 new-api，发现它三个真实缺陷，用三个对口的工程手段修掉，并压测验证。」**
> 学会这个故事，整场面试你都有「主线」可抓。

---

## 一、30 秒电梯故事（背下来）

> 我做了一个多租户 AI 模型网关，核心是**计费正确性**。它有三个服务：
> gateway 负责对外鉴权和转发，billing 负责计费账本，router 负责上游选择和熔断切换。
>
> 我拿市面开源的 new-api 对标，发现它有三个真实缺陷：**并发下额度会超卖成负数、
> 退款重试会双倍扣钱、网关崩溃后预扣的额度永久卡死**。
>
> 我对应做了三件事：用 **Redis Lua 原子扣减**防超卖，用**幂等键 + 数据库唯一索引**
> 防重复结算，再加一个**对账服务**自动收敛滞留账单。
>
> 最后我压测验证：100 并发 30 秒，212 req/s，P99 800ms，**零错误，Redis 余额和账本分毫不差**。

---

## 二、叙事主线：new-api 三个缺陷 → 本项目三个修复

这是整场面试的「记忆钩子」。每一条都要能讲出「缺陷是什么 → 后果是什么 → 我怎么做 → 怎么证明」。

### 缺陷 1：钱包扣减 check-then-act，无「余额≥N」守卫

**缺陷**：new-api 先 SELECT 读余额，判断够不够，再 UPDATE 扣减。两个并发请求都读到
余额 = 10、都判断够扣 8，于是都扣，余额变 -6。

**后果**：**并发超卖，余额为负**。白嫖 / 账不平。

**修复**：Redis Lua 脚本**原子**完成「判余额 ≥ pre → DECRBY」两步，Lua 在单线程的 Redis
里执行，天然互斥（[reserve.lua](../../internal/billing/store/lua/reserve.lua)）。

**证明**：单测起 100 个 goroutine 并发 Reserve，断言**余额恰好归零、从不为负、不足返回
INSUFFICIENT**（[reserve_test.go](../../internal/billing/store/reserve_test.go)）。

> 面试句式：**「我对比过 new-api 是 check-then-act，我改成 Redis Lua 原子操作——
> 因为『判断 + 扣减』必须是不可分割的一步，中间插不进其他请求。」**

### 缺陷 2：退款/结算非幂等，重试双倍扣钱

**缺陷**：new-api 的退款源码注释明确写着「不能重试」——因为退款没有防重机制。
网络抖动导致重试一次，就退了两次。

**后果**：**重试 = 双倍退款/双倍扣钱**。计费系统重试本是常规操作，这里却成了事故源。

**修复**：三层幂等：
1. 每个请求带全局唯一 `request_id`；
2. 账单表唯一索引 `uk_request_phase (request_id, phase)`——并发重试只有一行能插入
   （[schema.sql](../../scripts/schema.sql)）；
3. Redis `billing:delta:{request_id}` SETNX 保证余额**恰好冲正一次**
   （[settle.lua](../../internal/billing/store/lua/settle.lua)）。

**证明**：压测断言「同一 request_id 的 settle 行 ≤ 1」；单测并发重放同 request_id，恰好一行。

> 面试句式：**「我把『不允许重试』这个系统缺陷，改成了『重试无害』——幂等键 + 唯一索引
> + 状态守卫，三层兜底，任何一层都能让重复请求变 no-op。」**

### 缺陷 3：没有对账，网关崩溃后额度永久卡住

**缺陷**：new-api 预扣后、结算前，如果网关进程崩溃（或上游超时），这笔钱**既没结算也没退款**，
额度永远卡住，只能人工捞。

**后果**：**资金滞留 + 数据不可信**。

**修复**：新增独立 **reconciler 对账服务**，周期扫描滞留 pending 账单：
- 有 `usage_reported_at`（流跑完了，只差结算）→ 补结算；
- 无 marker（流没跑完）→ 全额退款（[reconciler.go](../../internal/billing/reconciler/reconciler.go)）。

**证明**：M4 场景脚本 kill -9 网关，分别打在 ReportUsage 前后，断言账单全部收敛、
Redis 余额 == 账本求和。

> 面试句式：**「崩溃是常态不是异常，所以计费系统必须能自愈——对账扫描滞留单、
> 按 marker 一锤定音，这就是最终一致的落地。」**

## 三、3 分钟答辩版（把故事展开讲）

（30 秒版 + 展开细节。面试官明显对某个点感兴趣时，从这里挑。）

### 背景：这个项目要解决什么问题

现在公司里 LLM 网关很常见（OpenAI 兼容代理、按量计费、多上游路由）。但计费系统有
「教科书上没人讲、线上才炸」的三类问题：并发超卖、重试非幂等、崩溃丢账。
我选择自己实现一个网关，**故意把计费正确性作为核心目标**。

### 架构一句话

`gateway（对外 HTTP，鉴权/限流/幂等/转发）→ billing（gRPC 计费，账本 + 投影）→ router（上游选择 + 熔断）→ mock-provider（可注入故障）`，
外加 reconciler 对账，MySQL 存账本，Redis 存余额投影。

### 技术选型三句话

- **Redis Lua 做原子预占**：要的是「跨请求原子」，单机锁不够（多实例）、DB 行锁太慢；
  Lua 在 Redis 单线程里跑，够快且天然互斥。
- **gRPC 做服务间调用**：强类型 proto、自带超时/重试语义，比 HTTP 更适合控制面。
- **Go**：并发模型直接命中场景（每请求一个 goroutine）、http.Client 长连接池、
  单一静态二进制部署。

### 正确性怎么证明（这是你区别于「会 demo」的候选人的点）

不只是「能跑」。三类断言：
1. **无错误**：压测 6359 请求全 200，0 个 402/429/5xx/连接错误；
2. **余额守恒**：Redis 余额 == 独立 SQL 从账本重算的期望值（10000000 - 2329315 = 7670685）；
3. **无重复结算**：settle 行按 request_id 去重后零重复。

压测还揪出两个真实 bug（连接池风暴、rebuild 竞态），修复后所有断言通过——
**这些数字和 bug 就是你的可信度**。

## 四、面试官顺着故事问什么（预判 + 参考答案）

| 追问 | 指向 | 参考回答 |
|---|---|---|
| 为什么用 Redis Lua 而不是 MySQL 事务？ | 超卖 | Lua 跨进程原子且单次往返；DB 行锁也能做但拖慢热路径；Lua 在 Redis 单线程天然互斥 |
| 对账会不会误伤正常请求？ | 对账安全性 | 只扫 `created_at < now - grace` 的超龄行 + 每行写操作幂等，重复执行 no-op；宽限期挡住 in-flight 请求 |
| 账本和 Redis 不一致时以谁为准？ | 一致性 | MySQL 是权威账本，Redis 是投影；RebuildBalance 定期从账本重算，压测显式断言一致 |
| 熔断状态重启就没了怎么办？ | 熔断 | 内存熔断兜瞬时抖动；持久 AutoBan 写库，重启不失效——两层分工 |
| 流中途断了为什么不重试上游？ | 流式计费 | 分不清谁先断；重发 = 双扣上游。只有首个字节前失败才重试，其余交给对账收敛 |
| 吞吐瓶颈在哪？ | 性能 | billing 串行化边界：每请求 4 次 gRPC + Lua + MySQL；扩展方向是按租户分片 + 批量 settle |
| 这项目用了什么设计模式？ | 模式 | 依赖注入（New 注入 DB/Redis/日志）、状态机（账单 + 熔断）、幂等重试、Saga 补偿、接口抽象（可 mock） |

## 五、口述自检（对着录音讲，讲不顺的就是薄弱点）

1. 三个缺陷 → 三个修复，各自一句话说清「缺陷 → 后果 → 修复 → 证明」。
2. 「为什么 Redis Lua」「为什么唯一索引」「为什么对账」这三个为什么能脱口而出。
3. 压测三个数字（212 rps / P99 800ms / 0 error）+ 余额一致性数字（7670685）能背下来。
4. 能讲出压测揪出的两个 bug（连接池、rebuild 竞态）——这是「我真的压过」的证据。
5. 被追问「如果流量再翻 10 倍？」能答出扩容方向（gateway 水平扩 / billing 分片 / 批量 settle）。
