## 0. 概念地图（先建立全局）

```
一次请求在微服务之间牵扯多份数据 → 单机事务失效
        │
        ├─ 事务失效 → Saga / TCC / 2PC（本项目：Saga + 对账兜底）
        ├─ 网络不可靠 → 幂等（重试不产生副作用）
        ├─ 多副本/多存储 → 最终一致 + 缓存一致性（本项目：账本 vs 投影）
        ├─ 流量洪峰   → 限流（本项目：Redis 滑动窗口）
        ├─ 上游不稳定 → 熔断 / 降级 / 重试（本项目：熔断状态机 + failover）
        └─ 服务怎么拆 → 微服务拆分原则（本项目：gateway/billing/router）
```

## 1. 分布式事务：2PC / TCC / Saga

### 问题

单机数据库里，`BEGIN ... COMMIT/ROLLBACK` 保证一组 SQL 要么全成功要么全失败。
但跨服务（扣费在 billing、状态在 gateway、选择在 router）没有共享事务，**本地事务管不到别的服务**。

### 三种方案

| 方案 | 核心思想 | 优点 | 缺点 |
|---|---|---|---|
| **2PC（两阶段提交）** | 协调者问所有参与者「能提交吗？」→ 都点头才 COMMIT | 强一致 | 协调者单点、参与者阻塞占资源、实现复杂 |
| **TCC（补偿事务）** | 每步 Try（预留）→ Confirm（确认）/ Cancel（补偿），业务自己实现补偿 | 不需全局锁、灵活 | 每步要写三套方法，补偿逻辑易错 |
| **Saga（长事务）** | 正向流程 + 每步记录状态；失败时反向执行补偿；用「对账」兜底漏网之鱼 | 简单、可异步、容错强 | 最终一致（中间态对别人可见） |

### 本项目落点：Saga，而且是「Saga + 对账 cron」的增强版

billing 的账单状态机就是一条 Saga（[store/mysql.go](../../internal/billing/store/mysql.go)）：

```
Reserve（预占）→ [pending]
  ├─ ReportUsage（写持久 marker）→ [pending + marker]
  │     └─ Settle（按实际结算）→ [settled]
  └─ Reverse（冲正）→ [reversed]
```

- **正向**：Reserve → ReportUsage → Settle
- **补偿**：Reverse（客户端断连/上游失败时退回预扣）
- **兜底**：如果补偿也没跑（gateway 崩溃），**对账 cron** 扫描滞留 pending，按 marker 一锤定音
  ——无 marker 全退，有 marker 补结算（[reconciler.go](../../internal/billing/reconciler/reconciler.go)）。

面试一句话：**「我的项目用的是 Saga + 对账兜底：正向流程每步落库留痕，失败走补偿，
补偿没跑到就靠对账 cron 收敛——最终一致由『权威账本 + 定时收敛』保证。」**

### 为什么不用 2PC/TCC？（面试必被追问）

- 2PC 要协调者 + 两轮 RPC，且协调者崩溃全挂——对计费这种长流程不划算；
- TCC 每步三套方法（Try/Confirm/Cancel），代码量爆炸；
- Saga 最符合实际：计费本来就是「扣 → 结/退」两个天然可补偿的动作，边界清晰，
  不需要全局锁。**选型要讲「为什么」**：流程短、补偿动作天然存在 → Saga 最优。

## 2. 幂等：重试不产生副作用

### 问题

网络不可靠，RPC 可能「发了但响应丢了」→ 客户端重试 → 服务端执行了两次 → 双扣、双退。
**要求：同一个请求无论执行几次，效果和一次相同。**

### 三件套（层层兜底，缺一不可）

1. **业务幂等键**：请求带全局唯一 `request_id`，服务端用它在表里查「做没做过」。
2. **数据库唯一索引**（权威）：`UNIQUE KEY uk_request_phase (request_id, phase)`——
   并发重试两个 goroutine 同时插入，只有一个能插进去（另一个撞 1062 变成 no-op）。
3. **状态守卫**：`UPDATE ... WHERE status='pending'`，`RowsAffected==1` 才算成功——
   已结算/已冲正的行再 UPDATE 影响 0 行，天然 no-op。

### 本项目落点

- Reserve 幂等：`billing:req:{request_id}` SETNX + `uk_request_phase`（[mysql.go:151](../../internal/billing/store/mysql.go)）
- Settle/Reverse 幂等：`billing:delta:{request_id}` SETNX 保证 Redis 恰好冲正一次
  （[settle.lua](../../internal/billing/store/lua/settle.lua)）+ 唯一索引兜底
- 压测断言「同一 request_id 的 settle 行 ≤ 1」（[loadtest/main.go](../../scripts/loadtest/main.go)）——
  **用测试证明幂等成立**。

面试金句：**「幂等有三层：请求键去重 + 唯一索引兜底 + 状态守卫 CAS；缺一层就可能在
『应用层查到已存在但数据库其实没落』的竞态窗口里重放。」**

## 3. 最终一致：账本 vs 投影

### 问题

高并发下不能每笔都强一致（太慢/锁太多）。**强一致**：任何时刻任何节点读到的都是同一份；
**最终一致**：允许短暂不一致，但保证「不再写入后，会收敛到一致」。

### 本项目落点：MySQL 是权威账本，Redis balance 是缓存投影

```
Redis balance（热投影，快）     MySQL bills（权威账本，准）
    │ 读/写都在投影上走               │ 每笔落库留痕
    └────── 对账 + 重建 job 把账本扩散到投影 ──────┘
```

- 每笔预扣/结算先改 Redis（快），再落 MySQL（准）——如果 Redis 和账本短暂不一致没关系，
  因为有 **RebuildBalance**：`balance = initial_quota - Σpending - Σsettled`（[mysql.go:334](../../internal/billing/store/mysql.go)），
  定期从账本重算投影。
- 面试被问「Redis 崩了怎么办」→ 答：Redis 是投影，重启后从 MySQL 重建；MySQL 崩了才是真灾难，
  靠主从 + 备份。

### 缓存一致性（容易被混进来问）：旁路缓存 / 双删

- **Cache-Aside（旁路缓存）**：读 miss → 查库回填；写 → 更新 DB 后**删缓存**（不是更新缓存）。
  删缓存比更新缓存好，因为「更新缓存」要先算出新值，多一次读写还容易把旧值写进去。
- **双删**：删缓存 → 写 DB → 延迟再删一次。解决「删缓存后、写 DB 前，别的请求把旧值回填缓存」的窗口。
- 本项目：`route` 缓存用 TTL 30s + `ban` 时主动 `clearCache()`（[registry.go:247](../../internal/router/registry.go)），
  本质是「TTL 兜底 + 主动失效」组合。balance 不是普通缓存而是**可重建投影**——所以不用双删，
  用「重建 job」整套收敛。

面试区分点：**「balance 是可从账本重建的投影，不是加速用的缓存；对可重建投影，
正确姿势是『定期重建收敛』而不是双删。」** 这句话很能体现思考深度。

## 4. 限流

### 算法家族

| 算法 | 原理 | 特点 |
|---|---|---|
| 固定窗口 | 每窗口内计数，到上限拒绝 | 实现简单，但窗口边界瞬间可以双倍流量 |
| **滑动窗口** | 用时间戳集合，只统计窗口内的请求 | 平滑，消除边界毛刺；Redis ZSET 天然支持 |
| 令牌桶 | 匀速发放令牌，取令牌才放行 | 允许一定突发；单机内存版很常见 |
| 漏桶 | 固定速率流出，积压则丢弃 | 平滑到极致，但突发流量直接被丢 |

### 本项目落点：Redis ZSET 滑动窗口

- 每个租户每分钟限 `RATE_LIMIT_PER_MIN` 次，key = `rate:win:{tenant_id}:{ts_floor}`，
  每次请求 ZADD 时间戳 + ZREMRANGEBYSCORE 清掉窗口外的 + ZCARD 数在窗口内的。
- 为什么用 Redis？限流状态要跨 gateway 实例共享（多实例各自计数 = 形同虚设）。
- 为什么滑动窗口？固定窗口在边界能放双倍流量（59 秒和 60 秒各放满一个窗口），
  滑动窗口把毛刺磨平。

面试答法：**「限流状态必须存在共享存储（Redis），否则多副本下各自计数就废了；选滑动窗口
是平衡『平滑』和『实现成本』，Redis 的 ZSET 正好是现成的滑动窗口。」**

## 5. 熔断 / 降级 / 重试：上游不稳定时

### 三兄弟分工

- **熔断**：上游持续失败 → 快速失败，别让流量全堆在坏节点上（保护下游 + 保护自己）。
- **降级**：核心功能不可用时返回兜底结果（缓存/默认值），别让故障拖垮整体。
- **重试（+ 退避）**：瞬时失败重来几次；但要**退避 + 幂等**，否则雪崩。

### 本项目落点：熔断状态机 + failover + AutoBan（M5）

```
CLOSED →(5 连败)→ OPEN →(cooldown)→ HALF-OPEN（放 1 个探测）
  成功回 CLOSED / 失败回 OPEN
AutoBan：累计 20 连败 → 写库 status=banned，重启不失效
failover：重试换一个没试过的节点（RouteExclude），流中途失败绝不重试
```

- 三层各司其职：**重试**兜瞬时抖动、**熔断**兜持续故障、**AutoBan** 兜持久故障。
- 面试必答的追问：探测（HALF-OPEN）发出去网关崩了怎么办？→ 探测位带 30s 超时自动释放
  （[registry.go:181](../../internal/router/registry.go)）。**任何「等外部回报」的状态都要有超时兜底。**

## 6. 微服务拆分原则

### 怎么拆

- **按业务能力/边界**（限界上下文）：谁拥有哪些数据，谁就负责它的写。
- **数据独有**：每服务自己的库/表，不共享表；别人要数据走 API。
- **可独立部署/独立扩缩容**：链路瓶颈单独扩。

### 本项目落点：为什么拆三个服务

| 服务 | 拥有什么数据 | 为什么单独 |
|---|---|---|
| **gateway** | 无持久数据，纯编排 | 对外唯一入口，鉴权/限流/幂等集中，可水平扩 |
| **billing** | MySQL bills 账本 + Redis balance | **计费是核心资产**，所有写账入口必须收敛到一家，可独立演进/审计 |
| **router** | providers 路由/熔断状态 | 上游健康与路由是独立关注点，失败切换逻辑不外泄到 gateway |

- 为什么不拆更多？**够用原则**：三个服务已经能讲清「数据所有权 + 独立部署」，
  再拆是过度设计。面试被问「会不会太碎/太大」→ 答：billing 是唯一写账入口（防多写源），
  gateway 无状态可水平扩，router 有状态但单实例即可——这个粒度对应「数据所有权」边界。

## 7. 一致性哈希（面试常问，本项目未用）

- 目的：`key % N` 的哈希在节点增删时会**大范围迁移**（N 变了，几乎全部 key 落点变化）。
  一致性哈希让增删节点只影响 `1/N` 的 key。
- 变体：虚拟节点（均匀分布）、带权（容量大节点多虚拟节点）。
- 本项目可用场景：gateway → billing 的**按租户分片**（同一租户的账单打到同一 billing 实例），
  但当前单 billing 实例不需要。**面试主动说**：「当前单实例，如果 billing 要分片，
  会用一致性哈希按 tenant_id 路由，保证同一租户落在同一实例（结算顺序一致）。」

## 8. 面试快问快答

### Q1 分布式事务选型你用了什么？为什么？
Saga + 对账。计费流程短、补偿动作天然存在（Reverse 退款）、对账 cron 兜底崩溃。
不用 2PC（协调者单点+阻塞）、不用 TCC（每步三套方法成本高）。

### Q2 怎么保证不超卖/不双扣？
四层：① Redis Lua 原子「判余额≥N 再 DECRBY」防超卖；
② `request_id` 幂等键 + `uk_request_phase` 唯一索引防双扣；
③ `billing:delta` SETNX 保证 Redis 恰好冲正一次；
④ 对账 + 重建 job 兜底任何漏网。

### Q3 Redis 和 MySQL 不一致了怎么办？
以 MySQL 账本为权威，RebuildBalance 定期从账本重算投影覆盖 Redis。
压测里显式断言「Redis balance == 账本求和」，把一致性变成可验证的不变量。

### Q4 限流为什么用 Redis + 滑动窗口？
多实例共享状态必须 Redis；滑动窗口消除固定窗口的边界毛刺；ZSET 是现成的实现。

### Q5 熔断探测失败回 OPEN，那探测的意义在哪？
意义是用最少代价确认「没恢复」。探测成功才回 CLOSED。失败回 OPEN 再冷却一轮，
避免一个坏节点被反复试探。配合探测超时，防「网关崩了探测位卡死」。

### Q6 你的系统如何应对流量洪峰？
限流（滑动窗口）挡在入口 + 熔断（坏上游快速失败）+ gateway 无状态可水平扩容 +
billing 是瓶颈时可按租户分片（一致性哈希）——但当前单实例，压测已验证 P99 800ms@212rps。
